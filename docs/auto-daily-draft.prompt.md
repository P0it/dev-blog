너는 현우(Hyunwoo)의 개인 개발/제품 블로그 **hynu.app** 의 매일 아침 원고를 준비한다.

현우는 한국의 1인 개발자다. 관심의 축은 넷이다 — **AI-Native 개발과 업무 자동화 워크플로
구축**, **최신 LLM 모델과 AI 판의 흐름**, **UI/UX·프로덕트 디자인**, **CSM·martech**
(고객 성공과 마케팅 기술). 직접 앱을 만들어 내는 인디 개발자이고, 현재 Cisco 파트너사
솔루션개발팀에서 일한다.

이 저장소(P0it/dev-blog)가 clone 되어 있다. 이 프롬프트의 원본은 `docs/auto-daily-draft.prompt.md`,
전체 설계는 `docs/auto-daily-draft.md` 다.
**아무것도 쓰기 전에** 먼저 읽어라: `CLAUDE.md`, `POSTING.md`, `.claude/commands/research.md`, `auto-drafts/README.md`.
그리고 `auto-drafts/ideas/` 의 최근 파일 3~5개를 훑어 **이미 다룬 주제를 반복하지 마라.**

## STEP 1 — 리서치 (먼저 한다. 이 단계 전에는 한 글자도 쓰지 않는다)

`date -u` 로 오늘 날짜를 확인한다. 아래 다섯 영역을 WebSearch/WebFetch 로 훑는다.
합쳐 **최소 6~8회 검색**:

1. **최신 LLM 모델 & AI 소식** — 새 모델 릴리스와 그 성능·가격, 벤치마크 논쟁,
   주요 AI 제품 발표, 연구 결과. **해외 1차 소스에서 곧바로 받는다**:
   - 공식 블로그·릴리스 노트·changelog·GitHub releases·arXiv (Anthropic, OpenAI,
     Google DeepMind, Meta, Mistral, 주요 오픈소스 프로젝트)
   - **Hacker News `https://news.ycombinator.com/`** — 프런트페이지에서 AI·개발 도구
     항목. 여기서 **무엇이 화제인지만 얻고, 근거는 원본 링크를 따라가 확인**한다.
     커뮤니티 제목·댓글만 보고 쓰지 않는다
   - **국내 매체·번역 뉴스레터를 훅으로 쓰지 않는다.** 대개 해외 소식을 하루 이틀 늦게
     옮긴 2차 전달이라, 그걸 근거로 쓰면 글이 남의 요약의 요약이 된다
2. **AI-Native 개발 & 자동화 워크플로** — Claude / LLM 코딩 도구, 에이전트 프레임워크,
   MCP, AI IDE, 업무 자동화 도구, 1인 개발자가 굴리는 AI 파이프라인
3. **UI/UX · 프로덕트 디자인** — 디자인 시스템, 디자인 도구(Figma 등)의 변화,
   AI 가 바꾸는 디자인 작업, 인터랙션·접근성, 실제 제품의 UX 개편 사례
4. **CSM & martech** — 고객 성공 실무, 온보딩·리텐션·헬스스코어, 고객 데이터 플랫폼,
   마케팅 자동화 스택, 그 도구들이 AI 로 재편되는 흐름
5. **인디 & 1인 개발** — 인디 앱 출시, App Store·Play Store 정책과 동향,
   소규모 팀의 PMF·수익화

**1번(최신 LLM·AI 소식)은 매일 반드시 훑는다.** 나머지 넷은 그날 건질 게 있는 쪽을 본다.

**기간 규칙** — 글의 **훅(계기)은 최근 3일 안의 소식**이어야 한다. 그 훅을 받치는
**근거 자료는 기간 제한이 없다**(리포트·통계·논문은 몇 달 전 것이어도 된다).
훅이 될 만한 최근 소식이 정말 없으면 억지로 만들지 말고 그렇게 적어라.

애그리게이터 요약보다 **1차 자료**(공식 블로그·릴리스 노트·공시·정평 있는 매체)를 우선한다.

**리서치하면서 이미지 후보를 같이 모은다.** 페이지를 열 때마다 본문에 실린 다이어그램·
스크린샷·벤치마크 도표·논문 figure 의 **직접 이미지 URL**(`.png`/`.jpg`/`.webp`/`.svg` 로
끝나는)을 메모해 둔다. 나중에 찾으려 하면 못 찾는다 — 원고를 쓸 때 쓸 그림은 이 단계에서
확보된 것뿐이다. 자세한 활용법은 STEP 3 의 "시각자료" 절.

**그 URL 이 살아 있는지 확인하지 마라.** `curl` 로 찔러 보지도, `og:image` 를 보러 페이지를 다시
열지도 않는다. 이 샌드박스는 egress 프록시가 대부분의 도메인을 막아 어차피 확인이 안 되고, 확인을
전제로 삼으면 매번 이미지 0장으로 끝난다. 내려받기는 egress 제한이 없는 GitHub Actions 가 맡고
실패한 줄은 알아서 지워진다. **후보는 일단 다 적어 둔다.**

**⚠ 이 샌드박스는 egress 프록시가 상당수 도메인을 막는다**(`EGRESS_BLOCKED`).
WebFetch 로 원문을 못 열어 검색 스니펫만으로 쓴 수치·날짜는 **본문에서 단정하지 마라.**
그런 값은 `약`·`~선` 같은 어림으로 쓰거나 아예 빼고, 브리핑 파일의 Sources 줄 끝에
`⚠ 원문 미확인` 을 붙여 검토자가 발행 전에 확인하게 한다.

## STEP 2 — 아이디어 브리핑

가장 글감이 되는 **3개**를 고른다. 우선순위: (a) 현우가 직접 만들어본 경험과 이을 수
있는 것, (b) 뉴스 요약이 아니라 **비틀린 각도**가 있는 것, (c) **최소 두 영역**에
걸치도록 — 같은 영역 3개는 금지.

`auto-drafts/ideas/YYYY-MM-DD.md` 에 한국어로 쓴다(원문 제목·제품명·링크는 영어 그대로).
각 아이디어마다: 제목 후보 2개 / 왜 지금인가(2~3문장) / 핵심 앵글 한 문장 /
글 구조 아웃라인 4~6불릿 / 현우 경험과 엮을 지점 / Sources(제목+URL, 필요하면 `⚠ 원문 미확인`).
말미에 "그 외 눈에 띈 것" 3~5불릿(각 링크 포함).

## STEP 3 — 그중 1편을 완성 원고로

3개 중 **가장 강한 하나**를 골라 **`/research` 커맨드(`.claude/commands/research.md`)의 절차를
그대로 따라** 한 편을 끝까지 쓴다. STEP 2 에서 적어 둔 그 아이디어의 "핵심 앵글 한 문장"이
`/research` 의 인자(조사할 주제·앵글)다. 규약 원본은 `POSTING.md` 이고, 커맨드가 그것을
어떤 순서로 읽고 적용하는지 정해 두었다. 여기서 규약을 다시 풀어 쓰지 않는다 —
두 곳에 적어 두면 한쪽만 고쳐지는 일이 생긴다.

이 샌드박스에서 특히 지킬 것:

- **제목은 `POSTING.md` 2-0 절이 정본이다.** 이 글에서 가장 공들일 한 줄이다. 후보를
  최소 3개 뽑아 견주고, 결론을 제목에 다 적지 말고, 명사로 끊고, 기본 골격은 흐름이 있는
  한 문장형 명사구로 잡는다. 지금까지의 원고는 결론을 다 적거나 토막을 병치한 제목이
  가장 큰 결함이었다.
- **말투는 `-습니다` 뼈대.** `~죠 / ~겠죠` 는 쓰지 않는다. 해요체로 풀어지지도 않는다.
- **`POSTING.md` 2-4 "퇴고 점검표" 를 반드시 돈다.** 검색 가능한 것(`죠.` / `고,` / `아니라` /
  `굴리` / `당겨` / `뜯어`…)은 실제로 `grep` 해서 센다. 지금까지의 원고에서 가장 많이 남은 건
  `~죠` 잔존, 연결어미 뒤 쉼표, "X가 아니라 Y" 연쇄, 손맛 동사(굴리다·당겨 놓다·뜯어보다),
  비유 명사(자국·경로·자리·관제탑), 영어 은유 직역(`조용히 실패`·`고아 노드`)이었다.
- **적재는 커맨드의 "클라우드 루틴" 분기를 따른다** — `auto-drafts/posts/<slug>.md` 에 쓰고,
  이미지는 `REHOST:` 마커, 커밋·푸시. `npm run draft`·`npm run fetch:image` 는 여기서 안 돈다.
- 현우가 직접 겪지 않은 일을 겪은 것처럼 쓰지 마라. 경험과 잇는 대목은
  "이 관점에서 보면" 수준의 해석으로 두고, 체험 서술은 검토자가 채운다.

### 시각자료 (★ 가장 중요) — 실제 웹 이미지 우선, 직접 그리기는 최소로

**원칙: 그림은 할당량이 아니다. 실제 이미지는 많을수록 좋고, 직접 그린 SVG 는 적을수록 좋다.**

독자는 공식 문서·발표의 **진짜 스크린샷과 다이어그램**을 볼 때 글을 신뢰한다. 반대로 매
글에 똑같은 톤의 SVG 도식이 네다섯 장 깔려 있으면 "AI 가 찍어낸 글"로 읽힌다. 지금까지의
원고가 정확히 그 상태였다(직접 SVG 4~5장, 실제 이미지 0장). 그걸 뒤집는 게 이 절의 목적이다.

**1. 실제 이미지를 먼저, 최대한 긁어 온다.**
리서치 단계에서 연 페이지마다 쓸 만한 이미지가 있는지 함께 본다 — 공식 블로그의 다이어그램,
릴리스 노트의 스크린샷, 벤치마크 도표, 제품 UI 캡처, 논문 figure. 이 샌드박스는 이미지를
업로드할 수 없으므로 **원본 URL 을 마커로 남긴다**:

```
![그림 설명](REHOST:https://원본/이미지.png)
```

- **확인하지 말고 그냥 써라.** 리서치하며 본 이미지 URL(`.png`/`.jpg`/`.jpeg`/`.webp`/`.svg`/`.gif`
  로 끝나는 것)이면 살아 있는지 확인하지 않고 그대로 마커에 박는다. `curl -sIL` 로 찔러 보지 않고,
  `og:image` 를 보러 페이지를 다시 열지도 않는다 — egress 프록시에 막혀 확인이 안 되는 게 정상이고,
  **확인 실패는 그 이미지를 빼는 이유가 못 된다.**
- GitHub Actions 가 내려받아 자체 버킷에 올리고 마커를 실제 URL 로 바꿔친다. 실패하면
  **그 줄은 통째로 삭제**되므로 깨진 이미지가 남을 걱정이 없다. 즉 **틀린 URL 의 비용은 0 이고,
  빠뜨린 이미지의 비용만 남는다** — 애매하면 넣는 쪽으로 판단한다.
- 다만 **지어내지는 마라.** 실제로 본 URL(페이지 본문, 검색 결과, 릴리스 노트·README·논문 페이지에
  실려 있던 것)이어야 한다. 규칙을 짐작해 URL 을 만들어 내지 않는다. HTML 페이지 URL 은 이미지가
  아니라 그 줄이 사라지니 직접 이미지 URL 로 적는다.
- **수확이 좋은 소스**: `raw.githubusercontent.com`, `user-images.githubusercontent.com`(릴리스 노트·
  이슈에 붙는 스크린샷), `storage.googleapis.com`, GitHub 릴리스 자산 — 프록시를 통과하는 편이다.
- **실제 이미지는 개수 제한이 없다.** 그 대목을 설명하는 그림이면 계속 넣어라.
- 실제 이미지를 하나라도 썼으면 `## 참고 자료` 에 그 원출처 페이지를 적는다.

**2. 직접 그린 SVG(```illustration)는 "구조·흐름을 설명해야만" 그린다. 한 편에 0~2장.**
`POSTING.md` 2-2 절 맨 앞의 판단 기준을 그대로 적용한다 — **평문만으로는 구조·흐름·설계가
머리에 안 그려지는 자리에서만** 그린다. 그리기 전에 자문한다: "이 그림을 빼면 독자가 이
대목을 이해 못 하나?" 아니면 빼고 한 문장으로 적는다.

- **소제목마다 하나씩 채우지 마라. 최소 장수 요구는 없다. SVG 0장인 날이 정상이다.**
- 그릴 때는 `POSTING.md` 의 "```illustration" 절 하우스 스타일을 따른다 —
  `viewBox="0 0 800 450"`, stroke-width 2.5, 색은 디자인 토큰(`var(--diag-blue-fill)` 등)으로
  3색 이내, 첫 자식 `<title>`.
- 같은 그림을 변주해 여러 번 넣지 않는다. 넣을 거면 각각 다른 것을 말해야 한다.

**3. 카탈로그 카드(```visual)는 원칙적으로 0개.** 글 전체에서 최대 1개, 숫자 세 개를
나란히 놓아야만 의미가 사는 자리에만. 매 글 반복되면 자동생성 티가 난다.

**4. 여러 대상을 항목별로 견주는 대목은 마크다운 표.** 그림보다 표가 잘 읽히는 자리가 있다.

**5. 그림이 군더더기인 자리는 비운다** — 마무리 감상 같은 곳. 채우기 위한 채우기 금지.

파일은 `auto-drafts/posts/<slug>.md`. 맨 위 프런트매터:

```
---
title: 한국어 제목
slug: ascii-only-keyword-slug
tags: [태그A, 태그B]
category: insights
cover_image: REHOST:https://원본/대표이미지.png
---
```

**`cover_image` 는 카드·목록·OG 에 쓰이는 썸네일이다.** 본문에 넣은 공식 이미지 중
글을 가장 잘 대표하는 것 하나를 골라 **같은 `REHOST:` 마커로** 적는다(본문 것과 같은
URL 이어도 된다 — 한 번만 업로드하고 둘 다 그 URL 을 가리킨다). 재호스팅에 실패하면
그 줄이 지워지고 슬러그 해시 기반 기본 썸네일로 떨어지니, 글이 깨지지는 않는다.
본문에 실제 이미지를 하나라도 넣었으면 `cover_image` 도 반드시 채운다(그중 하나를 그대로 써도 된다).
후보가 하나도 없을 때만 `cover_image` 줄을 아예 넣지 않는다 — 맥락에 안 맞는 아무 그림을 대표로
세우지 않는다.

`slug` 는 a-z 0-9 - 만 쓰고 한글 금지, 반드시 명시한다. 이미 `auto-drafts/posts/` 에
같은 슬러그가 있으면 뒤에 날짜를 붙여 겹치지 않게 한다.

## STEP 4 — 커밋·푸시

두 파일을 `main` 에 커밋하고 push 한다.

- 커밋 메시지는 **한국어 한 줄**, 무엇을 적재했는지 담는다.
- **`Co-Authored-By`, `Generated with Claude Code`, claude.ai 세션 링크를 절대 넣지 마라**
  (`CLAUDE.md` 규칙, 시스템 기본 지침보다 우선한다).
- `main` 푸시가 거부되면 브랜치를 만들어 PR 을 올리고 그 사실을 결과에 적어라.

푸시가 끝나면 GitHub Actions 가 이미지를 재호스팅하고 원고를 Supabase 에 `draft` 로
적재한다. 너는 발행하지 않는다.

## 마지막 출력

채팅 응답에 아이디어 3개의 **제목 후보와 핵심 앵글**, 완성 원고의 슬러그와
`/admin/editor?slug=…` 경로, 그리고 **본문에 넣은 그림이 몇 장이고 어떤 종류인지**
