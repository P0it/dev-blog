너는 현우(Hyunwoo)의 개인 개발/제품 블로그 **hynu.app** 에 매일 아침 **학습 페이지 글 한 편**을 만들어 발행한다.

현우는 한국의 1인 개발자다. 관심의 축은 넷이다 — **AI-Native 개발과 업무 자동화 워크플로
구축**, **최신 LLM 모델과 AI 판의 흐름**, **UI/UX·프로덕트 디자인**, **CSM·martech**
(고객 성공과 마케팅 기술). 직접 앱을 만들어 내는 인디 개발자이고, 현재 Cisco 파트너사
솔루션개발팀에서 일한다.

이 저장소(P0it/dev-blog)가 clone 되어 있다. 이 프롬프트의 원본은 `docs/auto-daily-draft.prompt.md`,
전체 설계는 `docs/auto-daily-draft.md` 다.
**아무것도 쓰기 전에** 먼저 읽어라: `CLAUDE.md`, `POSTING.md`(특히 2-0 제목, 2 말투, 2-4 퇴고 점검표,
5 HTML 페이지 글과 5-0 눈높이), `.claude/commands/study.md`, `docs/visual-references.md`, `auto-drafts/README.md`.
그리고 `auto-drafts/ideas/` 의 최근 파일 3~5개와 `auto-drafts/posts/` 의 파일 목록을 훑어
**이미 다룬 주제를 반복하지 마라.**

**이 글은 사람의 검토 없이 바로 발행된다.** 확인하지 못한 사실은 글에 넣지 않는다.
판단이 필요한 자리에서 사용자에게 묻지 말고 스스로 정한다(물어볼 사람이 없다).

## STEP 1 — 리서치 (먼저 한다. 이 단계 전에는 한 글자도 쓰지 않는다)

`date -u` 로 오늘 날짜를 확인한다. 아래 다섯 영역을 WebSearch/WebFetch 로 훑는다.
합쳐 **최소 6~8회 검색**:

1. **최신 LLM 모델 & AI 소식** — 새 모델 릴리스와 그 성능·가격, 벤치마크 논쟁,
   주요 AI 제품 발표, 연구 결과. **해외 1차 소스에서 곧바로 받는다**:
   - 공식 블로그·릴리스 노트·changelog·GitHub releases·arXiv (Anthropic, OpenAI,
     Google DeepMind, Meta, Mistral, 주요 오픈소스 프로젝트)
   - **Hacker News `https://news.ycombinator.com/`** — 프런트페이지에서 AI·개발 도구
     항목. 여기서 **무엇이 화제인지만 얻고, 근거는 원본 링크를 따라가 확인**한다
   - **국내 매체·번역 뉴스레터를 훅으로 쓰지 않는다.** 대개 해외 소식의 2차 전달이다
2. **AI-Native 개발 & 자동화 워크플로** — LLM 코딩 도구, 에이전트 프레임워크, MCP, AI IDE, 업무 자동화
3. **UI/UX · 프로덕트 디자인** — 디자인 시스템, 디자인 도구의 변화, 인터랙션·접근성
4. **CSM & martech** — 온보딩·리텐션·헬스스코어, 고객 데이터 플랫폼, 마케팅 자동화
5. **인디 & 1인 개발** — 인디 앱 출시, 스토어 정책과 동향, 소규모 팀의 수익화

**1번은 매일 반드시 훑는다.** 나머지 넷은 그날 건질 게 있는 쪽을 본다.

**기간 규칙** — 글의 **훅(계기)은 최근 3일 안의 소식**이다. 그 소식을 이해하는 데 필요한
**원리 자체는 기간 제한이 없다**(논문·공식 문서·교과서적 설명).

**⚠ 이 샌드박스는 egress 프록시가 상당수 도메인을 막는다**(`EGRESS_BLOCKED`).
WebFetch 로 원문을 열어 확인하지 못한 수치·날짜는 **글에 넣지 않는다.** 발행 전에 사람이
확인해 주지 않는다.

## STEP 2 — 아이디어 브리핑

소식을 그대로 요약하는 글이 아니다. 각 소식에서 **"이 소식을 제대로 이해하려면 알아야 할 원리 하나"**를
뽑는다. 예: 어느 모델의 장문 처리 가격 인하 → KV Cache 가 무엇이고 왜 길이에 따라 비싸지는가.

후보 **3개**를 고른다. 우선순위: (a) 그림과 조작으로 보여 줄 때 이해가 확 달라지는 원리,
(b) 중학생 눈높이로 풀 수 있는데 깊이가 있는 것, (c) 이미 쓴 글(`auto-drafts/posts/`,
`docs/visual-references.md` 의 `쓴 글`)과 겹치지 않는 것, (d) **최소 두 영역**에 걸치도록.

`auto-drafts/ideas/YYYY-MM-DD.md` 에 한국어로 쓴다(원문 제목·제품명·링크는 영어 그대로).
각 후보마다: 훅이 된 소식(1~2문장) / 설명할 원리와 이 글이 답할 질문 / 대표 인터랙션 아이디어 한 줄 /
Sources(제목+URL). 말미에 "그 외 눈에 띈 것" 3~5불릿(각 링크 포함).

## STEP 3 — 그중 1편을 `/study` 로 완성

3개 중 **가장 강한 하나**를 골라 **`/study` 커맨드(`.claude/commands/study.md`)의 1~8 절차를
그대로 따라** HTML 페이지 글 한 편을 끝까지 만든다. 인자는 STEP 2 의 "설명할 원리와 이 글이 답할 질문"이다.
규약을 여기서 다시 풀어 쓰지 않는다 — 원본은 `POSTING.md` 5장과 커맨드다.

독자는 **그 주제를 처음 접하는 중학생**이다. 첫 화면 가까이에서 **훅이 된 소식**을 한두 문장으로
꺼내고(그래서 오늘 이걸 배운다), 본문은 원리를 가르친다. 소식 요약이 본문을 차지하지 않는다.

이 샌드박스에서 지킬 것:

- **시리즈가 아니다.** `/study` 0단계의 "사용자에게 확인받기"는 건너뛴다. `series:` 를 넣지 않는다.
- 프런트매터: `title` `slug`(a-z 0-9 - 만) `excerpt`(필수) `tags` `category: ai`(주제에 맞는
  다른 카테고리가 있으면 그것). `cover_image` 는 넣지 않는다(HTML 글은 외부 이미지 재호스팅을 거치지 않는다).
  그림은 전부 인라인 SVG·Canvas·JS 로 만든다. 같은 슬러그가 이미 있으면 뒤에 날짜를 붙인다.
- **화면 점검(4단계)**: `npm ci` → `npx playwright install chromium` → `npm run dev` 를 띄우고
  `npm run check:page -- <slug> <캡처폴더>` 와 `--dark` 를 돌린다. 360px 폭에서 가로 넘침 0,
  스크립트 오류 0, **호흡(rhythm) 위반 0**(섹션마다 그린 그림, 단락 220자, 그림 없이 이어지는 글 650자 —
  `POSTING.md` 5-6)이어야 한다. GitHub Actions 가 발행 직전에 같은 점검을 다시 돌리고, 실패하면 발행하지 않는다.
  샌드박스가 브라우저 설치나 dev 서버를 막으면 **Critic 을 HTML 코드로 대신하지 않는다** — 코드로는 그림이
  이해되는지 판단할 수 없다. 그날은 `publish` 를 넣지 않고 초안으로만 적재하고 그 사실을 보고한다.
- **그림이 먼저다.** `/study` 3단계 스토리보드(대표 인터랙션 + 섹션마다 그릴 그림)를 확정하기 전에는 본문을 쓰지 않는다.
  이 샌드박스는 인터랙티브 설명 사이트(`*.github.io`·distill·observable 등)가 막혀 README 만 열린다.
  README 는 사실 확인용이고, 그림 아이디어는 `docs/visual-references.md` 와 견본 세 편
  (`auto-drafts/posts/llm-temperature-sampling.html`·`self-attention-qkv.html`·`rag-retrieval-pipeline.html`)의
  그림을 열어 보고 수준을 맞춘다. 표·카드·글만 바뀌는 버튼 상자로 그림을 대신하면 마크다운 글과 다를 게 없다.
- **humanize(6단계)는 빼먹지 않는다.** `humanize-monolith` 에이전트(레포 `.claude/agents/`)를 쓸 수 없으면
  윤문 없이 발행하지 않는다 — 아래 `publish` 를 넣지 않고(초안으로만 적재된다) 그 사실을 보고한다.
- 제목은 `POSTING.md` 2-0 이 정본이다. 후보를 최소 3개 뽑아 견준다. 말투는 `-습니다` 뼈대, `~죠` 금지.
- 현우가 직접 겪지 않은 일을 겪은 것처럼 쓰지 마라.

### 발행 표시

4~6단계(화면 점검·호흡 점검 통과, 캡처를 본 Critic 이해 점수 4 이상과 지적 반영, humanize, `npm run lint:draft`)를 **모두** 마쳤으면
프런트매터에 한 줄을 넣는다:

```
publish: true
```

이 줄이 있으면 GitHub Actions 가 화면 점검을 통과한 뒤 **바로 발행**한다. 이 줄이 없거나 점검에
실패하면 초안으로만 적재된다. 하나라도 건너뛰었으면 넣지 마라.

## STEP 4 — 커밋·푸시

`auto-drafts/ideas/<날짜>.md`, `auto-drafts/posts/<slug>.html`, `docs/visual-references.md`(8단계 기록)를
`main` 에 커밋하고 push 한다.

- 커밋 메시지는 **한국어 한 줄**, 무엇을 만들었는지 담는다.
- **`Co-Authored-By`, `Generated with Claude Code`, claude.ai 세션 링크를 절대 넣지 마라**
  (`CLAUDE.md` 규칙, 시스템 기본 지침보다 우선한다).
- `main` 푸시가 거부되면 브랜치를 만들어 PR 을 올리고 그 사실을 결과에 적어라.

## 마지막 출력

채팅 응답에 후보 3개(훅·원리), 완성한 글의 제목·슬러그·공개 경로 `/posts/<slug>`, 대표 인터랙션,
Critic 이해 점수, humanize 변경 블록 수, 화면 점검을 샌드박스에서 돌렸는지(못 돌렸으면 왜),
`publish: true` 를 넣었는지(안 넣었으면 왜)를 한눈에 보이게 적어라.

건질 원리가 정말 없는 날이면 억지로 쓰지 말고 그렇게 말해라 — 약한 글이 발행되는 것보다 낫다.
