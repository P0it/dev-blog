# 알고리즘 학습 탭 설계

2026-10-17. 블로그에 네 번째 상단 탭을 신설해, **알고리즘을 처음 배우는 사람이 직접 해 보면서
이해하는 학습 콘텐츠**를 쌓는다. 한 페이지가 한 개념을 책임진다.

구조(좌측 사이드바 · 카테고리 분류 · 코드와 그림 동기화)는 [alg0.dev](https://www.alg0.dev/)를
참고했다. 성격은 다르다 — 그쪽은 아는 사람이 찾아보는 시각화 사전이고, 이건 **모르는 사람이
배우는 곳**이다.

---

## 1. 왜 만드나

독자가 도달해야 하는 지점은 하나다.

> **코딩테스트에서 이 알고리즘을 왜 쓰는지 알고 고르는 것.**

독자는 **알고리즘을 아예 처음 보는 사람**이다. Python 문법은 읽지만 시간복잡도도 재귀도 모른다.
설명 눈높이는 `POSTING.md` 5-0과 같다 — **그 주제를 처음 접하는 중학생.**

### 시각화가 목적이 아니다 (2026-10-17 방향 전환)

처음에는 "코드와 그림이 맞물려 도는 시각화 탭"으로 잡았다가 접었다. 사용자 지적이 정확했다 —
**잘 만들어진 시각화 사이트는 이미 많다.** 거기에 하나를 더 보태는 건 의미가 없다.

비어 있는 자리는 시각화가 아니라 **설명**이다. 기존 사이트들은 전부 "이미 아는 사람이 동작을
확인하는 곳"이라, 처음 보는 사람이 거기서 배우지는 못한다. 그래서 이 탭은 설명이 주인공이고
시각화는 설명의 수단이다.

### 핵심 규칙 — 먼저 해 보게 하고, 그다음 풀어쓴다 (2026-10-17 사용자 결정)

**페이지 맨 위는 설명이 아니라 독자가 직접 하는 것이다.** 설명은 방금 겪은 걸 되짚는 자리에 온다.

이분 탐색 샘플이 이 규칙을 보여 준다. 페이지를 열면 바로 1~100 up-down 게임이 떠서 독자가
숫자를 부른다. `더 커요 ↑`가 뜨고 남은 후보 막대가 실제로 좁혀진다. 맞히고 나서야 판정이 나온다 —
`12번 걸렸습니다. 매번 가운데만 골랐다면 최대 일곱 번이었습니다.` 일곱 번이라는 숫자를 미리
알려 주지 않는다. 독자가 자기 횟수를 본 뒤에 듣는다. **맞히기 전에는 그 뒤 설명 문단도 숨어 있다.**

이렇게 하면 독자는 설명을 읽기 전에 이미 "절반씩 날아가는구나"를 몸으로 안다.

샘플: `.superpowers/sample-binary-search.html` (이 문서의 기준점이다. 새 페이지를 만들 때 먼저 연다.)

### 쉬움의 기준 — 아침에 머리가 안 깬 상태로 읽어도 후루룩 (2026-10-17 사용자 지시)

"중학생 눈높이"는 재기 어렵다. 이 기준으로 바꾼다. **집중해서 읽어야 이해되는 문장은 실패다.**
멍한 상태로 훑어도 걸리는 데 없이 넘어가야 한다. 퇴고할 때 다음을 센다.

- **한 문장은 한 가지만 말한다.** `~때문입니다`, `~인 이유는`, `~했던 것은` 같이 한 문장 안에
  원인과 결과가 겹쳐 있으면 두 문장으로 자른다
- **되돌아가 읽어야 하는 문장을 남기지 않는다.** 주어가 멀거나 수식이 길어 끝까지 가서야
  뜻이 잡히는 문장은 앞에서부터 순서대로 풀리게 다시 쓴다
- **한 문단은 세 문장을 넘지 않는다.** 넘으면 쪼개거나 버린다
- **용어는 겪은 뒤에 붙인다.** 독자가 ①에서 직접 해 보기 전에 `이분 탐색`·`포인터`·`재귀` 같은
  말을 먼저 꺼내지 않는다
- **괄호와 쉼표로 끼워 넣지 않는다.** 끼워 넣고 싶은 설명은 다음 문장으로 빼거나 지운다
- **한 화면에 글만 가득한 자리를 만들지 않는다.** 설명이 길어지면 그림이나 해 볼 것이 빠진 것이다
- **줄글로 쓰지 않는다 (2026-10-17 사용자 지시).** 핵심이 딱딱 읽히게 끊는다.
  문단 셋이 될 자리는 **키워드를 머리에 둔 불릿 셋**으로 바꾼다 (`버릴 수 있던 이유 — …`).
  수가 이어지는 설명은 문장이 아니라 체인으로 (`100 → 50 → 25 → … → 1`).
  정의는 등호로 (`매번 절반씩 버리는 방법 = 이분 탐색`)

이 기준은 `humanize` 뒤에 한 번 더 돈다. 윤문은 문체를 고치지 길이와 겹침을 줄이지 않는다.

### 읽는 자리 — 출퇴근길 (2026-10-17 사용자 지시)

주 사용처는 책상이 아니라 **지하철·버스 안이다.** 모바일이 기본 화면이고 데스크톱이 덤이다.
이게 앞의 규칙들보다 위에 있다 — 데스크톱에서 아무리 좋아도 **서서 한 손으로 못 보면 실패다.**

- **한 페이지는 한 정거장.** 3~5분. 이 기준에서 벗어나면 개념을 더 쪼갠다
- **한 손 엄지로 다 된다.** 조작은 화면 아래쪽에 두고, 손가락이 닿는 크기(최소 44px)로 만든다.
  **타이핑을 요구하지 않는다** — 숫자 입력이 필요하면 버튼이나 슬라이더로 받는다
  (샘플의 up-down 게임도 입력창 대신 누르는 방식으로 고쳤다)
- **가로 스크롤 금지.** 코드 블록도 줄을 접거나 좁은 폭에 맞게 다시 쓴다.
  좁은 화면에서 플레이어는 그림/코드 탭 전환이다
- **중간에 끊긴다.** 내려야 해서 닫고 다음 날 다시 연다. 어디까지 봤는지 표시하고,
  **같은 자리에서 이어 보게 한다**(페이지 안 진행 위치를 `localStorage` 에 둔다)
- **네트워크가 끊긴다.** 터널에서 멈추지 않게 페이지는 자기 완결이어야 한다.
  외부 폰트·이미지·CDN 라이브러리에 기대지 않는다
- **소리는 없다.** 소리로만 전달되는 정보를 만들지 않는다
- **한 화면에 그림 하나.** 작은 화면에서 그림 둘이 겹쳐 보이면 둘 다 안 보인다

### 제목은 알고리즘 이름, 소제목은 독자가 아는 장면 (2026-10-17 사용자 결정)

```
탐색                        ← 카테고리
이분 탐색                   ← 제목(h1) = 알고리즘 이름
업-다운 게임 잘하는 법       ← 소제목(lede) = 독자가 이미 해 본 장면
```

**제목은 알고리즘 이름 그대로 쓴다.** 목록에서 훑을 때 바로 보이고, 검색으로 들어오는 길도 여기다.
사이드바 항목명과 제목이 같아서 어디에 있는지 헷갈리지 않는다.

**읽을 이유는 소제목이 만든다.** 독자가 이미 해 본 것, 잘하고 싶은 것, 몰랐던 것으로 건다.
설명을 요약하지 않는다 — `정렬된 배열에서 값을 찾는 방법` 같은 소제목은 아무도 누르지 않는다.

소제목 검사 기준 두 가지다.

- **한 눈에 들어오나.** 읽고 무슨 얘기인지 바로 안 잡히면 실패다.
  `스무고개로 백 개를 일곱 번에 줄이는 법`은 무슨 백 개인지 안 보여서 버렸다
- **읽을 이유를 만드나.** 설명만 하는 문장은 눌리지 않는다

예시 — 왼쪽이 제목, 오른쪽이 소제목이다.

| 이분 탐색 | 업-다운 게임 잘하는 법 |
|---|---|
| 버블 정렬 | 옆 사람과 키 순서로 서 보기 |
| 스택 | 왜 Ctrl+Z 는 방금 한 것부터 되돌릴까 |
| BFS | 소문은 어떻게 퍼질까 |
| 해시 | 사물함을 번호 대신 이름으로 찾기 |
| 재귀 | 거울 앞에 거울을 두면 |

본문에서는 **용어를 ②되짚기 전까지 쓰지 않는다.** 제목에 이름이 떠 있어도, 독자가 직접 해 보기
전에 `이분 탐색`·`포인터`·`재귀` 같은 말을 꺼내지 않는다.

## 2. 목표 · 비목표 · 실패 조건

### 목표

1. 상단 네비에 네 번째 탭을 신설한다(`Posts · Series · Labs` 옆).
2. 좌측 고정 사이드바 — 검색(`/` 단축키) · 접히는 카테고리 그룹 · 개수 배지.
   **사이드바 순서가 곧 학습 순서다.**
3. **한 페이지 = 한 개념.** 한글 1,200~1,800자, 작은 그림 네댓 개, 읽는 데 5~7분.
   스크롤 서너 번이라 챕터 넘김 장치가 필요 없다.
4. 페이지마다 맨 위에 **직접 하는 것**이 있다(1절 규칙).
5. 코드와 그림이 맞물려 도는 **플레이어** — 설명 중간, 원리를 겪은 뒤에 온다.
6. **입력을 바꿀 수 있다.** 내 배열, 최악 입력.
7. **확인 문제** — 틀려도 그 자리에서 이유가 나온다.
8. 라이트·다크 모두 제대로 산다.

### 비목표

- **여러 언어 제공 안 한다.** Python 하나다(사용자 결정).
- **압축 카테고리를 넣지 않는다.** LZ77·LZW·DEFLATE·Brotli는 코딩테스트에 안 나온다.
- 채점 서버·문제 제출·로그인·진도 저장은 1차 범위 밖이다.
- 다국어. 블로그 자체가 다국어를 껐다.
- **블로그 글 시리즈로 만들지 않는다.** 검토하다 접었다 — 알고리즘은 순서대로 읽는 것보다
  필요할 때 찾아 들어가는 쪽이고, 사이드바로 옮겨 다니는 경험이 시리즈 네비게이션으로는 안 나온다.
- **Supabase 를 쓰지 않는다.** 아래 7절.

### 실패 조건 (기술적으로 돌아가도 실패)

- 페이지를 다 보고도 **"그래서 이 문제에 이걸 왜 쓰지"에 답을 못 하면** 실패다.
- **처음 보는 사람이 읽다가 막히면** 실패다. 아는 사람이 보기 좋은 페이지는 목표가 아니다.
- 설명이 길어져 독자가 첫 화면에서 창을 닫으면 실패다. **직접 할 것이 먼저 나와야 한다.**
- 그림이 멋있는데 코드와 안 맞으면 실패다.
- 스크립트가 꺼졌을 때 페이지가 백지가 되면 실패다.

## 3. 한 페이지의 구성

위에서 아래로. **순서를 바꾸지 않는다.**

| | 자리 | 내용 |
|---|---|---|
| ① | **직접 해 보기** | 독자가 하는 것. up-down 게임, 카드를 직접 정렬해 보기, 미로를 손으로 짚어 보기. 알고리즘 용어는 아직 안 나온다 |
| ② | **방금 한 것 되짚기** | ①의 결과를 숫자로 보여 주고 이름을 붙인다. `12번 걸렸습니다 → 가운데만 고르면 최대 일곱 번 → 이걸 이분 탐색이라고 부릅니다` |
| ③ | **조건 짚기** | 이게 되려면 무엇이 필요한가(정렬돼 있어야 한다). 규칙으로 주지 않고 ①에서 끌어낸다 |
| ④ | **코드와 플레이어** | 방금 한 걸 코드로 옮긴다. 한 칸씩 돌리며 켜진 줄이 그림의 무엇을 바꾸는지 본다 |
| ⑤ | **확인 문제** | 조건을 바꿔 물어본다. 틀려도 그 자리에서 이유가 나온다 |
| ⑥ | **틀리는 자리** | 경계 조건, Python 특유의 함정(재귀 깊이, `list.pop(0)`의 O(n)) |
| ⑦ | **꺼내라는 신호** | 문제에서 이것들이 같이 보이면 이걸 쓴다. 칩 형태 |

②가 비면 이 프로젝트의 목적이 페이지에서 사라진다. ⑦이 비면 코딩테스트 목표가 사라진다.
**둘 다 빈 채로 올리지 않는다.**

## 4. 시각 규약

편마다 다시 고르지 않는다. 독자가 열 페이지쯤 돌면 **색만 봐도 안다**가 목표다.

### 상태 무대 여섯 종

| 이름 | 쓸 곳 |
|---|---|
| `track` 칸 트랙 | 배열·리스트. 값이 든 칸이 한 줄 |
| `flag` 포인터 깃발 | 칸 아래 꽂히는 `left` `mid` `right` |
| `lane` 레인 | 스택·큐·덱·힙. 들어가는 쪽과 나오는 쪽을 화살표로 못박는다 |
| `map` 노드 지도 | 그래프·트리. 간선을 타고 번지는 것 |
| `tower` 호출 탑 | 재귀. 쌓이고 되돌아 걷히는 층 |
| `grid` 격자 | 2차원 DP 표·미로. 칸이 채워지는 **순서**가 그림의 내용이다 |

### 상태 색 여섯 개 — 고정

`globals.css` 디자인 토큰에 매핑한다. 하드코딩하지 않는다.
(토큰 이름은 `--fg-primary`·`--fg-cautionary` 등으로 다르다. 매핑은 builder 몫이다.)

| 상태 | 역할 | 뜻 |
|---|---|---|
| 현재 | primary | 지금 보고 있는 칸·노드 |
| 비교 중 | warn | 견주는 중 |
| 확정 | success | 정렬 완료·방문 끝·최단거리 확정 |
| 버림 | danger | 범위에서 잘려 나간 것 |
| 범위 밖 | mute | 아직 안 건드린 것 |
| 대기 | accent | 큐·힙에서 차례를 기다리는 것 |

### 숫자 뒤 조사는 함수로 고른다

이 탭은 문장에 숫자가 계속 박힌다(`31이 찾는 42일까요?`). 문자열을 그냥 이으면
`31 가 42 보다` 같은 문장이 나온다. 받침 유무로 `이/가`·`은/는`·`을/를`을 고르는 공용 함수를 둔다.
숫자는 **마지막 자리를 읽는 소리**로 판단한다(0·3·6·7·8 받침 있음 — 영/삼/육/칠/팔).

### 모션

- 단계 전환은 CSS 전환(투명도 + 이동, 0.35~0.55초, `cubic-bezier(.2,.7,.2,1)`).
  `innerHTML` 다시 그리기나 `display:none` 토글로 끊어 보이게 하지 않는다.
- `prefers-reduced-motion`에서는 전환을 끄고 상태만 바뀐다.
- **플레이어는 처음에 멈춰 있다.** 자동 재생하지 않는다. alg0.dev는 들어가자마자 돌아서
  설명을 읽기 전에 중반을 지나가 있다.

### `POSTING.md`와의 관계

`POSTING.md`는 **글**의 규약이고 이 탭은 글이 아니다. 5-3의 "단계 흐름은 스크롤로, 버튼은 체험용"
규칙은 적용하지 않는다 — 알고리즘은 되감아 느리게 다시 보는 게 학습의 핵심이라 재생 컨트롤이
맞다(사용자 결정).

반대로 **5-0(처음 접하는 중학생)과 5-6(그림 먼저, 글은 짧게)은 그대로 적용한다.**

`POSTING.md`에 **"5-8. 알고리즘 학습 탭은 별도 규약을 따른다"** 한 줄과 이 문서 링크를 남긴다.
안 남기면 다음에 5-3을 읽은 쪽이 이 탭을 스크롤 방식으로 되돌린다.

## 5. 범위

레퍼런스 목록을 따라가지 않는다. 기준은 **코딩테스트 출제 빈도**이고, 온라인 저지(백준·프로그래머스)와
기업 시험(삼성 SW역량테스트·카카오 등)을 **전부 커버**한다(사용자 결정).

**단위는 알고리즘이 아니라 개념이다.** "이분 탐색" 하나였던 게 이렇게 갈린다.

- 반으로 자르면 왜 빨라지나 (비유와 직관만, 코드 없음)
- 이분 탐색 — 정확히 있는 값 찾기
- 왼쪽 끝·오른쪽 끝 찾기 (`bisect_left` / `bisect_right`)
- 경계 조건에서 틀리는 자리
- 답을 이분 탐색하기 (파라메트릭 서치)

한 페이지가 한 가지만 책임지니 독자가 어디서 막혔는지도 분명해진다. 항목 수는 늘지만
학습 콘텐츠에서는 그게 맞다.

### 카테고리와 티어

티어 1을 먼저 완성하고 2·3을 붙인다.

| 카테고리 | 티어 1 | 티어 2 | 티어 3 |
|---|---|---|---|
| **기초 개념** | 시간복잡도(Big-O), 재귀, 완전탐색, 투 포인터, 슬라이딩 윈도우, 누적합 | 공간복잡도, 비트마스크, 그리디 vs DP | 좌표압축 |
| **자료구조** | 배열·리스트, 스택, 큐·덱, 해시(dict·set), 힙(우선순위 큐) | 트리, 유니온파인드, 연결리스트 | 트라이, LRU 캐시 |
| **정렬** | 선택·삽입·버블(원리용), 병합, 퀵, Python `sort`와 커스텀 키 | 힙 정렬, 계수 정렬 | 기수 정렬 |
| **탐색** | 선형 탐색, 이분 탐색, `bisect`(lower/upper bound) | 파라메트릭 서치 | — |
| **그래프 탐색** | BFS, DFS, 격자 BFS·DFS, 연결요소 | 다중 시작점 BFS, 위상정렬, 사이클 판별 | 0-1 BFS |
| **최단경로·MST** | 다익스트라 | 플로이드-워셜, 크루스칼 | 벨만-포드, 프림 |
| **DP** | 메모이제이션(피보나치), 1차원 DP, 0/1 배낭 | LIS, LCS, 편집거리 | 구간 DP, 비트마스크 DP, 트리 DP |
| **그리디** | 거스름돈, 활동 선택 | 최소 회의실(힙), 교환 논증 | — |
| **백트래킹·구현** | 순열·조합 만들기, N-퀸, 시뮬레이션(델타 배열) | 스도쿠, 미로 경로 | — |
| **문자열** | 문자열 기본·회문 | KMP | 라빈-카프, 아호코라식 |
| **수학** | GCD·LCM(유클리드), 소수·에라토스테네스 | 모듈러 연산, 빠른 거듭제곱 | 조합론 |
| **고급 자료구조** | — | 세그먼트 트리 | 펜윅 트리(BIT), LCA |

알고리즘 기준 티어 1이 35개, 전체 75개다. **개념 단위로 쪼개면 티어 1만 60~70 페이지가 된다.**

**이 분류는 결정판이 아니다.** 만들다 보면 옮겨야 할 항목이 나온다(투 포인터를 기초 개념에 둘지
탐색에 둘지). 옮기면 이 문서를 같이 고친다.

## 6. 1차 출시

**파일럿 2~3개**로 시작한다(사용자 결정). 무대 종류가 서로 다른 것으로 고른다.

1. **이분 탐색** — `track` + `flag`. 샘플이 이미 있다
2. **버블 정렬** 또는 **선택 정렬** — `track`. 비교·교환 카운트가 살아 있는 것
3. **BFS (격자)** — `grid` + `lane`. 큐가 어떻게 번지는지

셋을 만들면서 규약(무대 컴포넌트 경계·테이프 인터페이스·페이지 구성)을 확정하고, 그 뒤에 늘린다.

**"탭을 띄운다"의 기준**: 세 페이지가 ①~⑦ 전부 채워진 상태 + 사이드바 전체 목록이 보이고
아직 없는 항목은 비활성으로 떠 있는 상태. 2~3주.

## 7. 기술

### 콘텐츠는 전부 레포 안에 둔다 — Supabase 를 쓰지 않는다

처음에는 `/lab` 패턴(Supabase `projects` 테이블 + 어드민)을 복제하려 했다가 접었다.
블로그 글은 "써서 발행하고 그 뒤엔 거의 안 건드리는 것"이라 DB가 맞지만, 알고리즘 페이지는 다르다.

- **글과 시각화 코드가 한 몸이다.** 함정 문단을 고치는 일은 보통 테이프 생성기도 같이 고치는 일이다.
  둘이 다른 저장소에 있으면 한쪽만 고쳐진다
- **Python 코드 ↔ JS 구현 대조 테스트가 레포에 있어야 한다.** 코드가 DB에 있으면 테스트가 DB를 읽어야 한다
- 어드민에서 폰으로 고칠 일이 거의 없다. 알고리즘 수정은 대개 코드 수정을 동반한다
- 변경 이력·리뷰가 git 에 남는다

따라서 **어드민 화면도, 적재 스크립트도 만들지 않는다.** `src/content/algo/<slug>.tsx` + 컴포넌트. (MDX 를 쓰지 않는다 — 레포에 MDX 설정이 없고, 페이지가 글과 인터랙션의 뒤섞임이라 TSX 한 벌이 더 단순하다.)

### URL

`/algo/<slug>`. 레퍼런스는 `/bubble-sort`처럼 루트에 평평하게 두지만, 이 사이트는 루트에
`posts`·`series`·`lab`·`tags`·`categories`가 이미 있어 충돌한다. 카테고리 인덱스는 `/algo/c/<category>`.

### 보여 주는 Python 과 실제로 도는 코드 — JS 구현 + 대조 테스트 (사용자 결정)

입력을 바꿀 수 있어야 하므로 스텝을 미리 구울 수 없고 브라우저에서 계산해야 한다.
그런데 독자에게 보여 주는 코드는 Python 이다. 세 갈래 중 **JS 로 구현하고 줄 번호를 매핑하는**
쪽을 골랐다. 가볍고, 스크립트가 꺼져도 서버에서 스텝 0 을 그릴 수 있다.

Pyodide 는 어긋날 수 없다는 장점이 있지만 첫 로드에 10MB 가까이 받고, 서버에서 테이프를 못 구워
"스크립트가 꺼지면 스텝 0 이 보인다"는 실패 조건을 지킬 수 없어 뺐다.

**조건이 하나 붙는다.** Python 코드와 JS 구현이 같은 결과를 낸다는 것을 **스텝 단위로**
테스트로 못박는다 — 최종 출력만이 아니라 줄 번호·변수 값 시퀀스를 대조한다.
Python 쪽에 tracer 하니스를 두고 CI 에 Python 런타임을 들여야 한다. 현재 레포 테스트는
`node --experimental-strip-types --test "src/**/*.test.ts"` 하나뿐이고 Python 도구가 없다.

### 스텝 테이프

```
{ line: 8,                       // 켤 코드 줄 번호
  vars: { left: 5, right: 9, mid: 7 },
  stage: { ... },                // 그림의 상태
  note: "더 오른쪽에 있습니다. 왼쪽 5칸을 버립니다" }
```

**지연 생성한다.** 버블 정렬에 N=200 을 넣으면 수만 스텝이라 전부 구우면 메모리가 터진다.
제너레이터로 흘리고 스텝 상한을 건다(상한에 닿으면 "여기까지만 보여 줍니다"로 끊는다).

### 그 밖의 설계자 판단

- **비유 히어로는 선택 항목이다.** 알고리즘마다 고유한 일회용 모션이라 재사용이 0이고,
  공들이면 항목당 공수가 몇 배로 뛴다. 단순 SVG 두세 컷 수준을 기본으로 하고,
  ①의 "직접 해 보기"가 그 역할을 대신하면 생략한다
- **확인 문제는 공통 엔진 + 손으로 쓴 이유 문장.** 문항 틀은 테이프 diff 에서 뽑되,
  틀렸을 때 보여 줄 이유는 자동 생성으로 안 나오므로 페이지마다 쓴다
- **계수기는 가벼운 카운팅 함수**로 충분하다. 비교군까지 테이프를 만들지 않는다
- **모바일에서 플레이어는 그림/코드 탭 전환.** 둘을 위아래로 쌓으면 화면을 다 먹는다
- **사이드바 검색은 클라이언트에서 전량 거른다.** 이름 + 한/영 별칭(`이분탐색`/`binary search`/
  `bisect`) + 신호 칩까지 걸고 한글 초성을 받는다. 항목이 100 개 이하라 서버 질의가 필요 없다
- **본문 집필은 `/algo` 커맨드를 새로 만든다.** `/draft`·`/study` 는 Supabase `posts` 에
  적재하므로 그대로 못 쓴다. 눈높이·`humanize` 규약은 `POSTING.md` 를 그대로 타되
  결과를 `src/content/algo/<slug>.tsx` 로 떨어뜨린다

### builder 몫

- 사이드바 상태(접힘·검색어·스크롤 위치)를 페이지를 옮겨도 유지하는 방법
- 테이프 생성기의 공통 인터페이스 — 페이지마다 각자 짜지 않게
- 무대 여섯 종의 컴포넌트 경계
- 입력 받는 문법(그래프·트리를 텍스트로 어떻게 받나) 과 잘못된 입력 처리
- 상태 색 여섯 개를 기존 토큰에 매핑
