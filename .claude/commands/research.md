# /research — 개념 → 다중소스 조사 → 종합 글 (직접 경로)

조사할 개념 / 주제 / 앵글: **$ARGUMENTS**

URL 하나를 번역·요약하는 `/draft` 와 달리, 이 커맨드는 **여러 소스를 조사해
하나의 글로 종합**한다. 출처를 그대로 옮기는 게 아니라 **여러 자료를 녹여
작성자 자신의 개념으로 재구성**한다. `ai_jobs` 큐·워커·`claude` CLI 를 거치지
않고 이 세션이 직접 쓴다.

## `/draft` 와 다른 점 (먼저 숙지)

- **소스가 여럿**이다 — 단일 원문이 아니라 검색으로 찾은 여러 글·문서·저장소를 취합.
- **고정 구조에 매이지 않는다** — "개념→사례→생태계" 같은 순서 강제 없음.
  모은 내용을 작성자 관점에서 가장 자연스러운 흐름으로 재구성한다.
- **시각자료는 "실제 웹 이미지 우선, 없으면 생략"** — 카탈로그 카드를 글마다
  기본으로 깔지 않고, 직접 그린 SVG 로 소제목을 채우지도 않는다(매 글 같은 그림은
  자동생성 티가 난다). 아래 "시각자료 방침" 을 따른다.
- **참고 자료는 공식 이미지를 쓸 때만 단다** — 이미지를 가져오면 `## 참고 자료`
  로 원출처를 밝힌다. 이미지를 안 쓰면 참고 자료·저작권 줄도 넣지 않는다(여러
  소스를 녹여 작성자 개념으로 쓴 글이므로).
- 그 외 **말투·제목·헤드라인 규약은 POSTING.md 를 그대로** 따른다.

## 시각자료 방침 (★ 핵심) — 실제 웹 이미지 우선, 직접 그리기는 최소로

**그림은 할당량이 아니다.** 소제목마다 하나씩 채우지 않고, 최소 장수 요구도 없다.
실제 이미지는 많을수록 좋고, 직접 그린 그림은 적을수록 좋다.

1. **실제 이미지를 먼저, 최대한.** 조사하며 연 페이지에 쓸 만한 그림이 있는지 함께 본다 —
   공식 문서의 다이어그램, 릴리스 노트 스크린샷, 벤치마크 도표, 제품 UI 캡처, 논문 figure.
   독자가 글을 신뢰하는 건 진짜 화면을 볼 때다. **개수 제한 없다.**
   - **자체 버킷에 재호스팅**(핫링크 금지): `npm run fetch:image -- <원본 이미지 URL>`
     → 출력 공개 URL 을 `![설명](그 URL)` 으로 박는다.
     클라우드 루틴(`.env.local` 없음)에서는 이 명령을 못 돌린다 — `![설명](REHOST:원본URL)` 마커로 남기면 Actions 가 치환한다.
   - 쓰기 전 `curl -sIL <URL>` 로 200·image/* 인지 확인하면 헛수고를 던다.
   - **내려받을 그림이 없으면 화면을 찍는다.** 공식 문서의 표·파일 목록·리더보드·토크나이저 같은
     도구 페이지는 `npm run shot -- <url> out.png --clip x,y,w,h` 로 잘라 찍고
     `npm run capture -- upload out.png` 로 올린다(Playwright, 옵션은 `scripts/shot.mjs` 머리말).
     Hugging Face 파일 목록·safetensors 뷰어처럼 "진짜 화면"이 개념 설명보다 잘 먹히는 자리가 많다.
2. **직접 그린 SVG(```illustration)는 구조·흐름을 설명해야만. 한 편에 0~2장.**
   POSTING.md 2-2 절 맨 앞의 판단 기준을 그대로 적용한다 — 평문만으로는 구조·흐름·설계가
   머리에 안 그려지는 자리에서만. 그리기 전에 자문한다: "이 그림을 빼면 독자가 이 대목을
   이해 못 하나?" 아니면 빼고 한 문장으로 적는다. **SVG 0장인 글이 정상이다.**
   - 그릴 때는 POSTING.md "```illustration" 절 하우스 스타일을 따른다 —
     `viewBox="0 0 800 450"`, stroke-width 2.5, 색은 디자인 토큰(`var(--diag-blue-fill)` 등)으로,
     3색 이내, 첫 자식 `<title>`. 라인아트는 워커 없이 본문에 바로 인라인 렌더된다
     (`markdownRender.tsx` → `Illustration`).
   - 디자인 토큰: `--diag-{blue,purple,teal,green,yellow,red,mute}-{fill,stroke}`,
     `--diag-edge`, `--diag-cluster-bg`, `--fg-strong`, `--fg-neutral`.
3. **카탈로그 카드(```visual)는 원칙적으로 0개.** 최대 1개, 숫자 세 개를 나란히 놓아야만
   의미가 사는 자리에만.
4. 그림보다 한 줄 문장이 나은 자리(마무리 감상 등)는 **비운다** — 억지 채우기 금지.
5. **여러 대상을 항목별로 견주는 대목은 마크다운 표**로 적는다. 카탈로그 카드를 안 쓴다는
   방침은 ` ```visual ` 블록 이야기지 본문 표까지 막는 게 아니다. 견줄 대상이 2~3개이고
   항목이 4줄 이상이면 표가 가장 잘 읽힌다(형식은 POSTING.md "마크다운 표" 절 —
   첫 칼럼은 행의 키, 헤더에 대상 이름, 셀은 한 줄).
6. **실제 이미지를 하나라도 썼으면 `## 참고 자료`** 에 그 원출처(이미지가 실린
   페이지·라이선스)를 적는다. 직접 그린 SVG 만 있으면 참고 자료는 불필요하다.
7. 외부 AI 래스터 이미지 생성(DALL·E 등)은 아직 미설치 — 쓰려면 별도 셋업 필요.

## 절차

1. **규약 숙지** — `POSTING.md` 의 "2-0. 제목"(후킹+SEO), "2. 말투·본문 골격",
   "2-1. 강조", "2-2. 시각자료 카탈로그" 를 읽는다. [[korean-writing-style]] 준수.

2. **다중소스 조사** — 주제를 여러 각도로 검색한다. 깊은 조사가 필요하면
   `deep-research` 스킬을 써도 된다(팬아웃 검색·소스 페치·사실 검증·종합).
   가볍게는 `WebSearch` 로 후보를 찾고 `WebFetch` 로 핵심 소스를 읽는다.
   - **개념** 자체: 공식 문서·대표 소개 글로 정확히 잡는다.
   - **실제 outcome·사례**: 그 기술을 써서 나온 결과(예: 토큰 절감, 성능 개선)를
     다룬 공개 글·벤치마크·케이스 스터디.
   - **생태계**: 그 기술로 만들어진 도구·저장소·Claude skill 등.
   - 주제에 따라 어떤 갈래가 중심인지는 달라진다 — $ARGUMENTS 의 앵글을 따른다.

3. **사실 검증** — 종합 글이라 출처를 본문에 밝히지 않더라도, **수치·고유명사·
   인용은 실제 소스에서 확인된 것만 쓴다**. 토큰 절감률·벤치마크 점수 같은
   숫자를 지어내지 않는다(POSTING.md "사실은 정확하게"). 소스마다 수치가
   엇갈리면 보수적으로 쓰거나 범위로 적는다. 감상·해석은 자유롭게 얹되 사실과
   구분되게.

4. **종합·집필** — 모은 내용을 **작성자의 개념으로 재구성**해 한국어 글 1편을 쓴다.
   - 본문은 `> 요약`(두괄식 훅·excerpt) → 서술형 문어체 `##` 헤드라인 순서.
     맨 위에 `# 제목` 을 다시 쓰지 않는다.
   - 순서·구조는 자유 — 가장 잘 읽히는 흐름으로. 한 헤드라인 = 한 메시지,
     그 아래는 가볍게(분량과 호흡).
   - `-습니다`체 + 부드러운 종결(`~까요?`/`~거든요`) 양념(`~죠` ✗ — POSTING.md 2절).
     **압축 문체 ✗** — "셋입니다"·"~의 정체"·중점 나열로 눌러 담지 말고 풀어서 말하듯(POSTING.md "풀어서 말하듯").
   - **제목은 독자가 실제로 물을 법한 짧은 질문**이 기본(`LLM 모델 뒤에 붙는 B가 뭘까요?`). 명사구에 정보를 눌러 담은 긴 제목 ✗.
   - **서두는 제목의 질문에 바로 답한다** — 독자가 겪은 장면 → 질문 → 직답 → 예시 → 이 글에서 얻는 것 (POSTING.md "서두").
     번역체·매문장 출처표딱지 금지.
   - **시각자료는 위 "시각자료 방침"** 대로 — 실제 웹 이미지(재호스팅)를 최대한 쓰고,
     직접 그린 SVG 는 구조·흐름이 평문으로 안 잡히는 자리에만 0~2장. 카드는 안 쓴다.
   - **실제 이미지를 하나라도 넣었으면** 끝에 `## 참고 자료` 로 원출처를 적는다.
     직접 그린 SVG 만 있으면 참고 자료 없이 마지막 헤드라인(정리·시사점 또는
     작성자의 마무리 감상)으로 맺는다.

   - **문체 퇴고 — POSTING.md 2-4 "퇴고 점검표" 를 그대로 돈다 (필수, 생략 금지).**
     사실·구조·링크·이미지는 그대로 두고 문장만 다시 읽는다. 검색 가능한 것(`죠.` / `고,` /
     `아니라` / `굴리`…)은 실제로 `grep` 해서 센다 — `npm run lint:draft -- drafts/<slug>.md` 가 한 번에 센다. 정리 글은 여러 소스를 옮기다 보니
     **손맛 동사(4번)·연결어미 뒤 쉼표(2번)** 가 특히 잘 쌓인다.

5. **파일 작성** — `drafts/<slug>.md` 를 만든다(`drafts/` 는 .gitignore 됨).
   ```
   ---
   title: 후킹+검색어를 담은 한국어 제목
   tags: [태그A, 태그B]
   category: ai            # 선택 — tech/business/design/claude/infra/ai/insights 중
   ---
   > 요약 인용구…
   ## 헤드라인…
   ```
   `source_url` 은 단일 출처가 없으므로 넣지 않는다.

6. **적재 — 실행 환경에 따라 갈린다.** `.env.local` 이 있으면 로컬, 없으면 클라우드 루틴이다.
   - **로컬**: `npm run draft -- push drafts/<slug>.md` 실행. 출력된 `/admin/editor?slug=…` 경로를 사용자에게 알린다. 검토 후 에디터에서 발행한다.
   - **클라우드 루틴**(Supabase 시크릿 없음, egress 제한): 파일을 `drafts/` 가 아니라 **`auto-drafts/posts/<slug>.md`** 에 쓴다. 이미지는 `npm run fetch:image` 대신 `![설명](REHOST:원본URL)` 마커로, 대표 이미지도 `cover_image: REHOST:원본URL` 로 남긴다. 커밋·푸시하면 GitHub Actions 가 재호스팅·적재한다(`docs/auto-daily-draft.md`). 커밋 메시지에 AI attribution 을 넣지 않는다.

형식·옵션 상세: `docs/draft-in-claude-code.md`. 단일 URL 글은 `/draft`.
