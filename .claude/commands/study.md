# /study — 학습 주제 → 인터랙티브 HTML 페이지 글

입력: **$ARGUMENTS**

입력은 셋 중 하나다. 수업 PDF·슬라이드·헷갈린 점 메모가 함께 오면 같이 읽는다.
- **주제 하나** — "RAG", "KV Cache"
- **시리즈 + 목차** — "LLM 기초 시리즈: 1. 토큰화 2. 임베딩 3. …"
- **수업 자료** — 파일 경로. 자료는 **무엇을 다룰지 고르는 데만** 쓴다. 내용은 조사로 다시 구성하고,
  자료의 문장·도식·디자인은 옮기지 않는다.

목표는 ByteByteGo·Jay Alammar 처럼 **그림만 보고도 원리와 관계가 이해되는** 글이다.
**그림이 이야기를 끌고 가고 글은 그 사이를 잇는다.** 호흡 규칙은 `POSTING.md` 5-6(섹션마다 그림, 단락 220자, 글만 이어지는 구간 650자).
**독자는 그 주제를 처음 접하는 중학생이다.** 눈높이 규칙은 `POSTING.md` 5-0 을 따른다.
글 하나가 그 주제만을 위한 페이지다. 견본: `auto-drafts/posts/llm-temperature-sampling.html`,
`self-attention-qkv.html`, `rag-retrieval-pipeline.html`. 견본은 수준을 맞추는 기준이지 복제할 틀이 아니다.
길이·섹션 수도 견본을 따르지 않는다. 다룰 개념이 정한다(`POSTING.md` 5-0 "분량").

## 0. 준비

- 규약을 읽는다: `POSTING.md` 의 2-0 제목, 2 말투, **2-4 퇴고 점검표**, **5 HTML 페이지 글**(특히 **5-0 눈높이**),
  그리고 2 말투 안의 **AI·LLM 업계 용어** 조항(청크·리랭킹처럼 업계가 부르는 대로).
- `docs/visual-references.md` 를 읽는다. 앞서 확인한 레퍼런스와 그때 쓴 설명 기법이 있다.
- 시리즈면 목차 전체를 먼저 보고 편마다 **겹치지 않는 핵심 질문** 하나씩을 정해 사용자에게
  한 번 확인받는다. 시리즈 행(`series` 테이블)이 없으면 `/admin/series` 에서 만들어 달라고 한다.
  그 뒤로는 편마다 아래 1~8을 반복한다.

## 1. 개념 분석 (메모만 — 본문은 아직 쓰지 않는다)

- 이 글이 답할 질문 하나(제목이 된다), 독자가 끝까지 읽고 손에 쥘 원리 한 문장.
- 흔한 오해 2~4개. 사용자가 헷갈린 점을 줬다면 그게 맨 앞이다.
- 이 글에 나올 용어 목록과 각 용어의 한 문장 풀이. 중학생이 모를 말은 전부 넣는다(벡터·확률·가중치 포함).
- 이 원리를 처음 보여 줄 일상 장면이나 작은 예 하나(구체 → 추상 순서의 출발점).
- 핵심 개념마다 중학생이 겪어 본 일상 비유 하나와 그 비유가 맞지 않는 부분 한 줄(`POSTING.md` 2 말투의 "눈높이").
- 2026년 기준으로 무엇이 바뀌었는지(요즘 쓰는 방식, 새 모델·API 의 제약). 근거 URL 과 함께.

## 2. 레퍼런스 탐색 (서브에이전트)

general-purpose 에이전트에게 맡긴다. 아래 지시문을 주제에 맞게 채워 그대로 쓴다(견본 세 편을 만든 지시문이다).

> 주제 "<주제>" 를 그림과 조작으로 설명하는 학습 페이지를 만든다. 세 축으로 레퍼런스를 찾아라 —
> 개념(무엇을 보여 줘야 하나), 표현(잘 만든 설명은 어떻게 그리나), 인터랙션(독자가 무엇을 조작하나).
> 다른 분야(물리·지도·사회 연결망·암호·음악 등)에서 하나 이상. 후보: Transformer Explainer, Jay Alammar,
> 3Blue1Brown, Distill, Bartosz Ciechanowski, Nicky Case, Red Blob Games, ByteByteGo, Observable 등.
> **이번 세션에서 실제로 연 것만 보고하고, 못 연 것은 "미확인"으로 적어라.** 후보 8~12개를 보고 3~5개를 남긴다.
> 출력(900단어 이내):
> - 남긴 레퍼런스: URL, 빌려 올 **설명 기법** 한 줄(그림체 아님), 언제 먹히는지
> - 학습자가 흔히 하는 오해 2~4개(출처)
> - **구체적인 그림 아이디어 2~3개: 무엇을 그리는가 / 독자가 무엇을 조작하는가 / 조작하면 무엇이 바뀌는가 / 어느 레퍼런스에서 빌렸는가**
> - 글에 넣을 사실(수식·수치·날짜)과 출처 URL
> 파일은 쓰지 마라.

인터랙티브 설명 사이트가 막힌 환경(클라우드 루틴 샌드박스는 `*.github.io`·distill·observable 등이 막힌다)에서는
README·문서만 열린다. 그건 **사실 확인용**이다. 표현 아이디어는 `docs/visual-references.md`(확인된 기법·"잘 먹힌 기법")와
견본 세 편에서 가져온다. 글로 된 자료만 보고 그림을 설계하면 그림도 글처럼 나온다.

## 3. 스토리보드 — 글보다 먼저 (한 글자도 쓰기 전에)

견본은 **그림 목록을 먼저 확정하고 글을 나중에 붙여** 만들었다. 이 순서를 지킨다.

1. **대표 인터랙션 하나** — 첫 화면(히어로)에 둔다. 이 글의 원리를 한 번의 조작으로 겪게 하는 장치다.
   견본 예: 온도계 하나가 페이지의 모든 그림을 함께 움직인다 · 마지막 단어를 바꾸면 "it"의 연결선이 옮겨 간다 ·
   질문 점을 끌면 가까운 청크가 바뀐다. 장치에 그 글만의 **시각 언어**(연결선, 지도, 입자, 색 섞기…)를 정한다.
2. **섹션 목록 = 그림 목록.** 섹션마다 한 줄씩:
   `소제목(질문형) | 첫 문장(이 섹션의 답) | 그림: 무엇을 그리나 | 조작: 무엇을 움직이나 | 깨는 오해 | 그리는 방식(SVG·Canvas·data-figure)`
   그림을 정할 수 없는 섹션은 따로 두지 않고 이웃 섹션에 합친다(맺음·참고 두 개만 예외, `data-text-only`).
3. 그림마다 후보 A·B·C 를 적고 하나를 고른다(예: 막대그래프 · 수직선 · 입자 시뮬레이션). 이유 한 줄.
4. **일상 비유(5-0)는 그림으로 그린다.** 비유 문단을 길게 쓰지 않는다.

원칙:
- 개념마다 **표현을 새로 고른다.** 카드 묶음, 매 섹션 같은 막대그래프처럼 같은 부품을 찍어 내지 않는다.
- **표·글만 바꾸는 버튼 상자·카드는 그림이 아니다.** 값을 위치·길이·색·모양으로 그린 것만 그림이다.
- 중학생이 그림만 보고 이해할 수 있게, 행렬·로그 같은 기호 대신 작은 숫자와 모양으로 그린다.
- 예시 값으로 그린 그림은 "설명을 위한 예시 값"이라고 밝힌다. 실제 데이터처럼 보이게 하지 않는다.
- 이미 시리즈에 나온 편과 첫 화면 구성·섹션 리듬이 겹치지 않게 한다.

## 4. 구현 — 그림을 먼저 만들고, 글은 그 사이에

- 파일: `auto-drafts/posts/<slug>.html`. 형식은 `POSTING.md` 5장(프런트매터 `excerpt` 필수,
  첫 줄 `<!-- page -->`, 모든 선택자는 `.post-page` 아래, 사이트 토큰, 다크모드, 360px, reduced-motion,
  스크립트는 `window.postPage.{root,signal}`).
- 스토리보드 순서대로 **그림과 인터랙션을 먼저** 구현하고 화면에서 돌아가는 걸 본 뒤, 섹션마다 글을 붙인다.
  글은 **5-6 호흡**을 지킨다: 첫 문장이 답, 단락 220자 이하, 그림 없이 이어지는 글 650자 이하, 곁가지는 `<details>`.
- DOM 으로 그린 그림(막대·격자·색칠한 문서)에는 `data-figure` 를 단다. 표·카드에는 달지 않는다.
- 슬러그는 ASCII 영문. 시리즈면 `series:` `series_order:` 를 넣는다.
- `npm run dev` 를 띄우고 `/internal/page/<slug>` 로 본다.
- `npm run check:page -- <slug> <캡처폴더>` 와 `--dark` 로 데스크톱·모바일을 찍는다.
  **가로 넘침 0, 스크립트 오류 0, 호흡(rhythm) 위반 0** 이어야 다음 단계로 간다. 캡처는 직접 열어 본다.

## 5. Critic (서브에이전트)

general-purpose 에이전트에게 **글의 의도를 알려 주지 않고 캡처 폴더만** 준다(HTML 원본은 주지 않는다 —
코드를 읽어서는 그림이 이해되는지 판단할 수 없다). 묻는 것:
1. 본문을 거의 읽지 않고 그림만으로 어떤 원리를 이해했는가 (1~5점)
2. 겹침·작은 글씨·다크모드 대비·모바일 비좁음·오해를 부르는 인코딩
3. 그림과 본문 설명이 어긋나는 곳 (기본값에서 그림이 본문과 다른 말을 하는지)
4. 템플릿 냄새, 같은 시리즈 앞 편들과 구성이 겹치는지 (앞 편 캡처도 함께 준다). 그림 자리를 표·카드·버튼 상자가 대신하는 곳
5. **이 주제를 처음 보는 중학생이라고 생각하고** 읽었을 때 풀이 없이 나온 용어, 막히는 문장, 건너뛴 단계. 반대로 비유만 있고 원리 설명이 얕은 대목
6. 읽다가 그만두고 싶어지는 글 벽이 있는 곳 (캡처 파일·위치)

**이해 점수 4 이상이어야 다음 단계로 간다.** 3 이하면 그 그림은 표현을 다시 고른다(3단계로).
2~6번 지적은 전부 고치고 4의 점검을 다시 돈다. 캡처를 만들 수 없는 환경이면 Critic 을 건너뛴 것으로 보고 발행하지 않는다.

## 6. humanize (빼먹지 않는다)

1. `npm run humanize:page -- extract auto-drafts/posts/<slug>.html <작업폴더>`
2. `humanize-monolith` 에이전트(`.claude/agents/`)에게 `<작업폴더>/<slug>.md` 를 주고
   `<slug>.final.md` 로 받는다. `quick_rules_path` 로 `<레포 절대경로>/.claude/skills/humanize-korean/references/quick-rules.md` 를 넘긴다. 프롬프트에 반드시 넣는다: `[[id]]` 블록 수·순서 유지, 태그·`${…}`·숫자 보존,
   장르 블로그, -습니다 체, `~죠` 금지, **AI·LLM 업계 용어는 영어·음차 유지**(이 글의 용어 목록을 적는다),
   사실·수치 변경 금지, **용어 풀이 문장을 지우거나 줄이지 말 것**(중학생 눈높이, `POSTING.md` 5-0).
3. 에이전트가 사실 오류를 짚으면 출처로 확인해서 고친다.
4. `npm run humanize:page -- apply auto-drafts/posts/<slug>.html <작업폴더>`
5. 추출 범위 밖 문구(aria-label, data-* 속성, a·span 라벨, 템플릿 문자열 속 문장)를 `grep` 으로 직접 훑는다.
6. `POSTING.md` 2-4 점검표를 돈다. `npm run lint:draft -- <파일>` 이 검색 항목을 센다.
7. `npm run check:page` 를 다시 돌려 오류 0 을 확인한다(윤문 뒤에도 스크립트가 멀쩡한지).

`humanize-korean` 은 레포 `.claude/` 에 들어 있다(`CLAUDE.md`). `humanize-monolith` 에이전트가 안 보이면 멈추고 알린다.

## 7. 적재

- `.env.local` 이 있으면: `npm run draft -- push auto-drafts/posts/<slug>.html`. 출력된 `/admin/editor?slug=…` 를 알린다.
- 없으면(클라우드 루틴): 파일을 커밋·푸시한다. GitHub Actions(`auto-draft-ingest`)가 적재한다.
  매일 루틴은 4~6을 모두 마쳤을 때 프런트매터에 `publish: true` 를 넣는다 — Actions 가 화면 점검을
  다시 돌려 통과하면 바로 발행한다(`docs/auto-daily-draft.md`). 로컬 실행에서는 넣지 않는다.
  HTML 글은 외부 이미지 재호스팅을 거치지 않으니 그림은 인라인 SVG·Canvas 로 만든다.
- 원고와 함께 커밋한다. 커밋 메시지에 AI attribution 을 넣지 않는다.

## 8. 레퍼런스 기록

`docs/visual-references.md` 에 이번에 실제로 열어 보고 쓴 레퍼런스를 추가하거나, 이미 있던 항목의
`쓴 글` 칸에 슬러그를 더한다. 잘 먹힌 설명 기법(예: "온도계 하나로 모든 그림 연동")도 한 줄 남긴다.
기록은 다음 글의 선택지를 넓히려는 것이지 재사용을 강제하려는 것이 아니다.

## 보고
