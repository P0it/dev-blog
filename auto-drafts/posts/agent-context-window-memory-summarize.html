대화가 길어지면 Agent는 무엇을 버려야 할까요?

Agent에게 사내 문서 정리를 맡겨 두고 한 시간쯤 지나면 답이 점점 느려지고 처음에 말한 조건을 잊은 듯한 답이 나오기도 합니다. 어느 순간에는 요청이 아예 거절됩니다. 대화가 길어질 때 Agent 안에서는 무슨 일이 일어나고 무엇을 남기고 무엇을 버려야 할까요?

대화가 길어지면 무엇이 문제인가요?

보내는 글이 context window를 채워 갑니다. 다 차면 요청이 거절됩니다.

LLM은 대화를 기억하지 못해서 프로그램이 매번 대화 전체를 다시 보냅니다. 모델이 한 번에 받을 수 있는 양에는 한도가 있습니다. 이 한도를 context window라고 합니다. 보낸 토큰과 받을 토큰을 합쳐 이 안에 들어와야 합니다.

Agent는 도구를 부를 때마다 결과가 대화에 붙어서 챗봇보다 훨씬 빨리 찹니다. 파일 하나를 읽은 결과만으로 수천 토큰이 들어오기도 합니다. 다 차면 API는 요청을 거절하거나 stop_reason을 model_context_window_exceeded로 돌려줍니다.

다 차기 전에도 문제가 생깁니다. 글이 길어질수록 LLM은 중간에 있는 내용을 놓치기 쉽습니다. 비용과 대기 시간도 보내는 토큰에 비례해 늘어납니다. 그래서 자리가 남아 있어도 필요 없는 글은 일찍 덜어 내는 편이 낫습니다.

가장 단순한 방법은 무엇인가요?

오래된 대화부터 잘라 냅니다. 대신 잘린 내용은 LLM이 영영 모릅니다.

잘라 내기는 코드 몇 줄로 끝나고 비용도 들지 않습니다. 짧은 상담처럼 앞의 대화가 금방 쓸모없어지는 서비스에는 이것으로 충분합니다.

하지만 처음에 정한 조건이나 앞에서 읽은 자료처럼 끝까지 필요한 내용도 같이 사라집니다. 그래서 오래 지켜야 할 규칙은 대화에 두지 않고 system 지시에 넣습니다. system은 잘라 내는 대상이 아니어서 매번 그대로 실려 갑니다.

잘라 낼 때 짝을 깨지 않도록 조심해야 합니다. 도구 부탁(tool_use)을 지우고 그 결과(tool_result)만 남기면 API가 오류를 냅니다. 부탁과 결과는 항상 함께 지우거나 함께 남깁니다.

내용을 잃지 않고 줄일 수는 없나요?

오래된 대화를 요약 한 칸으로 바꿉니다.

요약은 LLM에게 맡깁니다. 대화가 일정 길이를 넘으면 프로그램이 오래된 부분을 LLM에 보내 "앞으로 필요한 결정과 사실만 남겨 요약해 줘"라고 부탁합니다. 돌려받은 요약을 대화 맨 앞에 넣고 원래 칸은 지웁니다.

요약도 공짜는 아닙니다. 요약을 만드는 데 LLM을 한 번 더 불러야 하고 요약하면서 세부가 빠질 수 있습니다. 그래서 최근 몇 번의 대화는 원문 그대로 두고 그보다 오래된 부분만 요약하는 방식을 많이 씁니다.

Agent에서는 도구 결과가 가장 큰 덩어리입니다. 오래된 도구 결과만 "(결과 지움)"으로 바꾸고 부탁은 남기는 방법도 있습니다. LLM은 어떤 도구를 불렀는지는 알고 있어서 필요하면 다시 부릅니다. Claude API의 context editing은 이 일을 API 쪽에서 대신 해 줍니다.

다음 대화에서도 기억하게 하려면요?

대화 밖 저장소에 적어 두고 필요할 때 꺼내 옵니다. 이것을 장기 기억이라고 부릅니다.

지금까지 본 것은 대화 하나 안에서의 기억, 곧 단기 기억입니다. 대화가 끝나면 메시지 목록은 사라집니다. 다음 대화에서도 사용자의 취향이나 지난 결정을 알게 하려면 대화 밖 저장소에 따로 적어 둬야 합니다. 이것을 장기 기억이라고 합니다.

저장소는 데이터베이스여도 되고 파일이어도 됩니다. 무엇을 적을지는 두 방식이 있습니다. 대화가 끝날 때 프로그램이 LLM에게 "기억할 만한 것"을 뽑게 해서 적거나, 기억 쓰기 도구를 LLM에 주고 LLM이 필요할 때 적게 합니다. Claude API의 memory tool이 뒤쪽 방식입니다.

꺼낼 때가 더 중요합니다. 메모가 쌓이면 전부 넣을 수 없으니 이번 요청과 관련 있는 것만 골라 넣어야 합니다. 사용자마다 저장소를 나누지 않으면 남의 메모가 섞여 들어갑니다.

결국 무엇을 남기고 무엇을 버리나요?

이번 일에 필요한 글만 보내도록 고르는 일, 그것을 context engineering이라고 합니다.

방법하는 일이 시리즈에서
적어 두기대화 밖 저장소에 메모로 남긴다장기 기억, 할 일 목록 파일
골라 넣기이번 요청과 관련 있는 것만 꺼내 넣는다기억 검색, RAG
줄이기오래된 대화를 요약하거나 지운다잘라 내기, 요약, 도구 결과 지우기
나누기일을 다른 Agent에 맡겨 따로 처리하게 한다여러 Agent에 일 나누기

context engineering은 LLM에 보낼 글을 설계하는 일입니다. 프롬프트 한 줄을 잘 쓰는 것을 넘어, 지시·대화·도구 목록·도구 결과·기억 가운데 무엇을 어떤 순서로 얼마나 넣을지 정합니다. Anthropic은 이를 "원하는 결과를 낼 가능성이 가장 높은, 가장 작은 고신호 토큰 묶음을 찾는 일"이라고 설명합니다.

정답은 서비스마다 다릅니다. 짧은 상담은 잘라 내기로 충분하지만 몇 시간씩 일하는 Agent는 요약과 도구 결과 지우기, 장기 기억을 함께 씁니다. 실제 대화 기록을 보면서 무엇이 자리를 차지하는지부터 재는 것이 출발점입니다.

코드로 쓰면 어떻게 되나요?

길이를 재고 넘으면 오래된 부분을 요약해 바꾸는 함수 하나입니다.

import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"
# ① 이 길이를 넘으면 줄인다
LIMIT, KEEP_RECENT = 60_000, 6

def compact(messages, system):
    # ② 보내기 전에 토큰 수를 잰다
    n = client.messages.count_tokens(
        model=MODEL, system=system, messages=messages).input_tokens
    if n < LIMIT:
        return messages
    # ③ 최근 대화는 원문 그대로, 짝이 깨지지 않는 자리에서 자른다
    cut = safe_cut(messages, keep=KEEP_RECENT)
    old, recent = messages[:cut], messages[cut:]
    # ④ 오래된 부분은 LLM에게 요약을 맡긴다
    summary = client.messages.create(
        model=MODEL, max_tokens=800,
        system="앞으로의 작업에 필요한 결정·조건·숫자만 남겨 요약하라.",
        messages=[{"role": "user", "content": to_text(old)}],
    ).content[0].text
    # ⑤ 요약 한 칸을 맨 앞에 넣는다
    head = [{"role": "user", "content": f"[지난 대화 요약]\n{summary}"},
            {"role": "assistant", "content": "확인했습니다."}]
    return head + recent
  1. context window보다 넉넉히 작게 잡습니다. 다 찬 뒤에 줄이면 이번 답을 쓸 자리가 없습니다.
  2. count_tokens는 실제로 보내지 않고 토큰 수만 셉니다. 요금이 들지 않습니다.
  3. safe_cut은 자를 자리가 도구 부탁과 결과 사이에 걸리면 앞으로 당기는 도우미 함수입니다. 짝이 깨지면 API가 요청을 거절합니다.
  4. 요약에도 LLM 호출이 한 번 듭니다. 요약 지시에 무엇을 남길지 분명히 적어야 세부가 덜 빠집니다.
  5. user와 assistant가 번갈아 와야 해서 요약 칸 뒤에 짧은 답 칸을 붙였습니다.

반복문에서 LLM을 부르기 직전에 messages = compact(messages, system) 한 줄을 넣으면 됩니다. LangChain에서는 SummarizationMiddleware가 같은 일을 합니다. Claude API의 context editing을 켜면 오래된 도구 결과 지우기를 API가 대신 합니다.
