Agent 루프에 코드를 끼워 넣는 여섯 곳, Middleware

Agent 루프는 정해진 길을 돕니다. 시작하면 모델을 부르고 모델이 도구를 고르면 도구를 실행한 뒤 다시 모델로 돌아옵니다. 더 할 일이 없으면 끝납니다.

그런데 이 길 중간에 끼워 넣어야 할 일이 생깁니다. 입력에 개인정보가 있으면 가리고 모델을 너무 많이 부르면 멈추고 위험한 요청은 아예 막아야 합니다. 루프 코드를 고쳐서 이런 일을 넣으면 코드가 금방 복잡해집니다. LangChain에는 루프 자리마다 코드를 끼우는 Middleware가 있습니다. 코드를 어느 역에 끼울 수 있는지 아래 노선도에서 확인합니다.

  1. 1
    입력 검사before_agent시작할 때 한 번 입력을 검사하고 위험하면 jump_to: end로 모델을 부르지 않은 채 끝냅니다. 직접 실행해 보니 모델은 한 번도 호출되지 않았습니다.
  2. 2
    개인정보 가리기before_model모델을 부르기 직전마다 메시지에서 이메일 같은 개인정보를 찾아 [REDACTED_EMAIL]처럼 바꿉니다. 모델이 받은 요청에는 원문이 없었습니다.
  3. 3
    호출 횟수 세기before_model모델을 부르기 직전마다 이번 실행에서 몇 번 불렀는지 세고 한도에 닿으면 멈춥니다. 한도 2에서는 세 번째 호출 직전에 멈췄습니다.
  4. 4
    도구 오류 처리wrap_tool_call도구 호출을 감싸서 예외가 나면 오류 표시가 붙은 ToolMessage로 바꿔 돌려줍니다. 도구를 실행하는 쪽만 감싸는 훅입니다.
  5. 5
    답 검사after_agent끝날 때 한 번 최종 답을 검사해서 위험하면 안내 문장으로 고쳐 씁니다. 모델을 이미 다 부른 뒤라 입력 검사보다 비용이 더 듭니다.

실행 한 번을 노선도로 그렸습니다. 작은 흰 역이 훅(hook)인데, 코드를 끼울 수 있게 열어 둔 자리입니다. 역 이름은 LangChain 문서를 따랐습니다. 초록 고리와 번호가 붙은 역에서 위 다섯 가지 코드가 돌아가고, 점이 그 역을 지나면 그 역의 설명이 진해집니다.

훅에는 지나가며 확인하는 것과 감싸는 것이 있습니다

훅(hook)은 코드를 끼워 넣을 수 있게 열어 둔 곳입니다. LangChain 문서는 훅을 두 종류로 나눕니다. before와 after 훅은 흐름이 그 지점을 지날 때 한 번 실행되고 상태를 읽거나 고칩니다. 로그를 남기거나 입력을 검사하거나 메시지를 바꿀 때 씁니다.

wrap 훅은 모델 호출이나 도구 호출 자체를 감쌉니다. 호출을 실제로 하는 handler를 받아서 부를지 말지를 직접 정합니다. 한 번 부를 수도 있고 실패하면 다시 부를 수도 있고 아예 부르지 않고 결과를 만들어 줄 수도 있습니다. 그림 아래쪽 세 줄이 감싸는 쪽이 호출을 다루는 세 가지 방법입니다.

  • 한 번 부름handler를 한 번 부르고 결과를 그대로 돌려줍니다.
  • 실패하면 다시 부름handler가 실패하면 한 번 더 부릅니다. 그래서 모델 호출이 두 번 일어날 수 있습니다.
  • 부르지 않음handler를 부르지 않고 미리 만든 답을 돌려줍니다. 모델 호출은 일어나지 않습니다.

설명을 위한 그림입니다. 도구 호출을 감싸는 wrap_tool_call도 같은 방식으로 동작합니다.

from langchain.agents.middleware import before_agent

# ① 시작할 때 한 번: 입력을 검사하고 막을 수 있다
@before_agent(can_jump_to=["end"])
def guard(state, runtime):
    text = state["messages"][-1].content
    if "해킹" in text:
        # ② 답을 대신 넣고 바로 끝으로 간다
        return {"messages": [{"role": "assistant",
                 "content": "그 요청은 도와드릴 수 없습니다."}],
                "jump_to": "end"}

# ③ 에이전트에 끼운다
agent = create_agent(model, tools=tools, middleware=[guard])
터미널
$ python guard.py 그 요청은 도와드릴 수 없습니다.

출력은 예시 답입니다. 질문은 "옆 팀 와이파이 해킹하는 법 알려줘"를 가정했고 이 경우 모델은 한 번도 호출되지 않습니다. 코드는 langchain 1.4 기준입니다.

  1. 끼울 곳을 고릅니다. @before_agent는 실행을 시작할 때 한 번 도는 훅입니다. can_jump_to=["end"]를 적어 두어야 이 훅이 흐름을 끝으로 보낼 수 있습니다. 함수는 state(지금까지의 메시지)를 받아서 검사합니다.
  2. 막고 끝냅니다. 딕셔너리로 돌려주면 그 내용이 상태에 더해집니다. 여기서는 사용자에게 보여 줄 답을 메시지로 넣고 "jump_to": "end"로 모델을 부르지 않은 채 끝냅니다. 키워드 검사는 규칙 기반 검문이라 빠르고 싸지만 돌려 쓴 말은 놓칠 수 있습니다.
  3. 에이전트에 끼웁니다. middleware 목록에 넣으면 됩니다. 루프 코드는 한 줄도 바뀌지 않습니다.

내장 Middleware는 모델 호출 제한과 개인정보 가리기부터

자주 쓰는 검문은 LangChain이 미리 만들어 두었습니다. ModelCallLimitMiddleware는 모델을 몇 번까지 부를지 정하고 PIIMiddleware는 이메일이나 카드 번호 같은 개인정보(PII)를 찾아 처리합니다. 둘 다 실제로 실행해서 결과를 확인했습니다.

모델이 도구만 계속 부르면 루프가 끝나지 않고 비용만 쌓입니다. 첫째 그림은 한도가 1, 2, 3일 때 호출 제한이 각각 어디서 멈추는지 보여 줍니다. 둘째 그림은 같은 문장 속 이메일을 처리 방식 네 가지가 어떻게 바꾸는지 보여 줍니다.

ModelCallLimitMiddleware

두 칸 모두 langchain 1.4를 모의 서버에 붙여 실행한 결과입니다. 호출 칸은 도구만 계속 부르는 모델을 가정했습니다.

# ④ 개인정보를 가리고 모델 호출을 두 번으로 제한한다
agent = create_agent(model, tools=tools, middleware=[
    PIIMiddleware("email", strategy="redact"),
    ModelCallLimitMiddleware(run_limit=2, exit_behavior="end"),
])
result = agent.invoke(msg)
print(result["messages"][0].content)
print(result["messages"][-1].content)

출력은 예시입니다. 모델이 도구만 계속 부르는 경우를 가정했습니다.

  1. 여러 개를 한꺼번에 끼웁니다. middleware 목록에 순서대로 넣습니다. 첫 줄은 이메일을 [REDACTED_EMAIL]로 바꿔 모델에게 원문이 가지 않게 하고 둘째 줄은 모델을 세 번째로 부르려는 순간 멈춥니다. exit_behavior="end"면 위 출력처럼 안내 메시지를 답으로 남기고 끝나며 "error"면 예외가 납니다.

A, B 두 Middleware를 이 순서로 끼우고 직접 실행해 찍은 출력 순서입니다.

여러 개를 끼우면 before는 앞에서 뒤로 after는 뒤에서 앞으로 돕니다

Middleware를 여러 개 끼우면 괄호를 겹쳐 여는 것처럼 돕니다. 먼저 끼운 A가 먼저 열고 나중에 닫습니다. 그래서 들어갈 때는 A, B 순서로 지나고 나올 때는 B, A 순서로 지납니다. 로그를 찍어 보면 before_agent와 before_model은 A, B 순서이고 after_model과 after_agent는 B, A 순서입니다.

순서가 중요한 예가 있습니다. 개인정보를 가리는 Middleware를 입력 검사보다 바깥에 두면 검사는 가려진 글을 봅니다. 반대로 두면 검사가 원문을 보게 됩니다. 어느 쪽이 맞는지는 무엇을 먼저 처리해야 하는지로 정합니다.

Guardrail은 규칙으로 막거나 모델로 판단합니다

Guardrail은 입력이나 출력을 검사해서 위험한 내용을 걸러 내는 장치입니다. LangChain 문서는 두 가지로 나눕니다. 규칙 기반은 키워드나 정규식 같은 정해진 규칙으로 검사해서 빠르고 싸지만 미묘한 위반은 놓칠 수 있습니다. 모델 기반은 다른 모델이 의미를 보고 판단해서 더 정확하지만 느리고 비쌉니다.

자리도 나뉩니다. 입력 검사는 before_agent에서 모델을 부르기 전에 막고 출력 검사는 after_agent에서 최종 답을 확인해 고쳐 씁니다. 도구를 실행하는 Agent에서는 출력뿐 아니라 입력 쪽에서 막는 편이 비용도 위험도 줄입니다.

두 방식의 특징은 LangChain Guardrails 문서의 설명을 따랐고 입력과 판정은 설명을 위한 예시입니다. 모델 기반이 항상 잡는다는 뜻은 아닙니다.
