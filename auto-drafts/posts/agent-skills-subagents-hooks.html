같은 설명을 세 번째 붙여 넣기 전에 만드는 에이전트 스킬

동아리 출석 앱을 코딩 에이전트(coding agent)와 만들고 있습니다. 출석 기록은 데이터를 표로 저장하는 프로그램인 DB(Database)에 있습니다. 이 표를 바꿀 때마다 같은 말을 붙여 넣습니다. "마이그레이션 파일 이름은 날짜_설명.sql 로, 이미 적용된 파일은 고치지 말고, 다 쓰면 check.sh 를 돌려." 마이그레이션(migration)은 표의 구조를 바꾸는 변경 파일입니다. 지난주에도 그 전 주에도 이 설명을 붙여 넣었습니다.

이런 설명을 파일로 적어 두고 필요할 때만 꺼내 읽게 하는 것이 스킬(skill)입니다. 에이전트가 한 번에 보는 글인 컨텍스트 창(context window)을 여기서는 책상이라 부르고 그 양은 토큰(token)으로 셉니다. 책상에 많이 올릴수록 비용이 늘고 중요한 지시가 흐려집니다(컨텍스트 엔지니어링 글).

스킬은 폴더 하나와 SKILL.md 한 장입니다

스킬은 SKILL.md 라는 파일이 든 폴더입니다. 파일 맨 위 --- 두 줄 사이에는 이름과 설명을 적습니다. 이 머리말을 프런트매터(frontmatter)라고 부릅니다. 그 아래 본문에는 일하는 순서를 평범한 글로 씁니다.

레시피 카드와 비슷합니다. 앞면에 요리 이름과 언제 만드는지가 있고 안쪽에 순서, 뒤에 계량표가 붙어 있습니다. 다른 점이 하나 있습니다. 카드를 꺼낼지 말지는 모델이 앞면 설명만 보고 정합니다. 앞면은 세션(session), 즉 에이전트와 새 대화를 열 때마다 책상에 깔립니다.

그래서 description 한 줄이 가장 중요합니다. 규격은 무엇을 하는지와 언제 쓰는지를 함께 적으라고 합니다. "PDF를 도와줌"처럼 막연하면 필요한 때에 서랍이 열리지 않습니다.

폴더에는 참고 문서(references/), 실행할 스크립트(scripts/), 서식 같은 자료(assets/)를 함께 둘 수 있습니다. 스크립트는 명령을 순서대로 적어 둔 작은 프로그램입니다. 규격은 SKILL.md 를 500줄 아래로 두고 긴 내용은 이런 파일로 나누라고 권합니다.

스킬을 연다는 건 파일을 읽는다는 뜻입니다

스킬에는 따로 돌아가는 프로그램이 없습니다. 모델이 이름표를 보고 이 서랍이 맞다고 판단하면 그 파일 내용이 대화에 들어올 뿐입니다. 모델이 파일 읽기나 명령 실행처럼 바깥일을 맡기는 기능을 도구(tool)라고 합니다. Claude Code 에서는 모델이 Skill 도구를 부르면 SKILL.md 가 메시지 하나로 들어오고 부록은 평소처럼 Read 도구로 읽습니다.

이렇게 필요한 만큼만 한 층씩 펼치는 방식을 단계적 공개(progressive disclosure)라고 합니다. 맨 위 서랍장에서 보낸 "생일 칸 추가" 요청을 처리할 때 대화 기록에 쌓이는 순서는 아래와 같습니다.

비유가 안 맞는 곳이 하나 있습니다. 한 번 펼친 본문은 서랍에 다시 들어가지 않습니다. Claude Code 는 불러온 SKILL.md 를 대화에 남겨 둡니다. 대화가 길어져 앞부분을 요약으로 줄이는 압축(compaction) 때도 스킬마다 앞쪽 5,000 토큰, 모두 합쳐 25,000 토큰까지 다시 붙입니다.

배포처럼 함부로 실행되면 곤란한 스킬은 프런트매터에 disable-model-invocation: true 를 넣습니다. 그러면 이름표조차 책상에 올라가지 않고 사람이 /deploy 처럼 이름을 불러야만 열립니다. 에이전트를 바깥 서비스에 잇는 MCP(Model Context Protocol)에도 같은 생각이 있습니다. 도구 설명을 이름만 실어 두고 필요할 때 찾아 쓰는 MCP tool search 입니다(MCP 글).

Anthropic 이 그린 원래 그림 보기

여러 도구가 같은 SKILL.md 를 읽는 이유

Anthropic 은 2025년 10월 16일 Claude 에 스킬을 내놓았고 12월 18일 이 형식을 공개 표준(open standard)으로 풀었습니다. 공개 표준은 누구나 따라 만들 수 있게 공개한 약속입니다. 2026년 10월 15일 agentskills.io 첫 화면에는 이 형식을 지원하는 도구 46곳의 로고가 올라 있습니다. Codex, Cursor, Gemini CLI, GitHub Copilot, Kiro 도 그 안에 있습니다.

받아들이기 쉬운 형식이라서입니다. # 같은 기호로 제목을 표시하는 평범한 글인 마크다운(Markdown)이 든 폴더라 실행 엔진도 서버도 필요 없습니다. 도구는 시작할 때 이름표를 읽고 필요할 때 파일을 열기만 하면 됩니다. 만드는 쪽도 한 번 써 둔 스킬을 도구를 바꿔도 그대로 가져갑니다.

모두 같지는 않습니다. 표준이 정한 칸은 name·description 과 몇 가지 선택 칸뿐입니다. 이름을 불러야만 여는 칸, 일을 떼어 맡는 보조 에이전트인 서브에이전트(subagent)에서 돌리는 context: fork 같은 칸은 Claude Code 가 더한 것이라 다른 도구가 같은 뜻으로 읽는다는 보장이 없습니다. 폴더 위치도 도구마다 다릅니다.

남이 만든 스킬을 나눠 받는 곳도 생겼습니다. Vercel 이 운영하는 skills.sh 에서는 1위 스킬 find-skills 의 설치 수가 390만입니다(2026-10-15). 스킬에 든 스크립트는 내 컴퓨터에서 실행되니 받기 전에 폴더를 열어 보는 편이 안전합니다.

서브에이전트에게는 일을 봉투째 맡깁니다

서브에이전트는 메인 에이전트가 일을 떼어 맡기는 보조 에이전트입니다. 자기 책상(컨텍스트 창)을 따로 써서 파일을 수십 개 읽어도 메인 대화에는 요약만 돌아옵니다. 책상을 나눠 쓰면 무엇이 좋은지는 컨텍스트 엔지니어링 글에 정리했습니다.

이 글에서는 서브에이전트 하나를 파일 하나로 정의하는 쪽을 다룹니다. 일꾼에게 봉투를 건네 심부름을 보내는 것과 비슷합니다. 일꾼은 봉투에 든 쪽지와 자기 업무 지침만 들고 갑니다. 그래서 메인 대화에서 120턴 동안 나눈 이야기는 모릅니다. 필요한 사정은 쪽지에 다 적어야 합니다.

스킬과 헷갈리기 쉽습니다. 스킬은 내 책상에 펼쳐 놓고 따르는 설명서라서 단계마다 지켜보며 방향을 바꿀 수 있습니다. 서브에이전트는 다른 책상에서 일하고 결과만 가져옵니다. 중간 과정을 다시 볼 일이 없는 곁일이면 서브에이전트가 맞습니다.

---
# ① 이름과 언제 맡길지
name: migration-reviewer
description: 마이그레이션 파일을 만든 뒤 검토할 때 쓴다.
  적용된 파일 수정과 되돌릴 수 없는 삭제를 찾는다.
# ② 손에 쥘 도구
tools: Read, Grep, Glob
# ③ 쓸 모델
model: sonnet
# ④ 처음부터 펼쳐 둘 스킬
skills:
  - db-migration
---
<!-- ⑤ 여기부터 시스템 프롬프트 -->
너는 DB 마이그레이션 검토자다.
migrations/applied/ 아래 파일이 바뀌었으면 가장 먼저 알린다.
DROP 처럼 되돌릴 수 없는 명령을 찾는다.
고치지 말고 찾은 것만 짧게 보고한다.
  1. name 은 일꾼의 이름, description 은 메인 에이전트가 "이 일은 이 일꾼에게" 하고 고를 때 읽는 설명입니다. 스킬의 이름표와 같은 역할입니다.
  2. tools 에 적은 도구만 쓸 수 있습니다. 검토자는 읽기만 하면 되니 파일을 읽는 Read, 글자를 찾는 Grep, 파일 이름으로 찾는 Glob 만 줍니다. 파일을 고치는 Edit 이나 명령을 실행하는 Bash 는 빼 둡니다. 빼면 메인 에이전트가 가진 도구를 그대로 받습니다.
  3. 쓸 모델을 고를 수 있습니다. sonnet 은 중간급이고 haiku 가 더 빠르고 쌉니다. 빼면 메인 대화와 같은 모델을 씁니다.
  4. 여기 적은 스킬은 이름표가 아니라 본문 전체가 처음부터 책상에 깔립니다. 서브에이전트 안에서는 단계적 공개 대신 미리 실어 두는 셈입니다.
  5. 프런트매터 아래 본문은 이 일꾼의 시스템 프롬프트(system prompt)가 됩니다. 대화를 시작하기 전에 깔리는 기본 지시입니다. 쪽지는 이 지시 위에 얹혀 들어갑니다.

파일은 프로젝트의 .claude/agents/ 나 내 컴퓨터 전체에 쓰는 ~/.claude/agents/ 에 둡니다. Claude Code 에는 처음부터 든 일꾼도 있습니다. 읽기만 하며 코드를 찾는 Explore, 계획 모드에서 조사하는 Plan, 무엇이든 하는 general-purpose 가 그렇습니다.

서브에이전트는 다시 서브에이전트를 부를 수 있습니다. 기본값은 메인 대화에서 세 단계 아래까지, 동시에 20개까지입니다. 다만 일꾼이 쓰는 토큰도 내 사용량에 똑같이 잡힙니다.

훅은 정해진 순간마다 스크립트를 실행합니다

CLAUDE.md 와 스킬은 부탁입니다. 모델이 읽고 판단해서 따르기 때문에 어길 수 있습니다. Claude Code 문서도 ".env 를 고치지 마" 같은 지시는 보장이 아니라 요청이라고 적었습니다. .env 는 비밀번호 같은 설정값을 담는 파일입니다.

훅(hook)은 Claude Code 가 일하는 흐름의 정해진 순간마다 내가 정한 스크립트를 실행하는 장치입니다. 그 순간을 이벤트(event)라고 부릅니다. 실행 여부를 모델이 고르지 않고 Claude Code 가 매번 실행합니다. 학교 정문의 출입 확인과 비슷합니다. 다만 사람 경비원과 달리 적어 둔 검사만 합니다.

훅은 설정 파일에 등록합니다. 프로젝트 코드와 변경 기록을 모아 둔 곳을 저장소(repository)라고 하는데 저장소에 함께 올려 팀이 같이 쓰려면 .claude/settings.json, 나만 쓰려면 ~/.claude/settings.json 입니다. 어떤 이벤트에서 어떤 도구일 때(matcher), 무엇을 실행할지를 적습니다.

이 설정은 파일을 고치는 Edit·Write 도구가 실행되기 직전마다 protect-files.sh 를 돌립니다. 훅은 모델의 책상을 쓰지 않습니다. 결과를 돌려줄 때만 그 글이 대화에 들어갑니다.

{
  "hooks": {
    "PreToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh"
      }]
    }]
  }
}

막는 것은 종료 코드 2뿐입니다

스크립트가 끝날 때 돌려주는 숫자를 종료 코드(exit code)라고 합니다. 훅에서는 이 숫자가 결과를 정합니다. 0 은 이의 없음, 2 는 막기입니다. 그 밖의 숫자는 오류 표시만 남기고 그대로 진행합니다. 프로그래밍에서는 흔히 1 을 "실패"로 쓰는데 훅을 1 로 끝내면 아무것도 막지 못합니다.

에이전트가 시도할 도구 호출을 하나 골라 보세요. 검문소 그림에서 호출이 지나가거나 막히고 스크립트에서 실행된 줄이 칠해집니다.

막을 때 돌려줄 종료 코드를 골라 보세요. 스크립트 9번 줄과 검문소의 결과가 바뀝니다.

호출을 고르면 훅이 그 호출을 받아 스크립트를 실행합니다. 실행된 줄은 옅은 보라, 스크립트가 끝난 줄은 진한 보라로 칠해집니다.

.claude/hooks/protect-files.sh
  1. #!/bin/bash
  2. INPUT=$(cat) # 훅이 받은 도구 호출(JSON)
  3. FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // empty')
  4. PROTECTED=(".env" "migrations/applied/")
  5. for pattern in "${PROTECTED[@]}"; do
  6. if [[ "$FILE_PATH" == *"$pattern"* ]]; then
  7. echo "Blocked: $FILE_PATH is protected" >&2
  8. # 막을 때 돌려줄 종료 코드
  9. exit 2
  10. fi
  11. done
  12. exit 0

스크립트는 Claude Code 문서 hooks-guide 의 「Block edits to protected files」 예시에서 보호할 이름만 이 앱에 맞게 바꿨습니다. 2번 줄은 훅이 넘겨받은 도구 호출 내용을 $INPUT 에 담고 3번 줄은 JSON 형식 글을 읽는 프로그램 jq 로 그 안의 파일 경로만 꺼냅니다. 옅은 보라 줄은 고른 호출이 실행한 줄이고 진한 보라 줄은 스크립트가 끝난 줄입니다. 막힌 뒤 Claude 가 하는 말은 예시입니다.

막을 때 >&2 로 내보낸 글이 stderr(오류 메시지를 내보내는 통로)입니다. PreToolUse 훅이 2 로 끝나면 이 글이 Claude 에게 사유로 전달되고 Claude 는 다른 방법을 찾습니다. 0 으로 끝난다고 허락되는 것도 아닙니다. 훅이 반대하지 않았을 뿐이고 평소의 권한 확인, 즉 Claude Code 가 사람에게 실행해도 되는지 묻는 단계는 그대로 거칩니다.

Stop 훅에 테스트를 걸면 테스트가 통과할 때까지 Claude 가 일을 끝내지 못하게 할 수 있습니다. 끝없이 돌지 않도록 Claude Code 는 Stop 훅이 그 사이 도구 호출 없이 여덟 번 연속으로 막으면 훅을 넘기고 끝냅니다.

무엇을 어디에 둘지 고르는 기준

네 가지는 언제 책상에 올라오는지와 얼마나 확실히 지켜지는지가 다릅니다. 저도 처음에는 전부 CLAUDE.md 에 적었다가 파일이 길어지고 "절대 금지" 줄이 가끔 무시되는 걸 보고 나눴습니다.

Claude Code 문서는 무엇을 언제 더할지 신호로 알려 줍니다.

  • 같은 관례나 명령을 두 번 틀린다 → CLAUDE.md
  • 같은 절차를 세 번째 붙여 넣는다 → 스킬
  • 곁일의 출력이 대화를 덮는다 → 서브에이전트
  • 묻지 않아도 매번 일어나야 한다 → 훅
  • 두 번째 저장소에도 같은 설정이 필요하다 → 플러그인(plugin)

CLAUDE.md 를 다시 읽으며 고를 수도 있습니다. "매번 X 하면 Y 해"라는 줄은 훅 후보, "절대 하지 마"는 막는 장치가 필요한 줄, 30줄짜리 절차는 스킬 후보입니다.

네 가지를 한 폴더에 묶은 플러그인

플러그인은 스킬, 서브에이전트, 훅, MCP 서버를 한 번에 설치하는 묶음 폴더입니다. MCP 서버는 에이전트를 회사 시스템에 잇는 연결 프로그램입니다(MCP 글). 폴더 안 .claude-plugin/plugin.json 이 이름과 버전을 적은 안내 파일입니다. 출석 앱에서 만든 스킬과 검토자, 보호 훅을 db-kit 으로 묶으면 다른 저장소에서도 한 번에 쓸 수 있습니다.

플러그인은 플러그인 목록을 모아 둔 저장소인 마켓플레이스(marketplace)에서 받습니다. Claude Code 안에서 /plugin 을 열면 Anthropic 공식 목록이 보입니다. 플러그인 안의 스킬은 /db-kit:db-migration 처럼 플러그인 이름이 앞에 붙어 다른 플러그인과 겹치지 않습니다.

켜 둔 플러그인은 쓰지 않는 세션에도 붙어 있습니다. 스킬과 일꾼의 이름표가 매번 책상에 올라가고 훅은 이벤트마다 돕니다. 안에 든 코드는 내 권한으로 실행됩니다. 공식 목록은 설치 전에 책상을 얼마나 차지할지 어림한 값을 Context cost(컨텍스트 비용) 칸에 보여 주니 확인하고 받습니다.

한 번 설명한 것은 파일로 남기고 꼭 지킬 것은 코드로 막습니다. 이 두 가지면 같은 설명을 되풀이하지 않아도 됩니다.

에이전트가 이렇게 손에 익으면 코드는 빨리 늘어납니다. 다음 글은 늘어난 코드를 사람이 읽고 승인하는 리뷰가 왜 막히는지 다룹니다.
