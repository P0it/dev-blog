AI Service Track · 12

약관 챗봇이 '상품마다 다릅니다'로 얼버무리는 이유

펫보험 약관 PDF를 올려 둔 챗봇에 "통원 치료 자기부담금이 얼마예요?"라고 물었습니다. 약관에는 금액표가 분명히 있는데 답은 "상품마다 다릅니다"입니다. 모델이 약관을 통째로 읽고 답하는 게 아니라 검색이 골라 준 조각 몇 개만 읽기 때문입니다. 화면 뒤에서 모델이 받은 그 몇 칸을 펼쳐 보고 칸을 제대로 채우는 코드까지 만들어 봅니다.

챗봇은 약관 28쪽을 다 읽고 답할까요?

아닙니다. 약관과 용어집은 미리 잘게 잘라 저장해 둡니다. 이렇게 자른 조각을 청크(chunk)라고 부릅니다. 질문이 오면 질문과 뜻이 가장 가까운 조각 몇 개만 골라 질문과 함께 모델에게 넘깁니다. 이 방식을 RAG(Retrieval-Augmented Generation, 찾아서 보태 쓰는 생성)라고 합니다.

뜻이 가까운지는 임베딩(embedding)으로 잽니다. 글을 숫자 수백 개를 줄 세운 벡터(vector)로 바꾸는 일인데, 뜻이 비슷한 글일수록 숫자도 비슷하게 나옵니다. 이 벡터를 모아 두고 가까운 것을 빨리 찾아 주는 곳이 벡터 저장소(vector store)입니다. 이 글은 내 컴퓨터에 파일로 저장되는 오픈소스 저장소 Chroma를 씁니다. 몇 개를 고를지는 k로 정하고 LangChain의 기본값은 4입니다.

오픈북 시험인데 책 전체가 아니라 친구가 찢어 준 네 쪽만 들고 들어가는 것과 같습니다. 다만 친구는 내용을 읽고 고르지만 검색은 숫자가 가까운지로만 고릅니다. 전체 흐름은 RAG는 AI가 모르는 우리 회사 규정을 어떻게 답할까요에서 자세히 다뤘고 이 글은 그 네 칸에 무엇이 들어가는지만 봅니다.

금액이 적힌 표는 왜 네 칸에 못 들어왔을까요?

조각을 너무 작게 잘라 "자기부담금"이라는 말과 금액표가 서로 다른 조각으로 갈라졌기 때문입니다. 표만 남은 조각에는 무엇의 금액인지 적혀 있지 않아 질문과 멀어집니다. 검색은 뜻이 담긴 앞 조각을 고르고 모델은 그 조각에 있는 "고른 금액"이라는 말만 보고 답합니다.

LangChain의 RecursiveCharacterTextSplitter는 정한 글자 수(chunk_size)를 넘지 않게 빈 줄, 줄바꿈, 띄어쓰기, 글자 순서로 자를 곳을 찾습니다. 경계에서 뜻이 끊기지 않게 앞뒤를 겹치는 chunk_overlap도 있지만 이 예처럼 빈 줄에서 잘리면 겹치는 글자가 생기지 않습니다.

그래서 조각 크기는 하이퍼파라미터(hyperparameter), 곧 학습으로 정해지지 않고 사람이 실험해 정하는 값입니다. 기준은 "답의 근거 한 덩어리가 한 조각에 다 들어가는 가장 작은 크기"입니다. 약관이라면 조항 하나가 한 조각에 들어가게 맞춥니다.

같은 조각이 두 칸을 차지한 까닭

저장하는 코드를 두 번 돌려서입니다. Chroma.from_documents나 add_documents는 조각마다 번호표(id)를 새로 지어 붙이는데, 번호표를 따로 주지 않으면 실행할 때마다 처음 보는 이름이 붙어 같은 조각이 또 들어갑니다. 242조각이 484조각이 되고 검색은 똑같은 두 조각을 나란히 "가장 가깝다"고 내놓습니다.

네 칸 가운데 두 칸이 이미 읽은 내용으로 차면 모델이 볼 근거는 실제로 두 개뿐입니다. 조각마다 정해진 번호표를 직접 주면 간단히 해결됩니다. 은행 대기 번호처럼 조각 하나에 번호 하나를 붙이는 것입니다. 뒤에서 볼 꼬리표(어떤 종류인지 적은 분류 스티커)와는 다릅니다. LangChain의 Chroma는 번호표가 같은 조각이 이미 있으면 새로 쌓지 않고 덮어씁니다. 이를 upsert(있으면 고치고 없으면 넣기)라고 부릅니다.

파이썬 용어가 보험 질문에 끼어든 이유

저장소에 용어집과 약관이 섞여 있는데 검색은 내용만 보고 고르기 때문입니다. "자기부담금은 고른 금액"이라는 말과 "사람이 직접 정해 주는 값"이라는 하이퍼파라미터 풀이는 숫자로 바꾸면 꽤 가깝게 나올 수 있습니다. 그렇게 보험 질문에 파이썬 용어가 한 칸을 차지합니다.

막는 방법은 조각마다 메타데이터(metadata), 곧 "이 조각은 어디서 왔고 어떤 종류인지"를 적은 꼬리표를 달아 두는 것입니다. 도서관 책 등에 붙은 분류 스티커와 같습니다. 검색할 때 filter로 "약관만"을 걸면 용어집 조각은 아예 후보에서 빠지고 남은 약관 조각 안에서 네 개를 고릅니다. 스티커와 다른 점도 있습니다. 꼬리표는 코드가 파일 단위로 붙이므로 잘못 붙이면 필터가 정답 조각까지 지워 버립니다.

비슷한 조각만 네 개 오면 답이 왜 좁아질까요?

네 칸이 거의 같은 이야기로 차면 모델은 한쪽 이야기만 듣고 답하기 때문입니다. "보험 약관을 정리해 줘"처럼 넓게 물으면 약관 맨 앞의 "약관 이용 안내" 문단들이 질문과 가장 가깝게 나와 네 칸을 다 가져갑니다. 보장 내용, 청구 서류, 알릴 의무는 한 줄도 들어오지 못합니다.

MMR(Maximal Marginal Relevance)은 한 칸씩 채우면서 이미 고른 것과 닮은 후보의 점수를 깎는 검색 방식입니다. 1998년 정보 검색 학회 SIGIR에서 나온 방법입니다. 같은 후보 20개에서 두 방식이 무엇을 고르는지 차례로 봅니다.

유사도 검색: 가까운 순서대로 네 개

질문 별에서 가장 가까운 점 네 개를 고릅니다. 네 점 모두 "약관 이용 안내" 무리에 있습니다. 점끼리 가깝다는 건 내용도 거의 같다는 뜻입니다.

MMR 첫 칸: 가장 가까운 것 하나

MMR도 첫 칸은 똑같이 가장 가까운 점을 고릅니다. 대신 그 점 둘레의 빨간 원 안에 있는 후보는 "이미 고른 것과 닮았다"며 점수가 깎입니다.

둘째 칸: 덜 닮은 쪽으로

안내 무리의 나머지는 질문과 가깝지만 깎인 점수 때문에 밀립니다. 질문과 적당히 가까우면서 빨간 원 밖에 있는 "보험금 청구 서류"가 둘째 칸에 들어갑니다.

셋째, 넷째 칸까지

같은 계산을 되풀이해 "보장 내용"과 "알릴 의무"가 들어옵니다. 네 칸이 네 가지 이야기로 찼습니다. 질문과 먼 회색 점들은 끝까지 뽑히지 않습니다.

지도의 점 위치는 설명을 위해 그린 예시입니다. 실제 벡터는 수백, 수천 차원이라 평면에 그대로 그릴 수 없습니다. 점수 식은 langchain-chroma 1.1.0 소스의 maximal_marginal_relevance를 그대로 옮겼습니다.

MMR이 매기는 점수는 아래 한 줄입니다. 두 항의 무게를 정하는 값이 lambda_mult이고 LangChain Chroma의 기본값은 0.5입니다. 1에 가까울수록 유사도 검색과 같아지고 0에 가까울수록 다양한 쪽을 고릅니다. 후보를 몇 개 먼저 모을지는 fetch_k(기본 20)가 정합니다.

점수 = lambda_mult × 질문과 가까운 정도
　　 − (1 − lambda_mult) × 이미 고른 조각과 닮은 정도

가까운 정도와 닮은 정도는 0(전혀 다름)부터 1(똑같음)까지의 수입니다. 첫 칸에 "약관 이용 안내"가 들어간 뒤 둘째 칸 후보 둘을 0.5로 계산하면 이렇습니다.

후보질문과 가까움첫 칸과 닮음점수 약관 읽는 법0.90.95−0.025 보험금 청구 서류0.60.20.2

0.5×0.9 − 0.5×0.95 = −0.025, 0.5×0.6 − 0.5×0.2 = 0.2. 덜 가까워도 청구 서류가 둘째 칸에 들어갑니다(숫자는 예시 값).

MMR이 늘 나은 것은 아닙니다. "통원 자기부담금 얼마"처럼 답이 한 조항에 있는 좁은 질문에서는 둘째 칸부터 덜 관련된 조각이 들어오고 그 조항이 두 조각에 걸쳐 있으면 둘째 조각이 오히려 밀려날 수 있습니다. MMR은 넓게 정리해 달라는 질문에 잘 맞습니다.

k는 몇 개가 알맞을까요?

답에 필요한 근거는 다 들어오고 상관없는 조각은 가장 적게 들어오는 개수입니다. 너무 적으면 근거가 빠지고 너무 많으면 모델이 읽을 잡음과 토큰(모델이 글을 세는 단위이자 요금 단위)이 질문마다 늘어납니다. 상관없는 내용이 많을수록 모델이 엉뚱한 줄을 근거로 삼을 여지도 커집니다.

그래서 k부터 키우는 것은 순서가 거꾸로입니다. 아래는 앞의 세 문제를 그대로 둔 저장소에서 k만 바꿔 본 결과입니다.

맨 위 왼쪽 화면과 같은 저장소(200자로 자름, 두 번 저장, 필터 없음)에 같은 질문을 던졌습니다. 초록 칸은 답에 필요한 근거, 회색 칸은 상관없거나 겹친 조각입니다. 토큰은 조각 하나를 300토큰으로 잡은 예시 값입니다.

조각을 500자로 자르고 번호표와 필터를 고친 저장소에서는 k=4로도 첫 칸에 금액표가 들어옵니다. 중복과 용어집이 빠진 자리에는 19쪽, 21쪽처럼 제5조 앞뒤 조항이 들어오고 안내 문단은 밀려납니다. 맨 위 오른쪽의 네 칸이 그 결과입니다. 알맞은 k는 질문의 종류마다 다르므로 뒤의 코드에서는 Agent가 질문을 보고 k를 고르게 합니다.

PART 2 · 코드

조각 크기, 번호표, 꼬리표, 검색 방식, k를 코드로 정해 봅니다

자르고 꼬리표와 번호표를 달아 저장하기

한 번만 돌리는 저장 코드입니다. langchain 1.5, langchain-chroma 1.1, langchain-pymupdf4llm 1.28 기준입니다.

pip install langchain langchain-openai langchain-chroma \ langchain-text-splitters langchain-pymupdf4llm
from pathlib import Path
from langchain_core.documents import Document
from langchain_pymupdf4llm import PyMuPDF4LLMLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_chroma import Chroma

# ① 쪽마다 Document 하나
pdf = "data/pet_insurance.pdf"
pages = PyMuPDF4LLMLoader(pdf, mode="page").load()
text = Path("data/glossary.txt").read_text(encoding="utf-8")
glossary = [Document(text, metadata={"source": "data/glossary.txt"})]

# ② 조항 하나가 들어갈 크기
splitter = RecursiveCharacterTextSplitter(
    chunk_size=500, chunk_overlap=80)
chunks = []
for kind, docs in [("insurance", pages), ("glossary", glossary)]:
    for c in splitter.split_documents(docs):
        # ③ 어디서 왔는지 꼬리표
        c.metadata["source_type"] = kind
        chunks.append(c)
ids = [f"{c.metadata['source_type']}-{i:04d}" for i, c in enumerate(chunks)]

# ④ 저장할 때와 찾을 때 같은 임베딩 모델
emb = OpenAIEmbeddings(model="text-embedding-3-small")
store = Chroma(
    collection_name="docs",
    embedding_function=emb,
    persist_directory="chroma_data",
)
# ⑤ 같은 번호표는 덮어쓰기
store.add_documents(chunks, ids=ids)
print("저장된 조각:", len(store.get()["ids"]))
$ python index.py 저장된 조각: 131 $ python index.py 저장된 조각: 131

출력의 조각 수는 설명을 위한 예시 값입니다. 500자로 자르니 200자로 자를 때(242조각)보다 조각 수가 줄었습니다. 두 번 돌려도 개수가 그대로인 것이 이 코드의 요점입니다.

  1. 쪽마다 Document. 로더(loader)는 파일을 읽어 Document 목록으로 바꿔 주는 도구입니다. Document는 글(page_content)과 꼬리표 사전(metadata)을 묶은 LangChain의 상자입니다. 이 로더는 쪽 번호를 metadata["page"]에 0부터 담아 줍니다. 예전 글에 자주 나오는 PyPDFLoader, TextLoader는 지원이 끝난 langchain-community에 있어 새 코드에는 쓰지 않습니다.
  2. 조각 크기. 500자에 80자 겹침으로 잡았습니다. 빈 줄 없이 긴 문단은 글자 수로 잘리는데, 그때 겹침이 문장 끊김을 막아 줘서 남겨 둡니다. 예시 약관에서 제5조가 한 조각에 들어가는 크기입니다. 문서마다 다르니 저장한 조각을 몇 개 열어 조항이 반으로 갈리지 않았는지 눈으로 봅니다.
  3. 꼬리표. source_type은 뒤에서 필터와 Agent 도구가 함께 쓰는 열쇠입니다. 파일 종류처럼 틀릴 일이 없는 값만 꼬리표로 답니다.
  4. 임베딩 모델. 저장할 때와 검색할 때 같은 모델을 써야 합니다. 모델이 다르면 같은 글도 전혀 다른 숫자가 되어 가까운 조각을 찾지 못합니다. 대화 모델은 Claude를 쓰고 임베딩은 OpenAI를 쓰는 식으로 따로 골라도 됩니다.
  5. 번호표. ids를 주면 같은 번호표는 덮어써서 몇 번을 돌려도 중복이 쌓이지 않습니다. 조각 크기를 바꿔 다시 만들 때는 조각 수가 달라져 옛 번호표가 남으므로 store.reset_collection()으로 비우고 넣습니다.

같은 질문을 두 방식으로 검색해 보기

# ... (index.py 의 emb, store 설정과 같음)
store = Chroma(collection_name="docs", embedding_function=emb,
               persist_directory="chroma_data")

# ① 약관 조각만 후보로
only_ins = {"source_type": "insurance"}
plain = store.as_retriever(search_kwargs={"k": 4, "filter": only_ins})
# ② 20개 모아서 덜 닮은 4개
mmr = store.as_retriever(search_type="mmr", search_kwargs={
    "k": 4, "fetch_k": 20, "lambda_mult": 0.5, "filter": only_ins,
})

q = "보험 약관을 정리해 줘"
for name, r in [("유사도", plain), ("MMR", mmr)]:
    print(f"[{name}]")
    for d in r.invoke(q):
        head = d.page_content[:22].replace("\n", " ")
        print(f"  {d.metadata['page'] + 1:>2}쪽  {head}")

  1. 필터. 꼬리표 값이 같은 조각만 후보로 남깁니다. 값을 여러 개 허용하려면 {"source_type": {"$in": ["insurance", "glossary"]}}처럼 Chroma의 비교 기호를 씁니다. 필터를 빼면 저장소 전체에서 고릅니다.
  2. MMR. fetch_k개를 먼저 유사도 순서로 모은 뒤 그 안에서 k개를 고릅니다. fetch_k가 k와 같으면 고를 여지가 없어 유사도 검색과 같아집니다. 출력에서 유사도 쪽은 앞쪽 안내 문단만, MMR 쪽은 청구 서류와 보장 조항까지 가져왔습니다.
거리를 함께 받아 보면 숫자가 작을수록 가깝습니다

store.similarity_search_with_score(q, k=4)로 값을 같이 받으면 Chroma는 기본으로 거리(L2, 두 점 사이 직선거리의 제곱)를 돌려줍니다. 그래서 0에 가까울수록 질문과 가까운 조각입니다. 컬렉션을 만들 때 collection_configuration={"hnsw": {"space": "cosine"}}처럼 바꾸면 각도를 기준으로 잽니다. MMR 점수처럼 클수록 좋다고 생각하고 기준값을 정하면 정반대로 걸러지니 처음에 한 번 확인합니다.

k와 꼬리표를 Agent가 고르게 하기

질문마다 알맞은 문서 종류와 k가 다르니 검색을 도구로 감싸 Agent에게 맡깁니다. 도구와 Agent 기록 읽는 법은 11편에서 다뤘고 여기서는 검색 도구에 필요한 것만 봅니다.

from typing import Literal
from langchain.agents import create_agent
from langchain.tools import tool
# ... (store 설정은 search.py 와 같음)

# ① 고를 수 있는 값을 셋으로 못 박기
Kind = Literal["insurance", "glossary", "all"]

@tool
def search_docs(query: str, source_type: Kind = "all", k: int = 4) -> str:
    """사내 문서에서 질문과 관련된 조각을 찾습니다.
    source_type: insurance=펫보험 약관, glossary=파이썬·AI 용어집, all=전체"""
    kw = {"k": k, "fetch_k": max(20, k * 5)}
    if source_type != "all":
        kw["filter"] = {"source_type": source_type}
    retriever = store.as_retriever(search_type="mmr", search_kwargs=kw)
    docs = retriever.invoke(query)
    if not docs:
        return "찾은 조각이 없습니다."
    # ② 쪽 번호를 붙인 글로 돌려주기
    def cite(d):
        return f"[{d.metadata['source']} {d.metadata.get('page', 0) + 1}쪽]"
    return "\n\n".join(f"{cite(d)}\n{d.page_content}" for d in docs)

agent = create_agent(
    model="anthropic:claude-sonnet-5-5", tools=[search_docs],
    # ③ 찾은 조각 안에서만 답하기
    system_prompt=(
        "search_docs로 찾은 조각의 내용만 씁니다. "
        "금액에는 [파일 쪽]을 붙입니다. "
        "답이 없으면 k나 검색어를 바꿔 한 번 더 찾고 "
        "그래도 없으면 모른다고 합니다."
    ),
)
q = {"messages": [{"role": "user", "content": "통원 치료 자기부담금이 얼마예요?"}]}
for step in agent.stream(q, stream_mode="updates"):
    for update in step.values():
        for m in (update or {}).get("messages", []):
            calls = getattr(m, "tool_calls", None)
            text = m.content[:46].replace("\n", " ")
            print(m.type, calls[0]["args"] if calls else text)

출력은 설명을 위한 예시 답이고 줄마다 46자까지만 찍었습니다. Agent는 질문을 보고 약관만, k=4로 골랐고 검색 한 번에 금액표가 든 제5조 조각을 받아 바로 답했습니다. 마지막 줄의 답은 맨 위 오른쪽 화면의 답과 같습니다. 조각에 답이 없을 때만 k나 검색어를 바꿔 다시 찾습니다.

  1. 값 못 박기. Literal로 적으면 도구 설명서에 고를 수 있는 값 목록(enum)이 들어가서 모델이 "pet"처럼 없는 꼬리표를 지어내지 못합니다. 문자열로만 받으면 필터가 빈 결과를 돌려줘도 모델은 이유를 모릅니다.
  2. 글로 돌려주기. Document 목록을 그대로 돌려주면 모델은 PDF 만든 프로그램 이름 같은 꼬리표까지 글자로 읽어 토큰만 늘어납니다. 출처로 쓸 파일 이름과 쪽 번호만 앞에 붙여 이어 붙입니다.
  3. 지시문. 찾은 조각 안에서만 답하고 출처를 붙이라는 규칙입니다. 출처가 붙어 있으면 사람이 그 쪽을 열어 맞는지 확인할 수 있습니다. 다시 찾는 횟수는 Agent 루프가 정하므로, 무한히 되풀이하지 않게 지시문에 "한 번 더"처럼 한도를 적어 둡니다.

요즘 RAG는 네 칸을 어떻게 더 잘 채울까요?

찾는 방법을 여러 겹으로 쌓습니다. 첫째는 조각마다 "이 조각은 어느 문서의 어떤 내용인지" 설명을 50~100토큰 붙여 저장하는 Contextual Retrieval입니다. Anthropic이 2024년 9월에 공개했습니다. 앞에서 본 "무엇의 금액인지 적히지 않은 표 조각"을 고치는 방법입니다.

둘째는 BM25입니다. 책 뒤의 찾아보기처럼 질문의 낱말이 그대로 들어 있는 조각에 점수를 주는 오래된 검색 방식이라 "제5조" 같은 정확한 낱말에 강합니다.

셋째 리랭킹(reranking)은 후보를 150개쯤 넉넉히 뽑은 뒤 다른 모델이 하나씩 다시 읽고 20개로 줄 세우는 일입니다. 서류 심사 뒤에 면접을 한 번 더 보는 것과 같습니다. 셋을 다 쓰자 놓치는 비율은 처음의 3분의 1로 내려갔습니다.
