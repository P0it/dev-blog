회사 안에 sLLM을 두면 확실히 나아지는 한 가지

보안팀 공지가 내려옵니다. "회사 코드를 외부 AI 서비스로 보내지 마세요." 코딩 에이전트(coding agent)는 코드를 고치기 전에 모델에게 먼저 보여 줘야 해서 이 공지에 바로 걸립니다.

다른 회사의 모델을 인터넷으로 빌려 쓰면 클라우드 API(Application Programming Interface), 모델 파일을 받아 회사 서버에서 직접 돌리면 자체 호스팅(self-hosting)입니다. 이렇게 회사 안에 두는 작은 LLM(Large Language Model)을 국내에서는 흔히 sLLM 이라 부릅니다.

확실히 나아지는 건 코드가 밖으로 나가지 않는다는 한 가지입니다. 나머지는 회사 조건에 달렸습니다.

오픈 웨이트로 받는 것과 못 받는 것

회사 안에 둘 수 있는 모델은 가중치(weight)를 공개한 모델입니다. 가중치는 모델이 학습으로 맞춰 둔 숫자 수십억~수조 개로, 모델의 실력이 그대로 담긴 파일입니다. 이 파일을 누구나 받을 수 있게 푼 모델을 오픈 웨이트(open weight) 모델이라고 부릅니다.

밀키트를 떠올리면 쉽습니다. 상자를 열면 재료와 조리법이 들어 있지만 가스레인지와 요리할 사람은 집에 있어야 합니다. 오픈 웨이트 모델도 가중치 파일, 설계도인 config, 글을 숫자로 바꾸는 토크나이저(tokenizer)가 들어 있을 뿐입니다. 모델을 돌릴 계산용 칩 GPU(Graphics Processing Unit)와 운영은 받는 쪽이 마련합니다.

비유가 맞지 않는 곳도 있습니다. 밀키트는 사면 끝이지만 모델에는 쓰는 조건, 곧 라이선스(license)가 붙습니다. 예를 들어 Kimi K2.6 의 수정 MIT 는 월 사용자 1억 명이나 월 매출 2천만 달러를 넘는 서비스에 모델 이름을 표시하게 합니다.

sLLM 이라는 이름에도 정해진 크기 기준은 없습니다. 2026년 오픈 웨이트 코딩 모델은 작지도 않습니다.

총 파라미터와 활성 파라미터

2026년 코딩용 오픈 웨이트 모델은 대부분 숫자를 수천억에서 1조 개 넘게 갖고 있지만 글자 하나를 만들 때는 그중 몇 %만 계산에 씁니다. 모델이 읽고 쓰는 단위는 정확히는 토큰(token)이라는 글 조각입니다. 모델이 가진 숫자 전체가 총 파라미터(parameter), 한 번 계산에 실제로 쓰는 몫이 활성 파라미터(active parameter)입니다.

이 차이는 MoE(Mixture of Experts) 구조에서 나옵니다. 모델 안에는 계산 단계가 여러 겹 있는데 단계마다 전문가 묶음을 여러 벌 두고 토큰마다 몇 벌만 골라 씁니다. 파라미터가 무엇인지는 7B 가 무엇을 센 숫자인지 다룬 글에 있습니다.

계산은 칠한 칸만큼, 메모리는 테두리만큼 듭니다

넓이를 숫자 개수에 맞춰 그렸습니다. 큰 테두리 안의 칠한 칸이 작을수록 계산은 가볍고 메모리는 그대로 무겁습니다. 누르면 NVIDIA 의 데이터센터용 GPU 인 H100(메모리 80GB)이 몇 장 필요한지도 나옵니다.

계산이 가벼우니 같은 GPU 로 답을 빨리 낼 수 있습니다. 하지만 메모리는 총 파라미터를 따릅니다. 어떤 전문가를 고를지는 토큰마다 달라서 숫자 전체를 늘 GPU 메모리에 올려 둬야 하기 때문입니다. 숫자 하나를 몇 바이트로 적는지에 따라 이 양이 바뀌는 원리는 GPU 메모리와 양자화 글에서 다뤘습니다.

그래서 "활성 3B 면 노트북에서도 돌겠다"는 말은 반만 맞습니다. Qwen3-Coder-Next 는 활성이 3B 이지만 총 80B 입니다. 모델 카드는 GPU 두 장에 나눠 띄우는 명령을 적어 두었습니다. 1조 개 넘는 모델은 서버 여러 대를 묶어야 하고 그 방법은 GPU 여러 장에 나눠 싣는 글에 있습니다.

벤치마크 점수는 시험 조건까지 읽어야 합니다

모델의 코딩 실력은 보통 벤치마크(benchmark)로 잽니다. 모든 모델에게 같은 문제를 풀게 해서 점수를 견주는 공통 시험입니다. 코딩 에이전트에서는 SWE-bench Verified 가 가장 많이 인용됩니다. 이름의 SWE 는 소프트웨어 엔지니어링(Software Engineering)의 줄임말입니다.

문제는 실제 GitHub 저장소에 올라왔던 이슈 500개입니다. 사람이 문제마다 테스트가 제대로인지 확인해 골라서 Verified 라는 이름이 붙었습니다.

모델 카드의 실제 그림 보기

모의고사도 계산기를 쓰게 했는지에 따라 점수가 달라집니다. 벤치마크에서는 모델을 감싼 에이전트 프로그램(scaffold)과 몇 번 풀어 평균을 냈는지에 따라 같은 모델이 4~18점씩 오르내립니다. 이 조건은 각주에 작게 적히거나 아예 빠지기도 합니다.

그래서 모델 카드 숫자끼리는 견주지 않고 한 기관이 같은 프로그램으로 잰 표를 찾습니다. 2026년 새 모델은 SWE-bench Pro·Terminal-Bench 같은 더 어려운 시험 점수를 앞세웁니다. 우리 저장소에서 잘하는지는 우리 코드로 직접 시켜 봐야 압니다.

같은 조건이면 1점 차, 시간으로는 4개월

같은 프로그램으로 같은 달에 잰 공식 기록에서는 오픈 웨이트 1위와 닫힌 모델 1위가 1점 차이였습니다. 닫힌 모델은 가중치를 공개하지 않고 API 로만 쓰게 하는 모델입니다. 2026년 2월 SWE-bench 리더보드에는 모델 13개에 같은 에이전트 프로그램 mini-SWE-agent 2.0.0 을 씌워 한 번씩 풀게 한 기록이 올라왔습니다.

이 줄만 보면 오픈 웨이트가 다 따라잡은 것 같습니다. 하지만 이 측정은 2월에 멈췄습니다. 2026년 9월에 나온 Claude Opus 5.5 처럼 그 뒤의 닫힌 모델은 이 표에 없습니다. 한 시점 사진만으로는 누가 앞서 가는지 알기 어렵습니다.

Epoch AI 는 여러 시험을 묶은 지수 ECI(Epoch Capabilities Index)로 닫힌 모델과 오픈 웨이트 모델의 최고 기록을 시간에 따라 이었습니다. 2026년 5월 분석에서 오픈 웨이트는 2026년 1월 이후 평균 4개월 뒤처져 있었습니다. 두 계단의 가로 거리가 그 4개월입니다.

미국 기업에서는 오히려 줄어든 오픈 모델 몫

미국 기업이 LLM API 에 쓰는 돈에서 오픈 모델의 몫은 2024년 말 19% 에서 2025년 중반 13%, 2025년 말 11% 로 줄었습니다. 벤처 투자사 Menlo Ventures 가 2025년 11월 미국 기업 의사결정자 495명에게 물어 낸 숫자입니다.

보고서는 2025년 4월 Llama 4 이후 Meta 의 큰 새 모델이 나오지 않은 것을 이유로 들었습니다. 같은 보고서에서 코딩 쪽 API 지출의 54% 는 Anthropic 이었습니다. 개발자가 직접 고르는 중계 서비스 OpenRouter 에서는 오픈 모델이 약 3분의 1 로 더 컸습니다.

마음은 다른 쪽으로 움직였습니다. 미국 벤처 투자사 a16z(Andreessen Horowitz)의 대기업 임원 조사에서 직접 호스팅해도 괜찮다는 답은 2024년 약 40% 에서 약 80% 로 늘었습니다. 그런데 닫힌 모델을 더 선호한다는 답도 3분의 1 을 넘겼고 해마다 올랐습니다. 모델 품질이 바뀌는 속도와 사내 AI 인력 부족이 이유였습니다.

한국이 모델을 직접 두려는 이유

한국에서는 규제와 정부 사업이 자체 호스팅 쪽으로 밀고 있습니다. 금융·공공은 업무용 컴퓨터를 인터넷과 끊어 두는 망분리(network separation)를 오래 지켜 와서 외부 AI 서비스에 코드를 보내기 어렵습니다. 정부는 핵심 AI 기술을 다른 나라에 기대지 않고 갖추려는 소버린 AI(sovereign AI) 정책으로 독자 AI 파운데이션 모델(foundation model) 사업을 진행하고 있습니다. 파운데이션 모델은 여러 일에 두루 쓰도록 처음부터 크게 학습한 바탕 모델입니다.

이 사업의 모델은 sLLM 이라는 말과 달리 파라미터가 수천억 개입니다. LG 의 K-EXAONE 2.0 은 활성 37B, SK텔레콤의 A.X K1 은 활성 33B 이고 둘 다 Apache 2.0 입니다. 1차 평가에서는 가중치를 처음부터 직접 학습했는지 따지는 독자성 기준에 못 미친 팀이 떨어졌습니다.

기업 사례도 있습니다. 폐쇄망에 모델을 들이는 절차는 폐쇄망 LLM 글에 있습니다.

비용은 GPU 를 얼마나 쉬지 않게 쓰느냐에 달렸습니다

클라우드 API 는 쓴 만큼 내고 자체 호스팅은 쓰지 않아도 서버값을 냅니다. 그래서 서버 한 대가 맡을 사람을 꽉 채워 쓸 때만 자체 호스팅이 싸집니다.

공공 자전거와 내 자전거를 생각하면 쉽습니다. 따릉이는 탄 만큼 내고 내 자전거는 세워 둬도 산 값이 듭니다. 매일 타는 사람에게는 사는 편이 싸고 열흘에 사흘 타는 사람에게는 빌리는 편이 쌉니다.

나눠 쓰기에서는 비유가 어긋납니다. 자전거는 한 번에 한 명이 타지만 GPU 서버 한 대는 여러 개발자의 요청을 동시에 받습니다. 몇 명까지 받을 수 있는지는 모델 크기, 요청 길이, 서빙 프로그램의 설정에 따라 크게 달라집니다.

👆 그래프 위를 끌어 보세요

계단 모양에 결론이 보입니다. 서버를 한 대 더한 직후에는 빈자리가 많아 API 보다 비쌉니다. 서버가 꽉 찰수록 싸지고 다시 한 대를 더하면 비싸집니다. 여기에 운영할 사람의 인건비는 넣지 않았습니다. 넣으면 계단 전체가 위로 올라갑니다.

시간도 계산을 바꿉니다. a16z 는 같은 성능을 내는 LLM 의 가격이 해마다 약 10분의 1 로 떨어진다고 분석했습니다. 3년 쓸 GPU 를 오늘 값으로 사면 그사이 API 가격이 내려가는 것까지 따져야 합니다.

자체 호스팅에서 회사가 새로 맡는 일

클라우드 API 를 쓰면 모델 아래 층은 모델 회사가 맡습니다. 자체 호스팅으로 바꾸면 GPU 서버부터 에이전트 도구 연결까지 여섯 층을 회사가 직접 맡습니다. 그림의 게이트웨이(gateway)는 회사의 모든 AI 요청을 한곳에서 받아 넘기는 중계 서버입니다.

층마다 사람의 시간이 듭니다. 새 모델이 나오면 받아서 평가하고 바꿔 끼워야 하고 서빙 프로그램의 보안 패치도 따라가야 합니다. 아래 명령에 쓰는 vLLM 은 대표적인 오픈소스 서빙 프로그램으로 여러 사람의 요청을 GPU 메모리에 빈틈없이 채워 한꺼번에 처리합니다. 원리는 vLLM 서빙 글에 있습니다.

에이전트 도구도 다시 골라야 할 수 있습니다. Claude Code 문서는 게이트웨이를 거쳐 Claude 가 아닌 모델로 보내는 연결을 지원하지 않는다고 적었습니다. 오픈 웨이트 모델은 그 모델을 지원하는 다른 에이전트 도구와 짝을 맞춰야 합니다.

# ① 받을 모델 (Hugging Face 이름)
MODEL=Qwen/Qwen3-Coder-Next
ARGS=(
  # ② GPU 두 장에 나눠 싣기
  --tensor-parallel-size 2
  # ③ 도구 호출을 알아듣게
  --enable-auto-tool-choice
  --tool-call-parser qwen3_coder
  # ④ 이 주소로 요청을 받는다
  --port 8000
)
vllm serve "$MODEL" "${ARGS[@]}"

Qwen3-Coder-Next 모델 카드에 적힌 vllm serve 명령을 옵션마다 설명을 달 수 있게 나눠 적었습니다(vLLM 0.15.0 이상).

  1. Hugging Face 에 올라온 모델 이름입니다. 처음 실행하면 가중치를 다운받는데 폐쇄망이라면 미리 들여온 경로를 적습니다.
  2. 총 80B 를 GPU 한 장에 다 담을 수 없어 두 장에 나눠 싣습니다. 카드는 서버가 뜨지 않으면 컨텍스트 길이(context length)를 32,768 처럼 줄이라고 적었습니다. 컨텍스트 길이는 모델이 한 번에 읽는 토큰 수라 줄이면 그만큼 메모리가 남습니다.
  3. 에이전트는 "파일 읽기" 같은 도구를 정해진 형식으로 부릅니다. 모델이 내놓는 도구 호출을 그 형식으로 바꿔 주는 설정이고 모델마다 이름이 다릅니다.
  4. 포트(port)는 한 서버 안에서 프로그램마다 나눠 쓰는 문 번호입니다. 서버가 뜨면 8000번 문으로 OpenAI API 와 같은 형식의 요청을 받습니다. ChatGPT 를 만든 OpenAI 가 정한 요청 모양(보낼 주소와 항목 이름)을 그대로 따른다는 뜻입니다. 그 형식을 쓰는 에이전트 도구라면 이 주소만 모델 주소로 넣으면 됩니다.

모델보다 먼저 물어야 할 네 가지

고르는 순서를 정해 두면 회의가 짧아집니다. 보안이 문을 정하고 사용량과 사람이 비용을 정하며 마지막으로 나눠 쓸지 묻습니다. 어느 답에 닿든 성능 차이를 메우는 일은 남습니다.

1코드를 밖으로 보내도 되나

규정이나 고객 계약이 막으면 다른 질문은 의미가 없습니다. 자체 호스팅만 남습니다. 클라우드 업체가 회사 전용 공간에 모델을 띄워 주는 방식도 있지만 그것도 회사 밖 서버이므로 규정 문구를 확인해야 합니다.

2서버를 꽉 채울 만큼 쓰나

보내도 된다면 비용을 봅니다. 사용량이 적거나 들쭉날쭉하면 API 가 쌉니다. 작은 팀이 몇 주 시험 삼아 쓸 때도 API 로 먼저 써 보고 실제 사용량을 잰 다음 계산합니다.

3서버를 맡을 사람이 있나

사용량이 많아도 GPU 서버와 서빙 프로그램을 맡을 사람이 없으면 그 사람을 뽑는 비용이 계단 위에 얹힙니다. 이미 GPU 를 운영하는 팀이 있는 회사만 이 칸을 쉽게 넘습니다.

4민감한 일만 나눌 수 있나

둘 중 하나만 고를 필요는 없습니다. 민감한 저장소와 반복 작업은 사내 모델에, 어려운 설계는 클라우드 API 에 보내는 식입니다. 게이트웨이 하나가 요청을 받아 규칙대로 나눠 보내고 사용량도 사람별로 기록합니다. 나눌 수 없다면 전부 사내 모델로 보냅니다. 여기까지 왔다면 서버를 꽉 채워 쓰고 맡을 사람도 있는 회사라 자체 호스팅이 이미 쌉니다.

결론 · 격차는 검증으로 메운다

어느 쪽이든 사내 모델은 몇 달 뒤의 실력입니다. 테스트와 리뷰 같은 확인 단계를 더 촘촘히 걸어야 같은 결과가 나옵니다(에이전트 루프 글). 격차와 가격이 계속 움직이니 이 순서도는 반년마다 다시 그립니다.
