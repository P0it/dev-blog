vLLM이 같은 GPU로 요청을 몇 배 더 받는 이유

친구 열 명이 같은 챗봇에 동시에 질문을 보낸다고 해 봅시다. 모델은 하나, GPU도 한 장입니다. 이 GPU는 몇 명에게 한꺼번에 답할 수 있을까요?

사람 수를 먼저 막는 건 계산 속도가 아니라 메모리 자리입니다. 모델은 답을 쓰는 동안 앞 글자들의 계산 결과를 GPU 메모리에 쌓아 두는데, 이 자리를 어떻게 나눠 주느냐에 따라 같은 GPU에 태우는 사람 수가 몇 배 달라집니다. 좌석표에서 방식을 바꿔 가며 ▶를 눌러 보세요.

자리를 나눠 주는 방식

지금 답하는 요청3명
줄 서서 기다리는 요청5명
잡아 둔 칸 중 토큰이 든 칸30%
지난 스텝8
10명 모두 끝내는 데 걸린 스텝 미리 잡기 — · 블록씩 —

칸 하나가 토큰(token) 하나를 저장할 자리입니다. 토큰은 모델이 글을 읽고 쓰는 단위로, 단어보다 조금 작은 조각입니다. 모델을 한 번 돌리는 한 스텝(iteration)마다 답하는 요청이 토큰을 하나씩 씁니다. 블록(block)은 칸 몇 개를 묶어 한꺼번에 나눠 주는 단위입니다. 칸 96개, 요청 10개, 블록 4칸은 설명을 위한 예시 값입니다. 실제 vLLM의 블록은 16토큰이고 H100 한 장에 Qwen2.5-7B를 올리면 칸이 100만 개 안팎입니다.

generate()로는 한 번에 한 사람씩 답합니다

실험할 때는 Hugging Face의 transformers 라이브러리로 모델을 불러 generate()를 부르면 답이 나옵니다. 이 함수는 질문 하나를 받아 답의 마지막 토큰까지 만든 뒤에야 돌아옵니다. 그동안 들어온 두 번째 질문은 줄을 서서 기다립니다.

한 사람만 계산하는 동안 GPU는 대부분 놉니다. 답을 토큰 하나씩 쓰는 단계(Decode)는 토큰마다 모델의 숫자 전부를 메모리에서 읽어 오는데, 이 읽기가 계산보다 300배쯤 오래 걸립니다(자세한 계산). 이 그림의 300칸 가운데 초록 칸만 실제로 계산하는 시간입니다.

그래서 여러 사람의 질문을 묶어 한 번에 계산합니다. 이렇게 묶은 것을 배치(batch)라고 합니다. 숫자를 한 번 읽어 와 여러 사람 몫을 같이 계산하니 놀던 계산 장치를 쓸 수 있습니다. 그림의 토글을 4명, 64명으로 바꿔 보면 걸리는 시간은 그대로인데 초록 칸과 답을 받는 사람이 같이 늘어납니다. 요청을 받아 배치를 짜고 메모리를 관리해 답을 돌려주는 서버 프로그램을 추론 엔진(inference engine)이라고 부르고 vLLM이 대표적입니다.

이렇게 모델을 서버에 올려 여러 사람의 요청에 답하게 하는 일을 서빙(serving)이라고 합니다.

코드로는 이렇게 생겼습니다(transformers 5.19 기준). 노트북에서 데모를 만들기에는 충분하지만 이걸 웹 서버로 감싼다고 여러 사람을 받는 서비스가 되지는 않습니다.

  1. 모델 숫자를 GPU 메모리에 올립니다. dtype="auto"는 파일에 적힌 BF16 형식 그대로 쓰라는 뜻이고 device_map="cuda"는 NVIDIA GPU에 올리라는 뜻입니다. 이 숫자들은 서버가 켜져 있는 동안 그대로 메모리를 차지합니다.
  2. 질문 하나의 답을 끝까지 만듭니다. 질문 전체를 한꺼번에 읽는 Prefill과 Decode 반복이 이 한 줄 안에서 다 돌아갑니다. 여러 질문을 목록으로 넣어 한 번에 돌릴 수도 있지만 그러면 가장 긴 답이 끝날 때까지 다 같이 기다립니다.
from transformers import AutoModelForCausalLM, AutoTokenizer

model_id = "Qwen/Qwen2.5-7B-Instruct"
tok = AutoTokenizer.from_pretrained(model_id)
# ① 모델 숫자를 GPU 메모리에 올린다
model = AutoModelForCausalLM.from_pretrained(
    model_id, dtype="auto", device_map="cuda"
)

msgs = [{"role": "user", "content": "하늘은 왜 파란색인가요?"}]
inputs = tok.apply_chat_template(
    msgs, add_generation_prompt=True,
    return_tensors="pt", return_dict=True,
).to(model.device)

# ② 질문 하나의 답을 끝까지 만든다
out = model.generate(**inputs, max_new_tokens=128)
answer = out[0][inputs["input_ids"].shape[1]:]
print(tok.decode(answer, skip_special_tokens=True))

미리 잡아 둔 KV Cache 자리는 대부분 비어 있습니다

배치로 묶으려면 사람마다 메모리 자리를 따로 줘야 합니다. 모델은 답을 쓰는 동안 앞 토큰들의 계산 결과인 Key와 Value를 GPU 메모리에 저장해 두고 다시 꺼내 씁니다. 이 저장 공간이 KV Cache입니다. Qwen2.5-7B라면 토큰 하나에 57,344바이트가 듭니다(크기 계산).

그런데 답이 몇 토큰이 될지는 미리 알 수 없습니다. 그래서 vLLM 이전의 서버들은 요청마다 최대 길이만큼 이어진 자리를 먼저 잡아 두었습니다. 대부분의 딥러닝 프로그램이 숫자 표 하나를 메모리의 이어진 공간에 두어야 계산할 수 있었기 때문입니다. 이 그림은 그렇게 잡은 메모리 한 줄을 극장 좌석처럼 그린 것입니다.

극장에서 열 명이 올지도 모른다며 열 자리를 잡았는데 세 명만 오면 일곱 자리는 공연 내내 빕니다. 서버에서도 같은 낭비가 세 가지로 생깁니다.

  • 곧 쓸 자리: 다음 스텝들에 쓸 칸이지만 그때까지 다른 요청이 못 씁니다. 논문은 이것을 예약(reservation)이라고 부릅니다.
  • 끝내 안 쓴 자리: 답이 최대 길이보다 일찍 끝나 한 번도 쓰지 않은 칸입니다. 내부 조각화(internal fragmentation)라고 합니다.
  • 끼인 틈: 잡은 자리 사이에 남았지만 너무 짧아 다음 요청이 못 들어가는 칸입니다. 외부 조각화(external fragmentation)라고 합니다.

극장과 다른 점은 길이를 아는 때입니다. 단체 관객은 표를 살 때 인원을 알지만 모델은 답을 다 쓰고 나서야 길이를 압니다. 그래서 미리 잡는 크기를 아무리 잘 맞춰도 빈칸이 남습니다.

PagedAttention 논문은 이 낭비를 실제로 쟀습니다. 기존 방식에서 잡아 둔 KV Cache 자리 가운데 토큰이 든 칸은 20.4~38.2%뿐이었습니다. 답 길이를 미리 안다고 가정해도 38.2%입니다. vLLM 팀은 기존 시스템이 메모리의 60~80%를 버린다고 정리했습니다.

PagedAttention은 KV Cache를 블록으로 나눠 필요할 때 줍니다

vLLM은 KV Cache 자리를 블록이라는 작은 묶음으로 나눕니다. 블록 하나에는 정해진 수의 토큰이 들어가고 vLLM의 기본값은 16토큰입니다. 이 그림에서는 보기 쉽게 4토큰으로 줄였습니다.

요청이 들어오면 질문을 담을 만큼만 블록을 줍니다. 답을 쓰다 블록이 차면 그때 새 블록을 하나 더 줍니다. 새 블록은 GPU 메모리 어디에 있어도 됩니다. 대신 요청마다 블록 테이블(block table)을 두어 "내 몇 번째 블록이 실제로 몇 번 자리에 있는지"를 적어 둡니다. ▶를 눌러 토큰을 하나씩 더해 보세요.

요청 쪽에서 순서대로 센 블록을 논리 블록(logical block), GPU 메모리에 실제로 놓인 블록을 물리 블록(physical block)이라고 부릅니다. 블록 테이블은 이 둘을 잇는 표입니다.

이렇게 하면 버리는 칸은 요청마다 마지막 블록의 빈칸뿐입니다. 블록 크기가 모두 같아서 끼인 틈도 생기지 않습니다. 논문 실험에서 vLLM은 잡은 자리의 96.3%에 토큰을 채웠고 vLLM 팀은 낭비가 4% 미만이라고 밝혔습니다.

이 아이디어는 운영체제에서 왔습니다. 운영체제는 프로그램이 쓰는 메모리를 페이지(page)라는 같은 크기 조각으로 나누고 페이지 테이블에 적어 둔 대로 실제 메모리의 빈자리에 흩어 놓습니다. 이 방식을 페이징(paging)이라고 합니다. 프로그램 쪽에서는 메모리가 이어져 있는 것처럼 보입니다.

논문은 대응을 이렇게 적었습니다. 블록은 페이지, 토큰은 바이트, 요청은 프로세스(process)에 해당합니다. 프로세스는 실행 중인 프로그램 하나입니다. 학교 사물함으로 바꾸면 짐이 늘 때마다 아무 빈 사물함을 하나 더 받고 수첩에 번호를 적어 두는 것과 같습니다.

사물함과 다른 점도 있습니다. 사물함은 필요한 칸 하나만 열면 되지만 모델은 토큰 하나를 만들 때마다 그 요청의 블록 전부를 읽어야 합니다. 그래서 앞 토큰들의 Key·Value를 읽어 지금 토큰과 견주는 Attention 계산을 고쳤습니다. 블록 테이블을 보며 흩어진 블록을 찾아 읽는 GPU 계산 프로그램, 곧 커널(kernel)을 새로 만든 것입니다. PagedAttention이라는 이름이 여기서 나왔습니다. 논문에서 이 커널은 기존 것보다 20~26% 느렸지만 한 번에 태우는 요청이 늘어 전체 처리량(throughput)은 훨씬 커졌습니다.

Continuous Batching은 끝난 자리에 바로 다음 요청을 태웁니다

자리가 넉넉해도 언제 태우느냐가 또 문제입니다. 여러 요청을 한 배치로 묶어 시작하면 보통 배치 안의 모든 답이 끝날 때까지 새 요청을 받지 않습니다. 이것을 정적 배치(static batching)라고 합니다. 답 길이가 제각각이라 먼저 끝난 자리는 가장 긴 답이 끝날 때까지 빈 채로 남습니다.

Continuous Batching은 배치를 스텝마다 다시 짭니다. 스텝은 모델을 한 번 돌려 요청마다 토큰 하나씩을 만드는 단위입니다. 스텝이 끝날 때마다 끝난 요청을 빼고 기다리던 요청을 넣습니다. 2022년 Orca 논문이 이 방식을 iteration-level scheduling이라는 이름으로 내놓았습니다.

자리 네 개에 요청 여덟 개(A~H)를 태웁니다. 가로 한 칸이 한 스텝입니다.

색칸의 글자는 요청, 굵은 테두리는 그 요청의 마지막 토큰, 회색 빗금은 빈자리입니다. 답 길이(A 3, B 9, C 4, D 6, E 2, F 8, G 5, H 3토큰)는 설명을 위한 예시 값이고 새 요청이 질문을 읽는 Prefill 시간은 뺐습니다.

버스와 다른 점

단체 관광버스는 마지막 손님이 내릴 때까지 새 손님을 태우지 않고 시내버스는 정류장마다 내리고 탑니다. 다만 버스는 손님이 타는 데 시간이 거의 들지 않지만 새 요청은 질문 전체를 읽는 Prefill부터 해야 합니다. Prefill이 길면 같은 스텝에 있던 다른 사람의 답이 그만큼 늦게 나옵니다.

그래서 vLLM의 V1 엔진은 한 스텝에 계산할 토큰 수에 상한을 두고 긴 Prefill을 여러 스텝에 나눠 다른 요청의 Decode와 함께 넣습니다. 이것을 chunked prefill이라고 합니다. 스케줄러(scheduler)는 스텝마다 "요청마다 토큰 몇 개를 계산할지"만 정합니다.

이 방식은 PagedAttention과 짝을 이룹니다. 새 요청을 바로 태우려면 그 순간 KV Cache 자리가 있어야 하는데, 블록 단위로 나눠 주면 끝난 요청이 돌려준 블록을 다음 요청에 바로 줄 수 있습니다. Anyscale은 vLLM의 Continuous Batching과 메모리 관리를 함께 썼을 때 정적 배치보다 처리량이 최대 23배였다고 측정했습니다.

같은 앞부분은 한 번만 계산해 여러 요청이 나눠 씁니다

챗봇 서비스는 보통 모든 질문 앞에 같은 안내문을 붙입니다. "너는 친절한 상담원이다" 같은 시스템 프롬프트(system prompt)입니다. 앞부분 토큰이 같으면 그 부분의 KV Cache도 똑같으니, 한 번 계산해 둔 블록을 다른 요청이 그대로 가져다 쓰면 됩니다. vLLM은 이것을 prefix caching이라고 부르고 V1 엔진부터 기본으로 켜 둡니다.

같은 블록인지는 지문으로 찾습니다. 블록 안의 토큰과 그 앞 블록들의 내용을 함께 넣어 해시(hash) 값을 계산합니다. 해시는 내용이 한 글자만 달라도 완전히 달라지는 짧은 숫자입니다. 그래서 앞부분이 토큰 하나라도 다르면 공유되지 않습니다. 꽉 찬 블록만 공유하므로 덜 찬 마지막 블록은 요청마다 따로 둡니다.

같은 안내문을 사람마다 복사해 주는 대신 칠판에 한 번 써 두고 다 같이 보는 것과 비슷합니다. 다른 점은 아무도 안 보는 블록도 바로 지우지 않는다는 것입니다. 다음 요청이 또 쓸 수 있으니 남겨 두고 자리가 모자랄 때 가장 오래 안 쓴 블록부터 비웁니다. 논문 실험에서는 번역 예시 다섯 개를 공유하자 처리량이 기존 방식의 3.58배가 됐습니다.

vllm serve 한 줄로 OpenAI 호환 서버를 띄웁니다

지금까지 본 블록 관리와 스케줄링은 vLLM 안에 다 들어 있습니다. 쓰는 사람은 명령 한 줄로 서버를 띄웁니다. 명령과 옵션은 vLLM 0.31(2026년 10월 5일 공개) 기준입니다.

  1. 설치입니다. NVIDIA GPU가 달린 리눅스 기준이고 --torch-backend=auto는 GPU에 맞는 PyTorch를 골라 함께 설치합니다.
  2. 모델 이름만 주면 서버가 뜹니다. --max-model-len은 요청 하나가 쓸 수 있는 최대 토큰 수(질문+답)입니다. 빼면 모델 설정값(이 모델은 32,768)을 씁니다. --gpu-memory-utilization은 GPU 메모리 중 vLLM이 쓸 비율로, 기본값이 0.92입니다. 가중치를 올리고 남은 부분이 KV Cache 블록이 됩니다.

서버 로그의 GPU KV cache size 줄에 지금까지 본 내용이 숫자로 찍힙니다. 가중치를 올리고 남은 메모리에 토큰 약 103만 개 자리가 생겼습니다. 블록 64,368개 × 16토큰입니다. 한 사람이 8,192토큰을 꽉 채워도 125명이 함께 들어가고 실제 대화는 대부분 그보다 짧아 블록이 덜 듭니다.

# ① 설치 (NVIDIA GPU 기준)
uv pip install vllm --torch-backend=auto

# ② 서버 띄우기
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.92

H100 80GB 한 장을 가정한 예시 출력입니다. 실제 숫자는 GPU와 버전에 따라 다르고 로그 앞부분(시간·프로세스 이름)은 줄였습니다.

서버는 OpenAI API와 같은 모양으로 요청을 받습니다. 이것을 OpenAI 호환(OpenAI-compatible)이라고 합니다. /v1/chat/completions 같은 요청 주소, 곧 엔드포인트(endpoint)가 같아서 OpenAI용으로 짠 코드가 주소만 바꾸면 그대로 돌아갑니다. 앱은 뒤에 어떤 엔진이 있는지 몰라도 됩니다.

  1. 요청을 보낼 주소입니다. 서버를 띄운 컴퓨터의 8000번 포트(기본값)입니다. 서버를 --api-key 없이 띄웠다면 키는 아무 글자나 넣으면 됩니다.
  2. 서버를 띄운 모델 이름 그대로 넣습니다. 다르면 모델을 찾을 수 없다는 오류가 납니다.
  3. 답 길이 상한입니다. 작게 잡을수록 요청 하나가 차지하는 블록 수의 상한도 작아집니다.
  4. 이번 요청에 쓴 토큰 수입니다. 질문 41토큰(채팅 형식으로 감싼 길이)과 답 31토큰을 더한 값입니다.
from openai import OpenAI

# ① 주소만 내 서버로
client = OpenAI(
    base_url="http://localhost:8000/v1", api_key="EMPTY"
)

resp = client.chat.completions.create(
    # ② 서버를 띄운 모델 이름 그대로
    model="Qwen/Qwen2.5-7B-Instruct",
    messages=[{"role": "user", "content": "하늘은 왜 파란색인가요?"}],
    # ③ 답 길이 상한
    max_tokens=128,
)
print(resp.choices[0].message.content)
# ④ 이번 요청에 쓴 토큰 수
print(resp.usage.total_tokens)

vLLM 말고도 추론 엔진은 여럿입니다

블록 단위 KV Cache와 Continuous Batching은 이제 서빙 엔진 대부분이 갖춘 기본기입니다. 엔진마다 잘 맞는 하드웨어와 용도가 다르고 대부분 OpenAI 호환 서버를 함께 줍니다. 그래서 앱 코드는 그대로 두고 엔진만 바꿔 볼 수 있습니다.

이 그래프는 vLLM이 처음 공개된 2023년 6월에 vLLM 팀이 잰 결과입니다. LLaMA-13B 모델을 A100 40GB 한 장에 올리고 1분에 처리한 요청 수를 비교했습니다. Hugging Face transformers가 6.4개, 당시 Hugging Face의 서빙 도구 TGI가 61.8개, vLLM이 154.2개였습니다.

vLLM 팀은 여러 조건을 합쳐 transformers보다 최대 24배, TGI보다 최대 3.5배라고 발표했습니다. 다만 2023년 버전끼리의 비교입니다. 그 뒤로 TGI도 PagedAttention과 Continuous Batching을 넣었으니 지금 엔진끼리의 차이로 읽으면 안 됩니다.

엔진만든 곳잘 맞는 곳과 특징
vLLMUC Berkeley에서 시작한 오픈소스데이터센터 GPU 서빙의 기본 선택지. PagedAttention·Continuous Batching·prefix caching, vllm serve
SGLangLMSYS 쪽에서 시작한 오픈소스에이전트처럼 앞부분이 겹치는 요청이 많은 일. RadixAttention으로 KV Cache를 재사용하며 논문은 최대 6.4배 처리량을 보고
TensorRT-LLMNVIDIANVIDIA GPU에서 성능을 끝까지 끌어낼 때. 전용 커널, trtllm-serve로 OpenAI 호환 서버
llama.cppggml-org 오픈소스노트북·Mac·CPU에서 GGUF 파일로 돌릴 때. C/C++로 만들었고 llama serve로 OpenAI 호환 서버, Continuous Batching 기본 켜짐
TGIHugging Face2026년 현재 유지보수만 하는 상태(maintenance mode). 새 프로젝트에는 vLLM·SGLang을 권한다고 README에 적었다

같은 GPU에 요청을 몇 배 더 태우려고 vLLM이 손본 곳은 계산 속도보다 KV Cache 자리였습니다. 자리는 블록으로 쪼개 필요할 때 주고(PagedAttention), 빈자리가 나면 다음 스텝에 바로 다음 요청을 태웁니다(Continuous Batching).

모델이 GPU 한 장에 다 들어가지 않거나, 반대로 한 장이 남아돌 때는 어떻게 할까요? 다음 글에서는 여러 GPU와 여러 서버에 모델을 나누고 묶는 방법을 알아보겠습니다.
