챗봇의 '지난 대화' 목록 뒤에는 무엇이 저장돼 있을까요?

요즘 챗봇 앱은 왼쪽에 '지난 대화' 목록이 있습니다. 어제 대화를 눌러 질문을 이어 가면 챗봇은 어제 정한 규칙을 기억하고 답합니다.

모델은 원래 대화를 기억하지 못하니, 그 기억은 화면 뒤 어딘가에 저장돼 있어야 합니다. 이 글은 목록의 한 줄에서 출발해 LangGraph가 무엇을, 언제, 어디에 저장하는지 한 겹씩 내려가 봅니다.

에이전트는 왜 줄이 아니라 고리 모양으로 돌까요?

에이전트(agent)는 모델이 도구를 쓰고 결과를 보고 다시 생각하는 일을 되풀이하는 프로그램이라, 흐름이 앞으로만 가지 않고 되돌아옵니다. 그래서 LangGraph는 일을 그래프(graph)로 그립니다.

그래프는 할 일 한 칸인 노드(node)와, 다음에 어디로 갈지 정하는 엣지(edge)로 이루어집니다. 모든 노드가 함께 들여다보는 공책이 하나 있는데, 이걸 상태(state)라고 부릅니다. 대화 기록도 이 상태에 들어 있습니다.

기억은 이 상태에서 생깁니다. 노드가 일을 마칠 때마다 상태가 바뀌니, 바뀐 상태를 그때그때 저장해 두면 나중에 그 자리부터 이어 갈 수 있습니다. 노드와 엣지를 직접 짜는 법은 State·Node·Edge 글에 있습니다.

한 번 물으면 상태 사진은 몇 장 찍힐까요?

질문 한 번에 세 장입니다. 체크포인터(checkpointer)는 그래프가 한 걸음 옮길 때마다 그 순간의 상태 전체를 찍어 두는 부품이고, 한 장 한 장을 체크포인트(checkpoint)라고 부릅니다.

아래는 도구 없는 에이전트에 두 번 물었을 때 실제로 저장된 여섯 장입니다. 질문을 받은 순간, 질문을 공책에 적은 순간, 모델 답까지 적은 순간이 한 장씩 남습니다.

thread_id는 사람 이름표가 아니라 대화방 번호입니다

사진은 대화방마다 따로 쌓입니다. 그 대화방을 가리키는 번호가 thread_id입니다. 같은 번호로 물으면 그 방의 마지막 사진을 꺼내 이어 가고, 다른 번호로 물으면 빈 방에서 시작합니다.

예제 코드에는 사용자 아이디를 그대로 thread_id로 넣는 경우가 많아 헷갈리기 쉽습니다. 그러면 한 사람에게 대화방이 하나뿐이라, 앱의 '지난 대화' 목록처럼 대화를 여러 개 열어 둘 수 없습니다.

그래서 대화방마다 새 번호를 만들고, 어느 사용자의 방인지는 따로 적어 둡니다. 방을 넘어 기억할 것(이름, 말투)은 Store라는 다른 저장소에 둡니다(단기 기억과 장기 기억 글).

프로그램을 껐다 켜면 그 사진들은 어디로 갈까요?

어디에 찍어 두었느냐에 달렸습니다. InMemorySaver는 사진을 메모리(memory)에 둡니다. 메모리는 프로그램이 켜져 있는 동안만 쓰는 임시 작업대라, 프로그램을 끄면 같이 비워집니다.

SqliteSaver는 사진을 SQLite 파일에 씁니다. SQLite는 서버 없이 파일 하나로 돌아가는 작은 데이터베이스(database)이고, 데이터베이스는 자료를 표 모양으로 오래 보관하는 저장소입니다. 파일은 프로그램을 꺼도 디스크에 남습니다.

from langchain.agents import create_agent
from langgraph.checkpoint.sqlite import SqliteSaver

# ① 파일 하나에 사진을 쓰는 체크포인터
with SqliteSaver.from_conn_string("memory.db") as saver:
    agent = create_agent(
        model="openai:gpt-6.1-sol",
        checkpointer=saver,
    )

    # ② 대화방 번호
    config = {"configurable": {"thread_id": "t-0412"}}

    # ③ 이번 질문 하나만 보낸다
    question = input("사용자: ")
    new = {"messages": [
        {"role": "user", "content": question}]}
    result = agent.invoke(new, config)
    print("Agent:", result["messages"][-1].content)

  1. from_conn_string은 파일을 열고, 처음이면 저장용 표를 만들고, with 블록이 끝나면 파일을 닫습니다. 파일이 없으면 새로 만듭니다. "memory.db" 대신 ":memory:"를 넣으면 파일 없이 메모리에만 둡니다.
  2. 방 번호는 실행 설정을 담는 사전인 config, 그 안의 configurable 칸에 넣습니다. 번호를 빼면 어느 방에 저장할지 몰라 오류가 납니다. 실제 앱에서는 '새 대화'를 누를 때 겹칠 일이 거의 없는 긴 무작위 번호(uuid)를 만들어 씁니다.
  3. 앞 대화는 체크포인터가 방 번호로 찾아 붙여 주니, 보낼 때는 이번 질문 하나만 넣습니다. 앞 대화를 직접 이어 붙여 보내던 2편의 방식을 이제 그래프가 대신합니다. 버전은 langgraph 1.2, langgraph-checkpoint-sqlite 3.1 기준입니다.
다른 예제에서 check_same_thread=False를 보면 — 무슨 뜻일까요?

여기서 스레드(thread)는 대화방이 아니라, 한 프로그램 안에서 동시에 도는 일꾼 줄을 말합니다. SQLite는 기본으로 연결을 만든 일꾼만 그 연결을 쓰게 막는데, LangGraph는 저장 일을 다른 일꾼에게 맡기기도 합니다. 그래서 직접 연결할 때는 sqlite3.connect("memory.db", check_same_thread=False)로 이 제한을 풉니다. from_conn_string은 안에서 이 값을 알아서 넣습니다.

여러 서버가 같은 기억을 나눠 써야 하는 서비스는 PostgreSQL이라는 데이터베이스 서버에 저장하는 PostgresSaver를 씁니다(langgraph-checkpoint-postgres). async로 짠 앱이면 AsyncSqliteSaver처럼 이름 앞에 Async가 붙은 쪽을 고릅니다.

memory.db를 열어 보면 무엇이 들어 있을까요?

사진 한 장이 표의 한 줄입니다. 파일 안에는 checkpoints와 writes 두 표가 있습니다. checkpoints의 한 줄에는 방 번호, 사진 번호, 바로 앞 사진 번호, 그리고 그 순간의 상태 전체가 압축돼 들어 있습니다.

writes는 노드가 일을 마칠 때마다 상태에 써 넣은 내용을 따로 적은 쪽지입니다. 노드 여러 개를 돌리다 프로그램이 멈추면, 다시 켰을 때 쪽지가 있는 노드는 건너뛰고 나머지만 돌립니다.

from langchain.agents import create_agent
from langgraph.checkpoint.sqlite import SqliteSaver

with SqliteSaver.from_conn_string("memory.db") as saver:
    agent = create_agent(
        model="openai:gpt-6.1-sol",
        checkpointer=saver,
    )
    config = {"configurable": {"thread_id": "t-0412"}}
    # ① 가장 최근 사진 한 장
    now = agent.get_state(config)
    print(len(now.values["messages"]), now.next)

    # ② 모든 사진을 최신부터 거꾸로
    for snap in agent.get_state_history(config):
        m = snap.metadata
        print(m["step"], m["source"],
              len(snap.values["messages"]), snap.next)

  1. get_state는 그 방의 최신 사진을 돌려줍니다. values는 상태 내용, next는 다음에 돌 노드 이름입니다. 빈 괄호 ()는 할 일이 끝났다는 뜻이라, 다음 질문을 기다리는 상태입니다.
  2. get_state_history는 모든 사진을 최신부터 하나씩 꺼냅니다. source가 input이면 질문을 받은 순간, loop면 노드가 일을 마친 순간입니다. 사진마다 붙은 checkpoint_id를 config에 넣으면 그 시점으로 돌아가 다시 실행할 수도 있습니다(승인 대기 글의 시간 여행).
사진은 정확히 언제 디스크에 써질까요? (저장 시점 설정 durability)

invoke나 stream에 durability를 넘겨 정합니다. 기본값 "async"는 다음 노드를 돌리면서 동시에 저장합니다. "sync"는 저장이 끝나야 다음으로 넘어가 느리지만 가장 안전합니다. "exit"는 실행이 끝날 때만 저장해서, 중간에 프로그램이 죽으면 그 사이 사진이 남지 않습니다.

대화가 길어지면 모델은 무엇을 다 읽어야 할까요?

방에 쌓인 메시지 전부입니다. 체크포인터는 마지막 사진의 메시지 목록을 통째로 꺼내 모델에게 넘깁니다. 질문이 열 번이면 스무 개 가까운 메시지를 매번 다시 읽는 셈입니다.

모델 사용료는 읽은 토큰(token, 모델이 글을 읽는 단위로 단어보다 조금 작은 조각) 수만큼 붙습니다. 한 번에 읽을 수 있는 양인 컨텍스트 창(context window)도 정해져 있어서, 넘치면 오류가 납니다.

이럴 때 오래된 메시지를 짧은 요약 한 장으로 바꿉니다. LangChain의 SummarizationMiddleware가 이 일을 합니다. 미들웨어(middleware)는 모델을 부르기 직전처럼 정해진 순간에 끼어들어 일을 하나 더 하는 부품입니다.

from langchain.agents import create_agent
from langchain.agents.middleware import SummarizationMiddleware
from langgraph.checkpoint.sqlite import SqliteSaver

# ① 언제 요약하고 무엇을 남길지
summarize = SummarizationMiddleware(
    model="openai:gpt-6.1-sol",
    trigger=("tokens", 600),
    keep=("messages", 4),
    # ② 요약은 값싼 모델에게 맡긴다
    summarizer="openai:gpt-6-luna",
)

with SqliteSaver.from_conn_string("memory.db") as saver:
    agent = create_agent(
        model="openai:gpt-6.1-sol",
        checkpointer=saver,
        middleware=[summarize],
    )
    config = {"configurable": {"thread_id": "t-long"}}
    for n in range(1, 9):
        # ③ 단계마다 상태 전체를 받아 메시지 수만 센다
        q = {"role": "user", "content": f"질문 {n}"}
        new = {"messages": [q]}
        steps = agent.stream(new, config, stream_mode="values")
        print(n, [len(s["messages"]) for s in steps])

  1. trigger는 요약을 시작할 기준이고 keep은 요약하지 않고 남길 최근 분량입니다. 600토큰은 바로 보이게 일부러 작게 잡은 값이고, 실제로는 ("fraction", 0.8)처럼 모델 컨텍스트 창의 80%를 기준으로 삼곤 합니다. trigger를 빼면 요약을 한 번도 하지 않고, keep을 빼면 최근 20개를 남깁니다.
  2. summarizer를 주면 요약 글은 그 모델이 쓰고, model은 토큰 한도를 재는 데만 씁니다. 옛 예제의 max_tokens_before_summary, messages_to_keep은 이제 trigger, keep으로 바뀌었습니다(langchain 1.5).
  3. stream_mode="values"는 단계가 끝날 때마다 상태 전체를 내보냅니다. 6번째 줄의 [11, 5, 6]이 위 그림의 세 장입니다. 기준을 너무 낮추면 질문마다 요약해서, 한 번 물을 때 모델을 두 번 부르게 됩니다.

요약하면 memory.db도 가벼워질까요?

아닙니다. 요약은 모델이 읽을 목록을 줄일 뿐, 이미 찍어 둔 사진을 지우지 않습니다. 사진 한 장에는 그 순간의 대화 전체가 들어 있어서, 뒤로 갈수록 한 장이 커집니다. 요약한 순간부터는 다음 장이 가벼워지지만, 쌓인 총량은 계속 늘어납니다. 이 실험에서는 요약 미들웨어도 노드 하나로 끼어들어 질문 하나에 사진이 네 장씩 생겼습니다.

옛 사진도 그대로 열립니다. 위 실험에서 요약이 끝난 뒤 get_state_history로 첫 질문 때 사진을 꺼내 보면 '질문 1'이 원문 그대로 들어 있습니다.

정말 지우려면 방 단위로 지웁니다. 사용자가 목록에서 대화를 삭제할 때 saver.delete_thread("t-0412")를 부르면 그 방의 사진과 쪽지가 모두 사라집니다. SqliteSaver 3.1.3에는 오래된 사진만 골라 지우는 prune이 아직 없습니다(부르면 NotImplementedError).

기억하는 챗봇을 만들 때 정할 네 가지

  1. 어디에 저장할까코드를 고치며 확인할 때는 InMemorySaver, 혼자 쓰는 앱이나 실험은 SqliteSaver, 여러 서버가 함께 쓰는 서비스는 PostgresSaver가 공식 문서의 권고입니다.
  2. 방 번호를 어떻게 줄까'새 대화'마다 새 thread_id를 만들고, 어느 사용자의 방인지 서버가 따로 적어 둡니다. 화면에서 받은 번호를 그대로 믿으면 남의 방 번호를 넣어 남의 대화를 꺼내 볼 수 있으니, 그 사용자의 방이 맞는지 확인한 뒤 넘깁니다.
  3. 언제 요약할까trigger는 모델 컨텍스트 창보다 넉넉히 아래로, keep은 최근 대화의 흐름이 끊기지 않을 만큼 잡습니다. 요약 글을 쓰는 모델은 값싼 쪽으로 따로 정할 수 있습니다.
  4. 언제 지울까요약해도 저장소는 줄지 않으니 지우는 규칙이 따로 있어야 합니다. 대화 삭제 버튼에는 delete_thread를 잇고, 개인정보가 담긴다면 보관 기간을 정하고, 사진을 암호화해 저장하는 EncryptedSerializer도 씁니다. 체크포인트 패키지는 저장된 사진을 다시 읽어 들이는 부분 등에서 보안 결함이 여러 차례 고쳐졌으니(보안 권고 목록) 최신 버전으로 둡니다.
