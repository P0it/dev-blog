> Anthropic 이 2026년 10월 7일 공개한 Claude Haiku 5.5 는 공식 요금표에 한 모델이 두 줄로 적혀 있습니다. 프롬프트 길이로 요율이 갈리는 구조와 새 토크나이저가 같은 텍스트를 약 30% 더 많이 세는 효과를 공식 문서의 숫자로 확인해 정리했습니다.

모델 요금표를 볼 때는 보통 입력과 출력 두 칸만 확인하고 넘어갑니다. 그런데 Claude Haiku 5.5 의 요금표에는 같은 모델이 두 줄로 적혀 있습니다.

왜 두 줄일까요? 프롬프트 길이에 따라 요율이 갈리기 때문입니다. 프롬프트가 10만 토큰 이하면 입력이 100만 토큰당 $0.10 이고 넘으면 $0.50 입니다. 출력 단가도 $0.50 에서 $2.50 으로 같이 올라갑니다.

이 경계가 어디에 그려져 있는지 알면 Haiku 5.5 에 무엇을 맡길지, 프롬프트를 어디까지 키워도 되는지 미리 정할 수 있습니다.

## 발표문의 75% 와 요금표의 두 줄

Anthropic 은 [Haiku 5.5 발표문](https://www.anthropic.com/claude-haiku-5-5)에서 이 모델을 지금까지 내놓은 소형 모델 중 가장 싸고 빠르며 뛰어나다고 소개했습니다. 평균적으로 Haiku 4.5 보다 약 75% 저렴하게 돌아간다는 설명도 함께 적혀 있습니다.

그런데 같은 발표문의 각주에는 조건이 둘 붙어 있습니다. 10만 토큰 이하 요청에서는 90% 저렴하고 그보다 긴 요청에서는 50% 저렴하다는 내용입니다.

[공식 요금표](https://platform.claude.com/docs/en/about-claude/pricing)는 이 조건을 모델 두 줄로 나눠 적어 뒀습니다. 100만 토큰당 가격을 Haiku 4.5 와 비교해 보면 아래와 같습니다.

| | 10만 토큰 이하 | 10만 토큰 초과 | Haiku 4.5 |
|---|---|---|---|
| 입력 | $0.10 | $0.50 | $1.00 |
| 출력 | $0.50 | $2.50 | $5.00 |
| 캐시 읽기 | $0.01 | $0.05 | $0.10 |
| 5분 캐시 쓰기 | $0.125 | $0.625 | $1.25 |

네 줄이 모두 정확히 다섯 배씩 벌어집니다. 요금표가 한 모델을 두 줄로 적어야 했던 이유가 여기에 있습니다.

## 10만 토큰을 넘기면 요청 전체가 다음 요율로 간다

초과분에만 높은 요율이 붙는 구조가 아닙니다. 요금 문서는 Haiku 5.5 를 프롬프트 길이로 과금한다고 적고 10만 토큰을 넘는 프롬프트는 더 높은 가격을 낸다고 설명합니다. 경계를 넘으면 요청 전체가 다음 요율로 계산됩니다.

숫자를 넣어 보면 차이가 분명해집니다. 9만 토큰짜리 프롬프트로 1,000번 호출하면 입력은 9,000만 토큰이고 100만 토큰당 $0.10 이니 $9.00 입니다.

같은 호출을 11만 토큰짜리 프롬프트로 1,000번 하면 입력은 1억 1,000만 토큰이 되고 요율이 $0.50 으로 올라가 $55.00 이 됩니다. 프롬프트가 22% 길어지는 동안 비용은 **6.1배**가 됩니다.

여기에 한 가지가 더 겹칩니다. Haiku 5.5 는 컨텍스트 창이 100만 토큰인데 요금 문서의 긴 컨텍스트 항목을 보면 Claude 4.6 이후 모델은 1M 컨텍스트 전체를 표준 요금으로 제공한다고 적어 두고 **괄호로 Haiku 5.5 만 예외로 빼 놓았습니다**. 100만 토큰을 열어 주면서 그중 얼마를 쓰는지로 요율을 매기는 모델은 현재 이 하나뿐입니다.

## 같은 텍스트를 약 30% 더 세는 새 토크나이저

그럼 10만 토큰이라는 경계는 글자 수로 치면 어디쯤일까요. 이 질문이 중요한 건 Haiku 5.5 가 토크나이저를 바꿨기 때문입니다.

[migration guide](https://platform.claude.com/docs/en/models/haiku-5-5/migration-guide) 는 Claude 4.7 이후 모델과 같은 새 토크나이저를 쓰며 같은 입력 텍스트가 Haiku 4.5 에서보다 약 30% 더 많은 토큰으로 세어진다고 적었습니다. 정확한 증가폭은 내용에 따라 달라집니다.

문서는 이 변화가 요청과 응답의 모양은 바꾸지 않는다고 말합니다. 바뀌는 건 토큰으로 재거나 예산을 잡아 둔 모든 값입니다.

`usage` 수치와 토큰 카운팅 결과가 같은 텍스트에서 더 크게 나오고 같은 토큰 수가 담는 글자 수는 줄어들며 Haiku 4.5 기준으로 맞춰 둔 `max_tokens` 는 같은 분량의 출력을 자를 수 있습니다. 그래서 migration guide 의 체크리스트 두 번째 항목이 프롬프트를 다시 세고 비용 추정을 다시 하라는 내용입니다.

## 글자 수 기준으로 다시 계산한 인하율

토큰 수가 1.3배로 늘어난다면 토큰당 단가와 토큰 개수를 같이 봐야 합니다. 같은 글자 수를 처리하는 값으로 환산해 직접 계산해 보면 이렇습니다.

10만 토큰 이하 구간에서 입력은 $0.10 × 1.3 이니 Haiku 4.5 의 $1.00 에 대해 $0.13 선입니다. 약 87% 절감이고 토큰당으로 적힌 90% 와 큰 차이가 없습니다.

10만 토큰 초과 구간은 $0.50 × 1.3 으로 $0.65 선이고 절감률은 약 35% 로 내려앉습니다. 토큰당 50% 로 적힌 숫자가 글자 수 기준에서는 이만큼 줄어듭니다.

경계 자체도 같이 움직입니다. 10만을 1.3 으로 나누면 약 7만 7천입니다. Haiku 4.5 에서 7만 7천 토큰으로 세어졌던 분량의 텍스트가 Haiku 5.5 에서는 10만 토큰 경계에 닿습니다.

예전 토큰 수를 그대로 들고 "우리 프롬프트는 9만이라 안전하다"고 판단하면 실제로는 이미 넘은 상태일 수 있습니다. migration guide 가 `claude-haiku-5-5` 로 모델을 지정해 다시 세라고 당부한 것도 같은 이야기입니다.

## Claude Code 가 기본 Haiku 를 5.5 로 올렸다

이 요금 구조는 API 를 직접 부르는 쪽만의 일이 아닙니다. 같은 날 나온 [Claude Code 2.1.293 changelog](https://code.claude.com/docs/en/changelog) 는 Haiku 5.5 를 추가하면서 이 모델이 Anthropic API 의 기본 Haiku 모델이 됐다고 적었습니다.

changelog 는 요율까지 같이 적어 뒀습니다. 1M 컨텍스트에 100만 토큰당 $0.10/$0.50 이고 10만 토큰을 넘는 프롬프트는 $0.50/$2.50 이라는 내용입니다. 기본값이 바뀌었으니 Haiku 를 따로 지정하지 않은 쪽도 이 두 구간 위에서 돌아갑니다.

## 짧은 프롬프트 작업에서는 90% 가 그대로 맞는 숫자

이 경계는 Haiku 가 겨냥한 작업에서는 거의 걸리지 않습니다. 발표문이 예로 든 용도는 요약, compaction, 데이터베이스 질의, 분류입니다. 이런 작업의 프롬프트는 대개 10만 토큰 아래에 머물고 그 구간에서는 90% 인하가 그대로 적용됩니다. 캐시 읽기는 100만 토큰당 $0.01 까지 내려가 반복 호출에 특히 유리합니다.

성능도 같은 선에서 비교할 수 없습니다. 발표문의 벤치마크 표를 보면 Terminal-Bench 4.0 에서 Haiku 5.5 가 39.2%, Haiku 4.5 가 0.0% 이고 `OSWorld 2.1` 의 offline subset 에서는 72.4% 와 15.7% 입니다.

Asana 는 작업 완료 지연 시간이 30% 이상 줄고 에이전트 턴당 최대 2.5배 빨라졌다고 보고했고 Box 는 초기 테스트에서 Haiku 4.5 의 절반 수준 지연이라고 전했습니다. 조건을 숨긴 것도 아닙니다. 두 구간은 각주와 요금표에 그대로 적혀 있습니다.

그래도 경계를 설계 변수로 봐야 한다고 생각하는 이유는 에이전트의 작동 방식 때문입니다. 대화가 길어질수록 컨텍스트는 쌓이고 도구 호출 결과와 파일 내용이 프롬프트에 계속 들어갑니다. 분류 작업은 10만 토큰을 평생 넘지 않지만 코딩 에이전트의 긴 세션은 지나갑니다. 그리고 지나가는 순간 입력과 출력이 함께 다섯 배가 됩니다.

## 10만 토큰 아래에서 버티게 만드는 설계

그렇다면 무엇을 확인해야 할까요. 먼저 프롬프트 길이를 `claude-haiku-5-5` 기준으로 다시 세고 평소 요청이 경계에서 얼마나 떨어져 있는지 봅니다. 여유가 20% 안쪽이면 새 토크나이저만으로 넘어갈 수 있습니다.

긴 컨텍스트가 필요한 작업과 짧은 반복 작업을 갈라 두는 것도 방법입니다. 발표문은 Haiku 5.5 를 Opus 5.5·Sonnet 5.5 와 함께 서브에이전트로 쓰는 구성을 소개합니다. 긴 문서를 통째로 들고 있어야 하는 작업은 1M 컨텍스트를 표준 요금으로 주는 모델에 두고 짧고 많이 반복되는 작업만 Haiku 5.5 로 내리면 경계를 건드리지 않습니다.

thinking 토큰도 같이 봐야 합니다. Haiku 5.5 는 adaptive thinking 이 기본으로 켜져 있어 `thinking` 을 설정하지 않은 요청에도 응답이 thinking 블록으로 시작할 수 있고 이 토큰은 `max_tokens` 에 포함됩니다.

migration guide 는 Haiku 4.5 에서 thinking 없이 처리하던 요청이라면 effort 를 낮게 잡으라고 권합니다. Haiku 급에서 effort 를 조절할 수 있는 모델은 이번이 처음입니다. 같은 문서는 Haiku 5.5 가 Priority Tier 를 지원하지 않는다는 것도 함께 적어 뒀으니, Haiku 4.5 로 약정을 걸어 둔 쪽은 용량을 따로 계획해야 합니다.

같은 날 Sonnet 5.5 의 프롬프트 캐시 읽기 단가도 100만 토큰당 $0.20 에서 $0.10 으로 내려갔습니다. 기본 입력가의 0.05배입니다. 캐시가 잘 맞는 에이전트 작업이라면 Haiku 로 내리기 전에 Sonnet 5.5 에서 캐시 적중률을 올리는 쪽이 더 간단할 수 있습니다.

요금이 토큰당 단가 하나로 적히던 때는 모델을 고르고 나면 비용 계산이 끝났습니다. 프롬프트 길이가 요율을 가르기 시작하면 같은 모델 안에서도 설계에 따라 청구액이 여섯 배씩 달라집니다. Haiku 5.5 를 쓸지 정하기 전에 내 프롬프트가 10만 토큰에서 얼마나 떨어져 있는지부터 세어 보는 편이 좋겠습니다.
