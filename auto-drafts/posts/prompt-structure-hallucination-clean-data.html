같은 AI인데 왜 내 답만 쓸모없을까요?

ChatGPT에 "리뷰 정리해 줘"라고 치면 그럴듯하지만 쓸모없는 답이 옵니다. 가게에 없는 메뉴를 칭찬하기도 합니다. 옆 사람은 같은 모델에게서 바로 쓸 수 있는 표를 받습니다. 모델은 화면 뒤에서 답을 만드는 AI 프로그램입니다.

화면 뒤로 들어가 그 차이가 어디서 생기는지 봅니다. AI에게 보내는 글 전체를 프롬프트(prompt)라고 합니다. 치킨집 리뷰 요약 기능을 만들면서 프롬프트와 그 바깥의 데이터까지 고쳐 봅니다.

1장 · 프롬프트

무엇을 원하는지 적습니다

AI는 비어 있는 칸을 가장 흔한 답으로 채웁니다

심부름을 "마실 것 좀 사 와"라고 시키면 무엇이 올지 모릅니다. Claude를 만든 회사 Anthropic의 문서도 모델을 똑똑하지만 우리 사정은 전혀 모르는 새 직원에 빗댑니다.

LLM(Large Language Model)은 앞 글에 이어질 말을 계산하는 프로그램입니다. 누가 읽을지, 어떤 모양이 좋은지 적혀 있지 않으면 학습 때 많이 본 무난한 글로 이어 씁니다. 그래서 "리뷰 정리해 줘"에는 뻔한 답이 옵니다.

요즘 모델은 부탁하지 않은 일을 알아서 더 해 주지도 않습니다. Claude Opus 4.8 안내서는 지시를 글자 그대로 따르니 범위를 직접 적으라고 합니다.

프롬프트 다섯 칸을 채울수록 가능한 답이 줄어듭니다

칸을 하나 채울 때마다 모델이 쓸 수 있는 답의 범위가 좁아집니다. 역할(Persona)은 누구의 눈으로 볼지, 상황(Context)은 어떤 배경인지, 할 일(Task)은 무엇을 할지 정합니다.

여기에 조건(Constraint)과 결과 형식(Output Format)을 더하면 답의 모양까지 정해집니다. 아래 그림에서 칸이 늘수록 진한 점이 줄어듭니다.

점 하나를 모델이 쓸 수 있는 답 하나로 그렸습니다. 점의 개수는 설명을 위한 예시 값이고 실제로 잰 값은 아닙니다.

빠진 칸을 찾는 법

다섯 칸을 언제나 다 채울 필요는 없습니다. 결과를 보고 답이 흔들리는 칸부터 채우면 됩니다.

Anthropic은 맥락을 모르는 동료에게 프롬프트를 보여 주라고 권합니다. 그 사람이 헷갈리면 모델도 헷갈립니다.

"너는 전문가야"를 넣어도 정답률은 오르지 않습니다

프롬프트 팁에 빠지지 않는 첫 줄이 "너는 10년 차 전문가야"입니다. 모델에게 주는 이런 역할을 페르소나(persona)라고 합니다. 페르소나가 사실을 더 잘 맞히게 하지는 못한다는 연구가 쌓였습니다. 162개 역할로 사실 질문 2,410개를 풀게 한 실험(Zheng 외)과 2025년 12월 연구(Basil 외) 모두 전문가 역할의 뚜렷한 효과를 찾지 못했습니다. 그림의 세 모델도 정답률이 오르지 않았고, 떨어지는 폭은 Llama처럼 모델마다 크게 달랐습니다.

모델의 지식은 학습이 끝날 때 이미 정해져 있습니다. "너는 영양사야"라고 해도 없던 지식이 생기지 않습니다. 대신 말투와 관점, 무엇을 강조할지는 바뀝니다. Anthropic 문서도 역할이 행동과 어조를 잡아 준다고만 적습니다.

그래서 역할은 한 줄로 끝내고 힘은 상황과 자료에 씁니다. 정확도가 걱정이면 다음 장의 근거를 넣어야 합니다.

템플릿은 코드에 두고 안 바뀌는 칸을 앞에 둡니다

잘 나온 프롬프트를 메모장에서 복사해 쓰다 보면 조금씩 달라지고 결과도 흔들립니다. 그래서 칸은 고정하고 빈칸만 바꿔 끼우는 서식을 만듭니다. 이 서식이 템플릿(template)입니다.

칸의 순서에 따라 요금도 달라집니다. 프롬프트 캐싱(prompt caching)은 앞부분이 똑같은 요청의 계산 결과를 다시 쓰는 기능입니다. 앞에서부터 글자가 같아야 하므로 안 바뀌는 칸을 앞에, 리뷰처럼 바뀌는 칸을 맨 뒤에 둡니다.

요금은 토큰(token)으로 셉니다. 토큰은 모델이 글을 읽는 단위로, 낱말보다 조금 작은 조각입니다. 캐싱은 1,024토큰 이상인 요청부터 적용됩니다.

OpenAI 기준으로 재사용한 부분은 원래 값의 10%만 받고(gpt-6.1-sol은 5%), 처음 저장할 때는 1.25배를 받습니다. 같은 앞부분을 여러 번 쓸 때 이득입니다.

from openai import OpenAI

client = OpenAI()

# ① 바뀌지 않는 칸: 역할·상황·할 일·조건·형식
INSTRUCTIONS = """\
# 역할
너는 배달 앱 리뷰를 읽는 분석가다.
# 상황
치킨집 사장님이 이번 주 리뷰를 보고 내일 할 일을 정한다.
# 할 일
불만을 많은 순서로 3개 뽑는다.
# 조건
- 리뷰에 없는 내용은 쓰지 않는다.
- 근거가 모자라면 "리뷰에 없음"이라고 쓴다.
# 형식
불만 | 건수 | 대표 리뷰 번호
"""

def summarize(reviews: list[str]) -> str:
    lines = [f"[{i}] {r}" for i, r in enumerate(reviews, 1)]
    numbered = "\n".join(lines)
    response = client.responses.create(
        model="gpt-6.1-sol",
        instructions=INSTRUCTIONS,
        # ② 매번 바뀌는 칸은 맨 뒤에
        input=f"<reviews>\n{numbered}\n</reviews>",
        # ③ 얼마나 오래 생각할지
        reasoning={"effort": "low"},
    )
    return response.output_text

with open("reviews.txt", encoding="utf-8") as f:
    reviews = f.read().splitlines()
print(summarize(reviews))

$ python summarize.py 배달 지연 | 12 | [2] 음식 온도 | 7 | [5] 포장 누락 | 3 | [9]

reviews.txt에 리뷰 120개를 넣었다고 가정한 예시 답입니다. 파이썬 라이브러리 openai 3.46과 Responses API 기준입니다.

  1. client.responses.create는 OpenAI의 API, 곧 프로그램끼리 요청을 주고받는 창구를 부릅니다. instructions에 다섯 칸을 넣으면 이번 요청에 한해 모델이 사용자 글보다 먼저 지킵니다.
  2. 리뷰는 input으로 보내고 <reviews> 같은 표시(태그)로 감쌉니다. 어디까지가 자료인지 알려 주면 리뷰 속 글이 지시로 읽힐 위험이 줄어듭니다.
  3. 추론 모델(reasoning model)은 답하기 전에 스스로 따져 보는 모델이고 effort는 그 정도입니다. OpenAI 문서는 품질이 낮으면 이 값보다 프롬프트를 먼저 고치라고 적습니다.
"단계별로 생각해"는 아직 써야 할까요?

분석 → 아이디어 → 결론처럼 단계를 적어 주는 지시는 옛 모델에서 효과가 컸습니다. OpenAI의 추론 모델 안내(o 시리즈 기준)는 think step by step 같은 지시가 필요 없다고 적습니다. 다만 결과에 그 단계가 보이길 원한다면 형식 칸에 적으면 됩니다.

저장형 프롬프트 기능은 어떻게 됐나요?

대시보드에 프롬프트를 저장하고 ID로 부르는 기능(prompt={"id": ...})은 2026-11-30에 종료됩니다. OpenAI도 프롬프트를 앱 코드로 옮기라고 안내합니다. 코드에 두면 Git으로 바뀐 내역을 볼 수 있습니다.

형식 칸을 코드로 강제하는 방법은 Structured Output 글에, 예시를 넣는 방법은 퓨샷 글에 있습니다.

2장 · 근거

모르면 멈추게 하고 맞는지 확인합니다

AI는 왜 없는 메뉴를 자신 있게 칭찬할까요?

처음 화면의 "마라 치킨"처럼 사실이 아닌 내용을 사실처럼 말하는 것을 할루시네이션(hallucination), 우리말로 환각이라고 합니다. 원인 가운데 하나는 찍기가 유리한 시험과 같습니다. 모르는 사람의 생일을 찍으면 365분의 1로 맞히지만 "모릅니다"는 언제나 0점입니다.

정답 수만 보면 o4-mini가 2개 앞섭니다. 하지만 틀린 답을 낸 횟수는 세 배 가까이 됩니다. OpenAI 연구진은 틀린 답에 감점을 주는 채점표를 쓰면 모델도 모를 때 멈추는 쪽을 배우게 된다고 제안합니다.

맞으면 +1, 틀리면 −9로 매겨 봅니다. 열 번 중 아홉 번 맞히는 사람은 9점을 얻고 한 번 틀려 9점을 잃어 0점입니다. 그보다 자신이 없으면 답할수록 손해이니 "모릅니다"가 낫습니다.

짧은 사실 질문 시험 SimpleQA 결과를 100칸에 칠했습니다. 값: OpenAI, Why language models hallucinate(2025-09).

모델 안에는 거절 쪽으로 깔린 선로가 있습니다

모델에 따라 "모르겠습니다"라고 답할 때도 많습니다. Anthropic이 2025년 3월에 Claude 한 모델의 내부 회로를 들여다봤습니다. 회로는 어떤 계산을 함께 맡는 모델 속 부분들의 연결입니다.

Claude에서는 답을 거절하는 회로가 기본으로 켜져 있었습니다. 잘 아는 대상을 만나면 "아는 이름" 신호가 그 회로를 눌러 답하게 합니다.

Anthropic이 Claude 안에서 찾은 회로를 선로로 쉽게 다시 그렸습니다. 신호가 없으면 선로는 거절 쪽으로 이어집니다. 실제 회로는 훨씬 복잡합니다.

잘못 켜진 신호

할루시네이션은 "이름만 들어 본 사람" 그림에서 생깁니다. 이름은 익숙한데 내용을 모를 때 신호가 잘못 켜지면 거절이 풀립니다. 그다음 모델은 하던 대로 그럴듯한 문장을 이어 씁니다.

Anthropic은 이 신호를 일부러 켜서 가짜 인물 Michael Batkin이 체스 선수라고 답하게 만들기도 했습니다. 이 한 가지로 모든 할루시네이션을 설명할 수는 없습니다.

Anthropic의 원본 회로 그림 보기

"모르면 모른다고 해"는 첫 번째 레이어입니다

먼저 모르겠다고 말해도 된다고 허락합니다. 지시에 이 세 줄을 넣습니다.

  • 모르면 "모르겠습니다"라고 쓴다.
  • 불확실한 내용은 "불확실"이라고 표시한다.
  • 주어진 자료에 없는 내용은 쓰지 않는다.

Anthropic 문서도 이 방법을 맨 앞에 두지만 할루시네이션을 완전히 없애지는 못한다고 적습니다. 그래서 레이어(layer)를 쌓습니다. 안전 분야의 스위스 치즈 모델(Swiss cheese model)처럼 레이어마다 구멍이 있어도 구멍이 겹치지 않으면 막힙니다.

자료는 모델이 그대로 옮길 원문을 줍니다. 인용은 문장마다 근거 위치를 달아 사람이 따라가 보게 합니다. 마지막 레이어에서는 코드와 사람이 숫자·이름을 원문과 대조합니다.

자료를 넣어도 레이어 하나입니다

RAG(Retrieval-Augmented Generation)는 질문과 관련된 문서를 찾아 프롬프트에 넣어 주는 방식입니다. 이것도 레이어 하나일 뿐입니다.

법률 RAG 도구를 조사한 Stanford 연구(Magesh 외)에서 유명 도구들도 질문의 17~33%에서 할루시네이션을 냈습니다. "자료를 붙였으니 믿어도 된다"는 생각은 위험합니다.

"자세히"도 "짧게"도 각자 다른 거짓을 부릅니다

"자세히 써 줘"와 "한 줄로 답해 줘"는 누구나 치는 말입니다. 이 분량 지시에 따라 정확도도 달라집니다.

길게 쓰게 하면 아는 사실이 바닥나 뒤쪽이 지어낸 내용으로 채워집니다. 너무 짧게 시키면 질문에 숨은 틀린 사실(거짓 전제)을 반박할 공간이 없어 그대로 받아 버립니다.

앞 그래프의 세로축은 90%부터 시작해 차이를 크게 보여 줍니다. 값: Zhao 외(2025), Giskard Phare(2025-04). 서로 다른 시험이라 두 값을 직접 비교하면 안 됩니다.

길이보다 범위를 좁힙니다

길이만 지시하기보다 범위를 좁히는 쪽이 낫습니다. "AI 역사 설명해 줘" 대신 "2020년 이후 변화 3가지"라고 묻습니다.

그러면 모델이 아는 범위 안에서 답하기 쉬워지고 채워 넣을 공간이 줄어듭니다. 다만 답할 내용이 없을 때 "모르겠습니다"를 허용하는 규칙은 그대로 둡니다.

말투도 영향을 줄까요?

"100% 확실한데요"처럼 자신 있게 물으면 모델이 틀린 주장을 반박하는 능력이 중립적으로 물을 때보다 최대 15% 떨어졌습니다. 영향이 거의 없는 모델도 있습니다. 질문할 때 답을 미리 정해 두지 않는 편이 안전합니다.

자기 답을 보면서 고치면 같은 실수를 반복합니다

"다 쓴 뒤 스스로 검토해"라는 지시는 절반만 맞습니다. 자기 시험지를 보며 채점하면 틀린 답도 맞아 보입니다. 문제만 보고 다시 풀어야 틀린 곳이 드러납니다.

Chain-of-Verification(CoVe)이 이 방법입니다. 초안에서 확인할 질문을 뽑고 초안을 가린 채 그 질문에 답한 뒤 어긋나는 주장을 지웁니다.

치킨집 리뷰 두 개로 만든 예시입니다. 리뷰에 없는 "마라 치킨"이 2번에서 드러납니다.

2023년 논문에서 답한 것 중 맞은 비율이 초안 그대로일 때 0.17, 초안을 보며 검증하면 0.29, 초안을 가리고 검증하면 0.36이었습니다. 지어낸 항목은 답변 하나에 2.95개에서 0.68개로 줄었습니다. 옛 모델이라 0.36 자체는 낮지만 방향은 분명합니다.

대가도 있습니다. 검증을 거치면 쓰는 사실 수가 함께 줄어듭니다. 인물 소개 시험에서는 16.6개가 12.3개로 줄었습니다.

논문의 원래 흐름 그림 보기 
from openai import OpenAI

client = OpenAI()

def ask(rule: str, text: str) -> str:
    response = client.responses.create(
        model="gpt-6.1-sol",
        instructions=rule,
        input=text,
    )
    return response.output_text

reviews = "[1] 배달이 늦었어요\n[2] 치킨이 식었어요"

draft = ask("리뷰를 한 줄로 요약한다.", reviews)
# ① 초안에서 확인할 질문만 뽑는다
questions = ask("주장을 확인할 질문만 쓴다.", draft)
# ② 초안을 빼고 원문과 질문만 준다
answers = ask(
    "리뷰만 보고 답한다. 없으면 '리뷰에 없음'이라고 쓴다.",
    f"{reviews}\n\n{questions}",
)
# ③ 확인 결과와 어긋나는 주장을 지운다
final = ask(
    "확인 결과와 다른 주장을 지운다.",
    f"{draft}\n\n{answers}",
)

print("초안:", draft)
print("확인:", answers)
print("최종:", final)

3장 · 데이터

모델에 넣는 글을 목적에 맞게 다듬습니다

같은 리뷰도 목적에 따라 남길 글자가 다릅니다

앱에서 "배달"로 검색했는데 리뷰가 안 나오거나 요약이 엉뚱하면 프롬프트만 탓하기 쉽습니다. 원인이 넣은 글에 있을 때가 많습니다. 쓰레기를 넣으면 쓰레기가 나온다(Garbage In, Garbage Out)는 오래된 말 그대로입니다.

글을 다듬는 정제(text cleaning)는 많이 지운다고 좋아지지 않습니다. 이 글로 무엇을 할지가 기준입니다.

같은 리뷰입니다. 빨간 줄은 지운 글자, 초록은 일부러 남긴 글자, "전화번호" 칩은 바꿔 넣은 글자입니다.

지운 뒤에 뜻이 그대로인지 먼저 봅니다. 자주 나오는 낱말을 지우는 불용어(stopword) 제거가 대표적입니다. '안'이나 '못'은 흔하지만 뜻을 뒤집습니다.

정제 원칙은 세 가지면 됩니다. 분야와 목적을 먼저 정하고 뜻은 바꾸지 않습니다. 되돌릴 수 있게 원문은 따로 보관합니다.

"배달"이 안 잡힌 이유는 조사입니다

앞의 검색창에서 1건만 나온 이유가 여기 있습니다. 검색은 글을 낱말로 잘라 목록으로 저장해 둡니다. 한국어는 낱말 뒤에 조사가 붙어서 공백으로 자르면 '배달이'와 '배달'이 다른 낱말이 됩니다.

이때 형태소(morpheme) 분석기를 씁니다. 형태소는 뜻을 가진 가장 작은 말 단위로, '배달이'는 '배달'과 '이'로 나뉩니다. 파이썬에서는 Kiwi를, 검색 서버 Elasticsearch에서는 Nori를 많이 씁니다. 낱말 검색과 뜻으로 찾는 검색을 함께 쓰는 방법은 RAG 글에 있습니다.

kiwipiepy 0.24.1로 직접 돌린 결과입니다.

분석기도 틀립니다

'256기가'를 그냥 넣으면 '256', '기', '가'로 나뉘어 '가'가 조사로 처리됩니다.

업종 낱말은 사전에 직접 넣어야 합니다. 뒤에 나오는 코드에서 한 줄로 처리합니다.

눈에는 같아도 컴퓨터에게는 다른 글자입니다

맥에서 받은 한글 파일 이름이 'ㅊㅣㅋㅣㄴ'처럼 풀려 보인 적이 있다면 이 문제를 이미 본 것입니다. 전 세계 글자에 번호를 매긴 표준인 유니코드는 '치'를 한 글자(NFC)로도, 자음과 모음의 조합(NFD)으로도 저장할 수 있습니다.

이 글을 쓴 맥북의 다운로드 폴더를 세 보니 한글 이름 파일 83개 중 23개가 NFD였습니다. 본문 글에도 NFD가 섞이면 검색이 빗나가고 토큰 수도 불어납니다. 낱자 자모는 드물어서 한 칸이 세 토큰으로 쪼개지기 때문입니다.

그래서 정제 맨 앞에 정규화(normalization)를 둡니다. 표현이 여럿인 글자를 하나로 맞추는 일입니다. 기본은 NFC입니다.

NFKC는 언제 쓸까요?

NFKC는 더 세게 합칩니다. 폭이 넓은 숫자 １을 1로 바꾸는 식이라 상품 검색에는 쓸모가 있습니다. 대신 x²가 x2가 되고 ①이 1이 됩니다. 유니코드 표준(UAX #15)도 아무 글에나 적용하지 말라고 경고합니다.

모델은 글자가 아니라 토큰을 읽습니다

챗봇에 긴 글을 붙여 넣으면 "메시지가 너무 깁니다"라는 오류가 나옵니다. 그 길이를 재는 단위가 앞에서 본 토큰입니다. 글을 토큰으로 자르는 일을 토큰화(tokenization)라고 합니다. 같은 내용이라도 한글은 영어보다 대개 토큰이 많습니다.

모델의 토크나이저(tokenizer)는 모델과 한 벌이라 우리가 바꿀 수 없습니다. 우리는 세어 보기만 합니다. 정확한 수는 client.responses.input_tokens.count()로 받습니다. tiktoken은 일반 글을 어림할 때 씁니다.

사전에 없는 낱말은 어떻게 처리할까요?

사전에 없는 말을 뜻하는 OOV(Out-Of-Vocabulary)는 단어 사전을 쓰던 시절의 큰 골칫거리였습니다. BPE(Byte Pair Encoding)는 자주 붙어 나오는 조각끼리 합쳐 사전을 만드는 방식입니다. 바이트 단위로 시작하면 어떤 글자든 끝까지 쪼개 처리합니다. 바이트는 컴퓨터가 글자를 저장할 때 쓰는 단위입니다.

입력은 "치킨집 뷁맛"입니다. 위 두 줄은 방식을 보여 주려고 만든 예시, 마지막 줄은 o200k_base로 실제 자른 결과입니다.

같은 정제 함수가 분야마다 다른 것을 망가뜨립니다

"특수문자를 지운다"는 정제 코드의 흔한 첫 줄입니다. 리뷰에서는 큰 탈이 없어 보입니다.

분야가 바뀌면 지운 글자가 곧 내용일 수 있습니다. 같은 함수를 다섯 분야의 글에 돌려 봤습니다. 빨간 글자가 결과입니다.

한글·영문·숫자만 남기는 함수 하나를 그대로 돌린 실제 결과입니다. 그래서 분야마다 규칙이 다릅니다. 의료는 기호와 단위를, 법률은 원문 전체를, 코드는 공백과 기호를 남깁니다. SNS는 반복만 줄이고 쇼핑은 256기가와 256GB 같은 표기를 맞춥니다.

글을 자르는 위치도 분야를 따릅니다. 긴 문서를 나눈 토막을 청크(chunk)라고 합니다. 글자 수로만 자르면 함수와 조항이 중간에 끊깁니다. 코드를 문법 구조로 자르는 방법을 실험한 cAST 연구에서 상위 5개 결과 안에 정답 코드가 든 비율(Recall@5)이 4.3포인트 올랐습니다.

법률도 비슷합니다. 독일 민법으로 실험한 2026년 연구에서 조항 단위 자르기가 글자 수 자르기보다 앞섰습니다. 개인정보는 Microsoft Presidio 같은 도구로 찾을 수 있습니다. 다만 Presidio 문서도 전부 찾는다고 보장하지 않으니 사람이 표본을 확인해야 합니다.

cAST 논문의 원래 그림 보기 
import re
import unicodedata
from kiwipiepy import Kiwi

URL = re.compile(r"https?://\S+")
PHONE = re.compile(r"01[016789]-?\d{3,4}-?\d{4}")
REPEAT = re.compile(r"(.)\1{2,}")

kiwi = Kiwi()
# ① 이 가게·이 업종의 낱말을 사전에 넣는다
kiwi.add_user_word("256기가", "NNP")

def clean_review(text: str) -> str:
    # ② 글자 표현부터 하나로 맞춘다
    text = unicodedata.normalize("NFC", text)
    text = PHONE.sub("[전화번호]", text)
    text = URL.sub("", text)
    # ③ 세 번 넘는 반복만 두 번으로 줄인다
    text = REPEAT.sub(r"\1\1", text)
    return " ".join(text.split())

KEEP = ("NN", "VV", "VA", "MAG", "SN", "SL")

def search_tokens(text: str) -> list[str]:
    # ④ 조사·어미를 떼고 검색에 쓸 말만 남긴다
    tokens = kiwi.tokenize(text)
    return [t.form for t in tokens if t.tag.startswith(KEEP)]

raw = ("배달이 안 늦었어요!!!! 😍😍😍 "
       "https://bit.ly/3xYz 문의 010-1234-5678")
print(clean_review(raw))
print(search_tokens(clean_review(raw)))
print(search_tokens("아이폰 256기가 배달"))

직접 돌린 출력입니다. kiwipiepy 0.24.1 기준입니다.

  1. 사전에 넣으면 '256기가'가 한 낱말이 됩니다. 업종이 바뀌면 이 목록을 다시 만듭니다. 위쪽 re.compile은 URL처럼 정해진 글자 패턴을 찾는 도구(정규식)를 만듭니다.
  2. NFC로 맞추는 일은 언제나 맨 앞입니다. 뒤에 나오는 규칙이 모두 이 글자 모양을 기준으로 돌아가기 때문입니다.
  3. 감정 표현은 완전히 지우지 않습니다. '!!!!'를 '!!'로 줄이면 토큰을 아끼면서 강조는 남습니다.
  4. tag는 품사 표시입니다. 낱말의 종류를 나타내는 약자입니다. 여기서는 조사와 어미만 뺐습니다. 부사(MAG)를 남겼기 때문에 '안'이 살아 있습니다.
4장 · Eval

eval 데이터셋을 만들어 나아졌는지 잽니다

프롬프트를 고쳤는데 정말 나아졌는지 어떻게 알까요?

챗봇을 고친 다음 날 어제까지 잘 되던 질문이 틀리는 일은 흔합니다. 질문 몇 개를 눈으로 봐서는 알 수 없습니다.

지시·입력·정답을 묶은 문제를 모은 것이 eval 데이터셋(eval dataset)입니다. 프롬프트 버전마다 이것을 전부 돌려 봅니다. 이렇게 재는 일을 평가(evaluation)라고 합니다. 결과를 모으면 eval 리포트가 나옵니다.

좋은 eval 데이터셋에는 쉬운 문제만 있지 않습니다. 돌려 말한 표현, 경계에 있는 예외, 답이 없어야 하는 질문도 넣습니다. "옆집 마라 치킨"의 정답을 "모르겠습니다"로 두면 앞서 넣은 규칙이 통하는지 잴 수 있습니다.

틀린 칸을 보면 고칠 칸도 보입니다. 답이 뻔하면 상황을, 없는 말을 지어내면 조건을, 모양이 틀리면 형식을 고칩니다. 그리고 다시 전체를 돌립니다. 고치다가 잘 되던 문제를 망가뜨리는 회귀(regression)를 잡으려면 일부만 돌리면 안 됩니다.

문제 하나는 지시와 입력, 정답으로 적습니다

이런 문제 묶음을 Instruction 데이터라고 부릅니다. 데이터는 JSON으로 적습니다. JSON은 이름과 값을 중괄호로 묶어 적는 형식입니다.

이 데이터셋은 모델을 더 학습시키는 파인튜닝(fine-tuning)의 학습 데이터로도 쓰여서 그쪽 형식을 따릅니다. 2023년 Stanford 연구진이 모델 Alpaca를 학습시키며 쓴 세 칸 형식이 널리 퍼졌습니다. 지금 표준은 대화 그대로 적는 messages입니다. system은 지시, user는 사용자 입력, assistant는 모델이 해야 할 답입니다.

모델이 학습할 때는 어떤 글로 보일까요? 
<|system|>
리뷰를 긍정·부정·섞임으로 분류해</s>
<|user|>
맛은 좋은데 늦었어요</s>
<|assistant|>
섞임</s>

칸들이 이런 표시가 붙은 글 한 줄로 이어집니다. 표시는 모델마다 달라서 손으로 쓰지 않고 Hugging Face의 apply_chat_template에 맡깁니다. 공식 문서는 표시가 어긋나면 성능이 크게 떨어진다고 경고합니다. 파인튜닝 자체는 따로 다룬 글에서 볼 수 있습니다.

같은 문제 하나입니다. 초록 글자는 그대로이고 바깥 포장만 바뀝니다.

JSONL은 한 줄이 문제 하나인 파일입니다

학습 데이터를 다운받으면 확장자가 .jsonl인 파일이 많습니다. JSONL(JSON Lines)은 JSON 한 덩어리를 한 줄에 하나씩 쌓은 파일입니다.

규칙은 세 가지입니다. 글자는 가장 널리 쓰는 저장 방식인 UTF-8로 씁니다. 줄마다 그 자체로 완전한 JSON입니다. 줄 끝은 줄바꿈입니다.

줄이 길어지지 않게 text·label 두 칸으로 줄여 그렸습니다. 실제 파일의 한 줄은 앞에서 본 messages 형식입니다.

한 줄씩 읽으니 파일이 커도 메모리를 적게 쓰고 깨진 줄만 버릴 수 있습니다. 대신 형식을 손으로 맞추면 금방 깨집니다.

파일은 언제나 코드로 만듭니다. 아래 코드도 messages 형식으로 저장합니다. 지시는 문제마다 같으니 system 칸을 빼고 eval 코드의 PROMPT에 한 번만 둡니다. 일부러 나쁜 행도 넣었습니다. 잘못된 라벨(label, 정답 표시)과 중복을 걸러 내고 저장한 파일을 다시 읽어 봅니다.

import json
from pathlib import Path

LABELS = {"긍정", "부정", "섞임", "모르겠습니다"}
rows = [
    ("치킨이 바삭하고 배달도 빨랐어요", "긍정", "easy"),
    ("배달이 \"1시간\" 늦었어요\n치킨도 식었고요", "부정", "easy"),
    ("맛은 좋은데 배달이 늦었어요", "섞임", "medium"),
    ("맛은 좋은데 배달이 늦었어요", "섞임", "medium"),
    ("ㅋㅋㅋ", "모르겠습니다", "edge"),
    ("존맛탱", "좋음", "easy"),
]

seen, kept = set(), []
for text, label, level in rows:
    # ① 정답이 약속한 값인지 본다
    if label not in LABELS:
        print("버림(라벨):", repr(text), label)
        continue
    # ② 같은 문제가 두 번 들어가지 않게 한다
    if text in seen:
        print("버림(중복):", repr(text))
        continue
    seen.add(text)
    kept.append({
        "messages": [
            {"role": "user", "content": text},
            {"role": "assistant", "content": label},
        ],
        "metadata": {"difficulty": level},
    })

path = Path("reviews.jsonl")
with path.open("w", encoding="utf-8") as f:
    for item in kept:
        # ③ 한 줄에 하나, 한글은 그대로
        f.write(json.dumps(item, ensure_ascii=False) + "\n")

# ④ 다시 읽어서 깨진 줄이 없는지 확인한다
lines = path.read_text(encoding="utf-8").splitlines()
print(len([json.loads(line) for line in lines]), "줄 저장")
print(lines[1])
터미널 · 누르면 출력이 처음부터 다시 찍힙니다
$ python build_dataset.py 버림(중복): '맛은 좋은데 배달이 늦었어요' 버림(라벨): '존맛탱' 좋음 4 줄 저장 {"messages": [{"role": "user", "content": "배달이 \"1시간\" 늦었어요\n치킨도 식었고요"}, {"role": "assistant", "content": "부정"}], "metadata": {"difficulty": "easy"}}

직접 돌린 출력입니다. 따옴표와 줄바꿈이 한 줄 안에 안전하게 들어갔습니다.

  1. 정답 목록을 미리 정해 두면 '좋음'처럼 약속에 없는 라벨을 바로 찾습니다. 일관성이 깨진 데이터는 모델도 헷갈리게 합니다.
  2. 같은 문제가 학습용과 시험용에 함께 들어가면 점수가 실제보다 좋게 나옵니다.
  3. ensure_ascii=False가 없으면 한글이 치처럼 저장됩니다. 따옴표와 줄바꿈은 dumps가 알아서 처리합니다.
  4. 저장 직후 다시 읽는 두 줄이 가장 값싼 검사입니다. 깨진 줄이 있으면 여기서 오류가 납니다.

eval 코드는 서른 줄이면 됩니다

eval 도구가 따로 없어도 시작할 수 있습니다. 파일을 한 줄씩 읽어 모델에 묻고 정답과 견주면 됩니다. 난이도별로 나눠 세면 어디가 약한지 드러납니다.

글자가 정확히 같은지 보는 평가는 분류처럼 답이 정해진 문제에만 맞습니다. 요약처럼 답이 여럿이면 기준을 정해 사람이나 다른 모델이 평가합니다. Anthropic은 문제의 질보다 양을 먼저 늘리라고 권합니다.

import json
from collections import Counter
from openai import OpenAI

client = OpenAI()

PROMPT = """\
리뷰를 긍정, 부정, 섞임 중 하나로 분류한다.
근거가 없으면 '모르겠습니다'라고 쓴다.
다른 말은 쓰지 않는다."""

score, total = Counter(), Counter()
with open("reviews.jsonl", encoding="utf-8") as f:
    for line in f:
        item = json.loads(line)
        user, assistant = item["messages"]
        review, answer = user["content"], assistant["content"]
        level = item["metadata"]["difficulty"]
        response = client.responses.create(
            model="gpt-6.1-sol",
            instructions=PROMPT,
            input=review,
        )
        total[level] += 1
        # 정답과 글자가 같으면 맞은 것으로 센다
        guess = response.output_text.strip()
        score[level] += guess == answer

for level in total:
    print(f"{level:<8}{score[level]}/{total[level]}")
print("합계", sum(score.values()), "/", sum(total.values()))
터미널 · 누르면 출력이 처음부터 다시 찍힙니다
$ python evaluate.py easy 2/2 medium 0/1 edge 0/1 합계 2 / 4

출력은 예시 답입니다. reviews.jsonl은 앞 코드에서 만든 4줄입니다.

item["messages"]에서 문제와 정답을 꺼냅니다. 프롬프트를 고치면 PROMPT만 바꿔 다시 돌립니다.

문제가 많아지면 Promptfoo 같은 프롬프트 eval 전용 도구로 옮기면 됩니다. OpenAI도 자사 평가 기능의 대안으로 이 도구의 이전 안내서를 냈습니다.

eval 데이터셋과 프롬프트는 내 Git 저장소에 둡니다

쓰던 기능이 공지 한 줄로 사라지는 일이 실제로 벌어지고 있습니다. 내 코드와 함께 Git에 둔 파일은 그럴 걱정이 없고, 쓸 곳도 세 군데입니다. 프롬프트를 평가할 때, 오픈 모델을 학습시킬 때, 한꺼번에 처리하는 Batch API의 입력을 만들 때입니다. Batch는 모아 둔 요청을 한꺼번에 처리하는 기능으로, 비용이 절반입니다.

반대로 서비스 회사의 기능에 맡긴 것은 사라질 수 있습니다. OpenAI만 해도 파인튜닝과 평가 기능(Evals), 대시보드에 저장하는 프롬프트를 차례로 닫고 있습니다. "JSONL을 모으면 OpenAI에서 학습시키면 된다"는 설명은 이제 맞지 않습니다.

OpenAI 지원 중단 안내 기준이고 칸 간격은 실제 기간과 다릅니다. 이미 만든 파인튜닝 모델은 그 바탕이 된 모델이 종료될 때까지 쓸 수 있습니다.
