폐쇄망에 LLM을 들일 때 모델 파일 말고 챙길 것

시험장에서 휴대폰을 걷어 가면 계산기도 사전도 미리 챙겨 들어가야 합니다. 안에서는 아무것도 새로 찾아볼 수 없기 때문입니다. 인터넷이 끊긴 회사 안에서 사내 챗봇을 돌리는 일도 같습니다. 서버가 평소에 밖에서 받아 오던 파일을 전부 미리 들고 들어가야 합니다.

이렇게 회사 밖 파일을 검사한 뒤 안으로 들이는 일을 반입이라고 합니다. 무엇을 반입해야 할까요? 많은 사람이 15GB짜리 LLM(Large Language Model) 모델 파일 하나를 떠올립니다. 아래 그림은 모델 파일만 들고 들어간 상태입니다. 바깥 칸의 짐을 눌러 안으로 옮기면서 질문 하나가 어디까지 가는지 보세요.

크기는 2026-10-15에 Hugging Face·Docker Hub·PyPI에서 확인한 값입니다. 이미지는 linux/amd64 압축 크기, 가중치는 Qwen2.5-7B-Instruct, 임베딩 모델은 BGE-M3, 벡터 DB는 pgvector 0.8.7입니다. 고정폭 글씨로 적은 오류는 직접 재현한 원문이고 나머지는 무슨 일이 생기는지 풀어 쓴 것입니다. 답변 문장은 설명을 위한 예시입니다.

서버가 회사 안에 있는 것과 선이 끊긴 것은 다릅니다

회사 서버실에 직접 서버를 두고 쓰는 방식을 온프레미스(on-premise)라고 합니다. 남의 데이터센터를 빌려 쓰는 클라우드와 반대라는 뜻일 뿐이라 인터넷 선은 이어져 있을 수 있습니다. 그림의 첫 번째 상태입니다.

망분리(network separation)는 회사 네트워크를 업무용과 인터넷용으로 나누는 일입니다. 업무망에는 밖으로 나가는 선이 없어서 폐쇄망(closed network)이라고도 부릅니다. 두 망 사이에서는 망연계 장비로만 파일이 오갑니다. 망연계 장비는 파일을 검사한 뒤 한쪽 망에서 다른 쪽 망으로 넘겨 주는 전용 장비입니다.

에어 갭(air gap)은 선이 아예 없어 파일을 사람이 승인받은 저장 매체에 담아 옮기는 상태입니다. 이 글에서는 뒤의 두 가지를 함께 폐쇄망이라고 부르겠습니다. 다만 폐쇄망은 휴대폰을 걷는 시험장과 달리 몇 년을 돌아갑니다. 그사이 고칠 것이 생기면 또 들고 들어가야 하는데 이 일이 가장 어렵습니다.

한국 금융권은 2024년부터 망분리를 단계적으로 풀고 있습니다

금융위원회는 2024년 8월 13일 「금융분야 망분리 개선 로드맵」을 내며 "금융권 망분리 10년"을 돌아봤습니다. 로드맵의 첫째 항목은 "금융회사 등의 생성형 AI 활용을 허용한다"입니다. 한꺼번에 풀지는 않고 규제 샌드박스(regulatory sandbox)로 시작했습니다. 보안 조건을 붙여 정해진 기간 동안 예외를 허락하는 제도입니다.

넓은 화면에서 점 사이 간격은 실제 날짜 간격입니다. 2026년 4월 SaaS 제도화는 2026년 5월 26일 보도자료의 각주에 적힌 시점입니다. 금융위원회 보도자료 다섯 건을 바탕으로 했습니다(참고 자료). PoC(Proof of Concept)는 정식으로 들이기 전에 실제로 되는지 작게 시험해 보는 일입니다.

2026년 5월 26일 자료는 총자산 10조 원 이상·상시 종업원 1,000명 이상인 49개 금융회사가 신청하면 1년 동안 망분리 규제를 완화하겠다고 했습니다. 그보다 앞선 2024년 12월 12일 발표에는 "금융회사 내부망에 직접 설치하는 오픈소스 AI"를 따로 지원하겠다는 내용도 있었습니다. 밖으로 보내기 어려운 데이터가 있는 한, 모델을 망 안에 들이는 일도 계속 필요합니다.

모델 파일 말고도 여섯 가지가 더 들어가야 합니다

첫 그림의 짐 일곱 개를 한 줄로 이어 붙이면 이 띠가 됩니다. 절반 넘는 자리를 모델 가중치(weight)가 차지합니다. 가중치는 모델이 학습으로 얻은 숫자들이고 Qwen2.5-7B는 2바이트 숫자 76억 개라 15.2GB입니다(파라미터 학습 페이지).

  • GPU 드라이버 — 운영체제가 GPU를 쓰게 해 주는 프로그램입니다. 컨테이너 밖, 서버 자체에 설치합니다.
  • 엔진 이미지 — 컨테이너 이미지(container image)는 프로그램과 라이브러리를 한 묶음으로 얼려 둔 파일입니다. 추론 엔진(inference engine) vLLM 0.31.0 이미지가 9.04GB입니다.
  • 토크나이저(tokenizer) — 글을 모델이 읽는 번호, 곧 토큰으로 바꾸는 사전입니다.
  • 임베딩 모델과 벡터 DB — 사내 문서에서 질문과 비슷한 것을 찾아 붙이는 RAG(Retrieval-Augmented Generation)에 씁니다(벡터 DB 학습 페이지).
  • 앱 패키지 — 챗봇 화면을 만드는 파이썬 코드가 쓰는 라이브러리입니다.

pip install vllm 한 줄이 끌고 오는 183개

파이썬 패키지는 다른 패키지를 가져다 씁니다. 이렇게 기대는 관계를 의존성(dependency)이라고 합니다. 인터넷이 되면 pip가 알아서 줄줄이 받지만 폐쇄망에서는 그 목록 전부를 미리 받아 와야 합니다. 리눅스 서버·파이썬 3.12 기준으로 vLLM 0.31.0을 풀어 보니 wheel 파일 183개, 1.95GB였습니다. wheel은 설치할 수 있게 묶어 둔 파이썬 패키지 파일입니다.

크기로 보면 몇 개가 거의 다 차지합니다. torch·vllm·triton 세 개가 56%이고 183개 중 128개는 1MB도 안 됩니다. 그래도 개수가 문제입니다. 작은 것 하나만 빠져도 설치가 멈춥니다.

받는 컴퓨터와 쓰는 컴퓨터가 다르면 더 꼬입니다. 맥에서 그냥 받으면 맥용 파일이 내려옵니다. 리눅스 서버에서 쓸 파일은 받을 때 운영체제와 파이썬 버전을 직접 지정해야 합니다.

지정을 잘못하면 생기는 일

pip download에 --platform과 --python-version을 주면 다른 컴퓨터용 wheel을 받습니다. 처음에 manylinux 2.28 하나만 지정했더니 blake3 패키지에서 No matching distribution found로 멈췄습니다. manylinux는 여러 리눅스에서 돌아가게 만든 wheel의 꼬리표이고 뒤 숫자는 필요한 시스템 라이브러리(glibc) 버전입니다. blake3는 더 낮은 2.17판으로만 올라와 있어서 그 번호도 함께 지정해야 했습니다.

반입은 받기부터 등록까지 여섯 단계를 거칩니다

반입은 택배를 보안실에서 열어 보고 들이는 것과 비슷합니다. 다만 반입은 상자 겉만 보지 않고 파일 안의 바이트 하나하나까지 맞춰 봅니다. 스크롤을 내리면 정거장이 하나씩 켜집니다.

① 바깥에서 받기

인터넷이 되는 PC에서 필요한 파일을 받습니다. 모델은 hf download로, 이미지는 docker pull 뒤 docker save로 tar 파일 하나로 묶고 파이썬 패키지는 pip download로 wheel을 모읍니다. 이 PC는 회사 업무망에 연결하지 않습니다.

② 목록과 해시 적기

받은 파일마다 이름·크기·SHA-256 해시를 목록에 적습니다. 해시는 파일 내용으로 계산한 지문 같은 값이고 다음 절에서 직접 만져 봅니다. Hugging Face는 큰 파일마다 SHA-256 값을 같이 보여 줘서 받은 파일과 바로 맞춰 볼 수 있습니다.

③ 검사하기

백신으로 악성코드를 검사하고 파일 형식을 봅니다. 모델 파일은 형식이 특히 중요합니다. 옛 PyTorch의 .bin 파일은 파이썬 pickle 형식이라 여는 순간 그 안에 숨긴 코드가 실행될 수 있습니다. safetensors는 숫자 표만 담는 형식이라 열어도 코드가 돌지 않습니다.

④ 심사받고 옮기기

보안 담당자가 목록을 보고 승인하면 안쪽으로 옮깁니다. 승인된 저장 매체에 담아 가거나, 한쪽 방향으로만 보내는 전송 장비를 씁니다. 이 길은 들어오기만 하고 나가지 않게 만듭니다.

⑤ 안에서 다시 대조하기

안쪽에서 같은 목록으로 해시를 다시 계산해 맞춰 봅니다. 리눅스에서는 sha256sum -c 한 줄입니다. 옮기는 중에 깨지거나 바뀐 파일은 여기서 걸립니다.

⑥ 내부 저장소에 등록하기

통과한 파일을 용도별 저장소에 넣습니다. 이미지는 docker load로 풀어 내부 레지스트리(registry)에 올리고 가중치는 모델 저장소에, wheel은 패키지 미러(mirror)에 둡니다. 미러는 바깥 저장소를 본떠 안에 만든 사본입니다. 이제 서버들은 이 저장소에서만 받습니다.

NVIDIA의 추론 서버 NIM 문서도 같은 흐름을 두 단계로 적어 둡니다. 인터넷이 되는 쪽에서 받아 준비하고 격리된 쪽에서는 밖으로 나가는 연결 없이 실행합니다. 옮기는 길로는 압축 파일 복사, scp·rsync, 물리 매체를 듭니다.

안쪽 단계에서는 NGC_API_KEY·HF_TOKEN 같은 키를 넣지 말라고 따로 경고합니다. NGC는 NVIDIA가 컨테이너와 모델을 나눠 주는 카탈로그이고 이 키는 거기서 받을 때 씁니다. 안쪽에서는 모델 파일을 로컬 저장소에서만 읽어야 합니다. 키가 들어 있으면 프로그램이 밖에 물어보려다 멈출 수 있습니다.

해시는 파일 전체에서 뽑아낸 64글자 지문입니다

해시(hash) 함수는 아무리 큰 파일을 넣어도 정해진 길이의 값을 돌려주는 계산입니다. SHA-256은 256비트, 16진수로 64글자를 냅니다. 같은 파일이면 언제 어디서 계산해도 같은 값이 나옵니다. 그래서 바깥에서 적은 값과 안에서 다시 계산한 값이 같으면 파일이 그대로라는 뜻입니다.

아래 글은 Qwen2.5-7B-Instruct의 실제 config.json 663바이트입니다. 처음 상태의 해시는 터미널에서 shasum -a 256으로 계산한 값과 같습니다. 층 수 "num_hidden_layers": 28 줄을 고치거나 버튼으로 28을 29로 바꿔 보세요. 다른 글자를 고쳐도 됩니다.

'8'과 '9'는 컴퓨터 안에서 2진수 마지막 한 자리만 다릅니다(00111000 → 00111001). 663바이트 가운데 1비트를 바꿨는데 64칸 중 61칸이 바뀝니다. 비슷한 파일이라고 비슷한 해시가 나오지 않으니 아주 조금만 바뀌어도 바로 드러납니다.

사람의 지문과 비슷합니다. 지문이 같으면 같은 사람입니다. 다만 지문은 그 사람이 착한지 알려 주지 않습니다. 해시도 받은 파일이 목록에 적힌 파일과 같다는 것만 알려 줄 뿐, 그 파일이 안전한지는 말해 주지 않습니다.

pip는 이 대조를 설치할 때 해 줍니다. requirements.txt에 패키지마다 --hash=sha256:…을 적고 --require-hashes로 설치하면 목록과 다른 파일은 설치하지 않습니다. six 패키지 wheel(11,050바이트)의 1비트를 일부러 뒤집어 설치해 본 결과가 터미널 칸입니다.

터미널 — 사내 wheel 폴더에서 설치
$ pip install --no-index --find-links wheelhouse --require-hashes -r req.txt

해시 목록을 누가 만들었는지는 서명으로 확인합니다

해시는 목록과 파일이 같은지만 봅니다. 누군가 파일과 목록을 함께 바꿔치기하면 대조는 그대로 통과합니다. 그래서 목록에 만든 쪽의 서명(signature)을 붙입니다. 서명은 만든 쪽만 가진 비밀 열쇠로 찍고 누구나 공개된 열쇠로 확인할 수 있는 도장입니다.

모델 파일에도 이 방식이 들어오고 있습니다. OpenSSF는 2025년 4월 4일 Sigstore를 이용한 모델 서명 도구 model-signing 1.0을 냈습니다. NVIDIA는 NGC 카탈로그에 올리는 모델을 모두 이 OpenSSF Model Signing 방식으로 서명한다고 문서에 적었습니다. 서명 확인은 받은 파일의 해시를 원래 값과 맞춰 보는 체크섬(checksum) 검사와 별개로 더하는 단계라고 설명합니다.

폐쇄망에서는 확인에 쓰는 인증서도 짐입니다. NVIDIA 예시는 서명을 확인할 때 인증서 파일을 --certificate_chain cert.pem으로 넘깁니다. 이 파일도 반입 목록에 들어가야 합니다.

형식도 함께 봅니다. 많이 쓰는 다국어 임베딩 모델 BGE-M3의 저장소에는 PyTorch 가중치가 pytorch_model.bin(pickle) 하나로 올라와 있습니다(2026-10-15 확인). 이런 파일은 반입 전에 safetensors로 바꾸거나 형식 심사를 따로 받는 편이 안전합니다.

들어온 뒤에는 모든 화살표가 회사 안에서 끝납니다

반입한 파일을 저장소에 넣고 나면 구조는 인터넷이 되는 회사의 사내 AI와 거의 같습니다. 다만 밖으로 나가는 화살표가 하나도 없습니다. 버튼을 누르면 질문 하나가 지나는 길이 켜집니다.

GPU 서버 여러 대를 Kubernetes로 묶고 팀마다 API 키로 나눠 쓰는 방법은 엔터프라이즈 서빙 학습 페이지에 정리했습니다. NVIDIA 문서는 Kubernetes에 올린 경우 밖으로 나가는 통신을 기본으로 막는 NetworkPolicy를 걸 수 있다고 적어 둡니다. 선이 없더라도 한 겹 더 막아 둡니다.

코드로는 세 군데만 바뀝니다. 이미지를 어디서 받는지, 모델을 어디서 읽는지, 패키지를 어디서 설치하는지입니다.

  1. 들고 온 이미지를 사내 레지스트리에 올립니다. tar 파일을 이미지로 풀고 사내 주소로 이름표를 바꿔 올립니다. 다른 서버들은 이제 이 주소에서 받습니다.
  2. 밖에 묻지 않고 서버 안 경로에서 모델을 읽습니다. HF_HUB_OFFLINE=1이면 Hugging Face 라이브러리가 인터넷에 한 번도 묻지 않고 받아 둔 파일만 봅니다. --model에는 이름 대신 경로를 주고 키는 넣지 않습니다.
  3. 파이썬 패키지는 사내 wheel 폴더에서만 설치합니다. --no-index는 PyPI를 보지 말라는 뜻이고 --require-hashes를 붙이면 목록과 해시가 다른 파일은 설치하지 않습니다.

경로 대신 Qwen/Qwen2.5-7B-Instruct 같은 이름을 주면 라이브러리는 받아 둔 사본을 찾다가 터미널 칸의 오류로 멈춥니다. 오프라인 설정은 밖으로 나가는 시도를 막을 뿐이고 빠진 파일을 채워 주지는 않습니다.

# ① 들고 온 이미지를 사내 레지스트리로
docker load -i vllm-openai-v0.31.0.tar
docker tag vllm/vllm-openai:v0.31.0 \
  registry.corp.local/vllm-openai:v0.31.0
docker push registry.corp.local/vllm-openai:v0.31.0

# ② 밖에 묻지 않고 로컬 경로의 모델 띄우기
docker run --gpus all --ipc=host -p 8000:8000 \
  -v /models:/models \
  -e HF_HUB_OFFLINE=1 \
  registry.corp.local/vllm-openai:v0.31.0 \
  --model /models/Qwen2.5-7B-Instruct

# ③ 챗봇 앱 패키지는 사내 wheel 폴더에서만
pip install \
  --no-index --find-links /mirror/wheels \
  --require-hashes -r requirements.txt

선을 끊어도 정보가 빠져나가는 길은 남습니다

에어 갭은 네트워크로 나가는 길만 막습니다. 사람·종이·기록과 모델이 읽는 문서는 여전히 길이 됩니다. 금고 문을 잠가도 직원이 내용을 외워서 나가는 것까지는 막지 못하는 것과 비슷합니다. 버튼으로 하나씩 켜 보세요.

넷째 길은 RAG에서 생깁니다. 프롬프트 인젝션(prompt injection)은 모델이 읽는 글에 지시를 숨겨 모델이 그 지시를 따르게 만드는 공격입니다. OWASP LLM Top 10(2025)은 RAG가 쓰는 문서 저장소의 문서를 공격자가 고쳐 두면 그 문서를 검색한 답이 오염된다는 시나리오를 듭니다. 문서를 올린 사람이 회사 안에 있으면 선을 끊어도 막지 못합니다.

기본 대책은 권한입니다. 문서마다 볼 수 있는 부서를 표시해 두고 검색할 때 질문한 사람의 권한으로 먼저 거릅니다. 영업팀 직원의 질문에는 인사팀 문서가 아예 후보로 올라오지 않게 합니다. 질문과 답이 쌓이는 로그도 누가 볼 수 있는지, 얼마나 보관할지 정해 둡니다.

처음 설치보다 갱신이 더 어렵습니다

밖에서는 새 버전이 나오면 docker pull 한 줄이면 됩니다. 폐쇄망에서는 받기부터 등록까지 반입 절차를 처음부터 다시 밟습니다. 그래서 몇 주나 몇 달에 한 번씩 모아서 들입니다. 그사이에도 취약점은 계속 발견됩니다.

취약점(vulnerability)은 프로그램에서 공격에 쓰일 수 있는 결함이고 보안 권고(security advisory)는 그 결함과 고친 버전을 알리는 공지입니다. vLLM GitHub 저장소에는 2025년 10월부터 2026년 9월까지 1년 동안 정식 버전이 32번 나왔고 보안 권고가 66건 올라왔습니다. 보안 권고마다 심각도를 critical·high·medium·low 네 등급 중 하나로 매기고 critical이 가장 위험합니다. 66건 중 critical이 2건, high가 13건입니다.

아래 띠의 점 하나가 보안 권고 하나입니다. 주황 세로선이 반입하는 날이고 점에서 뻗은 막대가 고친 버전이 들어오기까지 기다린 날입니다. 막대 색은 점과 같은 등급 색입니다. 반입 주기를 바꿔 보세요.

석 달마다 들이면 권고 하나가 공개되고 고친 버전이 들어오기까지 평균 41일, 길게는 90일을 기다립니다. 매주로 줄이면 평균 3일이지만 반입 절차를 1년에 53번 밟아야 합니다. 대기 시간과 반입 횟수를 맞바꾸는 일이라 정답이 하나로 정해지지 않습니다.

이 계산의 가정

권고가 나온 날 고친 버전도 나왔다고 치고 반입 심사에 걸리는 날은 뺐습니다. 66건이 모두 우리 서버에 해당하지도 않습니다. 이미지·음성 입력처럼 특정 기능을 켰을 때만 생기는 결함이 많습니다.

어떤 권고가 우리 일인지 가리려면 안에 무엇이 어떤 버전으로 들어와 있는지 적은 목록, 곧 SBOM(Software Bill of Materials)이 있어야 합니다. 반입 때 적은 해시 목록이 그 출발점입니다. 모델도 새로 나오면 15GB를 다시 받아 같은 절차를 밟습니다.

폐쇄망 AI는 한 번 들이고 끝나지 않습니다. 들인 것을 목록으로 관리하고 몇 번이고 다시 들일 수 있어야 오래 씁니다.
