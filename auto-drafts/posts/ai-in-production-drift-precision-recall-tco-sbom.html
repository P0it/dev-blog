서버는 멀쩡한데 AI 모델 정확도가 떨어지는 이유

문자 앱에 스팸 필터를 배포했다고 해 보겠습니다. 배포 직전 시험에서 정확도는 96.1%였습니다. 그 뒤 1년 동안 코드는 한 줄도 바뀌지 않았고 서버는 오류를 한 번도 내지 않았습니다. 그런데 사용자 신고를 모아 다시 채점해 보니 열한 달째 정확도는 75.0%였습니다.

어디가 고장 난 걸까요? 고장 난 곳은 없습니다. 필터는 배포 전에 본 문자를 기준으로 판단하는데 그사이 스팸을 보내는 쪽이 짧은 문자에 링크 하나를 붙이는 수법으로 바꿨습니다. 아래 띠를 끌어 보면 서버 오류 줄은 바닥에 붙어 있고 문자 모양과 정확도만 움직입니다.

설명을 위한 예시 데이터로 직접 계산한 값입니다. 달마다 문자 3,000개를 만들었고 필터는 배포 때 문자로 학습한 간단한 모델(문자 길이와 링크 유무 두 가지로 점수를 매김)입니다. PSI 는 들어오는 문자 모양이 배포 때와 얼마나 다른지 재는 숫자이고 아래에서 직접 계산해 봅니다. 스팸이었는지는 사용자 신고가 모여야 알 수 있어서 정확도는 지난달까지만 그립니다.

모델 코드는 전체 시스템의 작은 상자입니다

2015년 Google 엔지니어들이 NeurIPS 학회에 낸 논문 「Hidden Technical Debt in Machine Learning Systems」에는 상자 그림이 한 장 있습니다. 모델을 학습하고 예측하는 코드는 가운데 작은 상자 하나뿐이고 나머지는 그 둘레에서 모델을 돌리는 장치라는 그림입니다.

그림 속 둘레 상자는 설정(Configuration), 데이터 수집(Data collection), 자원 관리(Resource management), 서빙 인프라(Serving infrastructure), 모니터링(Monitoring) 같은 장치입니다.

식당에 빗대면 모델 코드는 레시피입니다. 재료를 사서 검수하고 주방을 돌리고 손님 반응을 살피는 일이 식당 운영의 대부분입니다. 다만 레시피는 그대로 두면 맛도 그대로지만 모델은 코드가 그대로여도 들어오는 재료가 바뀌면 답이 달라집니다.

이 바깥 상자들을 자동으로 반복해 돌리는 일을 MLOps(Machine Learning Operations)라고 부릅니다. 논문은 바깥 세상이 거의 가만히 있지 않는다는 점을 운영 비용이 계속 드는 원인으로 꼽습니다. 그 변화는 크게 두 가지 모양으로 옵니다.

입력이 바뀌는 Data Drift, 정답 규칙이 바뀌는 Concept Drift

들어오는 입력의 모양이 학습 때와 달라지는 것을 Data Drift, 같은 입력인데 정답이 달라지는 것을 Concept Drift라고 부릅니다. drift는 배가 물살에 밀려 조금씩 떠내려가는 모습을 가리키는 말입니다. 둘은 감시하는 방법이 다릅니다.

점 하나가 문자 하나입니다. 가로 위치는 글자 수, 색은 진짜 정답(주황 스팸, 남색 정상)입니다. 필터는 90자를 넘으면 스팸으로 막는 단순한 규칙이라고 하겠습니다. 빨간 고리는 필터가 틀린 문자입니다.

Data Drift를 누르면 단체 공지처럼 긴 정상 문자가 늘어납니다. 회색 점선(배포 때 모양)과 청록 윤곽(지금 모양)이 어긋나서 입력만 지켜봐도 알아챕니다.

Concept Drift를 누르면 점은 그대로 있고 짧은 문자 몇 개의 색만 바뀝니다. 링크 붙은 짧은 사기 문자가 늘어 짧은 문자도 스팸이 된 경우입니다. 입력 모양은 그대로라 입력 감시에는 아무것도 걸리지 않습니다.

비유와 다른 점도 있습니다. 시험은 범위가 바뀌면 미리 알려 주지만 세상은 알리지 않고 바뀝니다. 그리고 실제로는 두 가지가 함께 옵니다. 맨 위 필터가 그랬습니다. 사기 문자가 늘자 짧은 문자의 비율이 늘었고(Data Drift) 짧은 문자가 스팸일 가능성도 올라갔습니다(Concept Drift).

정답이 늦게 오는 동안 지켜보는 것

Concept Drift는 정답이 모여야 보입니다. 스팸이었는지는 사용자가 신고해야 알고, 대출 심사 모델이라면 돈을 갚았는지 몇 달 뒤에야 압니다. 그래서 정답을 기다리는 동안에는 입력 분포와 모델이 낸 예측의 분포를 대신 지켜봅니다. 예측 분포가 달라지는 것은 prediction drift라고 따로 부릅니다.

기준 분포와 칸마다 견주는 PSI, 가장 크게 벌어진 곳을 재는 KS

입력이 달라졌는지 재려면 견줄 기준이 있어야 합니다. 보통 학습에 쓴 데이터나 배포 직후 한 달을 기준 분포(reference distribution)로 정해 두고 지금 들어오는 데이터와 비교합니다. 분포(distribution)는 값이 어느 범위에 몇 개씩 몰려 있는지를 뜻합니다.

PSI(Population Stability Index)는 글자 수를 20자 간격 열 칸으로 나누고 칸마다 기준 비율과 지금 비율이 얼마나 다른지 재서 모두 더합니다. 칸 하나의 몫은 두 비율의 차이에 '몇 배로 달라졌나'를 로그로 줄인 값을 곱해 구합니다. 그래서 드물던 칸이 갑자기 늘면 PSI가 크게 오릅니다. 주황 막대가 칸마다 보탠 몫입니다.

문턱은 관행입니다. 금융권에서 오래 써 온 신호등 기준은 0.1 아래 초록, 0.25 위 빨강입니다. Yurdakul과 Naranjo(2020)는 이 두 숫자에 학술 근거가 없고 표본 수와 칸 수를 따져야 한다고 지적했습니다. 오픈소스 감시 도구 Evidently는 PSI를 쓸 때 기본 문턱을 0.1로 둡니다.

KS(Kolmogorov–Smirnov) 검정은 칸을 나누지 않습니다. 짧은 문자부터 차례로 세어 올린 누적 비율 곡선 두 개를 겹쳐 놓고 세로로 가장 크게 벌어진 거리 하나를 봅니다. 계단 그림의 빨간 선이 그 거리입니다.

9개월째 KS 값 0.182는 43자 이하 문자의 비율 차이입니다. 기준 19.6%에서 지금 37.8%로 18.2%p 벌어졌습니다.

PSI 계산식과 KS 가 예민해지는 경우

PSI = Σ (지금 비율 − 기준 비율) × ln(지금 비율 ÷ 기준 비율). ln 은 자연로그이고 비율이 0인 칸은 나눌 수 없어서 0.0001 로 바꿔 계산했습니다. 두 비율 차이와 로그 값의 부호가 늘 같아서 칸마다 보태는 몫은 0 이상입니다.

KS 는 표본이 많을수록 작은 차이도 "달라졌다"고 판정합니다. 3,000개씩 견주면 간격이 약 0.035 만 넘어도 유의수준 5%에서 달라졌다고 봅니다. 이 예시에서는 3개월째(0.036)에 벌써 넘습니다. Evidently 는 숫자 열의 행이 1,000개 이하이면 KS 를, 그보다 많으면 Wasserstein 거리(문턱 0.1)를 기본으로 씁니다.

실제 감시 도구는 열마다 이 판정을 냅니다

실제 데이터에는 열(column)이 여럿입니다. Evidently 리포트는 열마다 기준 분포와 지금 분포를 작은 막대그래프로 나란히 놓고 검정 방법, 점수, 판정을 적습니다. 기본 설정에서는 절반 이상의 열이 달라졌을 때 데이터 전체가 달라졌다고 봅니다.

이 판정이 곧 모델이 틀렸다는 뜻은 아닙니다. 모델이 거의 보지 않는 열이 바뀌었을 수도 있습니다. 그래서 drift 알림은 "정답을 모아 확인해 보라"는 신호로 쓰고 확인이 끝나면 다시 학습할지 정합니다.

정확도 하나로는 틀린 종류가 보이지 않습니다

정확도(accuracy)는 전체 중 맞힌 비율입니다. 배포 첫 달 문자 3,000개 가운데 스팸은 626개였습니다. 그런데 모든 문자를 정상이라고 하는 '필터'도 정확도가 79.1%나 나옵니다. 스팸을 하나도 막지 않았는데도 그렇습니다.

그래서 결과를 네 칸으로 나눠 셉니다. 진짜 스팸을 막은 TP(True Positive), 정상 문자를 막은 오탐 FP(False Positive), 스팸을 놓친 미탐 FN(False Negative), 정상 문자를 통과시킨 TN(True Negative)입니다. 이 2×2 표를 confusion matrix라고 부릅니다.

화재경보기에 빗대면 오탐은 토스트를 굽다 울린 경보이고 미탐은 불이 났는데 울리지 않은 경보입니다. 다만 경보기는 어느 실수가 더 큰일인지 정해져 있지만 모델은 쓰는 곳마다 다릅니다. 그 선택을 다음 그림에서 직접 해 봅니다.

문턱값을 옮기면 precision과 recall이 맞바뀝니다

필터는 문자마다 0~100 사이 스팸 점수를 매기고 점수가 문턱값(threshold) 이상이면 막습니다. 스팸과 정상 문자의 점수가 겹치는 구간이 있어서 어디에 선을 그어도 실수가 남습니다. 어느 실수를 줄일지는 선의 위치로 고릅니다.

위쪽 주황 막대는 진짜 스팸들이 받은 점수, 아래쪽 남색 막대는 정상 문자들이 받은 점수입니다. 문턱선 오른쪽에 있는 문자가 막힙니다.

precision은 스팸이라고 막은 것 중 진짜 스팸의 비율(TP ÷ (TP + FP))이고 recall은 진짜 스팸 중 막아 낸 비율(TP ÷ (TP + FN))입니다.

문턱선을 왼쪽으로 끌면 더 많이 막아서 recall이 오르고 함께 막히는 정상 문자도 늘어 precision이 내려갑니다. 오른쪽으로 끌면 반대가 됩니다.

어느 쪽을 지킬지는 쓰임새가 정합니다. 스팸 필터는 중요한 문자를 막아 버리는 오탐이 더 아파서 precision을 높게 잡습니다. 암 검진처럼 놓치면 안 되는 일은 recall을 지키고 늘어난 오탐은 정밀 검사로 다시 거릅니다.

문턱값도 시간이 지나면 낡습니다

문턱값도 시간이 지나면 낡습니다. Sculley 외(2015)는 스팸 표시처럼 문턱으로 판정하는 시스템에서 사람이 손으로 정한 문턱이 모델이나 세상이 바뀌면 맞지 않게 된다고 적었습니다. 해법으로는 따로 떼어 둔 검증 데이터로 문턱을 다시 정하는 방법을 듭니다. scikit-learn의 precision_recall_curve가 이 곡선을 계산해 주는 함수입니다.

LLM 서비스는 평가 세트를 버전마다 다시 돌립니다

API로 LLM(Large Language Model)을 쓰는 서비스는 모델을 직접 학습하지 않으니 drift와 상관없어 보입니다. 실제로는 사용자의 질문이 계속 바뀌고 모델도 업체가 새 버전으로 바꾸거나 은퇴시킵니다. 게다가 답이 문장이라 스팸처럼 맞고 틀림이 한 칸으로 갈리지 않습니다.

그래서 평가 세트(evaluation set)를 만들어 둡니다. 실제 질문에서 고른 수십~수백 개 문항에 기대하는 답과 채점 기준을 붙인 묶음입니다. 모델이나 프롬프트를 바꿀 때마다 같은 세트를 다시 돌려 문항마다 통과했는지 봅니다. 채점은 사람이 하거나 다른 LLM에게 채점 기준을 주고 맡깁니다(LLM-as-judge).

총점만 보면 34점에서 35점으로 올랐는데 그사이 통과하던 문항 다섯 개가 깨졌습니다. 이 예시에서는 새 모델이 JSON 답 앞에 설명 문장을 붙이는 바람에 형식 문항이 실패했고 프롬프트에 출력 형식을 분명히 적자 다시 통과했습니다. 문항별로 보지 않으면 이런 변화를 놓칩니다.

평가 세트 말고 날마다 보는 신호

운영 중에는 평가 세트 말고도 사용자의 👍·👎 비율, 답을 다시 요청한 비율, 토큰 수와 응답 시간을 날마다 기록합니다. 정답표가 없는 대신 여러 신호를 겹쳐서 봅니다.

같은 이름의 모델도 바뀌고 오래된 모델은 은퇴합니다

Chen, Zaharia, Zou(2023)는 GPT-4의 2023년 3월판과 6월판에 같은 질문을 넣어 봤습니다. 어떤 수가 소수인지 맞히는 문제에서 정확도가 84%에서 51%로 떨어졌습니다. 서비스 이름은 같은 GPT-4였지만 석 달 사이에 행동이 달라진 것입니다.

업체는 오래된 모델을 은퇴시키기도 합니다. Anthropic 문서는 공개 모델의 은퇴를 최소 60일 전에 알리고 은퇴한 모델로 보낸 요청은 실패한다고 적어 둡니다. Claude Sonnet 4.5는 2026년 9월 30일에 은퇴 예고가 나왔고 11월 30일에 은퇴합니다. 그 전에 새 모델로 평가 세트를 돌려 봐야 합니다.

운영 비용은 배포한 다음 달부터 쌓입니다

TCO(Total Cost of Ownership)는 무언가를 들여서 쓰고 치울 때까지 드는 돈을 모두 더한 값입니다. 자전거를 살 때 값만 보지 않고 바퀴 바람·체인 교체·수리비까지 더해 보는 것과 비슷합니다. 다만 자전거는 타야 닳지만 모델은 세상이 바뀌면 그대로 둬도 낡습니다.

예시 서비스는 하루 질문 1만 건을 받습니다. Claude Sonnet 4.5 단가로 계산하면 한 달 토큰 비용은 3,600달러입니다. 막대를 '전부'로 바꾸면 청구서에 안 찍히는 사람·감시·평가 비용이 그 위에 쌓입니다.

8개월째 더 싼 Claude Sonnet 5.5로 바꿨는데도 토큰 비용은 13%만 줄었습니다. Claude 4.7 이후 모델은 새 토크나이저 때문에 같은 글에 토큰을 약 30% 더 쓰기 때문입니다.

토큰 비용 계산

질문당 입력 2,000·출력 400 토큰, 한 달 30일로 잡았습니다. Claude Sonnet 4.5는 100만 토큰당 입력 3달러, 출력 15달러라 입력 1,800달러와 출력 1,800달러를 더해 한 달 3,600달러입니다.

Claude Sonnet 5.5는 입력 2달러, 출력 10달러입니다. 가격 문서대로 토큰 수를 1.3배로 늘려 계산하면 입력 1,560달러와 출력 1,560달러로 한 달 3,120달러입니다.

모델을 직접 띄우면 토큰 대신 GPU를 켜 둔 시간이 비용이 됩니다. 요청이 없어도 켜 둔 만큼 나갑니다. 그래서 양자화로 GPU 수를 줄이고 여러 팀이 GPU를 나눠 쓰게 합니다. AWS는 머신러닝 인프라 지출의 최대 90%가 추론에서 나온다고 적어 둡니다.

SBOM은 서버 안에 든 부품 목록입니다

챗봇 서버 하나에는 내가 쓴 코드보다 남이 만든 코드가 훨씬 많이 들어 있습니다. vLLM, PyTorch, transformers 같은 패키지와 그 패키지가 다시 불러 쓰는 패키지들입니다. 남이 만든 부품이 내 서비스로 들어오는 이 길을 소프트웨어 공급망(supply chain)이라고 부릅니다.

SBOM(Software Bill of Materials)은 그 부품의 목록입니다. 과자 봉지 뒷면 원재료 표처럼 무엇이 어떤 버전으로 들어 있는지 적습니다. 원재료 표와 다른 점은 사람이 읽기보다 프로그램이 검색하려고 만든다는 것입니다. 미국 NTIA가 2021년에 정한 최소 항목은 공급자, 부품 이름, 버전, 고유 식별자, 의존 관계, 목록 작성자, 작성 시각 일곱 가지입니다.

쓸모는 보안 공지가 떴을 때 드러납니다. 공개된 취약점에 붙는 CVE(Common Vulnerabilities and Exposures) 번호는 폐쇄망 반입 글에서 다뤘습니다. 공지를 눌러 보면 목록에서 그 부품이 켜집니다.

SBOM은 손으로 쓰지 않고 도구로 만듭니다. 파이썬 패키지 목록이면 cyclonedx-py requirements requirements.txt 한 줄로 CycloneDX 형식 JSON이 나오고 컨테이너 이미지는 Syft·Trivy 같은 도구가 훑어서 만듭니다. 그 목록을 pip-audit나 Trivy가 공개 취약점 데이터베이스와 대조합니다.

  1. 형식 이름과 판입니다. 이 도구는 1.6판으로 썼고 최신판은 2025-10-21에 나온 1.7입니다.
  2. requirements.txt 한 줄이 부품 하나가 됩니다. purl(package URL)은 "어느 저장소의 어떤 패키지 몇 버전"을 한 줄로 적은 식별자라 취약점 데이터베이스를 찾는 열쇠로 씁니다.
  3. 모델도 부품으로 적습니다. CycloneDX는 1.5판(2023년 6월)부터 machine-learning-model 형식을 두고 이를 ML-BOM이라 부릅니다. 해시는 가중치 첫 파일의 SHA-256으로, 폐쇄망 반입 때 적는 해시 목록과 같은 값입니다.
두 형식의 표준 번호

CycloneDX는 Ecma 국제 표준 ECMA-424이고 또 하나의 표준 형식 SPDX는 ISO/IEC 5962:2021입니다.

{
  // ① 어떤 형식으로 적었나
  "bomFormat": "CycloneDX",
  "specVersion": "1.6",
  "components": [
    {
      "type": "library",
      // ② 패키지 하나 = 부품 하나
      "name": "jinja2",
      "version": "3.1.5",
      "purl": "pkg:pypi/jinja2@3.1.5"
    },
    // … fastapi, requests, torch,
    //   transformers, urllib3,
    //   vllm, pyyaml
    {
      // ③ 모델 파일도 부품으로
      "type": "machine-learning-model",
      "name": "Qwen2.5-7B-Instruct",
      "hashes": [{
        "alg": "SHA-256",

      }]
    }

SAST는 코드를 실행하기 전에 읽어서 위험한 줄을 찾습니다

SBOM이 남이 만든 부품을 본다면 SAST(Static Application Security Testing)는 우리가 쓴 코드를 봅니다. 프로그램을 실행하지 않고 소스 코드만 읽어 위험한 모양의 줄을 찾습니다. 글을 내기 전에 맞춤법 검사기가 틀린 곳에 밑줄을 긋는 것과 비슷합니다.

LLM 서비스에서는 특히 두 가지를 봅니다. 하나는 파일을 여는 순간 그 안의 코드가 실행될 수 있는 pickle 계열 불러오기입니다. pickle은 파이썬 객체를 파일로 저장했다가 그대로 되살리는 형식입니다.

다른 하나는 모델이 만든 글을 그대로 실행하는 코드입니다. 모델의 답은 프롬프트 인젝션(prompt injection)으로 조작될 수 있어서 남이 보낸 입력과 똑같이 다뤄야 합니다.

  1. API 키를 코드에 적어 두면 저장소를 볼 수 있는 사람 모두가 키를 갖게 됩니다. 그런데 Bandit은 이 줄을 잡지 못했습니다. 비밀번호를 코드에 직접 적은 것(하드코딩)을 찾는 규칙(B105)은 password·token·secret 같은 이름의 변수만 보는데 API_KEY는 거기에 들지 않습니다.
  2. torch.load와 pickle.load는 믿을 수 없는 파일을 풀다가 코드가 실행될 수 있다는 경고(CWE-502)를 받습니다. CWE는 결함 종류 번호이고 502번은 '믿을 수 없는 데이터 되살리기'입니다. 가중치는 숫자 배열만 담고 코드는 못 담는 safetensors 형식으로 받으면 이 걱정이 줄어듭니다.
  3. eval은 글자로 된 식을 파이썬 코드로 실행하는 함수이고 shell=True는 명령 문자열을 셸(명령어를 받아 실행하는 프로그램)에 통째로 넘기는 옵션입니다. 모델 답에 명령이 섞여 들어오면 서버에서 그대로 실행됩니다. 계산이 필요하면 정해진 함수만 부르게 바꿉니다.
import pickle
import subprocess

import torch

# ① 키를 코드에 적어 둠
API_KEY = "sk-live-1234abcd"


def load_model(path):
    # ② 열기만 해도 코드가 돌 수 있음
    return torch.load(path)


def load_cache(path):
    with open(path, "rb") as f:
        return pickle.load(f)


def run_tool(answer):
    # ③ 모델이 낸 글을 그대로 실행
    result = eval(answer)
    subprocess.run(f"echo {result}",
                   shell=True)
    return result

실제 출력에서 이슈마다 규칙 번호·심각도·위치 줄만 남기고 설명 문장과 신뢰도는 뺐습니다.

SAST가 모든 결함을 잡지는 못합니다. OWASP(Open Worldwide Application Security Project)는 이런 도구가 오탐이 많고 보안 결함 중 비교적 적은 부분만 자동으로 찾는다고 적어 둡니다. 키 줄을 놓친 것도 그 예입니다. 키는 비밀 정보 탐지 도구와 저장소 설정으로 따로 막고 SAST는 커밋마다 빠르게 돌려 아는 위험을 걸러 내는 데 씁니다.

미국 정부 지침 SSDF

미국 NIST는 이런 검사를 개발 과정 전체에 넣으라는 지침 SSDF(Secure Software Development Framework, SP 800-218)를 냈고 2024년 7월 생성형 AI 모델용 보충판 SP 800-218A를 더했습니다.

열두 편을 한 장의 지도로

이 시리즈는 모델 파일 안의 숫자 76억 개에서 출발했습니다. 그 숫자가 토큰을 읽고, GPU 메모리에 올라가 서버가 되고, 여러 팀이 나눠 쓰는 플랫폼이 되고, 회사 문서를 찾아 답하고, 이 글에서 1년 동안 운영됐습니다.

편마다 붙은 작은 그림은 맨 앞 상자 그림을 줄인 것이고 청록으로 칠한 칸이 그 편이 다룬 상자입니다. 모델 코드라는 작은 상자에서 시작해 바깥 상자로 한 칸씩 넓혀 왔습니다.

새 모델이나 새 도구가 나오면 "이건 어느 상자의 이야기인가"부터 물어보면 됩니다. 그 질문에 답할 수 있으면 처음 보는 용어도 제자리를 찾습니다.
