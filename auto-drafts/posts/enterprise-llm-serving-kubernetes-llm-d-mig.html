LLM 하나에 GPU 네 장, GPU 한 장에 LLM 일곱 개

회사에 NVIDIA H100 GPU(Graphics Processing Unit)가 16장 있다고 해 보겠습니다. 한 장의 메모리는 80GB입니다. 그런데 Qwen2.5-72B 모델은 안에 든 숫자만 145GB라 한 장에 들어가지 않습니다. 반대로 Qwen2.5-3B는 6GB라서 한 장을 통째로 주면 대부분이 놉니다.

그래서 회사는 큰 모델은 GPU 여러 장에 나눠 싣고 작은 모델에게는 한 장을 쪼개 한 칸만 줍니다. 모델 크기 자의 손잡이를 옮기면 같은 GPU 16장 위에서 모델이 차지하는 칸이 바뀝니다.

모델 크기 자 — 끌거나 눌러 고르기

    큰 모델은 층 안을 쪼개거나 층을 나눠 싣습니다

    LLM(Large Language Model)은 같은 모양의 층(layer) 수십 개를 차례로 지나며 계산합니다. 답을 이루는 글 조각인 토큰(token) 하나를 만들 때마다 모든 층을 한 번씩 지납니다. Qwen2.5-72B는 80층입니다. 층 하나 안에는 입력에 곱할 숫자를 가로세로로 줄지어 적은 큰 표, 곧 행렬(matrix)이 들어 있습니다. 한 장에 안 들어가는 모델은 두 가지 방법으로 나눕니다.

    Tensor Parallel은 층마다 그 행렬을 세로로 잘라 GPU마다 한 조각씩 맡깁니다. 네 장이면 모든 층에서 네 장이 동시에 계산하고, 층이 끝날 때마다 조각 결과를 모아 합칩니다. 넷이 한 문제를 나눠 풀고 문항마다 모여 답을 맞추는 조별 과제와 비슷합니다.

    Pipeline Parallel은 층을 순서대로 묶어 나눕니다. 네 장이면 1~20층, 21~40층처럼 맡고 앞 GPU가 끝낸 결과를 다음 GPU에 넘깁니다. 이어달리기에서 바통을 넘기는 것과 같습니다.

    Qwen2.5-72B(80층, 가중치 145.4GB)를 GPU 여러 장에 나누기 — 장수와 방식을 바꾸고 ▶을 눌러 보세요

    GPU 4장

    실험판을 돌려 보면 두 방식이 다르게 움직입니다. Tensor Parallel은 토큰 하나를 만드는 동안 GPU끼리 160번 주고받습니다. 80개 층에서 두 번씩 모아 합치니 160번입니다. Pipeline Parallel은 4장이면 세 번만 넘기지만 요청 하나를 계산하는 동안 한 장만 일합니다.

    모아 합치기의 정식 이름은 all-reduce입니다. GPU마다 가진 부분 결과를 더해 모두가 같은 합을 갖게 하는 통신입니다.

    왜 층마다 딱 두 번만 모을까요?

    Megatron-LM 논문은 첫 행렬은 열 방향, 두 번째 행렬은 행 방향으로 잘라서 층 안의 행렬 곱 두 번 사이에는 통신이 필요 없게 했습니다. 그래서 층마다 앞쪽 계산에서 all-reduce가 두 번만 일어납니다.

    요청이 여러 개 들어오면 Pipeline Parallel도 덜 놉니다. 앞 요청이 다음 GPU로 넘어가는 동안 뒤 요청이 첫 GPU에 들어오기 때문입니다. 그래도 차례가 비는 틈이 남는데, 이 빈 시간을 파이프라인 거품(pipeline bubble)이라고 부릅니다.

    GPU 사이 길이 넓어야 Tensor Parallel이 빠릅니다

    Tensor Parallel은 층마다 모아 합치니 GPU 사이 길이 좁으면 계산보다 기다리는 시간이 길어집니다. 길의 폭은 대역폭(bandwidth), 곧 1초에 옮길 수 있는 바이트 수로 잽니다.

    SXM은 GPU를 카드 대신 서버 보드에 바로 붙이는 방식입니다. SXM 방식의 H100 서버는 NVLink라는 GPU 전용 연결로 GPU를 묶고 한 장이 초당 900GB를 주고받습니다. NVLink가 없는 서버는 컴퓨터 부품을 잇는 일반 통로인 PCIe(PCI Express)를 지나는데 H100의 PCIe Gen5는 초당 128GB입니다. 일곱 배 차이입니다.

    그래서 vLLM 문서는 한 서버 안에서는 Tensor Parallel을, 서버를 넘어가면 서버 안은 Tensor Parallel로 서버 사이는 Pipeline Parallel로 나누라고 권합니다. NVLink가 없는 GPU, 예를 들어 PCIe 카드로 꽂는 L40S는 Pipeline Parallel이 낫다고도 적었습니다. 옵션 이름은 --tensor-parallel-size와 --pipeline-parallel-size입니다.

    Kubernetes는 서버 여러 대를 GPU 창고 하나처럼 다룹니다

    모델을 나눌 방법을 정했으면 어느 서버에서 돌릴지 정해야 합니다. 서버가 수십 대면 사람이 일일이 고를 수 없습니다. Kubernetes는 서버 여러 대를 묶어 두고 프로그램을 알아서 배치하는 오픈소스 시스템입니다.

    Kubernetes에서 서버 한 대는 노드(Node), 함께 실행할 프로그램 묶음 하나는 Pod입니다. Pod 안에는 프로그램과 필요한 파일을 한데 담은 컨테이너(container)가 들어갑니다. vLLM 서버 하나가 Pod 하나라고 보면 됩니다.

    스케줄러(scheduler)는 Pod가 들어갈 노드를 고르는 프로그램입니다. 먼저 GPU가 모자란 노드를 걸러 내고 남은 노드에 점수를 매겨 1등에 놓습니다. 식당 직원이 인원수에 맞는 빈 테이블을 찾아 안내하는 것과 비슷합니다. 다만 식당 손님은 두 테이블에 나눠 앉을 수 있어도 Pod의 GPU는 반드시 한 노드 안에서 나와야 합니다.

    그래서 점수 규칙에 따라 결과가 갈립니다. 덜 찬 노드에 높은 점수를 주면 흩어 놓기(spread), 많이 찬 노드에 높은 점수를 주면 꽉 채우기(bin packing)입니다. 흩어 놓기로 보내면 작은 Pod가 세 노드에 고르게 퍼집니다. GPU가 모두 합쳐 16장 남아도 8장이 한꺼번에 빈 노드가 없어서 마지막 Pod는 자리를 못 찾고 대기 상태(Pending)로 남습니다. 꽉 채우기는 이미 많이 쓴 노드부터 채워 큰 Pod 자리를 남깁니다.

    Pod는 필요한 GPU 장수를 nvidia.com/gpu로 적습니다. NVIDIA의 device plugin이 노드마다 GPU 개수를 Kubernetes에 알려 주기 때문에 쓸 수 있는 이름입니다. GPU는 정수로만 달라고 할 수 있고 두 컨테이너가 한 장을 같이 쓰지 못합니다.

    Kubernetes 기본 설정은 어느 쪽인가요?

    기본 점수 규칙은 CPU와 메모리만 보고 덜 찬 노드를 높게 칩니다(LeastAllocated). GPU를 점수에 넣으려면 스케줄러 설정에 nvidia.com/gpu를 더하고, 꽉 채우려면 MostAllocated로 바꿉니다. 2025년 Kubernetes 1.34부터는 장치를 더 자세히 골라 달라고 적는 Dynamic Resource Allocation(DRA)도 정식 기능이 됐습니다.

    apiVersion: v1
kind: Pod
metadata:
  name: qwen72b
spec:
  containers:
  - name: vllm
    image: vllm/vllm-openai:latest
    # ① 72B를 GPU 4장에 나눠 띄우기
    command: ["vllm", "serve",
              "Qwen/Qwen2.5-72B-Instruct",
              "--tensor-parallel-size", "4"]
    resources:
      limits:
        # ② GPU 4장을 달라는 요청
        nvidia.com/gpu: 4
    1. Pod 안에서 vLLM이 72B를 GPU 4장에 Tensor Parallel로 나눠 띄웁니다. 이 숫자는 ②의 장수와 같아야 합니다.
    2. GPU는 limits에만 적습니다. 스케줄러는 GPU 4장이 비어 있는 노드에만 이 Pod를 놓습니다.

    GPU가 남으면 MIG로 한 장에 칸막이를 세웁니다

    반대 상황도 흔합니다. Qwen2.5-3B 같은 작은 모델은 80GB 가운데 몇 GB만 씁니다. Kubernetes는 GPU를 정수로만 나눠 주니 그대로 두면 팀마다 한 장씩 차지하고 대부분을 비워 둡니다.

    MIG(Multi-Instance GPU)는 A100·H100 같은 데이터센터 GPU 한 장을 최대 7개의 독립된 GPU로 나누는 NVIDIA 기능입니다. 칸마다 계산 장치 묶음인 SM(Streaming Multiprocessor)과 캐시, 메모리를 따로 받습니다. 한 칸에 일이 몰리거나 오류가 나도 옆 칸은 영향을 받지 않습니다.

    교실 하나에 벽을 세워 작은 반 여러 개로 나누는 것과 비슷합니다. 다만 벽은 아무 데나 세울 수 없습니다. H100은 계산 칸 7개와 메모리 칸 8개(한 칸 10GB)로 나뉘고 정해진 모양의 조각만 만듭니다.

    H100 80GB 한 장 나누기 — 조각 이름을 눌러 넣어 보세요. 1g.10gb는 계산 칸 1개와 메모리 10GB라는 뜻입니다

    조각
    메모리 칸10GB × 8
    계산 칸SM 묶음 × 7

    처음 상태는 가장 작은 조각 1g.10gb 일곱 개에 작은 모델을 하나씩 올린 모습입니다. 메모리 칸은 하나 남지만 계산 칸 7개를 다 써서 여덟 번째 조각은 만들 수 없습니다. 조각마다 놓일 수 있는 칸은 NVIDIA 문서의 H100 배치표를 따랐습니다. Kubernetes에서는 노드가 nvidia.com/mig-2g.20gb처럼 조각 이름으로 GPU를 알리고, Pod가 그 이름으로 달라고 합니다.

    칸막이 없이 시간을 나눠 쓰는 time-slicing

    MIG를 쓰지 않는 GPU도 여러 Pod가 나눠 쓸 수 있습니다. time-slicing은 GPU 한 장을 아주 짧은 시간 단위로 돌아가며 쓰게 하는 방식입니다. NVIDIA device plugin에는 GPU 한 장을 몇 장으로 보이게 할지 정하는 값 replicas가 있습니다. 이 값을 10으로 적으면 GPU 8장짜리 노드가 Kubernetes에는 80장으로 보입니다.

    교실 하나를 시간표로 나눠 쓰는 것과 같습니다. 벽이 없으니 메모리도 다 같이 씁니다. NVIDIA 문서는 복제본 사이에 메모리 격리도 장애 격리도 없다고 적었고 한 작업이 죽으면 같은 장을 쓰던 작업이 모두 멈춥니다.

    그래서 time-slicing은 개발·실험처럼 가끔 쓰는 작업에, MIG는 서로 영향을 주면 안 되는 서비스에 맞습니다. MIG도 지원하는 GPU에서만 되고 칸 모양을 바꾸려면 그 GPU의 작업을 모두 비워야 합니다.

    LLM 요청은 아무 서버로나 보내면 손해입니다

    같은 모델을 띄운 Pod를 여러 개 두면 요청을 나눠 줄 문지기가 필요합니다. 일반 웹 서비스의 로드밸런서(load balancer)는 보통 차례대로 돌아가며 보내는 라운드 로빈(round robin)을 씁니다. LLM에서는 이 방식이 이미 해 둔 계산을 버립니다.

    LLM은 프롬프트 전체를 처음 읽는 Prefill 단계에서 토큰마다 계산 결과를 만들어 KV Cache로 저장해 둡니다(LLM 답변은 왜 첫 글자만 늦게 나올까요?). vLLM은 앞부분이 같은 요청이 오면 저장해 둔 KV Cache를 다시 씁니다. 이 기능이 prefix caching입니다(추론 엔진 vLLM 글). 그런데 이 캐시는 그 요청을 처리한 Pod의 GPU에만 있습니다.

    팀 세 곳의 요청 60개를 Pod 네 개에 나눠 보내기 — 방식을 고르고 ▶을 눌러 보세요

    법무팀 챗봇고객센터 챗봇코딩 도우미요청 점 테두리: 캐시 적중처음부터 계산방금 요청이 도착한 Pod

    예시 값입니다. 팀마다 같은 시스템 프롬프트 2,000토큰에 질문 50토큰이 붙습니다. Pod 하나는 앞부분 두 개까지 캐시에 두고, 답을 쓰는 몫을 600토큰만큼의 일로 쳤습니다. 실제 vLLM은 GPU 메모리가 허락하는 만큼 캐시를 둡니다.

    차례대로 보내면 같은 팀 요청이 네 Pod에 흩어져 절반 가까이 처음부터 계산합니다. 앞부분만 보고 보내면 거의 다 적중하지만 한 팀에 요청이 몰리면 그 팀을 맡은 Pod 하나에 줄이 길어집니다. 앞부분과 줄 길이를 함께 보면 붐비는 Pod를 피해 다른 Pod에도 그 팀의 캐시를 하나 더 만듭니다.

    llm-d는 이 판단을 맡는 오픈소스 프로젝트입니다. Red Hat·Google Cloud·IBM Research·CoreWeave·NVIDIA가 만들었고 2026년 3월 CNCF(Cloud Native Computing Foundation) Sandbox 프로젝트가 됐습니다. 계산은 그대로 vLLM이 하고 llm-d는 요청을 어느 Pod로 보낼지 정합니다.

    구조도의 Proxy는 요청을 받아 다른 서버로 넘겨 주는 중계 서버입니다. 요청이 들어오면 Proxy는 EPP(Endpoint Picker)에 묻습니다. EPP는 Pod마다 캐시에 든 앞부분, 대기 줄, KV Cache가 찬 정도를 읽어 점수를 매깁니다. 같은 모델을 띄운 Pod 묶음은 InferencePool이라고 부릅니다.

    Proxy와 EPP가 주고받는 규칙은 누가 정하나요?

    Kubernetes 공식 프로젝트인 Gateway API Inference Extension이 정합니다. InferencePool과 Endpoint Picker라는 이름도 이 규격에서 왔습니다.

    줄이 계속 길면 Pod를 누가 늘리나요?

    부하에 따라 서버 수를 자동으로 늘리고 줄이는 일을 오토스케일(autoscaling)이라고 합니다. Kubernetes에서는 HPA(Horizontal Pod Autoscaler)가 지표를 보고 Pod 수를 바꿉니다. llm-d v0.10은 EPP가 내놓는 대기 줄 같은 지표를 KEDA가 읽어 HPA를 움직이게 합니다. 늘어난 Pod도 GPU가 있어야 들어가니 결국 앞에서 본 스케줄러와 GPU 장수 문제로 돌아옵니다.

    Prefill과 Decode를 다른 GPU에 맡기기도 합니다

    LLM은 프롬프트를 한꺼번에 읽는 Prefill과 답을 한 토큰씩 쓰는 Decode 두 단계로 일합니다. Prefill은 계산량이, Decode는 메모리에서 숫자를 나르는 시간이 발목을 잡습니다. 한 GPU에서 둘을 섞으면 누군가의 긴 Prefill이 다른 사람의 Decode를 붙잡아 답이 끊겨 나옵니다.

    llm-d는 Prefill만 하는 Pod와 Decode만 하는 Pod를 따로 둘 수 있습니다. 이걸 분리 서빙(disaggregated serving)이라고 합니다. EPP가 Decode Pod를 먼저 고르고, 프롬프트 가운데 그 Pod 캐시에 없는 부분이 크면 Prefill Pod도 고릅니다. Prefill Pod가 만든 KV Cache는 NIXL이 RDMA로 Decode Pod에 옮깁니다. NIXL은 NVIDIA가 만든 GPU 메모리 전송 라이브러리입니다.

    RDMA(Remote Direct Memory Access)는 CPU를 거치지 않고 다른 서버의 메모리에 바로 쓰는 고속 네트워크 방식입니다. 옮기는 비용이 있어서 늘 이득은 아닙니다. llm-d 문서는 RDMA 같은 빠른 연결이 없으면 시험용으로만 쓰라고 적었습니다.

    나눠 맡기면 얼마나 빨라지나요?

    AWS는 B200에서 최대 70%, Oracle은 MI300X에서 10~30% 처리량이 늘었다고 보고했습니다. GPU와 네트워크, 프롬프트 길이에 따라 달라지는 값입니다.

    팀마다 서버를 세우지 않고 API 키와 쿼터를 나눠 줍니다

    여기까지 세우려면 GPU·Kubernetes·vLLM·llm-d를 다룰 줄 아는 사람이 필요합니다. 팀마다 따로 세우면 GPU도 사람도 모자랍니다. 그래서 플랫폼 팀이 한 번 세우고 다른 팀은 API 주소와 키만 받아 씁니다. 이 운영 방식을 MaaS(Models-as-a-Service)라고 합니다.

    모든 요청은 사내 API 게이트웨이(API gateway)를 지납니다. 게이트웨이는 키로 팀을 확인하고 팀마다 정한 사용 한도, 곧 쿼터(quota)를 셉니다. LLM 요청은 짧은 인사일 수도 긴 보고서일 수도 있어서 요청 수 대신 토큰 수로 셉니다.

    Red Hat OpenShift AI 문서의 예시는 developer 등급에 24시간 50,000토큰, enterprise 등급에 500,000토큰을 줍니다. 한도를 넘으면 게이트웨이가 요청이 너무 많다는 뜻의 HTTP 429 오류를 돌려주고 시간 창이 다시 시작될 때까지 막습니다. 휴대폰 데이터 요금제와 비슷하지만 다 써도 느려지는 대신 바로 막힌다는 점이 다릅니다.

    요청 하나가 GPU에 닿기까지

    지금까지 본 층을 사내 챗봇에 보낸 질문 하나의 경로로 이으면 이 그림과 같습니다. 칸마다 그 층이 답하는 질문을 적었습니다. 아래로 갈수록 GPU에 가까워집니다.

    모델이 한 장보다 크면 묶고, 작으면 쪼개고, 그렇게 만든 Pod를 Kubernetes가 노드에 놓습니다. 그 앞에서 라우터가 캐시와 줄 길이를 보고 Pod를 고르고, 맨 앞의 게이트웨이가 팀마다 쓸 양을 셉니다.
