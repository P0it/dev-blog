챗봇은 내 이름을 어떻게 기억할까요? API 안에서 벌어지는 일

ChatGPT 같은 챗봇에게 이름을 알려 주면 대화가 끝날 때까지 기억합니다. 그런데 개발자가 쓰는 API는 방금 한 말도 기억하지 못합니다. 이 글은 화면 뒤로 내려가서 챗봇이 실제로 어떻게 기억하는지 봅니다.

아래 두 채팅 화면은 똑같은 대화입니다. 다른 것은 화면 뒤에서 프로그램이 API에 보낸 내용 하나뿐입니다. 왼쪽은 마지막 질문만 보냈고, 오른쪽은 대화 전체를 보냈습니다.

AI의 답은 예시입니다.

화면 뒤의 API는 방금 한 말도 기억하지 못합니다

채팅 화면만 보면 AI가 대화를 기억하는 것 같습니다. 화면 뒤로 내려가 OpenAI API를 직접 불러 보면 사정이 다릅니다. API는 호출할 때마다 요청을 따로따로 처리하고 앞선 요청이 무엇이었는지 알지 못합니다.

아래 코드로 확인해 봅시다. 두 마디를 따로 보냈습니다. 두 번째 요청에는 첫 번째 말이 빠져 있으니 이름을 대답할 수 없습니다. 같은 현상을 AI Agent 시리즈 첫 글에서도 다뤘습니다.

from openai import OpenAI

# ① 키는 환경 변수 OPENAI_API_KEY 에서 읽는다
client = OpenAI()
MODEL = "gpt-6.1-sol"

for text in ["안녕? 내 이름은 홍길동이야.", "내 이름이 뭘까?"]:
    # ② 호출 하나가 요청 하나다
    response = client.responses.create(
        model=MODEL,
        instructions="너는 사용자를 도와주는 상담사야.",
        # ③ 이번에 한 말만 보낸다
        input=text,
    )
    print("사용자:", text)
    print("AI:", response.output_text)

출력은 예시입니다. 같은 코드라도 답하는 문장은 그때그때 달라집니다. 모델 이름 gpt-6.1-sol은 OpenAI 모델 문서(2026-10-29 확인)에서 성능과 비용의 균형이 좋다고 소개한 모델입니다. 모델 이름은 자주 바뀌니 쓰기 전에 문서를 확인하세요.

  1. OpenAI()는 환경 변수에서 API 키를 찾아 사용합니다. 키를 코드에 직접 적지 않으면 저장소에 올려도 새어 나가지 않습니다. 이 글의 코드는 openai 3.41(Python 3.10 이상) 기준입니다.
  2. responses.create는 OpenAI가 새 프로젝트에 권하는 호출 방법입니다. 같은 일을 하는 chat.completions.create도 계속 쓸 수 있지만 새로 만든다면 이쪽을 쓰면 됩니다.
  3. input=text에는 이번에 한 말 하나만 들어갑니다. 첫 번째 대화가 담기지 않았으니 AI는 이름을 알 수 없습니다.
02

챗봇 화면 뒤에서는 지난 대화를 매번 통째로 보냅니다

챗봇이 이름을 기억하는 비밀은 단순합니다. 프로그램이 지난 대화를 목록으로 가지고 있다가, 호출할 때마다 그 목록을 통째로 보냅니다. 모델은 받은 목록을 처음부터 읽고 이어질 답을 씁니다.

대화가 이어질 때 화면 뒤의 목록이 어떻게 자라는지 스크롤하며 따라가 봅시다. 턴은 한 번 말하고 한 번 답하는 주고받기를 뜻합니다.

1턴

사용자가 이름을 말합니다. 채팅 화면에 말풍선이 하나 생기고, 화면 뒤 API로 가는 input에도 항목이 하나 들어갑니다.

2턴

"내 이름이 뭘까?"를 보낼 때 프로그램은 앞의 두 말풍선도 함께 넣습니다. AI는 목록의 첫 항목에서 이름을 찾아 대답합니다.

3턴

주문 문의를 시작합니다. 화면에는 말풍선 하나가 늘었을 뿐이지만, input에는 앞의 네 항목이 다시 들어갑니다.

7턴

화면에서는 위로 한참 올려야 보이는 첫 인사도 input에는 빠짐없이 들어 있습니다. 항목은 13개가 됩니다.

대화 내용은 예시입니다.

1편에서 예시를 지난 대화처럼 넣은 방법도 같은 원리였습니다. 진짜 대화에서는 예시 대신 실제로 주고받은 말이 들어갈 뿐입니다. 우리는 채팅 화면에서 지난 대화를 훑어보지만, 모델은 받은 목록을 언제나 처음부터 끝까지 읽습니다.

from openai import OpenAI

client = OpenAI()
# ① 대화 기록은 프로그램이 들고 있는다
history = []

while True:
    history.append({"role": "user", "content": input("사용자: ")})
    response = client.responses.create(
        model="gpt-6.1-sol",
        instructions="너는 사용자를 도와주는 상담사야.",
        # ② 매번 기록 전체를 보낸다
        input=history,
        # ③ 서버에는 따로 저장하지 않는다
        store=False,
    )
    # ④ 답도 output 항목 그대로 기록에 붙인다
    history.extend(response.output)
    print("AI:", response.output_text)

출력은 예시입니다. 이제 두 번째 질문에 이름이 나옵니다.

  1. 대화 기록은 프로그램이 가지고 있습니다. API는 아무것도 저장하지 않으니 목록을 하나 만들어 두고 계속 늘려 갑니다.
  2. 호출할 때마다 목록 전체를 보냅니다. input은 모델에게 보내는 입력을 담는 칸이고, 여기에 목록 전체를 넘깁니다. instructions는 상담사 역할 같은 지시를 적는 칸으로, 1편의 developer 메시지가 들어가던 자리입니다.
  3. store=False는 응답을 OpenAI 서버에 저장하지 않게 합니다. 대화 기록을 프로그램이 이미 가지고 있으니 서버에 또 저장할 필요가 없습니다.
  4. 답은 글만 꺼내지 말고 response.output 항목 그대로 붙입니다. 추론 모델은 답 말고도 생각 과정 항목을 함께 돌려줍니다. 공식 문서는 이 항목을 하나도 버리지 말고 다음 요청에 다시 넣으라고 안내합니다.

03

대화가 길어질수록 한 마디에 드는 요금이 커집니다

채팅 화면에서는 말풍선이 하나씩 늘 뿐입니다. 화면 뒤에서는 목록을 통째로 보내니 토큰도 그만큼 보냅니다. 토큰은 모델이 글을 읽는 단위로, 단어보다 조금 작은 조각입니다. 보낸 토큰 수는 응답의 usage.input_tokens에 찍히고 요금도 이 수로 계산합니다.

막대 하나가 한 턴의 요청이고, 높이는 그때 보낸 입력 토큰 수입니다.

이번 턴에 새로 붙인 말(지시문 포함)앞 턴에서 이미 보낸 말을 또 보냄
12번째 턴에 보낸 입력1,700
12턴까지 낸 입력 합계10,500
그중 이미 한 말의 반복94%

토큰 수는 설명용 예시입니다(지시문 20, 사용자 말 30, AI 답 120). 실제 수는 글자와 모델에 따라 다릅니다.

턴마다 앞 대화가 150토큰씩 늘어나니 n번째 턴에서는 150×(n−1)토큰이 다시 들어갑니다. 이걸 모두 더하면 턴이 두 배일 때 합계는 대략 네 배가 됩니다. 그래서 대화가 길수록 같은 한 마디를 하는 데 드는 요금이 커집니다.

앞부분이 같으면 요금이 줄어드나요?

앞부분이 똑같이 반복되면 OpenAI가 그 부분을 저장해 두었다가 다시 쓰기 때문에 입력 요금이 줄 수 있습니다. 응답의 usage.input_tokens_details.cached_tokens에 그 수가 찍힙니다. 그래서 바뀌지 않는 지시문은 맨 앞에 두는 것이 좋습니다.

04

서버에 맡겨도 입력 요금은 그대로입니다

휴대폰에서 시작한 대화를 노트북에서 이어 가려면 기록이 어딘가에 남아 있어야 합니다. 대화 기록을 OpenAI 서버에 맡기는 방법은 두 가지입니다. 앞 응답의 번호인 previous_response_id만 보내는 방법, 그리고 대화 하나를 담는 상자인 Conversations API를 쓰는 방법입니다.

같은 대화의 12번째 턴을 세 가지 방법으로 보내면 이렇게 다릅니다.

직접 이어 붙이기기록을 보관하는 곳: 내 프로그램
보내는 양1,700
청구되는 입력1,700
서버 보관 기간없음
previous_response_id기록을 보관하는 곳: OpenAI 서버

서버 보관 기간제한 없음

빗금 막대는 서버에 보관되는 기간입니다. 토큰 수는 앞 그림과 같은 예시입니다. 응답은 기본으로 30일 보관되고 store=False로 끌 수 있습니다. Conversations의 항목에는 30일 제한이 없습니다. 다만 Conversations API의 요금은 따로 확인하지 못해 같은 방식으로 그렸습니다.

previous_response_id로 이어도 앞 응답들의 입력 토큰에는 모두 입력 요금이 붙습니다. 서버가 대화를 기억해 줘도 요금은 직접 이어 붙일 때와 같습니다. 줄어드는 것은 보내는 양과 코드뿐입니다.

# ... client 는 앞 코드와 같다
MODEL, INSTRUCTIONS = "gpt-6.1-sol", "너는 사용자를 도와주는 상담사야."
questions = ["안녕? 내 이름은 홍길동이야.", "내 이름이 뭘까?"]

# ① 방법 A: 앞 응답의 번호를 건넨다
last_id = None
for text in questions:
    response = client.responses.create(
        model=MODEL,
        # ② instructions 는 이어지지 않아서 매번 쓴다
        instructions=INSTRUCTIONS,
        input=text,
        previous_response_id=last_id,
    )
    last_id = response.id

# ③ 방법 B: 대화 상자를 만들고 상자 번호를 건넨다
conversation = client.conversations.create()
for text in questions:
    response = client.responses.create(
        model=MODEL,
        instructions=INSTRUCTIONS,
        input=text,
        conversation=conversation.id,
    )
  1. 방법 A는 번호만 보냅니다. 첫 호출에는 None을 넘기고, 그다음부터는 바로 앞 응답의 id를 넘깁니다. 그러면 서버가 앞 대화를 이어 붙여 줍니다.
  2. 지시문은 이어지지 않습니다. 앞 응답에 썼던 instructions는 다음 응답으로 넘어가지 않으니 매번 다시 적어야 합니다. 빠뜨리면 상담사 역할이 사라집니다.
  3. 방법 B는 대화 상자를 만듭니다. 호출할 때마다 상자 번호를 넘기면 같은 상자에 대화가 쌓입니다. conversation과 previous_response_id는 한 요청에 함께 쓸 수 없습니다.
그럼 어떤 방법을 고르면 되나요?

무엇을 보낼지 스스로 정하고 싶다면 직접 이어 붙이는 방법을 고릅니다. 오래된 말을 자르거나 요약하기 쉽고, 서버에 저장하지 않을 수도 있습니다.

코드를 짧게 쓰고 싶다면 previous_response_id가 편합니다. 다만 대화 중간을 고치기는 어렵습니다. 여러 기기나 작업에서 같은 대화를 이어 가야 한다면 Conversations가 알맞습니다.

서버에 맡기려면 조직의 보관 정책도 확인해야 합니다. 데이터를 보관하지 않는 계약(Zero Data Retention)을 맺은 조직은 서버에 저장하는 방식을 쓸 수 없습니다. 이때는 store=False로 직접 이어 붙여야 합니다.

05

창이 가득 차면 요청이 거절되거나 맨 앞부터 잊습니다

아주 긴 대화를 하다 보면 챗봇이 처음에 한 말을 잊거나 오류를 띄울 때가 있습니다. 화면 뒤의 모델이 한 번에 읽을 수 있는 양에는 한도가 있습니다. 이 한도를 컨텍스트 창(context window)이라고 합니다. 창에는 입력뿐 아니라 출력과 추론에 쓰는 토큰도 모두 들어갑니다.

창을 넘으면 어떻게 될까요? Responses API의 truncation 기본값은 disabled입니다. 그래서 요청이 400 오류(요청이 잘못되었다는 뜻의 응답 번호)로 실패합니다. auto로 바꾸면 대화의 맨 앞부터 항목을 버리고 답합니다.

창 안에 들어갈 때5턴 대화 · 창 6턴

홍길동님이라고 하셨어요.

창을 넘었고 truncation 기본값일 때8턴 대화 · 창 6턴

⚠ 400 오류. 요청이 거절되어 답이 오지 않습니다.

창을 넘었고 truncation=auto일 때8턴 대화 · 창 6턴

죄송하지만 이름을 알려 주신 적이 없어요.

칸 하나가 턴 하나입니다. 마지막 칸은 지금 하는 질문이고, 아래 말풍선은 그때 채팅 화면에 보이는 답입니다. 창은 설명하려고 6턴 크기로 아주 작게 그렸습니다.

실제 창은 훨씬 큽니다. OpenAI 모델 문서를 보면 gpt-6.1-sol의 창은 약 105만 토큰입니다. 수다만 떠서는 좀처럼 차지 않지만, 파일이나 검색 결과를 계속 붙이는 서비스에서는 금방 찹니다. 그보다 먼저 앞에서 본 요금이 부담이 됩니다.

긴 대화를 이어 가는 서비스는 잘리기 전에 줄입니다

압축 전: 9턴을 모두 보냄

123456789

압축 후: 앞 5턴이 압축 1칸으로 줄고, 최근 4턴은 그대로 보냄

압축6789

창이 차기 전에 대화를 줄이는 방법이 둘 있습니다. 하나는 오래된 대화를 모델에게 요약하게 해서 한두 항목으로 바꿔 끼우는 방법입니다. 이름처럼 꼭 남겨야 할 정보는 따로 챙겨 두면 안전합니다.

다른 하나는 OpenAI가 제공하는 압축(compaction) 기능입니다. 요청에 context_management로 기준 토큰 수를 적어 두면, 대화가 그 수를 넘을 때 서버가 앞부분을 압축한 항목으로 바꿔 줍니다. 압축 항목은 사람이 읽을 수 없게 섞어 놓은(암호화한) 형태입니다.

압축을 켜는 코드 보기 
# ... client, MODEL 은 앞 코드와 같다
history = [{"role": "user", "content": "긴 작업을 시작하자."}]

while True:
    response = client.responses.create(
        model=MODEL,
        input=history,
        store=False,
        # ① 입력이 20만 토큰을 넘으면 서버가 앞 대화를 압축한다
        context_management=[{"type": "compaction", "compact_threshold": 200000}],
    )
    # ② 압축 항목도 output 에 들어 있으니 그대로 붙인다
    history.extend(response.output)
    history.append({"role": "user", "content": input("사용자: ")})
  1. compact_threshold는 압축을 시작하는 기준 토큰 수입니다. 공식 문서의 예시는 20만이고 창보다 한참 작게 잡아서 여유를 둡니다.
  2. 직접 이어 붙이는 경우에는 압축 항목보다 앞에 있던 옛 항목을 지워도 됩니다. 하지만 previous_response_id로 이어 가는 중이라면 앞 항목을 직접 지우면 안 됩니다.

챗봇을 만들기 전에 정할 네 가지

정할 것은 네 가지입니다. 대화 기록을 누가 가지고 있을지, 턴마다 입력 토큰이 얼마나 쌓일지, 창이 차면 무엇을 할지, 서버에 맡긴다면 30일 보관과 매번 instructions를 보내는 일을 받아들일지입니다.

usage.input_tokens를 턴마다 찍어 보는 일부터 시작하면 쉽습니다. 요금이 어디서 늘어나는지 바로 보입니다. 기록을 이어 가는 방식을 하나로 정해 두면 같은 말이 두 번 들어가는 실수도 막을 수 있습니다.
