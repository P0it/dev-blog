도구를 이미 부를 수 있는데 MCP는 왜 필요할까요?

Agent에게 티켓 시스템을 쓰게 하려면 그 시스템의 API를 부르는 도구를 만들면 됩니다. 그런데 AI 앱이 여러 개이고 연결할 시스템도 여러 개라면 앱마다 시스템마다 따로 만들어야 합니다. 앱이 3개이고 시스템이 3개면 연결 부품이 9개입니다.

MCP(Model Context Protocol)는 AI 앱과 외부 시스템을 잇는 공개 표준입니다. 공식 문서는 AI 앱을 위한 USB-C 단자에 비유합니다. 앱과 시스템이 모두 이 규격을 따르면 연결 부품이 앱 수와 시스템 수의 합으로 줄어듭니다. 아래 두 그림은 앱 5개와 시스템 5개를 두 방식으로 이은 모습입니다. 화면을 내리면 선이 하나씩 그어지고 부품 수가 올라갑니다.

각자 따로 연결

앱 5개와 시스템 5개를 모두 따로 잇으면 25개를 만들어야 합니다. 앱이나 시스템이 하나 늘 때마다 5개씩 늘어납니다.

MCP로 연결

모두 MCP를 따르면 앱마다 하나, 시스템마다 하나만 만들면 되니 모두 10개입니다. 새 시스템은 서버 하나만 만들면 모든 앱이 씁니다.

설명을 위한 예시입니다. USB-C 비유는 MCP 공식 문서의 표현입니다. USB-C가 모양만 맞추는 것과 달리 MCP는 주고받는 메시지의 규칙까지 정합니다.

앱 안에 서버마다 클라이언트가 하나씩 생깁니다

MCP에는 세 역할이 있습니다. AI 앱인 호스트(host)가 연결을 총괄하고 서버마다 클라이언트(client)를 하나씩 만들어 전용 연결을 유지합니다. 서버(server)는 도구와 자료를 내놓는 프로그램입니다.

서버는 내 컴퓨터에서 실행될 수도 있고 원격에서 실행될 수도 있습니다. 위치가 아니라 연결 방식으로 나뉩니다. 내 컴퓨터의 서버는 표준 입출력(stdio)으로 연결하고 원격 서버는 HTTP 기반의 Streamable HTTP로 연결합니다. 아래 그림에서 실선이 stdio, 점선이 HTTP입니다.

  • 파일 서버stdio

    내 컴퓨터에서 앱이 서버를 직접 실행하고 표준 입출력으로 이야기합니다. 이런 서버는 보통 클라이언트 하나와만 이어집니다.

  • 데이터베이스 서버stdio

    역시 내 컴퓨터에서 도는 로컬 서버입니다. 네트워크를 거치지 않아 빠릅니다.

  • 오류 추적 서버HTTP

    원격에서 돌며 HTTP로 이어져 여러 클라이언트가 함께 씁니다. 인증이 필요하고 OAuth를 권장합니다.

서버가 내놓는 것은 도구, 자료, 프롬프트입니다

서버가 클라이언트에게 줄 수 있는 것은 세 가지입니다. 도구(tools)는 AI 모델이 실행하는 함수입니다. 자료(resources)는 사용자나 모델이 읽는 데이터이고 프롬프트(prompts)는 사용자를 위한 틀입니다. 셋은 쓰는 주체가 서로 다르니 눈여겨보세요.

공식 문서의 예는 데이터베이스 서버입니다. 이 서버는 질의를 실행하는 도구, 표 구조를 담은 자료, 질문 예시를 담은 프롬프트를 함께 내놓을 수 있습니다. 셋은 누가 쓰느냐로 갈립니다.

도구
도구 query_database는 SQL을 실행해 결과를 돌려주는 함수입니다. 모델이 필요하다고 판단하면 부릅니다.
자료
자료 db_schema는 표와 열의 구조를 적은 읽기용 자료입니다. 실행하지 않고 읽어서 맥락으로 씁니다.
프롬프트
프롬프트 few_shot_query는 질문 예시가 담긴 틀입니다. 사용자가 골라 대화를 시작하는 데 씁니다.
server.py · 데이터베이스 서버
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("database")
@mcp.tool()
def query_database(sql: str) -> str:
"""SQL을 실행해 결과를 돌려줍니다"""
← 모델이 골라서 부름
@mcp.resource("db://schema")
def db_schema() -> str:
"""표와 열의 구조"""
← 실행 없이 읽기만
@mcp.prompt()
def few_shot_query(question: str) -> str:
"""질문 예시를 담은 틀"""
← 사용자가 골라서 시작

MCP Python SDK의 FastMCP 모양으로 쓴 설명용 예시입니다. 함수 본문은 줄였고 직접 실행하지는 않았습니다.

클라이언트는 서버에게 먼저 묻고 그다음에 부릅니다

메시지는 JSON-RPC 2.0이라는 형식을 씁니다. 요청과 응답을 번호로 짝지어 주고받는 약속입니다. 클라이언트는 필요하면 서버의 능력을 묻는 server/discover를 보내고 tools/list로 도구 목록을 받은 뒤 tools/call로 하나를 실행합니다.

목록을 먼저 받으니 서버가 도구를 늘리거나 바꿔도 앱은 고칠 필요가 없습니다. 스크롤하며 메시지가 오가는 순서를 보세요.

능력을 물어봄 (선택)

클라이언트가 server/discover를 보내면 서버가 지원하는 규격 버전, 능력, 이름을 알려 줍니다. 꼭 거쳐야 하는 단계는 아닙니다.

도구 목록을 받음

tools/list 응답에는 도구마다 이름, 설명, 입력 모양(JSON Schema)이 담겨 옵니다. 앱은 이 목록을 모델에게 전해 줍니다.

도구를 호출함

모델이 도구를 고르면 앱이 tools/call에 도구 이름과 인자를 담아 서버에 보냅니다.

결과가 돌아옴

서버가 도구를 실행하고 content 목록에 결과를 담아 돌려줍니다. 앱은 이 결과를 모델에게 전합니다.

{ "jsonrpc": "2.0", "id": 3, "method": "tools/call",
  "params": {
    "name": "weather_current",
    "arguments": { "location": "San Francisco", "units": "imperial" }
  }
}

{ "jsonrpc": "2.0", "id": 3,
  "result": {
    "resultType": "complete",
    "content": [
      { "type": "text",
        "text": "Current weather in San Francisco: 68°F, partly cloudy ..." }
    ]
  }
}
  1. 도구 이름과 인자입니다. name은 tools/list로 받은 이름과 같아야 하고 arguments는 그 도구의 입력 모양을 따릅니다. 앞서 배운 도구의 이름과 설명, 입력 스키마가 그대로 쓰입니다.
  2. 같은 번호로 돌아옵니다. 응답의 id가 요청과 같아 어느 요청의 답인지 알 수 있습니다. content에는 글뿐 아니라 이미지나 자료도 담을 수 있습니다.

모든 요청에는 규격 버전과 클라이언트 정보를 담는 _meta가 붙는데 위 예시에서는 줄였습니다. 메시지는 MCP 2026-07-28 공식 문서에서 가져왔고 이 글에서 직접 실행한 것은 아닙니다.

tool calling과 MCP는 서로 다른 구간을 맡습니다

도구를 부르는 길에는 두 구간이 있습니다. 모델과 앱 사이에서 모델이 "이 도구를 이 인자로 불러 주세요"라고 말하는 구간이 tool calling입니다. 이 형식은 모델 제공사의 API가 정합니다.

앱과 도구 사이에서 도구 목록을 얻고 실제로 실행하는 구간이 MCP입니다. 모델은 도구가 MCP 서버에서 왔는지 직접 만든 함수인지 알 필요가 없습니다. 아래 두 줄은 도구 목록을 얻을 때와 도구를 호출할 때입니다. 화면을 내리면 오가는 말이 순번대로 나타납니다.

도구 목록 얻기

앱이 MCP 서버에 tools/list를 보내 도구를 받고 그 목록을 모델에게 줍니다. 모델 쪽 형식은 모델 제공사가 정합니다.

도구 호출하기

모델이 도구를 고르면 앱이 그것을 MCP의 tools/call로 바꿔 서버에 보냅니다. 서버가 시스템에서 실행해 결과를 돌려줍니다.

2026-07-28 규격에서는 요청이 혼자서도 읽힙니다

현재 최신 규격은 2026-07-28 판입니다. MCP가 무상태(stateless)가 된 것이 가장 큰 변화입니다. 모든 요청이 규격 버전과 클라이언트의 능력을 _meta에 직접 싣기 때문에 서버가 이전 요청을 기억하지 않아도 요청 하나만 읽고 처리할 수 있습니다. 덕분에 서버를 여러 대로 늘리기도 쉬워집니다.

서버가 처리 도중 사용자에게 물어야 할 때는 다중 왕복 요청(MRTR, Multi Round-Trip Requests) 방식을 씁니다. 서버가 먼저 사용자에게 묻는 대신 "추가 입력이 필요합니다"라는 결과를 돌려주고 클라이언트가 답을 모아 같은 요청을 다시 보냅니다. 화면을 내리면 화살표가 단계별로 쌓입니다.

  1. 클라이언트가 tools/call로 도구를 호출합니다. 서버는 아직 필요한 정보가 모자란다는 것을 압니다.
  2. 서버가 input_required 결과를 돌려주며 필요한 입력과 상태 값(requestState)을 알립니다. 요청은 여기서 끝납니다.
  3. 클라이언트가 사용자에게 물어 받은 답과 requestState를 그대로 실어 tools/call을 다시 보냅니다. 번호(id)는 새로 매깁니다.
  4. 서버가 상태 값으로 상황을 되살려 처리를 마치고 최종 결과를 돌려줍니다. 서버는 중간에 아무것도 기억할 필요가 없었습니다.

같은 규격은 오래 걸리는 작업을 위한 Tasks 확장도 정의합니다. 서버가 작업을 가리키는 표(handle)를 돌려주면 클라이언트가 나중에 상태를 확인하고 결과를 가져갑니다. 확장은 서버와 클라이언트가 모두 지원할 때만 쓰입니다. 서버가 모델 답변을 대신 요청하던 sampling과 로그 전달은 이번 판에서 폐지 예고(deprecated)되었습니다.

MCP는 도구와, A2A는 다른 Agent와 잇습니다

A2A(Agent2Agent)는 Agent끼리 일을 주고받는 규격입니다. A2A 공식 사이트는 MCP를 세로, A2A를 가로로 비유합니다. MCP는 Agent 하나를 도구로 깊게 만들고 A2A는 그 경계를 넘어 Agent들을 잇습니다.

두 규격은 경쟁하는 사이가 아니라 맡은 역할이 다릅니다. 각 Agent는 자기 도구를 쓸 때 MCP를, 서로 협력할 때 A2A를 함께 씁니다. 다음 글에서는 사내 티켓 시스템을 MCP 서버로 직접 만들어 보겠습니다.

MCP · 세로
MCP는 Agent 하나가 자기 도구와 데이터에 닿게 합니다. 세로로 깊어지는 연결입니다.
A2A · 가로
A2A는 서로 다른 Agent가 일을 주고받게 합니다. 경계를 넘어 가로로 잇는 연결입니다.
함께
각 Agent는 MCP로 자기 도구를 쓰고 Agent끼리는 A2A로 협력합니다. 공식 문서도 둘을 함께 쓰라고 말합니다.
