Agent의 흐름을 내가 직접 정하고 싶으면 어떻게 할까요?

환불 문의를 처리하는 Agent를 만든다고 해 보겠습니다. "주문 조회는 반드시 먼저", "환불 금액이 10만 원을 넘으면 담당자에게", "답장을 보내기 전에 말투 검사" 같은 순서가 있습니다. Agent 반복문에 맡기면 LLM이 이 순서를 건너뛸 수 있습니다. 반복문 대신 흐름을 그림처럼 그려서 정해 두는 방법이 있습니다.

Agent 반복문을 그림으로 그리면 어떻게 생겼나요?

칸 두 개와 화살표 네 개입니다. LLM 칸과 도구 칸 사이를 오가다가 끝으로 빠집니다.

지금까지 짠 Agent 반복문을 그림으로 그리면 위와 같습니다. 일을 하는 칸이 두 개 있고 LLM 칸에서 나가는 길이 LLM의 응답에 따라 두 갈래로 나뉩니다. 이렇게 칸과 화살표로 흐름을 정해 두는 구조를 그래프라고 합니다.

LangGraph는 이 그래프를 코드로 그려서 실행하는 라이브러리입니다. 앞 글의 create_agent도 안에서는 이 두 칸짜리 그래프로 돌아갑니다. 그래프를 직접 그리면 칸을 더하고 화살표를 바꿔서 흐름을 원하는 대로 정할 수 있습니다.

그래프는 무엇으로 이루어지나요?

상태, 노드, 엣지 세 가지입니다.

이름뜻Agent 그래프에서
State 상태칸들이 함께 들고 다니는 데이터메시지 목록
Node 노드일을 하는 칸. 상태를 받아 바꿀 부분을 돌려주는 함수LLM 부르기, 도구 실행
Edge 엣지다음에 어느 칸으로 갈지 정하는 화살표도구 칸 → LLM 칸
조건 엣지상태를 보고 갈 곳을 고르는 화살표LLM 칸 → 도구 칸 또는 끝

상태(State)는 모든 칸이 함께 보는 데이터입니다. Agent에서는 메시지 목록이 상태입니다. 환불 Agent라면 주문 번호·환불 금액·승인 여부 같은 칸을 더 둡니다. 노드(Node)는 상태를 받아 일을 하고 바꿀 부분만 돌려주는 평범한 함수입니다.

엣지(Edge)는 노드 다음에 어디로 갈지 정합니다. 늘 같은 곳으로 가는 엣지도 있고 상태를 보고 갈 곳을 고르는 조건 엣지도 있습니다. LLM이 판단하는 곳과 코드가 정하는 곳을 엣지로 나눠 그리는 것이 그래프의 핵심입니다.

환불 Agent는 어떻게 그리나요?

꼭 지켜야 할 순서는 코드 엣지로, 판단이 필요한 부분만 LLM에게 맡깁니다.

주문 조회는 늘 첫 칸이라 LLM이 깜빡하고 건너뛸 수 없습니다. LLM 판단 칸에서만 길이 세 갈래로 나뉘고, 어느 길로 가든 답장은 말투 검사 칸을 거쳐야 끝에 닿습니다. 금액 기준처럼 코드로 판단할 수 있는 갈림은 LLM에게 맡기지 않고 조건 엣지 함수에 직접 씁니다.

이 방식은 Agent와 워크플로의 중간쯤입니다. 순서가 정해진 부분은 워크플로처럼 코드가 정하고 판단이 필요한 부분만 Agent처럼 LLM이 고릅니다. 모든 것을 LLM에게 맡기는 반복문보다 덜 유연하지만 지켜야 할 규칙은 반드시 지켜집니다.

도중에 멈췄다가 이어 갈 수도 있나요?

checkpointer를 붙이면 칸을 하나 지날 때마다 상태가 저장되어 이어 갈 수 있습니다.

그래프를 실행할 때 checkpointer를 붙이면 노드 하나가 끝날 때마다 그때의 상태를 저장합니다. 저장은 대화방 번호(thread_id)별로 따로 됩니다. 같은 번호로 다시 부르면 지난 상태를 불러와 대화를 이어 가고 실행 중 오류가 나도 마지막으로 저장한 칸부터 다시 시작합니다.

개발할 때는 메모리에 저장하는 InMemorySaver를 쓰고 서비스에서는 SQLite나 Postgres에 저장하는 checkpointer를 씁니다. 메모리 저장은 서버가 꺼지면 함께 사라집니다. 저장해 둔 상태는 사람이 승인할 때까지 멈춰 기다리는 데도 쓰입니다.

코드로 쓰면 어떻게 되나요?

상태를 정하고 노드를 더한 뒤 엣지로 이어 컴파일합니다.

from typing import Literal
from langgraph.graph import StateGraph, START, END, MessagesState
from langgraph.checkpoint.memory import InMemorySaver

# ① 상태: 메시지 목록에 환불 정보 칸을 더한다
class RefundState(MessagesState):
    order: dict
    amount: int

def lookup_order(state: RefundState):      # 노드는 바꿀 부분만 돌려준다
    order = orders.find_from_text(state["messages"][-1].content)
    return {"order": order, "amount": order["price"]}

def decide(state: RefundState):            # LLM 판단
    return {"messages": [llm.invoke(state["messages"])]}

# ② 조건 엣지: 금액은 코드로, 나머지는 LLM 응답으로 고른다
def route(state: RefundState) -> Literal["escalate", "refund", "draft"]:
    if state["amount"] > 100_000:
        return "escalate"
    return "refund" if wants_refund(state["messages"][-1]) else "draft"

g = StateGraph(RefundState)
for name, fn in [("lookup", lookup_order), ("decide", decide),
                 ("escalate", escalate), ("refund", do_refund),
                 ("draft", draft_reply), ("tone", check_tone)]:
    g.add_node(name, fn)
# ③ 엣지로 순서를 정한다
g.add_edge(START, "lookup")
g.add_edge("lookup", "decide")
g.add_conditional_edges("decide", route)
g.add_edge("refund", "tone")
g.add_edge("draft", "tone")
g.add_edge("escalate", END)
g.add_edge("tone", END)
# ④ checkpointer 를 붙여 컴파일한다
app = g.compile(checkpointer=InMemorySaver())
app.invoke({"messages": [("user", "주문 A-1042 환불해 주세요")]},
           {"configurable": {"thread_id": "ticket-77"}})
  1. MessagesState는 메시지 목록 칸이 이미 들어 있는 상태입니다. 노드가 {"messages": [...]}를 돌려주면 목록 끝에 붙고 다른 칸은 돌려준 값으로 바뀝니다.
  2. 조건 엣지 함수는 다음 노드 이름을 돌려줍니다. 10만 원 기준처럼 코드로 판단할 수 있는 것은 LLM에게 묻지 않습니다.
  3. lookup이 START 바로 다음이라 주문 조회는 건너뛸 수 없습니다. 환불과 답장 초안은 모두 tone을 거쳐야 끝납니다.
  4. thread_id별로 상태가 저장됩니다. 같은 번호로 다시 부르면 이어서 실행합니다.

코드는 langgraph 1.2 기준입니다. orders·llm·escalate 같은 함수는 예시라 줄였습니다. LLM 판단 칸에 도구가 필요하면 도구를 실행하는 노드(ToolNode)와 조건 엣지(tools_condition)를 더해 맨 위 그림의 두 칸 구조를 LLM 판단 칸에 넣습니다.
