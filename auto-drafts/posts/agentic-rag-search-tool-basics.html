검색을 LLM에게 맡기면 무엇이 달라질까요?

사내 챗봇에 "고마워!"라고만 써도 규정 문서를 검색하고 "작년에 바뀐 숙박비"를 물으면 엉뚱한 조항을 가져온 뒤 그대로 답합니다. 질문이 오면 무조건 한 번 검색하는 구조라서 생기는 일입니다. 검색을 할지, 다시 할지를 LLM이 정하게 하면 어떻게 될까요?

무조건 한 번 검색하면 무엇이 문제인가요?

검색이 필요 없을 때도 하고 빗나가도 다시 하지 않습니다.

앞 글의 RAG는 질문이 오면 질문 문장을 그대로 검색어로 써서 한 번 찾은 뒤 그 결과를 붙여 LLM을 부릅니다. 순서가 코드에 고정된 워크플로입니다. 단순하고 빠르지만 두 가지 약점이 있습니다.

첫째, 인사말이나 계산처럼 검색이 필요 없는 질문에도 검색하고 쓸모없는 청크를 붙입니다. 둘째, 검색이 빗나가도 프로그램은 그것을 알 수 없어서 그대로 답하게 합니다. 사람이라면 검색어를 바꿔 다시 찾았을 텐데 말입니다.

검색을 도구로 바꾸면 어떻게 움직이나요?

LLM이 검색이 필요한지 정하고 검색어도 직접 씁니다. 부족하면 다시 찾습니다.

검색을 도구로 주면 Agent 반복문 그대로 움직입니다. LLM이 질문을 읽고 검색이 필요하다고 판단하면 검색 도구를 부탁합니다. 결과를 읽고 부족하면 검색어를 바꿔 다시 부탁합니다. 충분하면 답을 씁니다. 이렇게 Agent가 검색을 도구로 쓰는 방식을 Agentic RAG라고 합니다.

LLM이 검색어를 직접 쓴다는 점이 생각보다 큽니다. 사용자는 "작년에 바뀐 그거"처럼 말하지만 LLM은 "숙박비 개정 이력"처럼 문서에 있을 법한 말로 바꿔 찾습니다. 질문 하나를 여러 번, 다른 말로 검색할 수 있게 된 것이 가장 큰 차이입니다.

검색이 필요 없는 질문에는 어떻게 하나요?

LLM이 도구를 부르지 않고 바로 답합니다.

도구는 LLM이 필요할 때만 부르므로 인사말이나 앞 대화에 이미 답이 있는 질문에는 검색하지 않습니다. 반대로 검색해야 할 때 하지 않는 실수도 생깁니다. LLM이 자기가 아는 내용이라고 여기고 일반적인 답을 쓰는 경우입니다.

그래서 도구 설명과 system 지시에 언제 검색해야 하는지를 분명히 적습니다. "회사 규정·절차·금액에 관한 질문은 반드시 이 도구로 확인한 뒤 답한다"처럼 씁니다. 규정 질문인데 검색 없이 답했다면 지어낸 답일 가능성이 높습니다.

도구는 어떻게 정의하나요?

검색어와 함께 범위를 좁힐 값을 받고 결과마다 출처를 붙여 돌려줍니다.

search_policies 도구 정의 (줄임)
"name": "search_policies", "description": "사내 규정(출장·휴가·보안·구매)을 검색한다. 규정·절차·금액에 관한 질문은 반드시 먼저 이 도구로 확인한다. 결과가 질문과 맞지 않으면 다른 낱말로 다시 검색한다.", "input_schema": { "properties": { "query": { "type": "string", "description": "문서에 있을 법한 낱말" }, "category": { "enum": ["출장", "휴가", "보안", "구매"] } }, "required": ["query"] }

query 설명에 "문서에 있을 법한 낱말"이라고 적어 두면 LLM이 사용자의 말투를 그대로 옮기지 않고 검색어를 다듬습니다. category 같은 값으로 범위를 좁히게 하면 엉뚱한 문서가 섞이는 일이 줄어듭니다.

결과는 청크마다 출처와 함께 돌려주되 몇 개만 돌려줍니다. 도구 결과는 이후 모든 요청에 다시 실려 가기 때문입니다. 아무것도 못 찾았을 때는 빈 목록 대신 "검색 결과 없음. 다른 낱말로 다시 검색해 보세요"라고 돌려주면 LLM이 다음 행동을 고르기 쉽습니다.

무엇을 조심해야 하나요?

검색이 끝없이 늘어나는 것, 그리고 비용과 대기 시간입니다.

무조건 한 번 검색검색을 도구로
LLM 호출1번검색 횟수 + 1번
검색 필요 없는 질문그래도 검색바로 답
첫 검색이 빗나가면그대로 답다른 낱말로 다시
답이 나오는 시간일정함질문마다 다름

검색을 한 번 더 할 때마다 LLM 호출도 한 번 더 늘어서 비용과 대기 시간이 함께 늡니다. LLM이 같은 검색을 되풀이하는 일도 생기므로 반복 한도를 꼭 둡니다. 검색 횟수만 따로 세어 세 번을 넘으면 "지금까지 찾은 것으로 답하라"는 결과를 돌려주는 방법도 씁니다.

질문이 거의 늘 검색을 필요로 하고 빨리 답해야 하는 서비스라면 무조건 검색하는 쪽이 낫습니다. 질문이 다양하고 정확도가 더 중요하면 검색을 도구로 줍니다. 두 방식을 섞어, 첫 검색은 늘 하고 다시 찾을지만 LLM에게 맡기는 구성도 흔합니다.

코드로 쓰면 어떻게 되나요?

앞 글의 검색 함수를 도구로 감싸 Agent 반복문에 넣습니다.

import chromadb

docs = chromadb.PersistentClient(path="./kb").get_collection("policies")
MAX_SEARCH = 3
searches = 0

def search_policies(query: str, category: str | None = None) -> str:
    global searches
    searches += 1
    # ① 검색이 너무 많으면 멈추라고 알린다
    if searches > MAX_SEARCH:
        return "검색 한도에 닿았습니다. 지금까지 찾은 내용으로 답하세요."
    # ② 범위를 좁힐 값이 있으면 메타데이터로 거른다
    where = {"category": category} if category else None
    hits = docs.query(query_texts=[query], n_results=3, where=where)
    if not hits["documents"][0]:
        # ③ 빈 결과 대신 다음 행동을 알려 준다
        return "검색 결과 없음. 다른 낱말로 다시 검색해 보세요."
    # ④ 청크마다 출처를 붙여 돌려준다
    return "\n".join(
        f'[{m["source"]}] {d}'
        for d, m in zip(hits["documents"][0], hits["metadatas"][0]))
  1. LLM이 같은 검색을 되풀이해도 비용이 끝없이 늘지 않게 검색 횟수에 따로 한도를 둡니다. 한도에 닿으면 실패 대신 다음 행동을 글로 알려 줍니다.
  2. 저장할 때 청크마다 category를 메타데이터로 넣어 두었다면 검색 범위를 좁힐 수 있습니다.
  3. 빈 목록을 돌려주면 LLM은 무엇이 잘못됐는지 모릅니다. 다시 검색하라는 안내를 붙입니다.
  4. 답에 근거를 적을 수 있도록 결과마다 source를 앞에 붙입니다.

이 함수를 input_schema와 함께 도구 목록에 넣고 Agent 반복문에서 tool_use가 오면 이 함수를 부르게 하면 됩니다. 검색 횟수(searches)는 질문마다 0으로 되돌립니다.
