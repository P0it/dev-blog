노트북에서 돌던 Agent를 서비스로 내보내려면 무엇이 더 필요할까요?

터미널에서 잘 돌던 Agent를 사내에 공개했더니 첫날부터 일이 터집니다. 답이 나오기까지 20초 동안 화면이 멈춰 있고 두 사람의 대화가 섞이고, 서버가 재시작되자 승인을 기다리던 주문이 사라졌습니다. 월말에는 예상의 세 배인 요금이 청구됩니다. Agent를 여러 사람이 쓰는 서비스로 만들 때 더해야 할 것들을 봅니다.

사용자 앞에는 무엇을 두나요?

Agent를 감싼 API 서버를 두고 진행 상황을 조각으로 흘려보냅니다.

Agent는 여러 번 반복하느라 답이 나오기까지 수십 초가 걸리기도 합니다. 그동안 빈 화면을 보여 주면 사용자는 고장 난 줄 압니다. 그래서 API 서버는 결과를 한 번에 돌려주지 않고 진행 상황과 답의 글자를 나오는 대로 흘려보냅니다. LLM 답을 받을 때와 같은 스트리밍 방식인 SSE(Server-Sent Events)를 씁니다.

흘려보낼 것은 두 종류입니다. "주문 내역 확인 중"처럼 Agent가 어떤 도구를 쓰는지 알려 주는 상태 조각과, LLM이 쓰는 답의 글자 조각입니다. 사용자는 Agent가 일하는 모습을 보면 오래 걸려도 기다립니다.

여러 사람이 쓰면 무엇이 달라지나요?

사람마다, 대화방마다 상태를 나누고 그 상태를 서버 밖 저장소에 둡니다.

혼자 쓸 때는 대화 기록을 프로그램 안에 들고 있으면 됐습니다. 여러 사람이 쓰면 사람마다, 대화방마다 상태를 나눠야 합니다. 대화방 번호를 그대로 믿으면 남의 번호를 넣어 남의 대화를 볼 수 있으니, 대화방 번호는 로그인한 사용자와 묶어서 확인합니다.

상태는 서버 메모리 대신 Postgres 같은 저장소에 둡니다. 서버가 재시작돼도 승인을 기다리던 Agent가 사라지지 않고 서버를 여러 대로 늘려도 어느 서버든 같은 상태를 불러옵니다. 장기 기억도 사용자별로 나눠 저장합니다.

LLM API가 느리거나 멈추면요?

시간 제한과 재시도를 두고 계속 실패하면 다른 모델로 넘깁니다.

상황대비
잠깐의 과부하 (429·529)간격을 늘려 가며 재시도. 공식 SDK에 기본으로 들어 있음
답이 너무 오래 걸림호출마다 시간 제한, 요청 전체에도 제한
한 회사 API 장애다른 회사 모델로 넘기기 (fallback)
도구 서버 장애오류를 결과로 돌려 LLM이 다른 길을 고르게
사용자 한 명이 과하게 씀사용자별 호출·토큰 한도

LLM API도 바깥 서비스라 느려지거나 멈춥니다. 공식 SDK는 과부하 오류에 몇 번 자동으로 재시도하지만 요청 전체에 시간 제한을 두는 것은 우리 몫입니다. LangChain middleware에는 다른 모델로 넘기는 것도 있어서 한 회사 API가 장애일 때 다른 회사 모델로 이어 갈 수 있습니다.

사용자별 한도도 필요합니다. 반복 한도가 Agent 하나의 폭주를 막는다면, 사용자별 한도는 한 사람이 서비스 전체 비용을 다 쓰는 일을 막습니다.

배포하고 나서는 무엇을 보나요?

비용·시간·실패율을 대시보드로 보고 실패한 대화를 평가 질문 묶음에 더합니다.

배포하면 trace가 실제 사용자 요청에서 쌓입니다. 요청 하나당 토큰·LLM 호출 수·걸린 시간·실패율을 날마다 보고 비용이 튀거나 실패가 늘면 trace를 열어 원인을 찾습니다.

사용자가 싫어요를 누른 대화나 실패한 대화는 평가 질문 묶음에 더합니다. 프롬프트·도구·모델을 바꾸는 변경은 그 질문 묶음을 통과해야 배포하게 CI에 넣습니다. Agent는 한 번 만들고 끝나는 기능이 아닙니다. 기록을 보고 고치기를 되풀이하며 나아지는 서비스입니다.

코드로 쓰면 어떻게 되나요?

로그인 확인, 대화방 묶기, 진행 상황 흘려보내기를 하는 엔드포인트 하나입니다.

import json
from fastapi import Depends, FastAPI
from fastapi.responses import StreamingResponse
from langgraph.checkpoint.postgres import PostgresSaver

app = FastAPI()
# ① 상태는 서버 밖 저장소에. 재시작·여러 대에서도 이어진다
saver = PostgresSaver.from_conn_string(DB_URL)
agent = build_agent(checkpointer=saver)       # create_agent(...) 로 만든 Agent

@app.post("/chat")
async def chat(body: dict, user=Depends(current_user)):
    # ② 대화방 번호를 로그인한 사용자와 묶는다
    thread = f"{user.id}:{body['thread_id']}"
    config = {"configurable": {"thread_id": thread}}
    msg = {"messages": [{"role": "user", "content": body["text"]}]}

    async def events():
        # ③ 도구 진행 상황과 답의 글자를 나오는 대로 흘려보낸다
        async for kind, data in agent.astream(
                msg, config, stream_mode=["updates", "messages"]):
            if kind == "updates":
                yield sse("status", describe(data))       # "주문 내역 확인 중"
            elif kind == "messages":
                chunk, _ = data
                if chunk.content:
                    yield sse("token", chunk.content)
        yield sse("done", "")

    return StreamingResponse(events(), media_type="text/event-stream")

def sse(event, data):
    # ④ SSE 형식: event 줄, data 줄, 빈 줄
    return f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"
  1. 개발 때 쓰던 메모리 저장 대신 Postgres에 상태를 저장합니다. 승인을 기다리던 Agent도 재시작 뒤에 그대로 이어집니다.
  2. 사용자가 보낸 대화방 번호 앞에 로그인한 사용자 id를 붙여, 남의 대화방을 불러올 수 없게 합니다.
  3. stream_mode로 단계가 끝날 때마다 오는 소식(updates)과 LLM의 글자 조각(messages)을 함께 받습니다. describe는 도구 이름을 사용자가 읽을 문장으로 바꾸는 함수입니다.
  4. SSE는 event:와 data: 줄 뒤에 빈 줄을 두는 단순한 글 형식입니다. 브라우저의 EventSource나 fetch 스트림으로 받습니다.

current_user·build_agent·DB_URL은 예시라 줄였습니다. 실제로는 여기에 사용자별 한도, 요청 전체 시간 제한, 오류를 event: error로 알리는 처리를 더하고 Docker 이미지로 묶어 배포합니다. 시리즈는 여기까지입니다. LLM이 글만 쓰는 프로그램이라는 데서 출발해, 그 글을 실행하는 프로그램과 도구, 기억과 검색, 흐름과 승인, 연결과 보안, 평가와 배포까지 하나씩 얹었습니다.
