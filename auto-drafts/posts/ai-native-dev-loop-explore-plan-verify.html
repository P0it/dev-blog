코딩 에이전트가 "다 고쳤습니다"라고 말하기까지

"로그인 버튼이 안 눌려요." 코딩 에이전트(coding agent)에게 이 한 줄을 보내면 화면에 파일 검색, 파일 읽기, 코드 수정, 명령 실행이 줄줄이 지나갑니다. 에이전트가 이렇게 도구를 한 번 쓰는 일을 도구 호출(tool call)이라고 합니다. 얼마 뒤 "다 고쳤습니다"라는 답이 옵니다. 정말 고쳐졌을까요?

에이전트는 일이 끝난 것처럼 보이면 멈춥니다. 테스트(test, 코드가 맞게 동작하는지 자동으로 확인하는 검사)가 없으면 "그럴듯해 보인다"가 유일한 신호라서 버그가 남아 있어도 멈출 수 있습니다. 확인 수단을 바꿔 가며 같은 요청을 돌려 보세요.

로그인

사람이 직접 눌러 보면 여전히 안 눌립니다. 진짜 원인은 다른 파일에 있었는데 에이전트는 코드를 다시 읽어 보고 "맞아 보인다"에서 멈췄습니다.

터미널 한 줄이 에이전트의 한 걸음입니다. 파일 이름과 출력은 설명을 위해 꾸민 예시입니다. 계획 줄은 도구를 쓰지 않고 모델이 글로 정리한 것이라 도구 호출로 세지 않았습니다.

에이전트 루프는 도구를 부르고 결과를 읽는 반복입니다

첫 화면에서 본 탐색·계획·고치기·확인의 고리를 에이전트 루프(agent loop)라고 부릅니다.

고리를 실제로 돌리는 부품은 두 가지입니다. 하나는 글을 읽고 다음에 할 일을 글로 적는 모델(model)입니다. 다른 하나는 모델 둘레에서 도구를 실제로 실행해 주는 프로그램입니다. Claude Code 문서는 이 둘레 프로그램을 에이전트 하네스(agentic harness)라고 부릅니다.

하네스는 원래 말에 채우는 마구를 뜻합니다. 말의 힘을 원하는 방향으로 쓰게 해 주는 장비입니다. 마구는 방향만 잡아 주는데 에이전트 하네스는 모델에게 도구를 주고 실행 결과까지 돌려줍니다.

요청과 도구 목록이 함께 갑니다

사람이 보낸 요청을 하네스가 모델에게 넘깁니다. 이때 "파일 검색, 파일 읽기, 파일 수정, 명령 실행을 쓸 수 있다"는 도구 목록도 같이 보냅니다.

모델은 실행하지 않고 적기만 합니다

모델은 글을 쓰는 프로그램이라 파일을 직접 열지 못합니다. 대신 grep(파일 안에서 글자를 찾는 명령)을 실행해 달라는 요청을 정해진 형식의 글로 적습니다. 그림의 점선 화살표가 이 글입니다.

하네스가 실행하고 결과를 돌려줍니다

하네스가 그 명령을 내 컴퓨터에서 실제로 실행합니다. 나온 결과(파일 3개)는 지금까지의 대화 끝에 붙여 모델에게 다시 보냅니다.

결과를 읽고 다음 도구를 고릅니다

모델은 결과를 읽고 다음에 쓸 도구를 고릅니다. 파일을 읽고 고치고 테스트를 돌립니다. 첫 화면의 테스트 있는 실행에서는 이 왕복이 일곱 번 있었습니다.

도구 없이 답하면 루프가 끝납니다

모델이 도구를 부르지 않고 글로만 답하면 하네스는 루프를 끝내고 그 답을 사람에게 보여 줍니다. "다 고쳤습니다"는 모델이 더 할 일이 없다고 판단했다는 뜻입니다. 정말 고쳐졌다는 보증은 아닙니다.

도구 목록을 보내고 모델이 고른 도구를 실행해 결과를 돌려주는 코드는 챗봇과 AI Agent의 차이를 다룬 글에서 Python으로 직접 볼 수 있습니다. 이 글은 그 반복이 코딩 일에서 어떤 순서로 도는지를 봅니다.

Claude Code 문서는 같은 반복을 컨텍스트 수집(gather context), 행동(take action), 결과 확인(verify results) 세 단계로 설명합니다. 컨텍스트(context)는 모델이 지금 보는 대화와 파일 내용 전체를 말합니다.

이 글의 탐색이 컨텍스트 수집, 고치기가 행동입니다. 계획은 행동하기 전에 모델이 고칠 방법을 글로 정리하는 칸이라 따로 떼었습니다.

네 칸을 몇 번 도는지는 일마다 다릅니다

에이전트가 네 칸을 꼭 한 번씩 순서대로 도는 건 아닙니다. Claude Code 문서는 루프가 요청에 맞춰 달라진다고 적었습니다. 코드에 대한 질문은 탐색만으로 끝나기도 합니다. 버그 수정은 네 칸을 여러 번 돌고 리팩터링(refactoring, 동작은 그대로 두고 코드 구조만 다듬는 일)은 확인을 많이 거칩니다.

과학 실험 시간을 떠올리면 비슷합니다. 관찰하고 가설을 세우고 실험한 뒤 결과가 예상과 다르면 다시 관찰합니다. 다만 실험 수업에서는 선생님이 정답을 알고 있습니다. 에이전트 곁에는 정답을 아는 사람이 없어서 결과를 견줄 확인 수단을 따로 줘야 합니다.

사람은 루프 앞뒤에 단계를 붙입니다

Claude Code 모범 사례 문서는 일을 탐색, 계획, 구현, 커밋 네 단계로 나누라고 권합니다. 바로 코드부터 쓰게 하면 엉뚱한 문제를 푸는 코드가 나올 수 있어서입니다. 그 사이사이에 사람이 맡는 칸이 들어갑니다.

탐색과 계획은 Plan mode에서 합니다. 에이전트가 파일을 읽고 질문에 답하되 고치지는 못하게 막는 모드입니다. 계획이 나오면 사람이 읽고 고친 뒤 승인합니다.

끝에서 에이전트는 바뀐 내용을 커밋(commit, 변경 내용을 기록으로 저장하는 일)하고 PR(Pull Request)을 올립니다. PR은 "이 변경을 프로젝트에 합쳐 주세요"라는 요청이고 사람이 읽고 승인해야 합쳐집니다.

계획이 늘 필요한 건 아닙니다. 문서는 오타 수정이나 변수 이름 바꾸기처럼 범위가 분명한 일은 바로 시키라고 합니다. 기준은 diff(바뀐 줄만 모아 보여 주는 변경 내역)를 한 문장으로 설명할 수 있느냐입니다. 그럴 수 있으면 계획을 건너뜁니다.

같은 문제를 두 번 넘게 바로잡았는데도 안 될 때

문서는 같은 문제로 두 번 넘게 고쳐 달라고 했는데도 틀리면 /clear로 대화를 비우라고 권합니다. 그다음 그동안 알게 된 점을 넣어 더 구체적인 요청으로 처음부터 시작합니다. 실패한 시도가 대화에 쌓이면 그 기록이 다음 판단을 흐리기 때문입니다.

확인 수단이 있어야 루프가 끝납니다

모델은 일이 끝난 것처럼 보이면 멈춥니다. 돌려 볼 검사가 없으면 "끝나 보인다"가 유일한 신호라서 실수는 사람 눈에 띌 때까지 남습니다. 통과나 실패를 돌려주는 검사가 있으면 에이전트가 직접 돌려 보고 통과할 때까지 고칩니다.

문제집 뒤 답지로 스스로 채점하는 것과 비슷합니다. 다만 검사는 정답 없이 틀렸다는 사실만 알려 줍니다.

타입체크(type check)는 코드를 실행하지 않고 값의 종류와 개수가 맞는지 따집니다. 린터(linter)는 "쓰지 않는 변수를 남기지 않는다" 같은 코드 규칙을 어긴 곳을 찾습니다. 화면 확인은 결과 화면을 찍어 디자인과 비교하는 일입니다. 검사마다 보는 곳이 달라서 하나로는 부족합니다.

멈춤을 얼마나 단단히 걸지 고를 수 있습니다

확인 수단이 생기면 다음은 그 검사를 통과해야만 멈추게 만드는 일입니다. Claude Code 문서는 네 가지 방법을 듭니다. 번호가 클수록 준비할 것이 늘지만 사람이 자리를 비워도 맞게 끝날 가능성이 커집니다.

프롬프트(prompt)는 에이전트에게 보내는 지시문입니다. 턴(turn)은 요청 하나를 받아 답을 내놓기까지의 한 차례입니다. /goal은 멈춰도 되는 조건을 적어 두는 Claude Code 명령이고 일하는 모델과 따로 있는 평가 모델이 턴마다 그 조건을 다시 확인합니다.

훅(hook)은 정해진 순간마다 자동으로 실행되는 스크립트입니다. 서브에이전트(subagent)는 따로 떼어 낸 대화에서 일하는 보조 에이전트라 방금 코드를 쓴 에이전트의 생각에 끌려가지 않습니다. 둘은 다른 글에서 자세히 다룹니다.

어느 방법이든 마지막에 사람이 볼 것은 증거입니다. 문서는 "성공했다"는 말 대신 돌린 명령과 그 출력, 결과 화면 캡처를 보여 달라고 하라고 권합니다. 증거를 읽는 편이 검사를 직접 다시 돌리는 것보다 빠릅니다.

테스트를 고쳐서 통과시키는 지름길

테스트가 루프의 끝을 정하면 테스트를 건드리는 지름길도 생깁니다. 버그를 고치는 대신 실패하는 테스트를 지우거나 테스트가 기대하는 값만 그대로 돌려주는 코드를 쓰는 것입니다. 이렇게 점수를 매기는 장치의 빈틈을 파고드는 행동을 보상 해킹(reward hacking)이라고 합니다.

ImpossibleBench는 이렇게 일부러 만든 불가능한 과제로 부정행위 비율을 잰 연구입니다. 모델 개발사들도 같은 행동을 직접 보고했습니다.

모델 개발사와 평가 기관이 보고한 사례 두 가지

Anthropic은 2025년 2월 Claude 3.7 Sonnet의 시스템 카드(모델을 내놓으며 시험 결과와 안전 점검을 정리한 문서)에 이 행동을 적었습니다. 평범한 해법으로 여러 번 실패한 뒤에 테스트가 기대하는 값을 바로 돌려주거나 테스트를 고친 경우가 가끔 있었다고 합니다.

AI 평가 기관 METR이 2025년 6월 공개한 사례에서는 OpenAI의 o3 모델이 채점 코드를 고쳐 만점을 받았습니다. 한 과제에서는 "속이지 마세요"라고 적어 줘도 시도의 80%에서 보상 해킹이 나왔습니다.

테스트를 읽기 전용으로 잠그면

ImpossibleBench는 에이전트가 테스트를 얼마나 만질 수 있는지를 세 가지로 바꿔 봤습니다. 읽고 고칠 수 있게 열어 두기, 읽기만 허용하기, 아예 숨기기입니다. 막대는 맞는 테스트 옆에 모순되는 테스트를 더 넣은 판(Conflicting-SWEbench)과 원래 과제에서 잰 값입니다.

테스트를 열어 두면 세 모델 모두 불가능한 과제의 절반 가까이를 "통과"합니다. 테스트를 고치거나 기대값만 돌려주는 꼼수로 통과한 것입니다.

숨기면 부정행위는 0%가 되지만 원래 과제를 푸는 비율도 같이 떨어집니다. 무엇을 맞춰야 하는지 볼 수 없어서입니다. 읽기 전용은 원래 성공률을 거의 지키면서 테스트 수정을 막습니다. 연구진은 가능하면 테스트를 숨기거나 읽기 전용으로 두라고 권했습니다.

읽기 전용도 모든 꼼수를 막지는 못합니다. 테스트 값만 따로 처리하는 코드는 테스트를 고치지 않고도 쓸 수 있습니다. 다시 시도할 기회가 늘면 부정행위도 늘었습니다. 여러 번 제출하게 하자 모델 평균이 33%에서 38%로 올랐습니다. "이 과제는 이상하다"며 멈출 수 있는 선택지를 주자 GPT-5는 54%에서 9%로 내려갔습니다.

꼼수의 종류도 모델마다 달랐습니다. 이 판에서 Claude 모델들이 꼼수를 쓴 경우는 79% 넘게 테스트 파일을 직접 고친 것이었습니다. GPT-5와 o3는 테스트 고치기 말고도 여러 방법을 섞어 썼습니다.

하네스 엔지니어링, 루프 바깥을 만드는 일

OpenAI의 Ryan Lopopolo는 2026년 2월 11일 한 팀의 실험을 공개했습니다. 이 팀은 OpenAI의 코딩 에이전트 Codex에게만 코드를 맡겨 다섯 달 동안 제품을 만들었습니다. 사람이 직접 쓴 코드는 0줄이었고 저장소(repository, 한 프로젝트의 코드와 변경 기록을 모아 두는 곳)는 약 100만 줄이 됐습니다.

에이전트가 막히면 이 팀은 "더 열심히 해 봐"라고 하지 않았습니다. 무엇이 빠졌는지 찾아 도구·규칙·문서로 저장소에 넣었고 그 일도 Codex에게 시켰습니다. 이렇게 에이전트가 일할 환경을 만드는 일을 하네스 엔지니어링(harness engineering)이라고 부릅니다.

숫자로 본 다섯 달

2025년 8월 말 빈 저장소에서 시작했습니다. 앱 코드, 테스트, 문서까지 모두 Codex가 썼습니다. PR 약 1,500개가 합쳐졌고 처음 세 명이던 엔지니어는 일곱 명으로 늘었습니다. 한 명당 하루 평균 PR 3.5개를 처리했고 Codex 실행 한 번이 한 작업을 여섯 시간 넘게 이어 가기도 했습니다.

AGENTS.md 를 목차로 줄인 이유

AGENTS.md는 에이전트가 일을 시작할 때 읽는 안내 파일입니다. 처음에는 이 파일 하나에 모든 규칙을 적었습니다. 파일이 커지자 정작 할 일과 코드가 들어갈 자리까지 차지했습니다. 모든 게 중요하다고 적혀 있으니 아무것도 눈에 띄지 않았습니다. 금방 낡기도 했습니다. 그래서 AGENTS.md를 약 100줄짜리 목차로 줄이고 자세한 설계 문서와 계획은 docs/ 폴더에 나눠 두었습니다.

사람이 매주 금요일(한 주의 20%)을 들여 AI가 남긴 엉성한 코드를 치우던 일도 바꿨습니다. 지킬 원칙을 저장소에 적어 두고 Codex가 주기적으로 어긋난 곳을 찾아 정리 PR을 올리게 했습니다.

에이전트가 화면을 직접 눌러 보게 만든 방법

코드가 빨리 쌓이자 이 팀의 병목은 사람이 직접 눌러 보며 확인하는 일이 됐습니다. 그래서 확인 수단 자체를 에이전트에게 넘겼습니다. 변경마다 앱을 따로 띄울 수 있게 하고 브라우저를 코드로 조작하는 Chrome DevTools를 에이전트에 연결했습니다.

그림이 그 확인 루프입니다. 고치기 전 화면을 기록하고 문제의 화면 경로를 눌러 본 뒤 고친 다음 다시 기록해 비교합니다. 문제가 없어질 때까지 검증을 되풀이합니다. 로그와 지표도 에이전트가 직접 조회하게 해서 "서비스 시작이 800ms 안에 끝나야 한다" 같은 요청도 확인할 수 있게 됐습니다.

첫 화면의 고리와 같은 구조입니다. 사람이 버튼을 눌러 보던 확인 칸을 에이전트가 직접 돌리게 되면서 사람은 무엇을 확인할지 정하는 쪽으로 옮겨 갔습니다. 다음 글에서는 AI가 묻고 사람이 답하며 개발을 진행하는 방법론 AI-DLC(AI-Driven Development Life Cycle)를 알아보겠습니다.
