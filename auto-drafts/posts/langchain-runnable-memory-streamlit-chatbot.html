AI Service Track 10

Streamlit에 올린 LangChain 챗봇이 대화를 잊는 이유

배달 앱 고객센터 챗봇에 민지가 "떡볶이가 식어서 왔어요. 환불되나요?"라고 묻습니다. 답을 받은 뒤 "그럼 언제 들어와요?"라고 다시 묻습니다. 두 번째 질문에 답하려면 챗봇은 첫 질문을 알고 있어야 합니다.

LangChain으로 만든 챗봇은 스스로 기억하지 않습니다. 질문은 화면에서 대화 기록 서랍을 거쳐 체인(프롬프트·모델·출력 정리를 이어 붙인 LangChain의 처리 줄)으로 가는데, 그 길에서 대화가 사라지는 곳이 세 군데 있습니다. ①과 ②를 함께 쓸 때 생기는 함정도 따로 봅니다. 아래 그림의 빨간 글씨가 잊는 곳이고 그 밑 초록 글씨가 남기는 방법입니다.

① Streamlit은 메시지마다 app.py를 처음부터 다시 실행합니다

Streamlit은 파이썬 파일 하나로 웹 화면을 만드는 도구입니다. 입력칸에 메시지를 보내거나 버튼을 누르면 Streamlit은 app.py를 첫 줄부터 마지막 줄까지 다시 실행합니다. 그래서 평범한 변수에 넣은 대화는 매번 처음 값으로 돌아갑니다.

장면이 바뀔 때마다 막을 처음부터 다시 올리는 연극과 비슷합니다. 무대 위 소품(일반 변수)은 매번 제자리로 돌아가고 무대 뒤 소품실(st.session_state)에 둔 것만 남습니다. 연극과 달리 실제 화면은 통째로 지워지지 않고 바뀐 부분만 다시 그려집니다.

실행 1 · 페이지를 연 순간

처음 페이지를 열면 app.py가 위에서 아래로 한 번 실행됩니다. messages는 빈 목록이고 화면에는 입력칸만 있습니다.

app.py · 실행 1번째
  1. import streamlit as st
  3. messages = []
  4. prompt = st.chat_input("무엇을 도와드릴까요?")
  5. if prompt:
  6. messages.append(prompt)
  7. for m in messages:
  8. st.chat_message("user").write(m)

② 모델 대신 손님별 서랍이 대화를 기억합니다

화면이 대화를 들고 있어도 모델은 여전히 모릅니다. 모델 API는 요청 하나만 보고 답한 뒤 잊어버려서 지난 호출을 기억하지 못합니다. 이 성질은 앞에서 쓴 글에 자세히 있습니다. 그래서 챗봇은 대화를 서랍에 모아 두었다가 모델을 부를 때마다 꺼내 프롬프트에 함께 넣습니다.

서랍마다 손님 이름표를 붙여 두면 손님이 여럿이어도 섞이지 않습니다. LangChain에서는 이 이름표를 session_id라고 부릅니다. 민지 이름표로 부르면 민지 서랍만 열리고 준호 대화는 꺼내지 않습니다.

진짜 서랍과 달리 모델은 꺼낸 기록을 매번 처음부터 다시 읽습니다. 막대 그림처럼 대화가 쌓일수록 한 번에 보내는 메시지가 늘고 그만큼 요금과 시간도 늘어납니다.

# init_chat_model · StrOutputParser import 는 앞과 같습니다
from langchain_core.chat_history import (
    InMemoryChatMessageHistory,
)
from langchain_core.prompts import (
    ChatPromptTemplate, MessagesPlaceholder,
)
from langchain_core.runnables.history import (
    RunnableWithMessageHistory,
)

# ① 손님별 서랍장: 없으면 새 서랍을 만든다
store = {}
def get_history(session_id):
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()
    return store[session_id]

prompt = ChatPromptTemplate([
    ("system", "당신은 배달 앱 상담원입니다."),
    # ② 꺼낸 기록이 들어갈 빈칸
    MessagesPlaceholder("history"),
    ("human", "{question}"),
])
model = init_chat_model("openai:gpt-6.1-sol")
chain = prompt | model | StrOutputParser()

chat = RunnableWithMessageHistory(
    # ③ 체인 + 서랍을 여는 함수
    chain, get_history,
    input_messages_key="question",
    history_messages_key="history",
)
# ④ 이름표: 어느 서랍을 열지
minji = {"configurable": {"session_id": "minji"}}
q1 = "떡볶이가 식어서 왔어요. 환불되나요?"
print(chat.invoke({"question": q1}, config=minji))
print(chat.invoke({"question": "그럼 언제 들어와요?"},
                  config=minji))
print(len(store["minji"].messages))

  1. get_history는 이름표를 받아 그 손님의 기록 객체를 돌려주는 함수입니다. 처음 온 손님이면 빈 서랍을 새로 만듭니다. 손님이 여럿이라서 서랍 하나가 아니라 함수를 넘깁니다.
  2. MessagesPlaceholder는 프롬프트 안에 "메시지 여러 개가 들어갈 빈칸"을 만들어 둡니다. 꺼낸 기록이 system 지시와 새 질문 사이에 끼어 들어갑니다.
  3. RunnableWithMessageHistory는 체인을 감싸 서랍 일을 대신합니다. 부르기 전에 기록을 꺼내 빈칸에 끼우고 답이 나오면 질문과 답을 서랍에 넣습니다. input_messages_key는 새 질문이 든 키, history_messages_key는 기록을 넣을 빈칸의 이름입니다.
  4. config는 invoke에 덧붙이는 실행 설정이고 그 안 configurable에 이름표 session_id를 넣는 것이 정해진 모양입니다. 두 번 불렀으니 민지 서랍에는 질문 2개와 답 2개, 모두 4개가 쌓입니다. 노란 경고 줄은 바로 아래에서 설명합니다.

노란 경고가 뜨는 이유. 2026년 LangChain은 이 서랍 일을 LangGraph로 옮겼습니다. LangGraph는 LangChain 팀이 만든, 여러 단계로 움직이는 AI 앱을 짜는 도구입니다. 그 안의 체크포인터(checkpointer)가 대화를 이름표별로 저장하는 서랍장입니다. 이름표를 session_id 대신 thread_id라고 부를 뿐 원리는 같고, 아래 Streamlit 앱이 이 방식을 씁니다.

사용 중단 일정

RunnableWithMessageHistory는 langchain-core 1.3.3(2026-05-05)부터, InMemoryChatMessageHistory는 1.6.4(2026-09-21)부터 사용 중단 예정(deprecated) 경고를 내고 2.0에서 빠질 예정입니다. 수업 자료의 langchain_community ChatMessageHistory도 같은 클래스이고, 이 저장소는 2026-06-19에 보관 처리(archived)돼 더 고쳐지지 않습니다.

①+② 서랍을 app.py 맨 위에 두면 다시 잊습니다

①과 ②를 합칠 때 가장 흔한 실수입니다. 위 코드를 그대로 app.py에 옮기면 서랍장 store = {}도 app.py 안의 평범한 변수가 됩니다. 메시지를 보낼 때마다 서랍장이 새로 만들어지니 민지 서랍에 남는 메시지 수는 2, 2, 2에서 늘지 않습니다.

그래서 무엇을 어디에 둘지는 얼마나 오래 남아야 하느냐로 정합니다. 서버는 app.py를 실행하는 쪽 프로그램이라 탭을 닫아도 계속 켜져 있습니다. @st.cache_resource는 그 서버에 하나만 만들어 모든 탭이 함께 쓰는 보관 장소입니다. 아래 수명 막대는 같은 시간 동안 각 장소에 둔 값이 언제까지 남는지 그린 것입니다.

①+② 화면용 목록은 탭에, 모델용 서랍은 서버에 둡니다

챗봇에는 기억이 두 겹 있습니다. 화면에 말풍선을 다시 그리기 위한 목록과 모델에게 앞 대화를 넣어 주기 위한 서랍입니다. 말풍선 목록과 이름표는 탭마다 따로인 st.session_state에 둡니다.

서랍장은 2026년 방식대로 LangGraph 체크포인터를 씁니다. create_agent는 모델에 도구와 기억을 붙여 주는 LangChain 함수인데, 여기서는 도구 없이 모델과 체크포인터만 묶습니다. 모델 객체와 서랍장은 만드는 데 시간이 들고 모든 손님이 하나를 함께 써도 되니 @st.cache_resource에 둡니다. 손님 구분은 이름표가 맡습니다.

thread_id 값은 설명을 위한 예시입니다. 실제로는 uuid로 만든 긴 문자열입니다.

import uuid
import streamlit as st
from langchain.agents import create_agent
from langchain.chat_models import init_chat_model
from langgraph.checkpoint.memory import InMemorySaver

# ① 서랍장: 처음 한 번만 만들고 모든 탭이 함께 쓴다
@st.cache_resource
def get_agent():
    return create_agent(
        init_chat_model("openai:gpt-6.1-sol"),
        tools=[],
        system_prompt="당신은 배달 앱 상담원입니다.",
        checkpointer=InMemorySaver(),
    )
agent = get_agent()

# ② 이름표와 말풍선 목록: 탭마다 따로
if "thread_id" not in st.session_state:
    st.session_state.thread_id = str(uuid.uuid4())
    st.session_state.messages = []

for m in st.session_state.messages:
    st.chat_message(m["role"]).markdown(m["content"])

# ③ 입력이 있으면 prompt 에 담고 바로 검사
if prompt := st.chat_input("무엇을 도와드릴까요?"):
    msgs = st.session_state.messages
    msgs.append({"role": "user", "content": prompt})
    st.chat_message("user").markdown(prompt)
    config = {"configurable": {
        "thread_id": st.session_state.thread_id}}

    # ④ 새 질문 하나만 보내고 조각마다 내보낸다
    def tokens():
        new = {"messages": [
            {"role": "user", "content": prompt}]}
        stream = agent.stream(
            new, config, stream_mode="messages")
        for chunk, meta in stream:
            if chunk.text:
                yield chunk.text

    with st.chat_message("assistant"):
        answer = st.write_stream(tokens())
    msgs.append({"role": "assistant", "content": answer})

  1. 함수 위 @로 시작하는 줄은 데코레이터(decorator)로, 함수에 기능을 덧붙이는 표시입니다. @st.cache_resource를 붙이면 처음 한 번만 실행하고 그 뒤로는 만들어 둔 객체를 돌려줍니다. 그래서 체크포인터가 메시지마다 새로 생기지 않습니다.
  2. 이름표는 uuid로 만든 겹치지 않는 문자열입니다. 탭을 새로 열면 session_state가 비어 있으니 새 이름표를 받고 다른 서랍을 씁니다. 말풍선 목록도 여기 둡니다.
  3. :=는 값을 변수에 넣으면서 그 값을 바로 검사하는 연산자입니다. prompt = st.chat_input(...)과 if prompt: 두 줄을 한 줄로 쓴 것입니다.
  4. 앞 대화는 체크포인터가 이름표로 찾아 붙이니 보낼 때는 이번 질문 하나만 넣습니다. yield가 든 함수는 값을 한꺼번에 돌려주지 않고 하나씩 내보내는 제너레이터(generator)입니다. st.write_stream이 조각을 화면에 이어 붙이고 다 모인 글을 돌려줍니다(스트리밍 글). 버전은 streamlit 1.67, langgraph 1.2 기준입니다.

메모리 서랍장은 서버를 다시 켜면 비워지고, 탭을 새로고침하면 이름표가 바뀌어 앞 대화를 찾지 못합니다. 손님이 내일 다시 와도 대화를 이어 가야 한다면 로그인한 사용자 아이디를 이름표로 쓰고 데이터베이스에 저장하는 체크포인터로 바꿉니다(에이전트 메모리 글).

③ 담당 체인을 고르는 분기기에서 질문이 빠지는 이유

질문을 먼저 배달·환불·기타 중 한 단어로 분류하고, 그 단어를 보고 담당 체인을 고르는 것을 라우팅(routing)이라고 합니다. 철도의 분기기(선로를 바꾸는 장치)처럼 분류가 끝나야 고르는 함수가 실행됩니다.

이때 체인의 칸과 칸 사이로는 딕셔너리(이름표마다 값을 짝지어 담는 파이썬 자료형) 하나가 수레처럼 실려 갑니다. {"topic": classifier}처럼 딕셔너리를 새로 만들면 거기 적은 키만 수레에 실립니다. 환불 체인은 {question} 칸을 채울 값이 없어 KeyError(딕셔너리에 없는 키를 찾을 때 나는 오류)를 냅니다.

assign은 들어온 수레에 키 하나를 더 싣습니다. 그래서 질문과 분류 결과가 함께 도착합니다. 이 함정은 앞 글에서도 다뤘습니다.

분기기 자체는 이렇게 움직입니다. 질문마다 선로 하나로만 갑니다. 철도와 달리 분류하는 쪽도 모델이라 가끔 틀립니다.

담당마다 모델을 달리 둘 수도 있습니다. 아래 코드는 가벼운 기타 질문을 값싼 Claude Haiku로 보내 요금을 아낍니다.

from langchain_core.runnables import (
    RunnableLambda, RunnablePassthrough,
)
# ... 나머지 import 는 history.py 와 같습니다

classifier = (
    ChatPromptTemplate.from_template(
        # ① 한 단어로만 답하게
        "질문을 배달, 환불, 기타 중 "
        "한 단어로만 분류하세요.\n질문: {question}"
    )
    | init_chat_model("openai:gpt-6-luna")
    | StrOutputParser()
)

def make_chain(role, model_name):
    prompt = ChatPromptTemplate.from_template(
        role + "\n질문: {question}"
    )
    model = init_chat_model(model_name)
    return prompt | model | StrOutputParser()

delivery_chain = make_chain(
    "당신은 배달 지연 담당입니다.",
    "openai:gpt-6.1-sol")
refund_chain = make_chain(
    "당신은 환불 담당입니다. 규정부터 안내하세요.",
    "openai:gpt-6.1-sol")
general_chain = make_chain(
    "당신은 친절한 안내원입니다.",
    "anthropic:claude-haiku-5-5")

# ② 분류 결과를 보고 체인을 돌려준다
def route(info):
    if "배달" in info["topic"]:
        return delivery_chain
    if "환불" in info["topic"]:
        return refund_chain
    return general_chain

full_chain = (
    # ③ question 은 두고 topic 만 더한다
    RunnablePassthrough.assign(topic=classifier)
    | RunnableLambda(route)
)
full_chain.invoke(
    {"question": "떡볶이가 식어서 왔어요. 환불되나요?"}
)
  1. 분류 결과를 코드가 읽어야 하니 답의 모양을 좁힙니다. 그래도 모델이 "환불 문의입니다"처럼 말을 덧붙일 수 있어서 코드 ②의 route에서는 ==(완전히 같은지) 대신 in(들어 있는지)으로 비교합니다. 보기 중 하나만 고르게 하는 Structured Outputs(with_structured_output)을 쓰면 더 튼튼합니다.
  2. route는 답을 만들지 않고 체인을 고르기만 합니다. RunnableLambda는 파이썬 함수를 체인의 한 칸으로 바꿔 줍니다. 함수가 체인을 돌려주면 LangChain이 그 체인을 이어서 실행하니 route는 고르기만 하면 됩니다. LangChain에서 |로 이을 수 있는 칸을 통틀어 Runnable이라고 부릅니다.
  3. assign은 받은 딕셔너리를 그대로 두고 topic 키 하나를 더합니다. 위 수레 그림의 아래 줄입니다.

덧붙여, 답과 추천 질문을 동시에 만들면 얼마나 기다릴까요?

가장 오래 걸리는 일 하나만큼 기다립니다. 챗봇이 답을 보여 주면서 입력칸 아래에 "다음에 물어볼 만한 질문"도 띄운다고 해 봅시다. 체인을 하나씩 차례로 부르면 두 시간을 더한 만큼 걸리고 RunnableParallel로 묶으면 둘이 함께 시작합니다.

화구가 둘인 분식집 주방과 같습니다. 떡볶이와 튀김을 함께 올리면 손님은 늦게 익는 쪽만큼 기다립니다. 다만 화구가 늘어도 재료값은 그대로입니다. 체인을 동시에 돌려도 모델은 두 번 불리고 요금도 두 번 나옵니다.

끝나면 결과는 딕셔너리 하나로 모입니다. 키 이름은 RunnableParallel을 만들 때 붙인 인자 이름입니다.

from langchain.chat_models import init_chat_model
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableParallel
from langchain_core.output_parsers import (
    StrOutputParser, CommaSeparatedListOutputParser,
)
model = init_chat_model("openai:gpt-6-luna")

# ① 답을 쓰는 체인
answer_chain = (
    ChatPromptTemplate.from_template(
        "배달 앱 상담원으로서 답하세요: {question}"
    )
    | model | StrOutputParser()
)
suggest_chain = (
    ChatPromptTemplate.from_template(
        "손님이 '{question}' 다음에 물을 법한 "
        "질문 3개를 쉼표로만 구분해 쓰세요."
    )
    # ② 쉼표로 이은 글을 목록으로
    | model | CommaSeparatedListOutputParser()
)
# ③ 두 체인을 함께 시작한다
both = RunnableParallel(
    answer=answer_chain, suggestions=suggest_chain
)
result = both.invoke(
    {"question": "떡볶이가 식어서 왔어요. 환불되나요?"}
)
print(result)
터미널 · 출력은 예시 답
{'answer': '불편을 드려 죄송합니다. 주문 내역에서 사진과 함께 환불을 신청하시면 …',
 'suggestions': ['환불은 언제 들어오나요?', '쿠폰으로 받을 수 있나요?', '사진을 꼭 올려야 하나요?']}
  1. init_chat_model은 회사 이름과 모델 이름을 문자열 하나로 받아 모델 객체를 만듭니다. 두 체인이 같은 모델을 함께 씁니다. 버전은 langchain 1.5, langchain-core 1.8 기준입니다.
  2. CommaSeparatedListOutputParser는 "a, b, c"처럼 쉼표로 이은 글을 파이썬 목록 ["a", "b", "c"]로 바꾸는 출력 파서(parser)입니다. 그래서 화면에 버튼 세 개로 바로 띄울 수 있습니다.
  3. 인자 이름 answer·suggestions가 결과 딕셔너리의 키가 됩니다. 두 체인 모두 {question}을 쓰니 invoke에 넘긴 딕셔너리 하나가 양쪽에 똑같이 들어갑니다.
정말 동시에 돌까요? 동시에 돌릴 수를 줄이려면

invoke로 부르면 LangChain이 체인마다 스레드(thread)를 하나씩 맡깁니다. 스레드는 한 프로그램 안에서 일을 나눠 맡는 일꾼입니다. 한 스레드가 모델 응답을 기다리는 동안 다른 스레드가 요청을 보내니 기다리는 시간이 겹칩니다. ainvoke로 부르면 asyncio로 같은 일을 합니다.

API에 분당 요청 한도가 있으면 both.invoke(입력, config={"max_concurrency": 1})처럼 동시에 돌릴 개수를 줄일 수 있습니다. 1로 두면 위 그림의 "하나씩 차례로"와 같아집니다. RunnableParallel(...) 대신 {"answer": answer_chain, ...}처럼 딕셔너리를 바로 써도 체인 안에서는 같은 것으로 바뀝니다.
