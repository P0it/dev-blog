Spec Kit과 Kiro가 코드보다 스펙을 먼저 쓰게 하는 이유

작은 동아리 게시판 서버에 코딩 에이전트(coding agent)를 붙여 놓고 "로그인 기능 만들어 줘"라고 한 줄만 보내 봤습니다. Claude Code는 1분 남짓 만에 회원가입·로그인·로그아웃을 붙였고 그사이 질문은 하나도 하지 않았습니다.

그럼 비밀번호는 몇 자 이상이어야 하고, 서버를 껐다 켜면 회원 정보가 남는지는 누가 정했을까요? 에이전트가 정했습니다. 요청에 없는 칸은 흔히 쓰는 값으로 채웁니다. 스펙(specification)은 그 칸을 코드보다 먼저 사람이 채워 두는 문서입니다. Spec Kit(GitHub이 만든 스펙 작성 도구)과 Kiro(AWS가 만든 에이전트 개발 도구)는 이 문서를 쓰고 따르는 순서를 정해 줍니다.

아래 server.js는 에이전트가 실제로 만든 코드에서 무언가를 정한 줄만 뽑은 것입니다. 토글을 SPEC.md와 함께로 바꾸면 같은 요청에 다섯 칸과 "정한 값" 칸을 채운 SPEC.md를 붙여 보낸 실행의 코드로 바뀝니다. 줄마다 그 값을 누가 정했는지가 붙어 있습니다.

에이전트는 빈칸을 흔한 답으로 채웁니다

같은 한 줄을 새 대화에서 한 번 더 보냈더니 에이전트가 정한 결정 13가지 가운데 10가지가 똑같이 나왔습니다. 두 번 모두 질문은 0개였습니다. 물어보라고 시키지 않으면 모르는 칸도 그럴듯한 값으로 채우고 끝까지 갑니다.

편의점 가는 친구에게 "마실 거 아무거나"라고 부탁하면 생수나 콜라처럼 무난한 걸 사 옵니다. 언어 모델은 많은 글과 코드에서 이어질 말을 맞히도록 학습했기 때문에, 적히지 않은 칸에는 가장 그럴듯한 값을 넣습니다. GitHub 블로그는 이를 두고 모델이 "패턴을 이어 쓰는 데는 뛰어나지만 마음을 읽지는 못한다"고 적었습니다.

다만 친구는 내 취향을 조금은 알지만 에이전트는 이번 대화와 저장소에 적힌 것만 압니다. 흔한 답이 틀린 답은 아닙니다. 비밀번호를 되돌릴 수 없는 문자열로 바꿔 저장하는 해시(hash)처럼 무난한 선택이 많았습니다. 하지만 "우리 동아리 회원만"처럼 우리에게만 있는 규칙은 흔한 답이 될 수 없습니다.

스펙은 무엇을, 계획은 어떻게를 적습니다

빈칸을 채우는 문서는 보통 두 장으로 나눕니다. 케이크를 주문할 때를 떠올리면 쉽습니다. 손님이 쓰는 주문서에는 몇 명이 먹는지, 무슨 맛인지, 견과류를 빼 달라는 말이 들어갑니다. 오븐 온도나 밀가루 양은 적지 않습니다. 그건 빵집의 레시피에 들어갈 내용입니다.

스펙이 주문서이고 계획(plan)이 레시피입니다. 스펙에는 누가 무엇을 왜 쓰는지와 무엇이 되면 끝인지를 적고 어떤 언어와 저장 방식으로 만들지는 계획에 적습니다. GitHub Spec Kit 문서도 스펙 단계에서는 "무엇과 왜"에 집중하고 기술 스택은 계획 단계로 미루라고 합니다.

비유가 어긋나는 곳도 있습니다. 빵집은 주문서에 빈칸이 있으면 전화를 걸어 묻지만 에이전트는 앞에서 본 것처럼 흔한 값으로 채우고 넘어갑니다. 그래서 스펙의 빈칸은 빵집 주문서보다 비용이 큽니다. 맨 위 실험의 SPEC.md는 짧게 보이려고 저장 파일 이름 같은 "어떻게"를 조금 섞었습니다. 일을 키우면 두 장으로 나누는 편이 고치기 쉽습니다.

좋은 스펙에 들어가는 다섯 칸

쓸모 있는 스펙은 다섯 가지를 담습니다. 누가 쓰는지, 무엇을 만드는지, 언제 끝났다고 볼지, 정상 흐름 밖에서 어떻게 할지, 무엇은 하지 않을지입니다. 맨 위 SPEC.md의 여섯 칸은 여기에 "정한 값"을 더한 것입니다.

완료 조건(acceptance criteria)은 일이 끝났는지 판단하는 문장입니다. "잘 동작한다" 대신 "5번 틀리면 맞는 비밀번호로도 10분 동안 거절된다"처럼 확인할 수 있게 써야 에이전트가 테스트로 옮길 수 있습니다. 예외 상황(edge case)은 비밀번호를 계속 틀리는 사람처럼 정상 흐름에서 벗어난 경우입니다.

하지 말 것은 범위 밖(out of scope)을 정합니다. 스펙 없이 보낸 두 실행은 둘 다 요청에 없던 보안 수정까지 했습니다. 이 칸을 적은 실행은 그 부분을 건드리지 않고 "따로 고치길 권한다"고 보고만 했습니다.

Claude Code 문서가 꼽는 좋은 스펙

가장 쓸모 있는 스펙은 그 문서만 읽어도 일할 수 있는 문서라고 합니다. 관련 파일과 인터페이스(interface, 코드끼리 주고받는 방식을 정한 약속) 이름을 적고 범위 밖을 밝히며 기능이 동작함을 증명하는 확인 단계로 끝납니다.

스펙을 사람이 처음부터 써야 하나요

Claude Code 문서는 에이전트에게 먼저 인터뷰를 받으라고 권합니다. "이걸 만들고 싶다, 어려운 부분을 캐물어라, 다 물으면 SPEC.md로 써라"라고 시키고, 스펙이 완성되면 새 세션에서 구현을 시작합니다. 인터뷰하느라 쌓인 대화가 구현을 방해하지 않게 하려고 세션을 나눕니다. 에이전트가 먼저 묻는 방식은 AI-DLC 글에서 자세히 다룹니다.

스펙 한 줄을 바꾸면 계획과 작업과 코드가 따라 바뀝니다

스펙 주도 개발(SDD, Spec-Driven Development)은 스펙 → 계획 → 작업 목록(task list) → 구현 순서로 내려갑니다. 작업 목록은 계획을 한 번에 끝낼 수 있는 작은 일로 쪼갠 것입니다. 문서마다 앞 문서의 번호를 달아 두기 때문에 스펙 한 줄이 바뀌면 어디를 다시 만들어야 하는지 따라갈 수 있습니다.

탭을 고르면 스펙 한 줄이 바뀌고 그 줄을 따라 계획·작업·코드에서 바뀐 줄만 차례로 주황이 됩니다.

문서 내용은 설명을 위한 예시입니다. 줄 끝의 작은 번호(R1, T3 같은)는 그 줄이 어느 스펙 줄이나 작업에서 나왔는지 가리키고 주황 동그라미 숫자는 바뀌는 차례입니다. Kiro의 실제 작업 목록도 작업마다 "Requirements: 1.1, 1.2"처럼 요구사항 번호를 답니다.

스펙 없이 코드부터 고치면 문서가 금방 낡습니다. Spec Kit의 방법론 문서는 지금까지 "코드가 진실이었고 스펙은 코드를 따라가지 못했다"고 적고, 순서를 뒤집어 스펙을 고치고 계획과 코드를 다시 만들자고 제안합니다. Kiro 문서도 요구사항이 바뀌면 requirements.md를 고치고 design.md를 갱신한 뒤 작업 목록에서 Sync Files(세 문서를 다시 맞추는 버튼)를 누르라고 안내합니다.

Spec Kit은 명령 하나에 문서 하나씩 만듭니다

GitHub Spec Kit은 단계마다 명령 하나를 부르면 그 단계의 문서가 하나씩 생기는 오픈 소스(open source) 도구입니다. 터미널에서 specify init으로 프로젝트에 틀을 깔면, 이미 쓰던 에이전트의 채팅창에서 슬래시 커맨드(slash command)로 단계를 하나씩 부릅니다. 슬래시 커맨드는 채팅창에 /로 시작해 입력하는 명령입니다.

GitHub이 2025년 8월 저장소를 열어 공개했습니다. 2026년 10월 13일 1.2.0이 나왔고 10월 15일 기준 GitHub Star(저장소에 관심 표시를 누른 수)는 141,297개입니다.

1 · 무엇을 정한다

/speckit.constitution 프로젝트에 한 번

"테스트를 먼저 쓴다"처럼 모든 기능에 적용할 원칙을 constitution.md에 적습니다. 뒤 단계는 이 원칙에 어긋나는지 늘 확인합니다.

/speckit.specify

"동아리 회원만 쓰는 로그인"처럼 말로 설명하면 에이전트가 spec.md를 씁니다. 애매한 곳에는 [NEEDS CLARIFICATION] 표시를 최대 3개까지 달고, 나머지 빈칸은 업계에서 흔한 값으로 채워 "가정" 칸에 적어 둡니다.

/speckit.clarify 골라 쓰는 확인 단계

덜 정해진 곳에 질문을 최대 5개 던지고 답을 spec.md에 다시 적습니다.

2 · 어떻게 만들지 정한다

/speckit.plan

여기서 처음으로 기술을 말합니다. "외부 패키지 없이 Node로"처럼 적으면 plan.md와 조사 기록, 데이터 모양이 생깁니다. 서버가 바깥과 주고받는 요청·응답의 약속(contracts)과 직접 돌려 확인하는 안내서(quickstart)도 함께 만듭니다.

3 · 작은 일로 쪼개고 점검한다

/speckit.tasks

준비 → 기반 → 사용자 스토리(user story, 사용자가 원하는 기능 하나)별 → 마무리 순서로 tasks.md를 만듭니다. 서로 다른 파일을 건드려 동시에 해도 되는 작업에는 [P] 표시를 붙입니다.

/speckit.analyze 골라 쓰는 확인 단계

세 문서를 읽기만 하고 요구사항에 없는 작업, 스펙과 다른 계획처럼 어긋난 곳을 보고합니다. 파일은 고치지 않습니다.

4 · 코드를 쓰고 빠진 것을 찾는다

/speckit.implement

작업 목록 순서대로 코드를 씁니다. 큰 기능이면 "준비 단계만"처럼 범위를 나눠 부르고 단계마다 동작을 확인합니다.

/speckit.converge

코드를 세 문서와 맞춰 보고 빠진 일을 tasks.md 끝에 덧붙입니다. 덧붙인 일이 없어 "Converged"(코드와 문서가 맞아떨어졌다는 뜻)가 나올 때까지 implement와 converge를 되풀이합니다.

명령 이름은 에이전트마다 표기가 조금 다릅니다. GitHub Copilot(GitHub의 코딩 도우미)에서는 /speckit-specify, Codex(OpenAI의 코딩 에이전트)에서는 $speckit-specify처럼 부릅니다. 꼭 거치는 순서는 specify → plan → tasks → implement이고, clarify·analyze와 점검표를 만드는 checklist는 애매한 게 많을 때 끼워 넣습니다.

기본 명령 밖의 과정

2026년에는 버그 수정(assess → fix → test)과 아이디어 평가 과정이 확장(extension)으로 더해졌습니다. 확장은 기본 명령에 더해 따로 붙여 쓰는 명령 묶음입니다.

Kiro는 요구사항을 WHEN과 SHALL 문장으로 씁니다

Kiro는 IDE(Integrated Development Environment, 코드 편집 프로그램)와 CLI(Command Line Interface, 터미널 명령), 웹에서 씁니다. 스펙은 requirements.md(요구사항), design.md(구조와 오류 처리), tasks.md(작업 목록) 세 파일로 나뉩니다.

요구사항(requirement)은 "회원으로서 나는 ~하고 싶다, 그래야 ~하니까" 꼴의 사용자 스토리와 그 아래 완료 조건으로 씁니다.

완료 조건은 EARS(Easy Approach to Requirements Syntax) 문장 틀을 따릅니다. 2009년 Rolls-Royce의 Alistair Mavin 팀이 제트 엔진 제어 장치의 규정을 분석하며 만든 표기법입니다. 틀이 단순해서 빈칸이 바로 드러나고 그렇게 적은 문장은 테스트 한 줄로 거의 그대로 옮길 수 있습니다.

Kiro에서는 기능 스펙을 시작하는 순서를 고릅니다. 무엇을 먼저 아느냐에 따라 출발점이 다릅니다.

  • Requirements-First: 원하는 동작을 요구사항으로 먼저 적고 설계와 작업을 거기서 끌어냅니다. 만들 기능의 동작을 알 때 씁니다.
  • Design-First: 거꾸로 구조 설계를 먼저 쓰고 요구사항을 설계에서 끌어냅니다. 이미 정한 구조나 엄격한 성능 조건이 있을 때 맞습니다.
  • Quick Spec: 질문에 먼저 답하면 세 파일을 중간 승인 없이 한 번에 만듭니다. 잘 아는 작은 기능에서 확인 단계를 줄입니다.

서로 기다릴 필요 없는 작업은 함께 돌립니다

작업 목록을 쪼개면 어떤 일이 어떤 일을 기다려야 하는지가 보입니다. 이렇게 앞 작업이 끝나야 시작할 수 있는 관계를 의존 관계(dependency)라고 합니다. 라면을 끓일 때 물 끓이기와 파 썰기는 동시에 해도 되지만 면은 물이 끓어야 넣을 수 있는 것과 같습니다.

Kiro에서 작업을 한꺼번에 실행하면 의존 관계를 분석해 작업을 차례대로 웨이브(wave)로 묶습니다. 첫 웨이브는 기다릴 게 없는 작업이고 다음 웨이브는 앞 웨이브가 끝나야 시작할 수 있는 작업입니다. 같은 웨이브 안의 작업은 동시에 실행합니다. Spec Kit의 [P] 표시도 같은 생각입니다.

라면과 다른 점이 있습니다. 사람은 파를 썰다가 물이 끓는지 흘끔 보지만 에이전트 둘은 서로의 작업을 모릅니다. 두 작업이 같은 파일을 고치면 부딪히기 때문에 [P]는 다른 파일을 건드리는 작업에만 붙입니다.

스펙을 언제까지 붙잡고 있을까요

스펙은 기능을 다 만든 뒤에도 남겨 둘 수 있고 버릴 수도 있습니다. 소프트웨어 컨설팅 회사 Thoughtworks의 Birgitta Böckeler는 이를 세 단계로 나눴습니다. 2025년 10월 글에서 그가 써 본 도구는 대부분 첫 단계인 spec-first에 머물렀다고 합니다.

문서를 먼저 쓴다는 점에서 워터폴(waterfall)과 닮았습니다. 요구를 처음에 다 정하고 설계·개발·검사를 한 번씩 차례로 하는 방식이며 AI-DLC 글에서 애자일(agile, 짧은 주기로 만들고 고치기를 되풀이하는 방식)과 함께 다뤘습니다. 다만 스펙은 제품 전체가 아니라 기능 하나 크기이고 요구가 바뀌면 고쳐서 계획과 코드를 다시 만듭니다.

스펙을 써도 확인은 따로 해야 합니다

스펙은 무엇을 확인할지 정해 줄 뿐, 확인을 대신하지 않습니다. 실험에서도 스펙을 다 채운 실행이 세 군데를 혼자 정했습니다. "하지 말 것"을 지키느라 글에 스크립트를 넣을 수 있는 원래의 보안 구멍도 그대로 남겼습니다. 스펙에 적은 대로 했으니 스펙이 틀리면 결과도 틀립니다.

문서가 지나치게 길어지는 문제도 있습니다. Böckeler가 작은 버그 하나를 Kiro에 맡기자 요구사항 문서가 사용자 스토리 4개와 완료 조건 16개로 불어났습니다. Spec Kit은 검토할 마크다운 파일을 많이 만들었고, 에이전트가 이미 있는 클래스(class, 관련 데이터와 기능을 묶어 둔 코드 단위) 설명을 새 요구사항으로 읽고 중복으로 다시 만든 일도 있었다고 합니다.

그래서 GitHub 블로그는 사람의 역할을 "방향만 잡는 게 아니라 확인하는 것"이라고 적었습니다. 단계마다 스펙이 의도를 담았는지, 계획이 현실 조건에 맞는지, 빠진 예외는 없는지 봐야 합니다. 에이전트가 스스로 확인하게 만드는 방법은 코딩 에이전트의 확인 루프 글에서 다뤘습니다.

모든 일에 스펙이 필요한 것도 아닙니다. Claude Code 문서는 바꿀 내용을 한 문장으로 말할 수 있으면 계획을 건너뛰라고 합니다. 오타 수정에 스펙 문서 세 개는 과합니다. 여러 파일을 건드리거나, 우리만 아는 규칙이 있거나, 결과를 확인할 기준이 필요할 때 스펙을 씁니다.

스펙은 에이전트가 읽는 문서 가운데 하나입니다. 다음 글에서는 스펙과 대화 기록, 규칙 파일이 에이전트의 컨텍스트 창(context window, 에이전트가 한 번에 읽어 두는 글의 범위)을 어떻게 채우고, 긴 작업에서 왜 에이전트가 점점 흐려지는지 알아보겠습니다.
