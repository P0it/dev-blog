Multi-Agent는 일을 어떻게
나눠 맡기고 다시 모을까요?

Multi-Agent 시스템은 오케스트레이터(orchestrator) 하나가 일을 쪼개 서브에이전트(subagent) 여럿에게 맡기는 구조입니다. 서브에이전트는 동시에 움직이고 각자 자기 컨텍스트에서 일합니다. 오케스트레이터에게는 요약이 한 장씩 돌아옵니다.

같은 요청을 실제 구성 요소 이름으로 다시 그리면 아래 흐름도가 됩니다. 헤드 셰프는 오케스트레이터이고 조리대는 서브에이전트, 주문 보드는 공유 상태입니다. 조리대에 쌓인 재료는 서브에이전트의 컨텍스트에 쌓인 검색 결과이고 패스로 올라오는 접시는 요약입니다.

이 글의 용어 · 위 장면에서 부른 이름

오케스트레이터헤드 셰프
일을 나눠 맡기고 돌아온 결과를 모아 답을 만드는 Agent
서브에이전트조리대
맡은 한 갈래만 따로 처리하는 Agent
컨텍스트조리대 위 재료
모델이 한 번에 읽는 글 전체. 서브에이전트마다 따로 있어 서로 섞이지 않는다
작업 지시티켓
서브에이전트에게 주는 목표, 결과를 낼 모양, 어디까지 할지
요약접시
서브에이전트가 돌려주는 짧은 결과. 찾은 자료를 전부 돌려주지 않는다
공유 상태주문 보드
여러 Agent가 함께 보도록 계획과 중간 결과를 적어 두는 곳
토큰재료의 양
모델이 읽고 쓰는 글의 단위. 비용과 속도가 이 수로 정해진다

Multi-Agent가 맞는 일과 안 맞는 일

Anthropic의 내부 조사 평가에서 Claude Opus 4를 오케스트레이터로, Claude Sonnet 4를 서브에이전트로 둔 구성은 Claude Opus 4 하나로 일할 때보다 90.2% 높은 점수를 받았다고 합니다. 대신 토큰을 일반 채팅보다 15배쯤 씁니다. 그래서 일을 서로 몰라도 되는 갈래로 나눌 수 있는지부터 따져야 합니다.

나눠 맡기면 나아지는 일

  • 넓게 찾는 조사후보 세 개, 지역 다섯 곳처럼 갈래끼리 몰라도 되는 일. 서브에이전트 3~5개를 동시에 띄우고 도구도 동시에 부르게 바꾸자 복잡한 조사에 걸리는 시간이 최대 90% 줄었다(Anthropic)
  • 한 컨텍스트에 다 안 들어가는 일읽을 자료가 많으면 서브에이전트마다 나눠 읽히고 요약만 받는다. 오케스트레이터의 컨텍스트에는 요약만 쌓인다
  • 도구가 너무 많은 Agent도구 수십 개를 한 Agent에 붙이면 잘못 고르기 시작한다. 갈래마다 그 일에 필요한 도구만 준다(LangChain 문서)
  • 결과가 토큰값보다 비싼 일Anthropic이 BrowseComp로 잰 성능 차이의 80%는 토큰을 얼마나 썼는지로 설명됐다. 토큰을 더 써서 나아지는 일이어야 값을 한다

Agent 하나로 두는 게 나은 일

  • 서로 얽힌 작업대부분의 코딩처럼 한 조각에서 내린 결정이 다른 조각에 영향을 주는 일. Anthropic도 코딩은 조사보다 나눠 동시에 할 일이 적다고 적었다
  • 결정이 부딪치는 일Cognition의 Flappy Bird 예. 배경을 맡은 서브에이전트는 슈퍼 마리오 같은 배경을, 새를 맡은 쪽은 전혀 다른 새를 만들어 합칠 수 없었다
  • 비용이 빠듯한 일Agent 하나는 채팅보다 토큰을 4배쯤, Multi-Agent는 15배쯤 쓴다(Anthropic, 2025년 6월)
  • 실시간으로 맞춰 가야 하는 일Anthropic은 2025년 6월 글에서 LLM Agent가 실시간으로 서로 일을 맡기고 조율하는 데는 아직 서툴다고 적었다

Cognition은 "Don't Build Multi-Agents"(2025년 6월)에서 컨텍스트를 끊지 않고 이어 가는 Agent 하나를 권합니다. 기록이 너무 길어지면 따로 둔 모델로 중요한 결정만 압축해 넘기라고 합니다.

서브에이전트에게 넘길 것과 돌려받을 것

서브에이전트는 오케스트레이터가 쓴 작업 지시 한 통만 보고 시작합니다. 대화 기록을 물려받지 않거든요. 지시가 짧으면 다른 서브에이전트와 같은 검색을 되풀이하거나 엉뚱한 곳을 찾습니다. Anthropic도 초기에 이 문제를 겪었다고 합니다.

예시 요청이라면 pgvector를 맡은 서브에이전트의 지시는 아래 왼쪽 네 줄을 다 채워야 합니다.

작업 지시에 적을 것

  • 목표"pgvector의 비용과 운영 부담을 조사한다"
  • 출력 형식"항목별 표와 출처 URL, 1,500토큰 이내". 오케스트레이터가 세 결과를 나란히 합칠 수 있게 형식을 맞춘다
  • 쓸 도구와 출처"웹 검색, 공식 문서와 가격 페이지 먼저"
  • 범위"다른 후보와 비교하지 않는다. 성능 벤치마크는 찾지 않는다". 어디서 멈출지 적어야 갈래끼리 겹치지 않는다

네 가지는 Anthropic이 작업 지시에 넣으라고 한 항목입니다.

구조에서 정할 것

  • 일의 크기에 맞춘 수Anthropic의 프롬프트 규칙: 사실 하나 찾기는 Agent 1개에 도구 호출 3~10번, 비교는 서브에이전트 2~4개에 10~15번씩, 복잡한 조사는 10개 넘게
  • 돌려받는 크기요약은 대개 1,000~2,000토큰. 긴 결과물은 공유 상태(파일)에 쓰고 위치만 돌려주면 옮기면서 빠지는 내용이 준다
  • 맡길지 넘길지OpenAI Agents SDK의 Agent.as_tool()은 매니저가 대화를 계속 맡은 채 다른 Agent를 도구로 부르고 handoffs는 대화를 넘긴다. LangChain도 Subagents와 Handoffs를 따로 둔다. 이 글의 구조는 앞쪽이다
  • 서브에이전트의 모델서브에이전트에는 더 작고 싼 모델을 쓸 수 있다. Claude Sonnet, Gemini Flash, GPT mini급이나 오픈 모델 Qwen처럼

Claude Code에서는 .claude/agents/ 아래 마크다운 파일 하나가 서브에이전트 하나입니다(name · description · tools · model). 2026년 11월 문서 기준으로 한 세션에서 20개까지 동시에 돌고 세 단계까지 겹쳐 띄울 수 있습니다.
