Data Lake에 파일만 쌓아 두면 생기는 일

학교 질문 챗봇이 학생들과 나눈 대화를 한 달 동안 모았다고 해 봅시다. 이 기록은 다음 모델을 가르칠 학습 데이터(training data)가 되고 자주 나온 질문은 RAG(Retrieval-Augmented Generation)에 넣을 문서를 고르는 근거가 됩니다. 기록이 100만 줄이면 어디에 어떤 모양으로 쌓아 둬야 할까요?

답의 절반은 디스크에 적는 순서에 있습니다. 같은 표라도 한 줄씩 적는 행 저장(row-oriented storage)이냐, 한 열씩 적는 열 저장(column-oriented storage)이냐에 따라 같은 질문에 읽어야 하는 양이 백 배 넘게 차이 납니다. 아래 표에서 저장 순서와 질문을 바꿔 보세요.

AI가 쓰는 데이터는 서비스 DB와 따로 쌓아 둡니다

챗봇 서비스가 돌아가려면 지금 이 순간의 상태를 적어 두는 데이터베이스(database), 줄여서 DB가 있어야 합니다. 누가 로그인했는지, 방금 들어온 질문이 무엇인지 한 건씩 빠르게 적고 읽습니다. PostgreSQL·MySQL 같은 DB가 이 일을 합니다.

그런데 같은 DB에 "지난 한 달 나라별 평균 나이"를 물으면 100만 줄을 훑느라 서비스가 느려집니다. 그래서 분석용 사본을 따로 둡니다. 정해진 표 모양으로 정리해 넣고 SQL로 집계하는 저장소가 데이터 웨어하우스(data warehouse)입니다. SQL은 표에 질문을 던지는 언어입니다.

AI에는 정리된 표보다 원본이 필요할 때가 많습니다. 대화 원문, 안내문 PDF, 급식 사진처럼 표에 담기 어려운 것도 있습니다. 이런 것까지 모양을 정하지 않고 일단 싸게 모아 두는 곳이 Data Lake입니다. 학습 데이터, RAG에 넣을 문서, 서비스 로그는 대개 여기에 먼저 쌓입니다.

Object Storage에는 폴더 없이 긴 이름표만 있습니다

Data Lake의 바닥은 대개 Object Storage입니다. 파일을 객체(object)라는 단위로 넣고 꺼내는 저장소이고 AWS의 S3(Simple Storage Service)가 대표입니다. 회사 안 서버에서는 S3와 같은 방식으로 부를 수 있는 MinIO·Ceph 같은 소프트웨어를 씁니다.

객체 하나는 키(key), 값(value), 메타데이터로 이루어집니다. 키는 객체의 이름, 값은 내용 바이트, 메타데이터는 크기·형식·올린 시각 같은 꼬리표입니다. 객체를 담는 큰 그릇은 버킷(bucket)이라고 부릅니다.

S3 문서는 버킷이 계층 없이 평평한(flat) 구조라고 적어 둡니다. raw/app-logs/2026-10-14/part-0001.json 전체가 키 하나입니다. 키 앞부분에 공통으로 붙은 raw/app-logs/ 같은 글자를 접두사(prefix)라고 하고 콘솔은 이 접두사를 폴더 이름으로 보여 줍니다.

옷 보관소로 치면 키는 번호표입니다. 번호표만 내밀면 옷을 꺼내 주니 선반이 어떻게 생겼는지 몰라도 됩니다. 키는 번호표와 달리 길고 뜻이 있어서 같은 접두사로 시작하는 키를 한꺼번에 나열할 수 있습니다. S3는 한 버킷에 담을 수 있는 객체 수에 정해진 한도가 없습니다. 객체 하나는 최대 50TB, 키는 최대 1,024바이트입니다.

Parquet은 같은 열끼리 모아 적습니다

맨 위 그림의 "한 열씩 적기"를 실제 파일 형식으로 만든 것이 Apache Parquet입니다. Spark와 Iceberg가 기본으로 쓰는 표 파일 형식입니다. Parquet은 줄을 수십만 개씩 묶어 row group을 만들고 row group 안에서는 열마다 column chunk라는 덩어리를 따로 적습니다.

파일 끝에는 footer가 붙습니다. 열마다 column chunk가 파일 어디서 시작하는지, 값이 몇 개인지, 가장 작은 값과 큰 값이 무엇인지 적어 둔 목차입니다. 읽는 쪽은 footer부터 읽고 필요한 column chunk로 바로 건너뜁니다.

목차가 왜 맨 뒤에 있을까요? 공식 문서는 데이터를 앞에서부터 한 번에 쭉 쓰고 끝낼 수 있게 하려는 것이라고 설명합니다. 다 쓰고 나야 덩어리마다 위치를 알 수 있기 때문입니다. 문서가 권하는 row group 크기는 512MB~1GB입니다.

압축한 Parquet은 CSV의 5분의 1 크기였습니다. 그중 71%를 질문 글 열 하나가 차지했고 숫자 열은 작았습니다. 평균 나이만 필요하면 나이 열 0.76MB만 읽으니 시간도 20분의 1로 줄었습니다. 반대로 질문 하나를 한 줄 통째로 꺼내야 하면 여섯 덩어리를 따로 찾아 읽어야 합니다. 그래서 한 건씩 읽고 쓰는 서비스 DB는 대개 행 단위로 저장합니다.

같은 열끼리 모으면 잘 줄어들고 건너뛸 곳도 보입니다

한 열에는 비슷한 값이 몰려 있습니다. 예시 표의 나라 열에는 KR·US·JP·DE·BR 다섯 가지 값만 100만 번 나옵니다. Parquet은 이런 열에 사전 인코딩(dictionary encoding)을 씁니다. 다섯 글자를 사전에 한 번씩만 적고 본문에는 0~4 번호만 적습니다.

같은 번호가 이어지면 "0이 세 번"처럼 줄여 적습니다. 이것이 RLE(Run-Length Encoding)입니다. 출석부에 "결석, 결석, 결석" 대신 "결석 3일"이라고 적는 것과 비슷합니다. 사람은 대충 줄여 써도 알아봅니다. 컴퓨터는 사전과 번호를 함께 보관해야 원래 값으로 정확히 되돌릴 수 있습니다.

실측 파일의 나라 열은 100만 칸이 0.30MB였습니다. 한 칸에 0.3바이트꼴입니다. 그 위에 zstd 같은 일반 압축을 한 번 더 씌웁니다.

최솟값·최댓값으로 묶음 건너뛰기

footer에 적힌 최솟값·최댓값은 읽지 않아도 될 묶음을 알려 줍니다. 질문 기록 100만 줄을 시간 순서로 정렬해 10만 줄씩 row group 10개로 나눠 저장했습니다. "28일째부터 들어온 질문의 평균 나이"를 물으면, 최댓값이 28일보다 이른 묶음은 열어 볼 필요가 없습니다.

28일째
열어 본 row group1 / 10
읽은 나이 열0.08MB

섞인 순서로 바꿔 보면 알 수 있듯이, 이 건너뛰기는 데이터가 그 열 기준으로 어느 정도 모여 있어야 통합니다. 그래서 자주 거르는 열(날짜 등)로 정렬하거나 나눠서 저장합니다.

파일만 쌓아 두면 어디까지가 표인지 아무도 모릅니다

S3에 Parquet 파일을 폴더별로 쌓아 두는 것만으로도 처음엔 잘 돌아갑니다. "chat_logs/ 밑의 파일 전부가 chat_logs 표"라고 약속하면 됩니다. 문제는 여러 작업이 같은 표를 동시에 쓰고 고치기 시작하면 생깁니다.

네 가지 모두 원인이 같습니다. "지금 이 표에 속한 파일이 정확히 무엇인가"를 적어 둔 곳이 없습니다. 폴더 목록을 읽는 순간의 상태가 곧 표가 되니, 언제 읽느냐에 따라 표가 달라집니다. 게다가 Parquet 파일은 한 번 쓰면 고치지 않고 통째로 새로 씁니다. 한 줄만 바꿔도 새 파일이 생기니 폴더에는 옛 파일과 새 파일이 섞여 쌓입니다.

Iceberg는 표에 속한 파일 목록을 따로 적어 둡니다

Apache Iceberg는 이 문제를 푸는 테이블 형식(table format)입니다. 데이터를 저장하는 프로그램이 아니라 어떤 파일이 표에 속하는지 적는 방법을 정한 약속(명세)입니다. 그래서 Spark·StarRocks처럼 서로 다른 엔진이 같은 표를 함께 읽고 씁니다. 명세는 버전 1·2·3이 채택됐고 4가 개발 중입니다(2026년 10월, 라이브러리 1.12.0).

층은 위에서 아래로 다섯 개입니다. catalog는 표 이름마다 "지금 최신 metadata file은 이것"이라는 주소 하나만 갖고 있습니다. metadata file에는 열 이름과 형식 목록인 스키마(schema), 그리고 스냅샷(snapshot) 목록이 들어 있습니다. 스냅샷은 어느 순간의 표 상태 하나입니다.

스냅샷마다 manifest list가 하나씩 있고 그 아래 manifest file이 실제 데이터 파일 목록과 열별 최솟값·최댓값을 적어 둡니다. 읽는 쪽은 이 통계로 열어 볼 manifest와 파일을 미리 거릅니다. Parquet footer에서 한 일을 파일 단위로 한 번 더 합니다.

쓰기 한 번마다 스냅샷이 하나씩 쌓입니다

Iceberg 표를 Python에서 다루는 라이브러리 pyiceberg 0.12.0으로 작은 질문 표를 만들어 네 번 고쳐 봤습니다. 세 줄 추가, 두 줄 추가, id 3번 지우기, lang 열 추가 순서입니다. 아래 그림의 파일 이름과 크기는 그때 실제로 생긴 것입니다. 시점을 바꿔 보세요.

이 시점에 읽으면 나오는 표
idquestionlang

③에서 pyiceberg는 파일 A를 고치지 않았습니다. id 3을 뺀 새 파일 C를 쓰고 manifest에 "A는 빠짐, C는 들어옴"을 적었습니다. A는 디스크에 그대로 남아 있어서 ①·② 시점을 고르면 다시 보입니다. 이렇게 지난 스냅샷을 그대로 읽는 것을 time travel이라고 합니다.

Spark SQL에서는 SELECT * FROM chat_logs VERSION AS OF <스냅샷 id>나 TIMESTAMP AS OF '2026-10-14 09:00'처럼 씁니다. 지난달 모델을 어떤 데이터로 학습했는지 다시 꺼내 볼 수 있어서 학습 데이터의 버전을 남길 때 씁니다. 게임의 세이브 파일과 비슷합니다. 세이브 파일은 매번 전체를 복사하지만 스냅샷은 바뀐 파일만 새로 쓰고 나머지는 그대로 가져다 씁니다.

④ 열 추가는 스냅샷을 만들지 않았습니다. metadata file만 새로 썼고 데이터 파일은 그대로입니다. Iceberg는 열을 이름이 아니라 번호(field id)로 찾기 때문에, 열을 더하거나 이름을 바꿔도 옛 파일을 다시 쓰지 않습니다. 이것을 스키마 변경(schema evolution)이라고 합니다. 옛 파일에 없는 lang 칸은 빈 값(null)으로 읽힙니다.

지울 때마다 파일을 다시 쓰면 느리지 않을까요?

그래서 명세 v2부터는 파일을 다시 쓰지 않고 "이 파일의 몇 번째 줄은 지움"만 따로 적는 delete file을 둡니다. v3에서는 이것을 줄 번호 비트맵인 deletion vector로 적습니다. 지울 때는 빠르고 읽을 때 지운 줄을 빼는 일을 조금 더 합니다. 실험에 쓴 pyiceberg는 ③처럼 파일을 다시 쓰는 쪽을 택했습니다.

스냅샷을 끝없이 남기면 옛 파일도 계속 남습니다. 그래서 일정 기간이 지난 스냅샷을 정리하는 작업(expire snapshots)을 돌려 더는 아무 스냅샷도 쓰지 않는 파일을 지웁니다. 정리한 시점보다 앞으로는 time travel할 수 없습니다.

두 작업이 동시에 써도 표가 반쯤 바뀐 채로 보이지 않습니다

표를 바꾸는 마지막 동작은 하나뿐입니다. catalog에 적힌 주소를 옛 metadata file에서 새 metadata file로 바꾸는 것입니다. 명세는 이것을 원자적 교체(atomic swap)라고 부릅니다. 바뀌었거나 안 바뀌었거나 둘 중 하나이고 반쯤 바뀐 상태는 없습니다.

읽는 쪽은 표를 열 때 받은 metadata file만 봅니다. 그사이 누가 새 파일을 써도 주소가 바뀌기 전에는 보이지 않습니다. 읽으려고 표를 잠그지(lock) 않아도 됩니다.

두 작업이 같은 버전에서 출발하면 먼저 주소를 바꾼 쪽이 이깁니다. 늦은 쪽은 "내가 출발한 버전이 아직 최신인가"를 확인하다 실패하고 새 최신 버전 위에서 다시 시도합니다. 일단 해 보고 겹치면 다시 하는 이 방식을 낙관적 동시성(optimistic concurrency)이라고 합니다.

공유 문서에서 저장을 눌렀더니 "다른 사람이 먼저 고쳤습니다"가 뜨는 것과 비슷합니다. 사람은 내용을 읽고 합치지만 Iceberg는 "내가 바꾸려던 파일이 아직 표에 있는가" 같은 정해진 조건만 보고 다시 할지 포기할지 정합니다.

Lakehouse는 창고 하나에 여러 엔진을 붙입니다

S3 같은 싼 저장소에 Parquet 파일을 두고 그 위에 Iceberg 같은 테이블 형식을 얹으면, Data Lake도 웨어하우스처럼 표와 트랜잭션(transaction)을 갖게 됩니다. 트랜잭션은 여러 변경을 다 되거나 다 안 되게 묶는 단위입니다. 이런 구조를 Lakehouse라고 부릅니다. Databricks 연구진이 2021년 CIDR 학회 논문에서 이 이름으로 정리했습니다.

Lakehouse는 복사본을 하나로 줄입니다. 학습 코드가 같은 Parquet 파일을 바로 읽을 수 있어서 논문은 Lakehouse의 조건으로 머신러닝 지원을 따로 꼽았습니다. 이제 그 위에 붙는 엔진 둘을 차례로 봅니다.

Spark는 큰 일을 조각내 여러 컴퓨터에 나눠 맡깁니다

100만 줄은 노트북 한 대로도 금방 처리합니다. 하지만 기록이 10억 줄이 되고 날마다 늘면 한 대로는 끝나지 않습니다. Apache Spark는 데이터를 조각내 여러 컴퓨터에서 동시에 처리하는 엔진입니다. 2026년 10월 최신 버전은 4.2.0이고 Python(PySpark)이나 SQL로 씁니다. "나라별 질문 수 세기"를 Spark가 어떻게 나누는지 스크롤하며 보세요.

① 조각 내기

Spark는 데이터를 파티션(partition)이라는 조각으로 나눕니다. 그림에서는 질문 기록을 12조각으로 나눴습니다. 점 하나가 질문 한 줄이고 색은 나라입니다. Spark 문서는 CPU 하나에 파티션 2~4개를 권합니다.

② 나눠 맡기

일을 하는 컴퓨터 세 대가 파티션을 네 개씩 맡습니다. Spark에서 이 일꾼 프로그램을 executor라고 부릅니다. 파티션 하나에는 작업 단위인 task가 하나씩 붙습니다.

③ 각자 미리 세기

컴퓨터마다 자기가 맡은 조각 안에서만 나라별 개수를 셉니다. 서로 말을 주고받을 필요가 없어서 컴퓨터를 늘린 만큼 거의 그대로 빨라집니다.

④ 셔플

이제 같은 나라 숫자끼리 한 컴퓨터에 모아야 합니다. KR은 1번으로, US는 2번으로, JP는 3번으로 보내는 식으로 데이터를 다시 나누는 일이 셔플(shuffle)입니다. 디스크에 쓰고 보낼 수 있는 모양으로 바꾸고 네트워크로 보내야 해서 Spark 문서도 비싼 작업이라고 적어 둡니다.

⑤ 합치기

모인 숫자를 더하면 끝입니다. 결과는 다시 Iceberg 표로 씁니다. 전교 설문을 반마다 먼저 세고 학년 대표에게 모아 더하는 것과 같습니다. 학교에서는 종이 한 장만 옮기면 되지만 Spark에서는 셔플로 옮길 데이터가 크면 그 시간이 전체 시간을 좌우합니다.

그래서 Spark 작업을 빠르게 만드는 요령은 대개 셔플을 줄이는 것입니다. 그림의 ③처럼 보내기 전에 각자 미리 세어 두면 보낼 양이 줄어듭니다.

Data Lake에서 Spark가 맡는 일은 주로 ETL(Extract·Transform·Load)입니다. 원본을 읽고 고치고 합치고 표로 쓰는 일입니다. RAG에 넣을 문서 수백만 개를 청크(chunk), 곧 검색하기 좋은 길이의 조각으로 자르는 일처럼 한 번에 많이 처리하는 배치(batch) 작업에 맞습니다.

StarRocks는 사람이 기다리는 질문에 바로 답합니다

대시보드에서 버튼을 누를 때마다 "오늘 질문 수"를 다시 계산하려면, 큰 배치 작업과는 다른 엔진이 필요합니다. StarRocks는 이런 분석 질의를 빠르게 처리하는 SQL 엔진입니다. 여러 컴퓨터가 질의 하나를 나눠 동시에 계산하는 MPP(Massively Parallel Processing) 구조이고 2026년 10월 최신 버전은 4.1입니다.

shared-data 구조에서는 FE(Frontend)가 SQL을 받아 실행 계획을 세우고 CN(Compute Node) 여러 대가 나눠 실행합니다. 데이터는 S3 같은 Object Storage에 있고 CN의 디스크에는 따로 두지 않습니다. CN은 자주 읽는 부분만 캐시(cache)에 둡니다. 캐시는 자주 쓰는 것을 가까이 두는 임시 보관함입니다.

external catalog를 쓰면 Spark가 써 둔 Iceberg 표를 StarRocks로 옮기지 않고 그대로 질의합니다. 저장은 한 곳, 엔진은 여럿이라는 Lakehouse 그림 그대로입니다.

열을 묶음째 계산하는 벡터 실행

StarRocks가 빠른 이유 중 하나는 벡터 실행(vectorized execution)입니다. 값을 한 줄에 하나씩 꺼내 계산하는 대신 한 열의 값 여러 개를 묶음으로 꺼내 같은 계산을 한꺼번에 합니다. 열 단위로 저장된 데이터와 잘 맞습니다.

CPU에는 숫자 여러 개에 같은 덧셈을 한 번에 하는 SIMD(Single Instruction, Multiple Data) 명령이 있습니다. 시험지를 채점할 때 한 장씩 1번부터 끝까지 매기는 대신 모든 시험지의 1번만 먼저 쭉 매기는 것과 비슷합니다. 사람은 손이 하나뿐이지만 SIMD는 정말로 여러 값을 같은 순간에 계산합니다.

학습 데이터도 RAG 문서도 이 길을 지나갑니다

지금까지의 부품을 학교 챗봇의 데이터 길로 이으면 아래 그림이 됩니다. 원본은 S3에 쌓이고 Spark가 정리해 Iceberg 표로 씁니다. 그 표가 파인튜닝(fine-tuning), RAG, 대시보드 세 갈래로 나뉩니다. 파인튜닝은 이미 학습된 모델을 내 데이터로 조금 더 학습시키는 일입니다. 사용처 칸을 누르면 그 길이 켜집니다.

파인튜닝 쪽에서는 학습에 쓴 표의 스냅샷 id를 모델과 함께 적어 둡니다. 그러면 나중에 모델 답이 이상할 때 그 모델이 본 데이터를 time travel로 그대로 다시 꺼낼 수 있습니다. 파인튜닝 자체는 LoRA 학습 페이지, 청크를 숫자 벡터로 바꾸는 임베딩(embedding)과 벡터 DB에서 찾는 과정은 벡터 DB 학습 페이지에 따로 정리했습니다.

데이터는 싼 저장소에 열 단위 파일로 쌓습니다. 표는 파일 목록을 적은 메타데이터로 만들고 계산은 그 위에 필요한 엔진을 붙입니다.
