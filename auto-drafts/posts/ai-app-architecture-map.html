AI 서비스에는 모델 말고
무엇이 더 필요할까요?

AI 서비스를 이루는 구성 요소는 크게 여덟 가지입니다. 모델은 그중 하나이고 나머지는 모델을 호출하기 전후에 필요한 일을 맡습니다. 왼쪽에서 오른쪽으로 보면 됩니다.

  1. 클라이언트사용자가 말을 거는 창구입니다. 웹 화면, Slack 같은 메신저 봇, 다른 서비스의 API 호출이 모두 여기로 들어옵니다.
  2. API 서버보낸 사람을 확인하고 요청 수를 제한합니다. 모델의 답변은 다 만들어질 때까지 기다리지 않고 생성되는 대로 보냅니다.
  3. 오케스트레이션모델을 언제 어떻게 호출할지 정하는 코드입니다. 실행 순서를 코드가 정하면 워크플로, 모델이 정하면 Agent입니다.
  4. 모델LLM Gateway가 요청을 알맞은 모델로 보내고, 한 모델에 장애가 나면 다른 모델로 넘깁니다.
  5. 지식 (RAG)모델이 모르는 사내 문서를 작게 나눠 벡터 DB에 저장해 두고 질문과 관련 있는 부분을 찾아 함께 전달합니다.
  6. 도구 (MCP)조회·전송처럼 실제 작업을 하는 함수입니다. MCP 서버로 만들어 두면 여러 앱이 같은 도구를 쓸 수 있습니다.
  7. 메모리 · 상태모델은 지난 대화를 기억하지 못합니다. 대화 기록과 작업 중간 상태는 앱이 저장해 두었다가 다음 호출에 다시 넣습니다.
  8. 운영 계층위험한 입력과 출력을 막고 모든 호출을 기록하며 답변 품질과 비용을 수치로 확인합니다.

요청 하나는 어떤 순서로 처리될까요?

사용자가 한 번 요청해도 모델은 보통 두 번 이상 호출됩니다. 오른쪽 그림은 "지난주 VPN 장애를 정리해서 팀 채널에 올려 줘"라는 요청이 처리되는 순서입니다.

모델이 직접 검색하거나 메시지를 보내지는 않습니다. 어떤 도구를 호출해 달라고 응답할 뿐이고 실제 호출은 오케스트레이션 코드가 합니다(5·6번, 8·9번). 그래서 대부분의 화살표가 오케스트레이션을 거칩니다.

설명을 위한 예시 흐름입니다. 초록 면이 우리가 운영하는 서비스이고 점선은 돌아오는 답입니다. 실제 서비스는 검색을 여러 번 하거나 사람 승인을 기다리기도 합니다.

처음부터 여덟 가지를 모두 갖출 필요는 없습니다

구성 요소는 필요할 때 하나씩 추가합니다. 질문에 답만 하는 챗봇이라면 앱과 모델만 있으면 됩니다. 사내 문서를 근거로 답해야 하면 지식(RAG)을, 실제 작업을 맡기려면 도구와 메모리를 추가합니다.

운영 계층은 사용자가 늘어나면 더 미룰 수 없습니다. 어느 요청에서 잘못됐는지 기록이 없으면 고칠 곳을 찾을 수 없습니다.

색이 들어간 항목이 그 단계에서 새로 추가되는 구성 요소입니다. 순서는 흔한 예시일 뿐이고 지식보다 도구가 먼저 필요한 서비스도 많습니다.
