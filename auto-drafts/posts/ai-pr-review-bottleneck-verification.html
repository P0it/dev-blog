AI가 만든 PR은 왜 리뷰 앞에서 5배 오래 기다리나

코딩 에이전트에게 일을 맡기면 PR이 하루에도 여러 건 올라옵니다. PR(Pull Request)은 "내가 고친 코드를 본 코드에 합쳐 달라"는 요청입니다. 합치는 일을 머지(merge)라고 하고 머지하기 전에 다른 사람이 그 코드를 읽고 판단하는 단계를 코드 리뷰(code review)라고 합니다.

AI 덕분에 쓰기는 빨라졌지만 읽기는 여전히 사람이 같은 속도로 합니다. 흐름에서 가장 좁아 전체 속도를 정하는 곳을 병목(bottleneck)이라고 하는데 그 자리가 리뷰로 옮겨 갔습니다. 실제 팀의 PR 810만 건을 모은 조사에서도 에이전트가 연 PR은 리뷰가 시작되기까지 사람이 혼자 쓴 PR보다 5.3배 오래 기다렸습니다.

PR 한 건이 머지되기까지

PR은 고친 코드를 바로 본 코드에 넣지 않고 "이 변경을 넣어도 될까요?" 하고 묻는 요청서입니다. 학급 신문에 기사를 싣는 과정과 비슷합니다. 로그인 버튼 색을 바꾸는 작은 PR 하나도 여섯 단계를 거칩니다.

고친 내용은 diff로 보입니다

개발자는 본 코드를 복사한 작업 공간인 브랜치(branch)에서 코드를 고칩니다. 고친 것을 저장한 한 덩어리를 커밋(commit)이라고 합니다. 무엇이 바뀌었는지는 diff로 봅니다. 지운 줄은 빨간 바탕에 −, 더한 줄은 초록 바탕에 +가 붙습니다.

PR을 열고 왜 바꿨는지 적습니다

브랜치를 본 코드에 합쳐 달라고 PR을 엽니다. 제목과 설명에는 무엇을 왜 바꿨는지 적습니다. 설명이 빈약하면 코드가 짧아도 리뷰어가 읽는 데 오래 걸립니다.

기계가 먼저 검사합니다

PR이 열리면 코드가 올라올 때마다 검사를 자동으로 돌리는 장치인 CI(Continuous Integration)가 돕니다. 빌드(build)는 코드를 실행할 수 있게 묶어 보는 일이고 린터(linter)는 코드 모양이 팀 규칙에 맞는지 보는 검사입니다. 하나라도 실패하면 빨간 ✗가 붙습니다.

사람이 읽고 줄마다 코멘트를 답니다

여기가 코드 리뷰입니다. 리뷰어가 diff를 한 줄씩 읽으며 버그가 없는지, 팀 규칙에 맞는지, 나중에 읽기 쉬운지를 보고 문제가 있는 줄에 코멘트를 답니다. 여기서는 바꾼 색이 어두운 화면에서 잘 안 보인다는 지적이 달렸습니다.

고쳐서 다시 올립니다

작성자가 지적을 반영해 커밋을 하나 더 올리면 같은 PR에 쌓이고 CI가 다시 돕니다. 리뷰어는 바뀐 부분을 다시 읽습니다. 한 PR이 이 고리를 여러 번 돌기도 합니다.

승인을 받아야 머지됩니다

리뷰어가 승인(Approve)하면 머지 버튼이 열립니다. 많은 팀이 승인 없이는 머지되지 않게 저장소(repository) 설정으로 막아 둡니다. 저장소는 프로젝트 코드를 모아 두는 곳입니다. 리뷰어가 읽지 않은 PR은 본 코드에 들어가지 못합니다.

신문과 다른 점도 있습니다. 코드는 머지된 뒤에도 다른 코드와 맞물려 계속 실행됩니다. 리뷰에서 놓친 결함이 몇 주 뒤 장애로 돌아오기도 해서 팀은 리뷰 단계를 쉽게 빼지 못합니다.

쓰기는 빨라졌는데 읽는 속도는 그대로입니다

개발 흐름이 나가는 속도는 가장 좁은 단계가 정합니다. 병 입구가 좁으면 병을 아무리 세게 기울여도 나오는 물의 양이 같은 것과 비슷합니다. 팀이 일정 시간에 실제로 머지하는 양을 처리량(throughput)이라고 하는데 처리량은 가장 가는 관의 굵기를 넘지 못합니다.

에이전트는 쓰기 관을 크게 넓혔습니다. Hao Li 등이 2025년 7월 공개한 AIDev 논문에는 한 개발자가 2025년 5월 30일부터 6월 3일 사이에 OpenAI의 코딩 에이전트 Codex로 PR 164건을 올린 사례가 나옵니다. 같은 사람이 앞선 3년 반 동안 손으로 올린 PR은 176건이었습니다.

읽는 관은 사람 눈의 속도라서 그대로입니다. SmartBear는 Cisco 팀의 리뷰 기록을 분석해 한 번에 200~400줄을 60~90분에 걸쳐 읽으라고 권합니다. 시간당 500줄보다 빨리 읽으면 찾아내는 결함이 크게 줄었다고 합니다.

병과 다른 점도 있습니다. 병 안의 물은 기다려도 상하지 않지만 PR은 기다리는 동안 본 코드가 바뀌어 서로 부딪치는 충돌(conflict)이 생기고 작성자도 무엇을 왜 바꿨는지 잊어 갑니다. 리뷰 관은 압력을 받으면 넓어지는 대신 대충 읽는 쪽으로 변하기도 합니다.

리뷰어가 바쁠수록 기다림은 몇 배로 늘어납니다

줄은 리뷰어가 꽉 차기 전부터 길어집니다. 점심시간 매점을 생각하면 됩니다. 손님이 일정한 간격으로 오지 않고 몰려오기 때문에 점원이 70~80%만 바빠도 줄이 생깁니다. 리뷰어가 일하는 시간 가운데 리뷰에 쓰는 비율을 가동률(utilization)이라고 합니다.

손님이 줄을 서서 기다리는 현상을 수학으로 다루는 대기행렬 이론(queueing theory)에는 이 관계를 적은 Kingman 근사식(정확한 값에 가깝게 맞춘 간단한 식)이 있습니다. 말로 풀면 "기다리는 시간 ≈ 가동률 ÷ (1 − 가동률) × 리뷰 한 건에 걸리는 시간"입니다. PR이 오는 간격도, 한 건을 읽는 시간도 그때그때 제각각인 흔한 경우에 맞춘 식입니다.

👇 리뷰어가 얼마나 바쁜지 바꿔 보세요

50%

리뷰 한 건이 1시간 걸릴 때, PR은 줄에서 평균 1.0시간 기다립니다.

그래서 리뷰어를 쉴 틈 없이 100% 가까이 쓰는 팀이 가장 느립니다. 맨 위 대기 줄 그림의 AI 모드에서는 하루에 들어오는 양(약 1,020줄)이 리뷰어가 읽을 수 있는 양(600줄)보다 많습니다. 곡선이 끝나는 100% 너머라 줄은 매일 길어지기만 합니다. Google 엔지니어링 가이드가 리뷰 요청에는 늦어도 하루 안에 답하라고 정해 둔 것도 기다림이 팀 전체 속도를 떨어뜨리기 때문입니다.

AI PR은 더 크고 더 오래 기다립니다

실제 팀 데이터에서도 리뷰 앞의 줄이 보입니다. LinearB는 여러 팀의 숫자를 모아 기준값을 보여 주는 2026년 벤치마크(benchmark) 보고서에서 42개국 4,800개 팀의 PR 810만 건 이상을 분석했습니다. PR을 사람이 혼자 쓴 PR, AI 도움을 받아 사람이 쓴 PR, 에이전트가 직접 연 PR 세 가지로 나눴습니다.

막대의 노란 부분이 대기 시간(Pickup Time)으로, PR이 열린 뒤 누군가 리뷰를 시작하기까지 걸린 시간입니다. 값은 P75로 셌습니다. 100건을 짧은 순서로 줄 세웠을 때 75번째 PR의 값이라 느린 쪽을 보여 줍니다. 에이전트 PR은 1,055분, 약 17.6시간을 기다렸습니다. 사람이 혼자 쓴 PR의 201분보다 5.3배 깁니다.

크기도 다릅니다. P75 기준 AI 도움 PR은 408줄, 에이전트 PR은 293줄로 사람이 혼자 쓴 157줄보다 큽니다. 열린 뒤 30일 안에 머지된 비율(보고서의 Acceptance Rate)은 사람 PR 84.4%, AI PR 32.7%였습니다. 보고서는 이것이 두 값이 함께 나타났다는 상관관계(correlation)일 뿐 AI가 원인이라는 증거는 아니라고 덧붙입니다.

리더 설문에서는 맥락이 빠졌을 것 같아 AI PR을 열어 보기부터 망설인다는 답이 많았습니다.

머지가 두 배 가까이 늘자 리뷰 시간도 두 배 가까이 늘었습니다

AI를 많이 쓰는 팀은 실제로 더 많이 머지합니다. 다만 그만큼 리뷰가 무거워집니다. Faros AI는 1,255개 팀 개발자 1만여 명의 작업 기록을 최대 2년 치 모아 AI를 많이 쓰는 팀과 적게 쓰는 팀을 견줬고 2025년 7월 23일 결과를 냈습니다.

머지한 PR이 98% 늘었는데 리뷰 시간도 91% 늘었습니다. 맨 위 대기 줄 그림에서는 리뷰어 시간을 하루 두 시간으로 묶어 머지가 늘지 않았지만 실제 팀은 리뷰에 시간을 더 써서 머지를 늘린 셈입니다.

그런데 회사 단위로 묶으면 AI 도입 정도와 성과 개선 사이에 뚜렷한 상관이 보이지 않았습니다. 보고서는 팀마다 AI를 쓰는 정도가 다르고 팀끼리 서로의 결과를 기다리기 때문이라고 풀이합니다. 한 팀이 빨라져도 리뷰·테스트·배포 같은 다음 단계나 옆 팀 앞에서 다시 막힙니다.

AI PR에서 더 자주 나오는 결함

줄이 길어지는 이유는 양만이 아닙니다. 한 건을 읽는 부담도 큽니다. 코드 리뷰 도구 회사 CodeRabbit은 2025년 12월 17일 보고서에서 GitHub 오픈소스 PR 470건을 같은 기준으로 검토했습니다. AI가 함께 썼다는 표시가 있는 PR 320건과 사람만 쓴 PR 150건입니다.

PR 한 건에서 찾은 이슈는 AI PR이 평균 10.83개, 사람 PR이 6.45개로 약 1.7배였습니다. 논리·정확성 문제는 75% 많았고 오류 처리 누락은 거의 2배, 보안 문제는 최대 2.74배였습니다. 가장 크게 벌어진 건 가독성으로 3배가 넘었습니다. 성능 문제(과한 입출력)는 약 8배였지만 건수 자체가 적었다고 합니다.

표본은 작고 한계도 있습니다. AI 표시가 없는 PR을 사람 PR로 봤기 때문에 사람 PR에도 AI가 쓴 코드가 섞였을 수 있다고 보고서가 직접 밝혔습니다. 그래도 방향은 앞의 조사와 같습니다. 더 꼼꼼히 읽어야 하는 코드가 더 많이 들어옵니다.

그럴듯한 코드에서 결함 찾기

아래 PR은 결함 세 개를 일부러 심은 예시입니다. 코드는 13줄뿐이고 문법 오류도 없습니다. 하나는 PR 설명을 같이 읽어야 찾을 수 있습니다.

주문 금액에 사용자의 쿠폰을 적용합니다. 쿠폰 표의 rate 는 10, 20처럼 퍼센트 숫자로 저장돼 있습니다. 쿠폰이 없는 학생도 있습니다.

표시한 줄 0개

✓찾은 결함!놓친 결함–결함이 아닌 줄

  1. 줄을 표시하고 답 맞춰 보기를 누르면 바로 여기에 결함 세 개와 풀이가 나옵니다.
  2. 3·5번 줄오류 처리쿠폰이 없는 학생은 user.coupon 이 비어 있어서 다음 줄에서 프로그램이 멈춥니다. 설명에 "쿠폰이 없는 학생도 있다"고 적혀 있습니다.
  3. 4번 줄보안로그에 카드 번호를 그대로 남깁니다. 로그는 여러 사람이 보는 곳이라 개인 정보가 새어 나갑니다.
  4. 8번 줄논리coupon.rate 는 10 같은 퍼센트 숫자인데 그대로 곱했습니다. 10% 할인이 1,000% 할인이 되고 최대 할인액에 걸려 언제나 최대 금액만큼 깎입니다. 설명을 읽지 않으면 찾을 수 없습니다.

세 결함은 CodeRabbit 보고서에서 AI PR에 더 많았던 범주(논리, 오류 처리, 보안)에서 하나씩 골랐습니다. 코드만 보면 멀쩡하고 PR 설명과 팀의 규칙을 알아야 보입니다. 리뷰어가 AI PR을 열기 전에 망설이는 이유가 여기에 있습니다. 작성자에게 "이건 왜 이렇게 했나요?"라고 물어도 답할 사람이 없는 경우가 많습니다.

첫 번째 대책, 리뷰 에이전트가 먼저 읽기

리뷰 관을 넓히는 가장 직접적인 방법은 첫 번째 읽기를 AI에게 맡기는 것입니다. Anthropic은 2026년 3월 9일 Claude Code용 Code Review를 공개했습니다. PR이 열리면 여러 에이전트가 동시에 diff와 주변 코드를 읽고 각자 다른 종류의 문제를 찾습니다.

Code Review는 찾은 후보를 그대로 내보내지 않습니다. 검증 단계가 후보마다 실제 코드 동작에 대조해 문제가 아닌데 문제라고 짚은 오탐(false positive)을 걸러 냅니다. 그림의 엣지 케이스는 쿠폰이 없는 학생처럼 드물게 들어오는 입력이고 회귀는 잘 되던 기능이 이번 변경으로 다시 깨지는 일입니다. 리뷰 한 건은 평균 20분, 비용은 PR 크기에 따라 평균 15~25달러입니다.

Code Review는 PR을 승인하지도 막지도 않습니다. 결과는 PR 화면의 검사 목록에 한 줄로 붙는 check run에 남는데 늘 중립으로 끝나 머지를 막지 않습니다. 조교가 시험지에 먼저 표시를 해 두면 선생님이 빨리 채점하는 것과 비슷합니다. 다만 조교도 틀린 답을 놓치고 점수는 선생님이 매깁니다.

GitHub의 Copilot code review도 같은 방향입니다. GitHub은 2026년 3월 5일, 2025년 4월 출시 뒤 리뷰가 6천만 건을 넘었고 GitHub 전체 코드 리뷰의 다섯 건 중 한 건 이상을 맡고 있다고 밝혔습니다.

리뷰의 71%가 고칠 만한 지적을 냈고 29%는 아무 말도 하지 않았습니다. 지적이 있는 리뷰에는 평균 5.1개의 코멘트가 달렸습니다. 1만 2천 개가 넘는 조직이 모든 PR에 자동으로 돌린다고 합니다. 두 도구 모두 사람 리뷰어를 빼는 게 아니라 사람이 읽기 전에 볼 곳을 표시하는 데 쓰입니다.

두 번째 대책, 사람보다 먼저 기계가 거르기

리뷰 에이전트도 결국 읽는 일이라 가끔 틀립니다. 그보다 앞에서 같은 코드면 늘 같은 판정을 내리는 검사는 CI에 맡깁니다. 빌드와 린터 말고도 타입체크(type check)가 있습니다. 숫자 자리에 글자를 넣는 식의 실수를 실행 전에 잡는 검사입니다. 에이전트가 이 검사들을 스스로 돌려 보는 과정은 에이전트 루프 글에 있습니다. 알려진 취약점(해커가 파고들 수 있는 약점)이 있는 라이브러리(library), 즉 남이 만들어 둔 코드 묶음을 쓰지 않는지도 봅니다.

사람 앞에 오는 PR이 이미 빌드되고 테스트를 통과한 상태라면 리뷰어는 "돌아가나"를 확인하지 않고 "이렇게 짜는 게 맞나"만 봅니다. Claude Code Review 문서도 리뷰 지침 파일 REVIEW.md 에 "CI가 이미 잡는 린트·포맷·타입 오류는 짚지 말라"고 적는 예를 듭니다.

PR을 작게 나누는 것도 같은 쪽의 대책입니다. Google 엔지니어링 가이드는 100줄 정도가 보통 알맞고 1,000줄은 보통 너무 크다고 적었습니다. 작은 PR은 짬이 날 때 5분씩 읽을 수 있어 더 빨리, 더 꼼꼼히 리뷰됩니다. 에이전트에게도 PR을 작게 쪼개 올리라고 지시할 수 있습니다.

맞춤법 검사기가 오타는 잡아도 기사 내용이 사실인지는 모르는 것처럼, CI 통과는 테스트가 확인한 범위만 맞다는 뜻입니다. 에이전트가 테스트까지 같이 쓰면 코드를 고치는 대신 테스트를 고쳐 통과시키는 일도 생깁니다. 목표 대신 점수만 맞추는 이런 행동을 보상 해킹(reward hacking)이라고 하며 에이전트 루프 글에 따로 정리했습니다.

세 번째 대책, 위험도에 따라 읽는 사람 나누기

모든 PR을 같은 강도로 읽지 않는 방법입니다. 공항 보안 검색에서 대부분은 일반 검색대를 지나고 일부만 정밀 검색을 받는 것과 비슷합니다. 여기서 위험도(risk)는 그 코드가 틀렸을 때 생기는 피해의 크기입니다. 결제와 로그인 코드는 높고 버튼 문구나 문서는 낮습니다.

Anthropic은 2026년 7월 21일 자기 개발 과정을 소개하며 코드베이스를 위험도로 나누고 그 등급에 따라 리뷰를 자동화한다고 밝혔습니다. 자동 승인한 건은 근거를 기록하고 위험도를 반영해 뽑은 표본을 사람이 다시 봅니다. 같은 글에 실린 Intercom 사례에서는 PR의 19%를 자동 승인했더니 배포가 두 배가 됐고 깨진 변경 때문에 서비스가 멈춘 시간은 35% 줄었습니다.

GitHub에서는 CODEOWNERS 파일에 경로마다 담당 팀을 적습니다. PR이 여러 파일을 바꾸면 파일마다 맞는 줄의 담당 팀이 모두 리뷰어로 지정됩니다. 본 코드에 머지하기 전에 지켜야 할 조건을 정하는 설정이 브랜치 보호 규칙(branch protection rule)입니다. 여기서 담당자 승인을 필수로 켜면 바뀐 파일마다 그 담당 팀의 누군가가 승인해야 머지됩니다.

공항과 달리 사람을 보고 고르지 않고 바뀐 파일 경로로 고릅니다. 자동 승인한 PR에 결함이 있으면 그대로 들어가기 때문에 표본 검사와 배포 뒤 감시를 함께 둡니다.

읽기에서 검증 설계로

맨 위 대기 줄 그림의 AI 모드에 대책 세 가지를 더했습니다. 리뷰어는 그대로 하루 600줄을 읽습니다. 스위치를 켜면 PR이 리뷰어에게 가기 전에 갈라집니다. 표의 왼쪽 칸은 대책을 모두 끈 결과로 맨 위 그림의 AI 모드와 같습니다.

하나씩 켜 보면 자동 검사와 리뷰 에이전트는 다시 읽는 양을 덜어 주고 위험도 나누기는 사람이 읽을 PR 자체를 줄입니다. 셋을 다 켜면 금요일 저녁에 줄이 비지만 사람이 한 번도 읽지 않은 코드도 함께 들어갑니다. 무엇을 기계에 맡길지는 팀이 정해야 합니다.

병목 이론으로 유명한 제약 이론(theory of constraints)도 같은 순서를 권합니다. 병목의 시간을 아끼는 일이 위험도 나누기이고 앞 단계를 병목에 맞추는 일이 자동 검사입니다. 그래도 모자라면 병목을 넓히는데 리뷰 에이전트가 그 일을 합니다.

개발자의 일도 모든 코드를 직접 읽는 데서 어떤 검사를 기계에 걸고 어떤 코드를 사람에게 보낼지 설계하는 쪽으로 옮겨 갑니다. 그런데 리뷰 에이전트가 읽는 PR 안에 에이전트를 속이는 문장이 들어 있다면 어떻게 될까요? 다음 글에서는 프롬프트 인젝션과 에이전트의 권한을 알아보겠습니다.
