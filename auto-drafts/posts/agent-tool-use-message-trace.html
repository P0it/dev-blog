AI Service Track · 11

Agent가 진짜 검색했는지 답만 봐서는 모르는 이유

AI 비서에게 "영상 좀 찾아 줘"라고 하면 제목과 링크가 붙은 답이 금방 돌아옵니다. 그런데 그 링크가 실제로 검색해서 얻은 것인지, 모델이 그럴듯하게 지어낸 글자인지는 화면만 봐서는 구별되지 않습니다. 화면 뒤로 내려가 Agent가 남기는 기록을 펼쳐 보고 답을 그 기록과 맞춰 보는 코드까지 만들어 봅니다.

Agent는 언제 도구를 꺼낼까요?

모델이 질문을 읽고 "이건 내가 아는 것만으로는 답할 수 없다"고 판단할 때 꺼냅니다. 여기서 모델은 글을 읽고 다음 글을 만들어 내는 AI 본체이고 도구(tool)는 그 모델이 실행을 부탁할 수 있는 함수(function), 곧 값을 받아 정해진 일을 하고 결과를 돌려주는 코드 묶음입니다. 모델과 도구를 묶어 스스로 다음 할 일을 고르게 만든 프로그램을 Agent라고 부릅니다.

백화점 안내 데스크를 떠올리면 쉽습니다. 화장실 위치는 바로 알려 주지만 "이 운동화 270 있어요?"라는 질문에는 재고 시스템을 조회합니다. 다만 직원은 재고 질문이면 늘 조회하지만 모델의 판단은 매번 조금씩 달라서 같은 질문에도 도구를 건너뛸 때가 있습니다.

도구를 쓰기로 하면 모델은 어떤 도구를 어떤 값으로 부를지 적어 보내고(행동, action), 실행 결과를 돌려받아 읽은 뒤(관찰, observation), 더 부를 게 없으면 답을 씁니다. 도구 설명서를 쓰는 법은 도구 설계 글에, create_agent가 이 반복을 대신 돌리는 구조는 create_agent 해부 글에 따로 정리했습니다.

화면 뒤에는 어떤 기록이 쌓일까요?

Agent가 한 번 일할 때마다 메시지(message) 목록에 카드가 한 장씩 쌓입니다. 메시지는 누가 무슨 말을 했는지 적은 기록 한 줄입니다. 채팅 창에는 마지막 카드만 보이고 나머지는 이 목록 안에 남습니다.

사용자의 질문이 첫 장입니다

LLM 앱을 만드는 파이썬 라이브러리인 LangChain은 사용자가 보낸 말을 HumanMessage로 담습니다. 질문 글자 말고는 아무것도 없습니다.

모델은 도구를 실행하지 않고 요청서만 씁니다

두 번째 장 AIMessage의 본문(content)은 비어 있습니다. 대신 tool_calls 칸에 부를 도구 이름과 넘길 값, 요청 번호(id)가 적혀 있습니다. 모델은 글을 만들 뿐 함수를 직접 돌리지 못합니다.

함수는 우리 프로그램이 실행합니다

create_agent 안에서 함수를 돌리는 차례인 tools 단계가 요청서대로 함수를 돌리고 결과를 도구 메시지(ToolMessage)로 붙입니다. 초록으로 칠한 요청 번호가 같아서 어느 요청의 결과인지 짝이 맞습니다.

모델이 앞의 세 장을 다 읽고 답을 씁니다

모델을 한 번 더 부르면 이번에는 tool_calls가 빈 목록이고 본문에 답이 들어 있습니다. 부를 도구가 더 없으니 반복도 여기서 멈춥니다.

채팅 창에 뜨는 것은 마지막 한 장입니다

앱은 보통 result["messages"][-1].content만 꺼내 화면에 보여 줍니다. 검색을 했는지는 가운데 두 장에만 남아 있으니, 답만 보면 알 수 없는 게 당연합니다.

ReAct는 생각을 글로 쓰게 한 방법이었습니다

Agent 이야기를 찾아보면 ReAct라는 이름이 꼭 나옵니다. 추론(Reasoning)과 행동(Acting)을 합친 말로, 프린스턴 대학과 구글 연구진이 2022년 10월에 공개하고 이듬해 인공지능 학회 ICLR에서 발표한 방법입니다. 모델에게 생각(Thought), 행동(Act), 관찰(Obs)을 번갈아 글로 쓰게 했습니다.

지금은 이 일을 모델 API가 맡습니다. 두 상자 가운데 첫째가 2022년 방식, 둘째가 지금 방식입니다. 그래서 LangChain 문서도 Agent를 "도구를 반복해서 부르는 모델"이라고만 설명합니다. 추론 모델(reasoning model)은 답하기 전에 속으로 따져 보지만 그 내용은 숨기거나 요약만 보여 줍니다.

2022년 ReAct: 한 덩어리 글 속에 섞여 있음

Thought: 영상을 검색해야겠다.
Action: search[와인 입문]
Observation: (프로그램이 결과를 글로 붙여 넣음)
Thought: 이제 답할 수 있다.

프로그램은 모델이 쓴 글에서 "Action:" 뒤를 잘라 내 함수를 불렀습니다. 형식이 조금만 어긋나도 실행이 깨졌습니다.

지금: 모델 API가 칸을 나눠 돌려줌

content""tool_calls[{name: "search_videos", args: {query: "와인 입문"}, id: "call_7f2a"}]

OpenAI·Anthropic API는 도구 요청을 정해진 칸으로 따로 돌려줍니다. 다른 글의 예제 코드가 [Reasoning]이라는 말머리를 붙여 찍는 줄도 대개 이 칸이지 모델의 생각이 아닙니다.

PART 2 · 기록과 답 맞춰 보기

기록이 있다고 끝이 아닙니다. 마지막 답은 모델이 기록을 읽고 새로 쓴 글이라서 기록과 다른 말을 할 수 있습니다.

도구는 22도라고 했는데 답은 왜 25도일까요?

모델이 도구 결과를 그대로 옮기지 않고 자기가 아는 내용과 섞어 다시 쓰기 때문입니다. 회계 감사관이 장부의 숫자마다 영수증을 찾아보듯, 답의 문장마다 도구 결과라는 영수증이 있는지 맞춰 보면 차이가 보입니다. 아래 두 장이 그렇게 맞춰 본 결과입니다.

①에서 도구는 제 몫을 했습니다. 모델이 답을 새로 쓰면서 숫자를 바꾸고 묻지 않은 조언까지 보탰습니다. 기온 3도는 웃고 넘길 수 있지만 재고나 가격, 약 복용량에서 같은 일이 생기면 그대로 사고가 됩니다. 그래서 기록이 있어도 답을 기록과 맞춰 봐야 합니다.

이런 실패는 따로 연구될 만큼 흔합니다. 2026년 7월에 나온 ToolFailBench는 19개 모델을 시험하면서 도구를 건너뛰기, 결과 무시하기, 결과를 지어내기 같은 유형을 나눴습니다. 가장 잘한 모델도 필요할 때 도구를 부르고 결과대로 답한 비율이 86.33%였습니다. 나머지 13.67%에서는 앞의 실패 가운데 하나가 나왔습니다(논문).

주소만 돌려주는 도구는 무엇을 버렸을까요?

LangChain의 YouTubeSearchTool은 검색으로 받은 제목·채널·길이·조회 수를 버리고 주소만 문자열로 넘깁니다. 그러니 ②의 모델은 주소만 보고 내용을 짐작할 수밖에 없었습니다. 도구가 모델에게 무엇을 넘기는지가 답의 품질을 정합니다.

그래서 이번에는 Google이 제공하는 YouTube Data API v3로 도구를 직접 만듭니다. 공식 검색 결과에는 제목, 채널 이름, 올린 날짜가 들어 있습니다. 길이와 조회 수는 다른 호출(videos.list)로 따로 받아야 합니다.

모델이 읽을 칸을 골라 넘기는 도구

도구는 검색 결과에서 모델이 근거로 쓸 칸만 골라 깔끔하게 넘기면 됩니다. 아래 코드는 langchain 1.5, google-api-python-client 2.202 기준입니다.

import os
from googleapiclient.discovery import build
from langchain.tools import tool

KEY = os.environ["YOUTUBE_API_KEY"]
youtube = build("youtube", "v3", developerKey=KEY)
# ① 모델이 읽는 설명서
@tool
def search_videos(query: str, max_results: int = 3) -> list[dict]:
    """YouTube에서 영상을 검색해 제목·채널·올린 날짜·주소를 돌려줍니다.
    영상 추천을 부탁받으면 씁니다."""
    # ② 검색 한 번
    res = youtube.search().list(
        q=query, part="snippet", type="video",
        maxResults=max_results, relevanceLanguage="ko",
    ).execute()
    return [
        # ③ 근거로 쓸 칸만 골라서
        {
            "title": it["snippet"]["title"],
            "channel": it["snippet"]["channelTitle"],
            "published": it["snippet"]["publishedAt"][:10],
            "url": f"https://www.youtube.com/watch?v={it['id']['videoId']}",
        }
        for it in res["items"]
    ]

args = {"query": "와인 입문 가이드", "max_results": 2}
print(search_videos.invoke(args))
[{'title': '와인 처음이라면 이 영상부터', 'channel': '한 잔의 기록', 'published': '2026-04-18', 'url': 'https://www.youtube.com/watch?v=q3RxW8mTn2A'}, {'title': '레드와 화이트, 10분 만에 구분하기', 'channel': '소믈리에 노트', 'published': '2025-12-02', 'url': 'https://www.youtube.com/watch?v=Lk9pZc41vEo'}]

출력은 설명을 위한 예시 값입니다.

  1. 설명서. 모델은 함수 코드를 보지 못하고 이름, 함수 바로 아래 따옴표 세 개로 쓴 설명(docstring), 인자 타입만 읽고 언제 쓸지 고릅니다. "영상 추천을 부탁받으면"처럼 쓰는 때를 적어 두면 건너뛰는 일이 줄어듭니다.
  2. 검색 한 번. type="video"로 재생 목록과 채널을 빼고 relevanceLanguage="ko"로 한국어 영상을 앞에 둡니다. 2026년 11월 공식 문서 기준 검색 호출은 프로젝트마다 하루 100번까지라서 같은 검색어 결과는 저장해 두고 다시 쓰는 편이 좋습니다.
  3. 칸 고르기. 응답 전체를 넘기면 썸네일 주소 같은 칸까지 들어가 토큰(모델이 글을 세는 단위이자 요금 단위)만 늘어납니다. 반대로 주소만 넘기면 앞의 ②처럼 모델이 짐작합니다. 답에 쓸 근거인 제목, 채널, 날짜, 주소만 고릅니다.

Agent가 남긴 기록을 코드로 펼쳐 보기

답 한 줄 대신 메시지 목록 전체를 찍어 보면 앞에서 본 카드 네 장이 그대로 나옵니다. 메시지마다 붙어 있는 pretty_print()가 종류별 머리줄을 달아 보기 좋게 찍어 줍니다.

from langchain.agents import create_agent
from tools import search_videos

agent = create_agent(
    # ① 두뇌와 도구
    model="openai:gpt-6.1-sol",
    tools=[search_videos],
    system_prompt=(
        # ② 지어내지 말라는 규칙
        "당신은 영상 큐레이터입니다. "
        "영상은 search_videos 결과에서만 고르고, "
        "결과에 없는 주소나 내용은 쓰지 마세요."
    ),
)

question = "와인 처음 마셔 보는 사람이 볼 만한 영상 찾아 줘"
messages = [{"role": "user", "content": question}]
result = agent.invoke({"messages": messages})

for msg in result["messages"]:
    # ③ 마지막 답이 아니라 기록 전체
    msg.pretty_print()

③을 실행한 결과입니다. 같은 질문을 다시 보냈을 때 나온 예시 답입니다. 이번에는 모델이 규칙을 어기고 세 번째 영상을 덧붙였습니다.

================================ Human Message ================================= 와인 처음 마셔 보는 사람이 볼 만한 영상 찾아 줘 ================================== Ai Message ================================== Tool Calls: search_videos (call_7f2a) Call ID: call_7f2a Args: query: 와인 입문 가이드 ================================= Tool Message ================================= Name: search_videos [{"title": "와인 처음이라면 이 영상부터", "channel": "한 잔의 기록", "published": "2026-04-18", "url": "https://www.youtube.com/watch?v=q3RxW8mTn2A"}, {"title": "레드와 화이트, 10분 만에 구분하기", ...}] ================================== Ai Message ================================== 처음이라면 세 편을 권합니다. 1. 와인 처음이라면 이 영상부터 (한 잔의 기록) https://www.youtube.com/watch?v=q3RxW8mTn2A 2. 레드와 화이트, 10분 만에 구분하기 (소믈리에 노트) https://www.youtube.com/watch?v=Lk9pZc41vEo 3. 와인 잔 고르는 법 https://www.youtube.com/watch?v=Hw2bN7xQe5U

세 번째 영상 주소는 검색 결과에 없는, 지어낸 주소입니다.

  1. 두뇌와 도구. "openai:gpt-6.1-sol"처럼 "회사:모델" 문자열을 주면 LangChain이 알맞은 연결 코드를 고릅니다. "anthropic:claude-sonnet-5-5"로 바꿔도 나머지 코드는 그대로입니다. 모델 ID는 2026년 11월 기준입니다.
  2. 규칙. 결과에 없는 내용은 쓰지 말라고 적으면 지어내는 일이 줄지만 사라지지는 않습니다. 위 출력의 세 번째 영상처럼 규칙을 어기는 답이 나올 수 있어서 다음 단계의 대조가 필요합니다.
  3. 기록 전체. result["messages"]에는 질문, 도구 요청, 도구 결과, 답이 순서대로 들어 있습니다. 도구를 안 썼다면 가운데 두 장이 아예 없습니다. 검색을 했는지는 이걸로 판정합니다.

다 끝난 뒤에 한꺼번에 받지 않고 진행되는 동안 조각조각 받아 보고 싶으면 stream을 씁니다. stream_mode="updates"로 받으면 한 단계가 끝날 때마다 어느 단계(model 또는 tools)가 무엇을 더했는지 하나씩 들어옵니다.

for chunk in agent.stream({"messages": messages}, stream_mode="updates"):
    # ① 어느 단계가 일했나
    for node, update in chunk.items():
        last = update["messages"][-1]
        tag = f"[{node}]"
        # ② 모델이 쓴 도구 요청
        if node == "model" and last.tool_calls:
            for call in last.tool_calls:
                print(tag, "도구 요청 →", call["name"], call["args"])
        elif node == "tools":
            print(tag, "도구 결과 →", last.content[:40])
        else:
            print(tag, "최종 답 →", last.content.splitlines()[0])
[model] 도구 요청 → search_videos {'query': '와인 입문 가이드'} [tools] 도구 결과 → [{"title": "와인 처음이라면 이 영상부터", "channel": [model] 최종 답 → 처음이라면 세 편을 권합니다.
  1. 단계 이름. 한 덩어리(chunk)는 {"model": …}이나 {"tools": …}처럼 단계 이름을 열쇠로 한 사전(dict, 이름표와 값을 짝지은 묶음)입니다. 모델을 두 번 불렀으니 model이 두 번 나옵니다.
  2. 도구 요청. 다른 글의 예제는 이 줄에 [Reasoning]이라는 말머리를 붙이기도 합니다. 그래도 모델의 생각이 아니라 도구 요청 칸이라는 걸 알고 이름을 붙이면 로그를 읽을 때 덜 헷갈립니다.

import re
from langchain.messages import ToolMessage

URL = re.compile(r"https://www\.youtube\.com/watch\?v=[\w-]{11}")

def check_links(messages):
    # ① 영수증: 도구가 실제로 돌려준 주소
    receipts = {
        u for m in messages if isinstance(m, ToolMessage)
        for u in URL.findall(m.content)
    }
    # ② 답에 적힌 주소를 하나씩 대조
    for u in URL.findall(messages[-1].content):
        print("기록 있음" if u in receipts else "기록 없음", u)

check_links(result["messages"])
기록 있음 https://www.youtube.com/watch?v=q3RxW8mTn2A 기록 있음 https://www.youtube.com/watch?v=Lk9pZc41vEo 기록 없음 https://www.youtube.com/watch?v=Hw2bN7xQe5U
  1. 영수증 모으기. 도구 결과(ToolMessage)에 든 주소만 모읍니다. 도구가 사전 목록을 돌려줘도 메시지 안에는 JSON(사전 모양을 글자로 적는 형식) 글자로 들어갑니다. 그래서 글자 모양 규칙으로 찾는 정규식(regular expression)으로 주소를 골라낼 수 있습니다. 영상 ID는 11글자입니다.
  2. 대조. 마지막 답의 주소가 영수증 묶음에 없으면 모델이 만든 주소입니다. 서비스라면 그 줄을 지우거나 다시 물어보게 합니다.

링크를 아예 모델 글에 맡기지 않으면 더 확실합니다. 영상 카드는 앱이 도구 결과로 직접 그리고 모델에게는 한두 줄 소개만 쓰게 합니다. 그러면 화면의 링크는 모두 검색 결과에서 나옵니다.

도구 결과를 모델에게 거치지 않고 바로 답으로 내보내려면

LangChain 도구에는 @tool(return_direct=True) 옵션이 있습니다. 켜면 도구 결과가 곧바로 최종 답이 되고 모델을 다시 부르지 않습니다. 지어낼 틈은 없어지지만 모델이 결과를 읽고 고르거나 설명하는 단계도 사라집니다. 검색 결과 목록을 그대로 보여 주면 되는 화면에만 맞습니다.

여러 사람이 쓰는 서비스에서 기록을 매번 찍어 볼 수는 없습니다. 실행 기록을 자동으로 모아 보는 trace와 점수 매기는 법은 Agent 평가 글에서 다룹니다.
