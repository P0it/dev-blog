Agent를 하나 더 두면 정말 나아질까요?

일이 복잡해지면 Agent를 역할별로 나누고 싶어집니다. 검색 담당, 글쓰기 담당, 검토 담당처럼 팀을 꾸리는 그림이 그럴듯해 보이기 때문입니다. 그런데 Agent가 늘면 모델을 부르는 횟수와 토큰(token, 모델이 읽고 쓰는 글자 조각의 단위)도 함께 늘어 비용이 불어납니다.

Anthropic은 Agent가 챗보다 약 4배, 여러 Agent가 함께 일하는 Multi-Agent 시스템은 챗보다 약 15배 토큰을 쓴다고 밝혔습니다. 세 가지 일을 각각 어느 쪽에 맡기면 되는지 막대 아래에 함께 적었습니다.

챗학교 규정 한 가지 질문

규정 한 줄을 찾는 일은 챗이나 단순한 호출로 충분합니다. Agent를 둘 이유가 없습니다.

Agent자료를 모아 보고서 쓰기

자료를 찾고 읽고 정리하는 일은 Agent 하나가 도구를 써서 하면 됩니다. 토큰은 챗의 약 4배입니다.

Multi-Agent수십 곳을 동시에 조사

수십 곳을 동시에 조사하는 일은 하위 작업을 나눠 병렬로 돌릴 수 있고 한 창에 담기 어렵습니다. 토큰은 약 15배라 일의 가치가 그만큼 커야 합니다.

막대 높이는 Anthropic이 공개한 토큰 사용량 비율(챗 1배, Agent 약 4배, Multi-Agent 약 15배)입니다. 일마다 어느 막대가 맞는지는 이 글이 정리한 판단입니다.

나누면 컨텍스트가 깨끗해집니다

모델은 한 번에 읽을 수 있는 양이 정해져 있고 그 범위를 컨텍스트 창(context window)이라고 부릅니다. 한 Agent가 도구 서른 개의 설명을 모두 들고 있으면 창이 복잡해지고 알맞은 도구를 고르기도 어려워집니다.

LangChain은 Multi-Agent를 고려할 이유로 한 창에 다 담기 어려운 전문 지식, 도구가 너무 많아 잘못 고르는 문제, 하위 작업을 동시에 돌릴 수 있는 경우, 팀별 독립 개발, 조건이 맞아야 열리는 기능을 듭니다. 나눈 Agent는 자기 일에 필요한 것만 들고 있다가 결과 요약만 위로 올립니다.

Agent 하나가 다 맡을 때

한 창에 서로 다른 팀의 도구 설명이 섞여 있습니다. 창이 커질수록 모델이 필요한 것을 놓치기 쉽습니다.

역할별로 나눴을 때

각 Agent는 자기 도구만 들고 있습니다. 주 Agent는 긴 중간 과정 대신 결과 요약만 받아 창이 깨끗합니다.

나누는 방식은 다섯 가지입니다

LangChain은 Multi-Agent 방식을 Subagents, Handoffs, Skills, Router, Custom workflow 다섯 가지로 정리합니다. 이름은 달라도 모두 같은 질문에 답합니다. 누가 제어권을 쥐고 있고 사용자와는 누가 말하느냐입니다.

다섯 모양을 차례로 놓고 옆에 잘하는 일과 약한 일을 적었습니다. 약한 점은 공식 문서에 적힌 것만 옮겼습니다.

Subagents

주 Agent가 하위 Agent를 도구처럼 부르고 모든 길을 정합니다.

  • 병렬 처리
  • 여러 단계가 이어지는 일
  • 팀별로 따로 개발
  • 하위 Agent는 사용자와 직접 말하지 못함
  • 요청마다 같은 흐름을 처음부터 반복

Handoffs

도구 호출로 상태를 바꿔 제어권을 다른 Agent에게 넘깁니다.

  • 사용자와 직접 대화
  • 여러 단계가 이어지는 일
  • 같은 사용자의 반복 요청
  • 차례로 실행해서 병렬에는 약함

Skills

한 Agent가 필요할 때 전문 프롬프트와 지식을 불러옵니다.

  • 반복 요청에 효율적
  • 사용자와 직접 대화
  • 불러온 내용이 쌓여 여러 분야 일에서 토큰 증가

Router

입력을 분류해 전문 Agent 하나 이상에 보내고 결과를 합칩니다.

  • 병렬 처리
  • 요청마다 분류 호출이 필요
  • 여러 단계가 이어지는 일은 지원하지 않음

Custom

LangGraph로 직접 짠 흐름에 고정 로직과 Agent 단계를 섞습니다.

  • 다른 패턴을 노드로 끼워 넣기
  • 정해진 틀 없이 설계
  • 문서에 적힌 특정 약점은 없음

방식에 따라 모델을 부르는 횟수가 달라집니다

LangChain은 같은 일을 네 방식으로 돌려 모델 호출 수를 비교한 표를 공개합니다. 한 번만 시킬 때는 Handoffs와 Skills와 Router가 3번으로 적게 들고 Subagents는 4번입니다. 같은 사용자가 이어서 두 번 요청하면 상태를 기억하는 Handoffs와 Skills가 5번으로 가장 적습니다.

여러 분야를 한꺼번에 물으면 Subagents와 Router가 약 9천 토큰으로 가장 적고 Skills는 약 1만 5천 토큰입니다. 일의 모양에 따라 순위가 바뀌어서 세 상황을 나란히 놓았습니다.

한 번 요청

한 번만 시키면 Handoffs·Skills·Router가 3번, Subagents가 4번입니다.

같은 사용자가 두 번

같은 사용자가 이어서 두 번 요청하면 상태를 기억하는 Handoffs와 Skills가 5번으로 가장 적습니다.

여러 분야를 한꺼번에

여러 분야를 한꺼번에 물으면 호출은 Skills가 가장 적지만 토큰은 Subagents와 Router가 가장 적습니다.

내 상황에는 어느 방식이 맞을까요

우선 하나로 충분한지 따져 봅니다. LangChain은 도구와 프롬프트를 잘 갖춘 Agent 하나가 비슷한 결과를 내는 경우가 많다고 말합니다. Anthropic은 모든 Agent가 같은 맥락을 나눠 써야 하거나 서로 의존이 많은 일은 지금의 Multi-Agent에 잘 맞지 않는다고 말합니다.

같은 맥락을 나눠 써야 하면 Agent를 나눠도 정보를 계속 주고받아야 해서 이득이 줄어듭니다. 두 관문을 지난 뒤에야 나눌 방식을 고릅니다.

그래도 나눠야 한다면 일의 모양으로 고릅니다. 아래 그림에서 내 일에 해당하는 열을 찾아 ✓가 많은 방식을 봅니다. 공식 문서가 적은 강점과 약점을 겹쳐 본 것이라 참고용입니다.

✓는 공식 문서가 강점으로 적은 것, ✗는 약점으로 적은 것, 빈칸은 따로 적지 않은 것입니다. 실제로는 직접 돌려 비교해야 합니다.

다음 글에서는 가장 널리 쓰는 두 방식, 일을 맡기는 Subagents와 제어권을 넘기는 Handoffs를 직접 구현해 보겠습니다.
