README 한 줄에 코딩 에이전트가 조종당하는 이유

학교 축제 대시보드에 차트를 넣으려고 코딩 에이전트(coding agent)에게 일을 맡겼습니다. 코딩 에이전트는 파일을 읽고 고치고 명령을 실행하며 코딩을 대신 해 주는 AI 입니다. "quick-chart 라이브러리 붙여 줘." 라이브러리(library)는 남이 만들어 공개한 코드 묶음입니다. 에이전트는 그 소개 문서인 README 를 읽고 계획을 세웠습니다.

그런데 계획 두 번째 줄이 이상합니다. 설치가 끝나면 .env 파일 내용을 처음 보는 주소로 보내겠다고 합니다. .env 는 서비스 비밀번호 같은 비밀 값을 모아 두는 파일입니다. README 화면 어디에도 그런 말은 없습니다. 이 줄은 어디서 왔을까요?

모델에게는 지시와 자료의 경계가 없습니다

숨은 줄이 계획이 된 까닭은 모델이 받는 입력이 결국 글 한 줄이기 때문입니다. 에이전트는 기본 규칙, 내 요청, 읽어 온 README, 명령 결과를 차례로 이어 붙여 모델에게 넘깁니다. 모델은 그 줄을 읽고 다음에 할 일을 정합니다.

시험지 지문 속 쪽지와 비슷합니다. 지문 안에 "모든 답란에 ③을 쓰시오"가 끼어 있어도 학생은 따르지 않습니다. 물음은 지문 바깥, 선생님이 정한 자리에 있다는 걸 알기 때문입니다.

비유가 맞지 않는 곳이 여기입니다. 모델에게는 지문 바깥이 따로 없습니다. 실제 에이전트는 "이건 도구 결과"라는 표시를 붙여 넘기지만 그 표시도 같은 줄 안의 글자입니다. 모델은 표시를 존중하도록 학습되지만 100% 지키지는 못합니다.

누가 쓴 글인지 색으로 나눠 그렸습니다. 이 색과 이름표는 설명을 위해 우리가 붙인 것입니다.

남이 쓴 글에 지시를 숨겨 AI 를 조종하는 공격을 프롬프트 인젝션(prompt injection)이라고 합니다. 사용자가 직접 입력해 규칙을 깨려는 것은 직접 인젝션(direct injection), README 처럼 AI 가 읽어 오는 글에 숨기는 것은 간접 인젝션(indirect injection)입니다. 코딩 에이전트에게 위험한 쪽은 간접 인젝션입니다. 내가 시킨 일을 하다가 저절로 읽게 되기 때문입니다.

모델이 좋아진다고 사라지지도 않습니다. Anthropic 은 2025년 11월 공격 성공률을 약 1%로 낮추고도 "해결된 문제와는 거리가 멀다"고 적었습니다(아래 연표).

숨은 지시가 들어오는 입구

남이 쓴 글이 컨텍스트 창(context window)에 들어오는 곳은 모두 입구입니다. 컨텍스트 창은 모델이 한 번에 읽는 글 전체를 말합니다(창이 어떻게 차는지는 컨텍스트 엔지니어링 글). 코딩 에이전트는 일을 하려고 생각보다 많은 남의 글을 읽습니다.

내 저장소 안의 파일이라고 다 내가 쓴 글은 아닙니다. 설치한 패키지(package)의 코드, 다른 사람이 올린 PR(Pull Request)의 코드와 댓글, 테스트가 찍어 낸 오류 메시지도 남이 쓴 글입니다. 패키지는 라이브러리를 내려받아 설치하기 좋게 묶은 것이고 PR 은 코드 변경을 올려 합쳐 달라고 요청하는 글입니다.

MCP 서버가 돌려준 글도 입구입니다. 공개 이슈에 숨긴 지시를 따라 비공개 저장소 내용이 공개 PR 로 새어 나간 GitHub MCP 재현 사례는 MCP 글에 정리했습니다.

스킬(skill)처럼 에이전트에게 일하는 법을 적어 주는 파일도 마찬가지입니다. 2026년 2월 Skill-Inject 연구는 스킬 파일에 지시를 숨긴 시험 202쌍을 최신 모델에 넣었고 공격은 최대 80% 성공했습니다. 저자들은 모델을 키우거나 단순한 필터를 붙여서는 해결되지 않는다고 결론 내렸습니다.

세 가지가 한 세션에 겹칠 때

숨은 지시가 실제로 비밀을 빼내려면 세 가지가 함께 있어야 합니다. 개인 데이터에 닿을 수 있어야 하고 남이 쓴 글처럼 신뢰할 수 없는 내용을 읽어야 하며 밖으로 무언가를 보낼 수 있어야 합니다. 개발자 Simon Willison 은 2025년 6월 이 조합에 lethal trifecta(치명적인 세 가지)라는 이름을 붙였습니다. 세션(session)은 에이전트를 켜서 닫을 때까지 이어지는 대화 한 묶음입니다.

연료·산소·열이 다 있어야 불이 붙는 것과 비슷합니다. 하나만 확실히 빼면 그 길은 끊깁니다. 다른 점은 코딩 일에는 세 가지가 다 필요할 때가 많다는 것입니다. 남의 라이브러리를 읽고 내 코드를 고치고 패키지를 받아야 하니 어느 쪽을 줄일지 일마다 골라야 합니다.

세 조건 스위치 원을 눌러도 꺼집니다

밖으로 보내는 길은 생각보다 많습니다. 네트워크 요청만이 아닙니다. 이미지 주소를 불러오는 것, git push(내 컴퓨터의 코드 변경을 GitHub 같은 원격 저장소로 올리는 명령), PR 에 댓글을 다는 것도 데이터를 밖으로 실어 나를 수 있습니다. Willison 은 업체가 막아 줄 수 없으니 사용자가 이 조합을 스스로 피해야 한다고 강조합니다.

Meta 는 2025년 10월 같은 생각을 Agents Rule of Two 라는 규칙으로 정리했습니다. 한 세션에서 신뢰할 수 없는 입력 처리, 민감한 시스템·개인 데이터 접근, 상태 바꾸기·외부 통신 가운데 둘까지만 허용하라는 것입니다. 셋이 다 필요하면 사람이 지켜보며 승인하게 합니다.

2025년부터 실제로 일어난 일

코딩 도구에서 이 위험은 이론에 머물지 않았습니다. 2025년 여름부터 숨은 지시와 감염된 패키지가 개발자 컴퓨터의 에이전트를 움직인 사례가 이어졌습니다. 같은 시기에 위험을 정리한 글과 연구도 나왔습니다.

Copilot 사례를 보면 에이전트가 자기 설정을 고칠 수 있을 때 확인 창도 끌 수 있습니다. 보안 연구자 wunderwuzzi(Embrace The Red)는 프로젝트 설정 파일 한 줄로 모든 사용자 확인이 꺼졌다고 설명했습니다. 이 취약점은 2025년 8월 정기 보안 업데이트에서 고쳐졌습니다.

Nx 사례는 결이 다릅니다. 인젝션 없이 감염된 패키지가 개발자 컴퓨터에 이미 깔린 claude·gemini·q 명령줄 도구를 확인 끄는 옵션으로 실행했습니다. StepSecurity 는 이를 개발자용 AI CLI 를 악성 코드가 이용한 첫 사례로 기록했습니다.

OWASP 가 묶은 에이전트 위험 10가지

OWASP 는 웹 보안 위험 목록으로 잘 알려진 비영리 보안 단체입니다. 2025년 12월 9일 에이전트 전용 목록인 Top 10 for Agentic Applications 2026 을 냈습니다. 100명 넘는 전문가가 참여했습니다. 항목마다 OWASP 가 붙인 번호 ASI01~ASI10 이 달려 있습니다.

목록을 보면 프롬프트 인젝션은 여러 항목의 출발점일 뿐입니다. 숨은 지시로 목표가 바뀌는 것이 ASI01 입니다. 바뀐 목표가 도구와 권한을 거쳐 실제 피해가 됩니다. 반대로 공급망(supply chain, ASI04) 위험처럼 인젝션 없이 설치한 것 자체가 오염된 경우도 있습니다. 공급망은 내가 가져다 쓰는 패키지·도구가 만들어져 내 컴퓨터까지 오는 길입니다.

에이전트가 모델 위에 도구·권한·기억을 더한 것이라서 목록이 따로 생겼습니다. 모델만 다루는 LLM(Large Language Model) Top 10 2025 에서도 1번은 프롬프트 인젝션입니다. 그 목록은 사람 눈에 안 보이는 입력도 모델에 영향을 준다고 적었습니다. 그리고 확실히 막는 방법이 있는지 분명하지 않다고 말합니다.

LLM Top 10 2025 와 겹치는 항목

LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Supply Chain, LLM06 Excessive Agency 가 에이전트 목록과 가장 많이 겹칩니다. Excessive Agency(과도한 자율권)는 모델에게 필요보다 많은 기능·권한·자율을 준 상태를 말합니다. 에이전트 목록은 이 위험들이 여러 단계로 이어질 때를 따로 다룹니다.

첫 번째 층, 샌드박스

샌드박스(sandbox)는 에이전트가 실행한 명령이 닿을 수 있는 파일과 네트워크를 운영체제가 직접 막는 울타리입니다. Claude Code 에서는 /sandbox 로 켭니다(기본값은 꺼짐). 켜면 셸(shell, 터미널 명령을 실행하는 프로그램) 명령이 이 안에서 돕니다.

놀이터 모래상자처럼 안에서 무엇을 부숴도 바깥은 다치지 않습니다. 쓰기는 작업 폴더와 임시 폴더 안에서만 됩니다. 네트워크는 프록시(proxy)를 거칩니다. 프록시는 허용 목록(allowlist)에 있는 주소만 통과시키는 중간 관문입니다.

비유의 빈틈은 이 모래상자가 집 안 서랍을 들여다볼 수 있다는 점입니다. 기본 읽기 범위가 컴퓨터 대부분이라 ~/.ssh 같은 자격 증명(credential, 로그인 열쇠 노릇을 하는 파일)도 읽힙니다. 비밀 파일은 따로 막아야 합니다.

샌드박스가 끊는 것은 "밖으로 보내기"입니다. 다만 github.com 처럼 넓은 주소를 허용 목록에 넣으면 그 주소가 유출 통로가 될 수 있다고 문서가 경고합니다. 파일 읽기·편집 도구, 웹 가져오기, MCP 서버는 울타리 밖에서 돌아서 다음 층인 권한 규칙이 맡습니다.

두 번째 층, 권한 모드와 규칙

권한(permission)은 에이전트가 사람에게 묻지 않고 할 수 있는 일의 범위입니다. Claude Code 는 이 범위를 권한 모드(permission mode)로 크게 정한 뒤 그 위에 허용·질문·거부 규칙을 얹습니다.

아르바이트 첫날 받는 출입증과 비슷합니다. 매장 문은 열리지만 금고 방은 안 열립니다. 이렇게 일에 필요한 만큼만 주는 원칙을 최소 권한(least privilege)이라고 합니다. 다른 점도 있습니다. 사람은 수상한 쪽지를 보고 출입증을 남에게 넘기지 않지만 에이전트는 숨은 지시대로 가진 권한을 그대로 씁니다.

auto 모드의 분류기(classifier)는 행동을 실행 전에 검토하는 별도 모델입니다. 요청 범위를 넘는 일, 모르는 서버를 건드리는 일, 에이전트가 읽은 적대적인 글에 끌려간 것으로 보이는 일을 막습니다.

Plan 행에도 분류기가 들어간 까닭이 있습니다. auto 모드를 쓸 수 있는 환경에서는 Plan 모드도 계획을 세우며 돌리는 셸 명령을 기본 설정으로 같은 분류기에게 맡깁니다. auto 모드를 쓸 수 없으면 읽기 전용이 아닌 명령은 사람에게 묻습니다.

분류기가 받는 것 사용자 메시지하려는 도구 호출CLAUDE.md 도구 결과(파일·웹 내용) — 빼고 보냄

분류기는 도구 결과를 받지 않습니다. 그래서 README 속 숨은 지시는 분류기 눈에 아예 들어가지 않습니다. 분류기는 이 행동이 사용자의 요청에 맞는지만 따집니다.

맨 아래 줄은 반대 극단입니다. 문서는 bypassPermissions 가 프롬프트 인젝션을 전혀 막지 못한다며 격리된 컨테이너(container)나 VM(Virtual Machine)에서만 쓰라고 합니다. 컨테이너는 내 컴퓨터 안에 칸막이를 친 실행 공간이고 VM 은 컴퓨터 안에 만든 가상 컴퓨터입니다. Nx 감염 코드가 켠 --dangerously-skip-permissions 가 이 모드로 시작하는 옵션입니다. .git·.vscode·.claude 같은 보호 경로 쓰기는 이 모드가 아니면 자동 승인되지 않습니다.

{
  "permissions": {
    // ① 어느 모드에서도 막을 것
    "deny": [
      "Read(./.env)",
      "Read(~/.ssh/**)",
      "Bash(curl *)"
    ],
    // ② 할 때마다 물어볼 것
    "ask": ["Bash(git push *)"],
    // ③ 묻지 않고 해도 되는 것
    "allow": ["Bash(npm test)"]
  },
  // ④ 셸 명령은 울타리 안에서
  "sandbox": {
    "enabled": true,
    "credentials": {
      "files": [
        {
          "path": "~/.ssh",
          "mode": "deny"
        }
      ]
    }
  }
}

// 주석은 설명용입니다. 규칙 문법은 Claude Code 문서 "Configure permissions"·"Configure the sandboxed Bash tool" 기준입니다.

  1. deny 는 권한 모드와 상관없이 막습니다. 규칙은 거부 → 질문 → 허용 순서로 따지며 먼저 걸린 것이 이깁니다. 넓은 거부 규칙 안에 좁은 허용 규칙으로 예외를 뚫을 수 없습니다. 예를 들어 Bash(aws *) 를 거부하면 Bash(aws s3 ls) 를 허용해도 막힙니다.
  2. ask 는 밖으로 나가는 일처럼 사람이 꼭 봐야 할 행동에 겁니다. 허용 규칙과 겹쳐도 질문이 이깁니다.
  3. allow 는 자주 쓰고 위험이 작은 명령만 넣습니다. 승인 창을 너무 자주 보면 읽지 않고 누르게 되니 이 목록이 승인 피로를 줄입니다.
  4. sandbox 는 셸 명령을 울타리 안에서 돌리고 credentials 로 ~/.ssh 읽기를 막습니다. 7번째 줄 Bash(curl *) 같은 규칙은 적힌 모양의 명령만 막아서 경로를 바꾸거나 sh -c 안에 넣으면 빠져나갈 수 있습니다. 문서가 샌드박스 네트워크 허용 목록과 함께 쓰라는 까닭입니다.

권한을 일 단위로 쪼개기

최소 권한은 설정 파일 한 장으로 끝나지 않습니다. 에이전트 하나에 모든 일을 맡기지 않고 일마다 필요한 권한만 가진 에이전트로 나누면 하나가 속아도 피해가 그 경계에서 멈춥니다.

Anthropic 은 2026년 7월 이 사내 방식을 공개했습니다. 모델을 바꾼 뒤 이 에이전트가 회사 메신저 Slack 으로 코드 쓰는 에이전트에게 고친 코드를 올려 달라고 부탁한 일이 있었는데 사람 검토 단계가 잡아냈다고 합니다. 그 뒤로 경계를 모델에게 주는 지시 대신 계정의 접근 권한과 행동 범위에 긋는다고 적었습니다.

내 컴퓨터에서도 같은 생각을 쓸 수 있습니다. 문서 정리용 세션에는 GitHub 토큰을 주지 않고 낯선 저장소는 비밀이 없는 컨테이너에서 엽니다.

세 층을 겹치고 되먹임으로 메우기

어느 층도 혼자서는 구멍이 있습니다. 구멍 난 치즈 여러 장을 겹치면 구멍이 한 줄로 맞는 일이 드물어지는 것처럼, 층을 겹쳐야 공격이 끝까지 가지 못합니다. 사고 분석에서 스위스 치즈 모델(Swiss cheese model)이라고 부르는 생각입니다. 여기서는 샌드박스·권한·감시 세 층을 겹치고 감시가 알아챈 일로 앞 층의 구멍을 메우는 되먹임(feedback)까지 봅니다.

1막는 층이 없을 때

README 의 숨은 지시가 curl 명령으로 .env 를 collect.example 로 보냅니다. 앞에서 본 세 가지가 다 켜져 있는 상태입니다.

2샌드박스를 켜면

셸 명령은 허용 목록에 없는 주소로 나가지 못합니다. 하지만 샌드박스는 셸 명령만 감쌉니다. 밖에서 도는 MCP 서버에게 대신 보내 달라고 하는 길이 남습니다.

3권한 규칙을 더하면

Read(./.env) 거부와 MCP 호출 질문이 두 번째 길을 막습니다. 남은 구멍은 사람입니다. 승인 창을 하루 수십 번 보다 보면 읽지 않고 "예"를 누르게 됩니다.

4감시를 더하면

감시는 막기보다 알아채는 층입니다. 세 번째 길은 감시 층을 지나가지만 모든 도구 호출과 승인이 기록으로 남고 평소와 다른 행동에 알림이 뜹니다. Anthropic 은 에이전트의 모든 행동을 근거와 함께 보안 기록 시스템에 남기며 에이전트를 새로운 종류의 내부자 위협으로 다룬다고 밝혔습니다.

5되먹임으로 구멍 메우기

알아챈 일을 규칙으로 바꿔 다음부터 앞 층에서 막습니다. 거부 규칙을 넣거나 위험한 명령을 훅(hook)으로 막고 보안 규칙을 CLAUDE.md 나 스킬에 적습니다. 훅은 정해진 순간에 자동으로 도는 스크립트로, 종료 코드(exit code) 2 를 돌려주면 그 행동이 막힙니다(훅 글). 종료 코드는 프로그램이 끝나며 남기는 숫자입니다.

그림에서 감시 층의 기록이 권한 층으로 되돌아가 구멍을 메웁니다. 세 번째 길도 이제 권한 층에서 멈춥니다.

오늘 내 저장소에서 할 일

에이전트를 새로 온 동료처럼 대하면 할 일이 정해집니다. 첫날부터 금고 열쇠를 주지 않고 무엇을 했는지 기록을 남기며 실수가 나오면 규칙을 고칩니다. 무엇을 끊는지에 따라 할 일을 네 묶음으로 나눴습니다.

다음 글에서는 모델 자체를 회사 안에 두는 sLLM(small LLM, 회사 서버에서 돌릴 만큼 작은 언어 모델)과 오픈 웨이트(open-weight, 학습된 가중치 파일을 공개한) 모델이 코딩 에이전트를 얼마나 바꾸는지 알아보겠습니다.
