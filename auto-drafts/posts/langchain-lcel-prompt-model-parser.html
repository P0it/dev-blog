AI Service Track 09

챗봇 답변이 화면에 나오기까지 LangChain이 잇는 세 칸

챗봇에 질문을 넣으면 답이 말풍선 하나로 돌아옵니다. 그 말풍선 뒤에서 질문은 세 칸을 지나며 모양을 바꿉니다. LangChain은 이 세 칸을 | 기호로 이어 주는 파이썬 도구입니다.

ChatGPT 화면 한 장에 모인 기능들

ChatGPT는 검색해서 출처를 달고 지난 대화를 기억합니다. 표를 차트로 그리고 달력 같은 외부 앱도 부릅니다. 그런데 모델의 API(프로그램끼리 요청을 주고받는 창구)를 한 번 부르면 돌아오는 것은 글 한 덩어리입니다.

나머지 기능은 개발자가 모델 호출 앞뒤에 코드를 붙여 만듭니다. 붙일 부품이 늘수록 잇는 코드가 복잡해집니다. 이 연결을 도와주는 뼈대 코드가 프레임워크(framework)이고, LangChain은 LLM(Large Language Model, 글을 만드는 AI 모델) 서비스용 프레임워크입니다.

이름은 Language와 Chain을 합친 말입니다. 체인(chain)은 앞 칸의 결과가 다음 칸의 입력이 되도록 줄줄이 이어 붙인 묶음입니다.

분식집 주문으로 보는 프롬프트·모델·파서

답 한 번을 만드는 체인은 세 칸입니다. 분식집에서 떡볶이를 시킬 때와 구조가 비슷합니다. 메모를 전표로 옮겨 적고 주방이 요리를 쟁반에 내면 음식만 덜어 상에 놓습니다.

비유가 맞지 않는 부분도 있습니다. 주방은 같은 전표에 같은 음식을 내지만 모델은 같은 프롬프트에도 답이 조금씩 달라질 수 있습니다.

프롬프트(prompt)는 모델에게 주는 지시문입니다. 모델(model)은 지시문을 읽고 글을 만듭니다. 출력 파서(output parser)는 모델이 돌려준 결과에서 필요한 부분만 꺼내 프로그램이 쓰기 좋은 모양으로 바꿉니다.

세 칸을 |로 잇는 문법을 LCEL(LangChain Expression Language)이라고 부릅니다. 터미널 명령을 이을 때 쓰는 파이프(pipe) 기호에서 가져왔습니다. 정원 호스 여러 개를 이어 물을 보내는 장면을 떠올리면 됩니다.

파이프를 지날 때마다 바뀌는 데이터 모양

체인을 이해하는 가장 빠른 방법은 값을 따라가는 것입니다. 칸의 이름보다 이음새를 지나는 값의 모양을 봐 주세요.

입력

처음 넣는 값은 딕셔너리(dictionary)입니다. 파이썬에서 이름표와 값을 짝지어 담는 자료형으로 줄여서 dict라고 씁니다. 주문 메모에 "메뉴: 떡볶이, 맵기: 보통"이라고 적는 것과 같습니다.

prompt 칸을 지난 뒤

프롬프트 칸이 {topic} 같은 빈칸에 값을 채웁니다. 결과는 메시지 묶음(ChatPromptValue)입니다. system 메시지는 모델의 역할, human 메시지는 사용자의 말입니다.

model 칸을 지난 뒤

모델 칸은 묶음을 API로 보내고 AIMessage를 받습니다. 쟁반처럼 답 말고도 많은 것이 실려 옵니다. usage_metadata는 토큰(token, 모델이 글을 읽고 쓰는 단위) 사용량입니다. 요금이 이 숫자로 정해집니다.

parser 칸을 지난 뒤

StrOutputParser가 쟁반에서 문자열(string, 글자를 이어 놓은 값)만 꺼냅니다. 이제 화면에 바로 찍을 수 있고 다음 체인에 넘기기도 쉽습니다. 파서를 빼면 체인은 AIMessage까지만 돌려줍니다. 파서가 꼭 필요한 칸은 아닙니다.

그림 속 답과 토큰 수는 예시 값입니다.

코드로는 세 칸을 만들어 |로 잇습니다.

from langchain.chat_models import init_chat_model
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate

# ① 빈칸이 있는 프롬프트
prompt = ChatPromptTemplate.from_messages([
    ("system", "친절한 과학 선생님입니다."),
    ("human", "{topic}을 {level} 눈높이로 설명해 주세요."),
])
# ② 어느 회사의 어떤 모델인지
model = init_chat_model(
    "openai:gpt-6.1-sol",
    use_responses_api=True,
)
parser = StrOutputParser()

# ③ 잇기만 합니다. 아직 아무것도 실행되지 않습니다
chain = prompt | model | parser
print(type(chain).__name__)

# ④ 빈칸 이름과 같은 키로 값을 넘겨 실행
answer = chain.invoke({"topic": "양자역학", "level": "중학생"})
print(answer)
터미널 · 누르면 출력이 다시 찍힙니다
$ python chain.py RunnableSequence 양자역학은 아주 작은 세계의 규칙입니다.

출력은 예시 답입니다. 설치는 pip install langchain langchain-openai이고 langchain 1.4.9, langchain-core 1.7.6, langchain-openai 1.7.4(2026-11-05) 기준입니다. 실행 전에 API 키를 환경 변수(프로그램 밖에서 넣어 주는 설정값) OPENAI_API_KEY에 넣어 둡니다.

  1. from_messages는 역할과 문장을 짝지어 받습니다. 중괄호 안 이름이 빈칸입니다. from_template은 human 메시지 하나만 만들 때 쓰는 짧은 형태입니다.
  2. "openai:gpt-6.1-sol"처럼 회사와 모델 이름을 문자열로 적습니다. "anthropic:claude-sonnet-5-5"로 고치면 Claude를 부릅니다(pip install langchain-anthropic 필요). use_responses_api=True는 OpenAI의 최신 API 창구로 보내라는 옵션입니다.
  3. |를 쓰면 바로 실행될 것 같지만 RunnableSequence라는 객체(object, 값과 기능을 묶은 것) 하나가 만들어질 뿐입니다. 호스를 연결만 하고 수도꼭지는 아직 열지 않은 상태입니다.
  4. invoke가 수도꼭지입니다. 넘기는 값의 키(딕셔너리의 이름표)는 빈칸 이름과 같아야 합니다. 칸 세 개가 차례로 실행되고 마지막 칸의 결과가 돌아옵니다.

답이 조금씩 나오는 스트리밍

ChatGPT는 답을 조금씩 찍어 줍니다. 모델이 다 쓸 때까지 기다리지 않고 조각을 받는 대로 보여 주는 스트리밍(streaming)입니다. 전체 시간은 같아도 사용자가 빈 화면을 보는 시간이 줄어듭니다.

체인에서는 invoke를 stream으로 바꾸면 됩니다. 조각 하나를 청크(chunk)라고 부릅니다.

답 끝에 "AI가 쓴 답입니다" 안내를 붙이려고 체인 끝에 함수(function, 입력을 받아 결과를 돌려주는 코드 묶음)를 더하면 스트리밍이 사라지기도 합니다. 일반 함수는 입력이 다 모여야 실행되기 때문입니다. 앞에서 조각이 흘러와도 이 칸이 전부 모아 둔 뒤 한 번에 내보냅니다.

해결법은 함수를 제너레이터(generator)로 바꾸는 것입니다. 제너레이터는 yield로 값을 하나씩 내보내는 함수입니다. 조각 하나를 받으면 바로 내보내고 다음 조각을 기다립니다. 앞선 조각은 이미 화면에 찍혀 있으니 흐름이 끊기지 않습니다.

# chain 은 앞 코드의 prompt | model | parser 입니다
# ① 메서드 이름만 stream 으로
for chunk in chain.stream({"topic": "양자역학", "level": "중학생"}):
    print(chunk, end="", flush=True)

# ② 일반 함수: 스트리밍이 끝까지 막힙니다
blocked = chain | (lambda text: text + "\n(AI가 쓴 답입니다)")

# ③ 제너레이터: 조각을 받자마자 넘깁니다
def add_notice(chunks):
    for chunk in chunks:
        yield chunk
    yield "\n(AI가 쓴 답입니다)"
kept = chain | add_notice
  1. 메서드(method)는 객체에 딸린 함수입니다. stream은 청크를 for 문(반복문)으로 하나씩 꺼내게 해 줍니다. flush=True를 빼면 터미널이 글자를 모아 뒀다가 찍어서 효과가 줄어듭니다.
  2. lambda는 이름 없는 짧은 함수입니다. | 옆에 함수를 두면 LangChain이 칸(RunnableLambda)으로 감쌉니다. 오류 없이 한 덩어리로 바뀌어서 눈치채기 어렵습니다.
  3. 입력으로 청크 묶음을 받고 yield로 내보냅니다. 답이 끝난 뒤 안내 문구를 덧붙이는 처리도 이렇게 하면 스트리밍을 유지합니다.

챗봇이 답 대신 오류로 멈추는 두 가지 이유

사용자에게는 "오류가 발생했습니다" 한 줄로 보이는 일이 개발 중에는 대개 KeyError나 ValueError입니다. 체인을 처음 만들면 이 둘을 가장 먼저 만납니다.

원인은 하나입니다. 앞 칸이 내놓은 모양이 다음 칸이 받는 모양과 다릅니다.

오류 문구는 langchain-core 1.7.6에서 직접 실행해 옮겼고 안내 링크 부분만 줄였습니다. 돌기 모양은 값의 종류를 나타내려고 그린 것입니다.

프롬프트의 빈칸은 언제 채워질까요?

챗봇이 오늘 날짜를 알고 늘 같은 말투로 답하는 것은 대개 개발자가 프롬프트에 미리 적어 두기 때문입니다. 빈칸마다 채우는 때가 다릅니다. 말투는 처음 한 번 정하고 날짜는 부를 때마다 계산하고 질문은 사용자가 줍니다.

앞의 두 가지를 미리 정하는 메서드가 partial입니다. 값을 넘기면 고정되고 함수를 넘기면 부를 때마다 다시 계산합니다. 전표에 "매장 식사"가 미리 인쇄돼 있고 주문 번호만 그때그때 찍히는 것과 비슷합니다.

전표와 달리 인쇄한 값도 바꿀 수 있습니다. invoke에 같은 이름의 값을 주면 그 값이 partial 값을 덮어씁니다.

챗봇이 지난 말을 기억하게 하는 빈칸

"3살이에요"라고만 답해도 챗봇은 무슨 이야기인지 압니다. 모델의 API는 앞 요청을 기억하지 않으니 서비스가 앞선 말을 매번 프롬프트에 넣어 보내는 덕분입니다. ("placeholder", "{history}")는 메시지가 몇 개든 통째로 들어가는 빈칸을 만듭니다.

from datetime import date
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    # ① 두 빈칸은 아래 partial 로 미리 채웁니다
    ("system", "오늘은 {today}입니다. {tone} 말투로 답합니다."),
    # ② 메시지 여러 개가 들어가는 빈칸
    ("placeholder", "{history}"),
    ("human", "{question}"),
]).partial(
    # ③ 함수: 부를 때마다 계산
    today=lambda: date.today().isoformat(),
    # ④ 값: 고정
    tone="친절한",
)

print(prompt.input_variables)
print(prompt.invoke({
    "question": "3살이에요",
    "history": [("human", "강아지가 눈을 긁어요"), ("ai", "몇 살인가요?")],
}).to_messages())
터미널 · 누르면 출력이 다시 찍힙니다
$ python prompt.py ['question'] [SystemMessage('오늘은 2026-11-05입니다. 친절한 말투로 답합니다.'), HumanMessage('강아지가 눈을 긁어요'), AIMessage('몇 살인가요?'), HumanMessage('3살이에요')]

읽기 쉽게 메시지의 부가 정보는 줄였습니다. 프롬프트에 JSON(JavaScript Object Notation, 이름표와 값을 글자로 적는 형식) 예시를 그대로 적으면 중괄호까지 빈칸으로 읽혀 KeyError가 납니다. 글자 중괄호는 {{ }}로 두 번 적습니다.

  1. 두 빈칸은 코드 아래쪽 partial이 채우므로 호출할 때 넘기지 않아도 됩니다.
  2. placeholder는 값을 안 넘겨도 오류가 나지 않습니다. 그래서 필수 입력 목록(input_variables)에 history가 없습니다.
  3. 함수는 입력값 없이 호출됩니다. 프롬프트를 만들 때가 아니라 부를 때 실행되므로 서버(서비스를 계속 돌리는 컴퓨터)를 오래 켜 둬도 날짜가 낡지 않습니다.
  4. 이 값이 입력 목록에서 빠져서 호출하는 쪽 코드가 짧아집니다. 필요하면 invoke에서 덮어쓸 수 있습니다.
다른 코드에서 만나는 프롬프트 표기
표기뜻
PromptTemplate.from_template("…")역할 구분 없는 문자열 프롬프트입니다. 챗 모델에 보내면 human 메시지 하나로 바뀝니다.
PromptTemplate(template=…, partial_variables=…)생성자로 직접 만드는 형태입니다. 하는 일은 .partial()과 같습니다.
MessagesPlaceholder("history")("placeholder", "{history}")와 비슷하지만 기본값은 필수 입력입니다. optional=True를 주면 같아집니다.

"깊게 생각하기" 버튼 뒤의 모델 옵션

챗봇 화면의 "빠른 답"과 "깊게 생각하기"는 코드에서 모델 옵션 하나입니다. 모델이 답을 쓰기 전에 생각하는 양을 reasoning_effort로 정합니다. 많이 생각할수록 답은 늦게 나오고 토큰도 더 씁니다.

낡은 예제에서 자주 부딪히는 옵션은 temperature입니다. 답에 우연을 얼마나 섞을지 정하는 값입니다. OpenAI 문서는 GPT-6 계열에서 생각하는 양이 none이 아니면 이 옵션을 빼라고 안내합니다. 그림의 GPT-6.1 Sol은 none을 지원하지 않아 쓸 수 없습니다.

use_responses_api를 켜면 달라지는 요청

OpenAI의 GPT-6 안내 문서는 Responses API로 시작하라고 적어 두었고 GPT-6.1 Sol의 도구 호출도 이쪽에서만 됩니다. 그래서 이 글의 코드에는 옵션을 켜 두었습니다. 같은 코드를 모의 서버로 받아 본 요청 본문은 아래와 같습니다.

옵션 없음POST /v1/chat/completions

{ "model": "gpt-6.1-sol","messages": [{ "role": "user", "content": "hi" }],"max_completion_tokens": 300,"reasoning_effort": "low" }

use_responses_api=TruePOST /v1/responses

{ "model": "gpt-6.1-sol","input": [{ "role": "user", "content": "hi" }],"max_output_tokens": 300,"reasoning": { "effort": "low" } }

옵션을 켜면 AIMessage.content가 문자열에서 블록 목록으로 바뀝니다. StrOutputParser와 .text는 두 경우 모두 글자만 돌려줍니다. 회사마다 제약이 달라 모델을 바꿀 때는 모델 교체를 다룬 글처럼 요청까지 확인하는 편이 안전합니다.

출력 파서가 만드는 세 가지 모양

반려동물 앱이 AI 답을 칩이나 입력 양식으로 보여 주려면 프로그램이 답을 항목별로 읽을 수 있어야 합니다. 출력 파서는 글자로 온 답을 파이썬 값으로 바꿉니다. 아래는 같은 질문을 세 파서로 받은 결과와 그 값으로 그릴 수 있는 화면입니다.

답은 예시입니다. 값 모양은 파서를 직접 실행해 확인했습니다.

여기서 많이 오해하는 부분이 있습니다. 파서는 모델이 그 모양으로 쓰게 만들지 못합니다. 이미 나온 글을 읽기만 합니다. 그래서 모델에게 원하는 형식을 프롬프트로 알려 줘야 합니다. get_format_instructions()가 그 지시문을 만들어 주지만 JsonOutputParser()가 주는 문장은 Return a JSON object. 한 줄이라 항목 이름까지 정해 주지 못합니다.

파서가 답을 읽다가 겪는 네 가지 상황

네 경우 모두 langchain-core 1.7.6의 파서에 직접 넣어 확인했습니다. 넷째가 가장 위험합니다. 오류가 나지 않아 화면에 잘못된 값이 그대로 나갑니다.

그래서 지금은 항목 이름과 타입이 정해진 답이 필요하면 with_structured_output을 먼저 씁니다. 원하는 모양을 스키마(schema, 항목 이름과 타입을 적은 양식)로 요청에 실어 보내고 지원하는 모델은 그 양식대로 답합니다. 답안을 빈 종이가 아니라 OMR 카드에 쓰게 하는 것과 비슷합니다. OMR 카드와 달리 내용이 맞는지까지 보장하지는 않습니다.

from pydantic import BaseModel
from langchain_core.prompts import ChatPromptTemplate

# ① 받고 싶은 답의 양식
class Disease(BaseModel):
    name: str
    symptoms: list[str]

prompt = ChatPromptTemplate.from_template("{name} 증상을 알려 주세요.")
# ② 모델 + 파서가 한 칸으로 합쳐집니다
chain = prompt | model.with_structured_output(Disease)

result = chain.invoke({"name": "결막염"})
print(result.symptoms)
터미널 · 누르면 출력이 다시 찍힙니다
$ python symptoms.py ['충혈', '눈곱', '가려움', '눈물']

출력은 예시 답입니다.

  1. Pydantic은 클래스(데이터 모양을 정하는 틀)로 양식을 적고 값을 검사해 주는 라이브러리(가져다 쓰는 코드 묶음)입니다. 항목 이름과 타입이 그대로 스키마가 됩니다.
  2. 실제 요청을 받아 보면 OpenAI에는 json_schema 형식과 "strict": true가 함께 나갑니다. 결과는 문자열이 아니라 Disease 객체라서 result.symptoms처럼 바로 꺼내 씁니다. 양식 설계와 검증은 구조화 출력을 다룬 글에서 다룹니다.

파서가 쓸모없어진 것은 아닙니다. JsonOutputParser를 stream과 함께 쓰면 지금까지 도착한 항목을 계속 내줍니다. 답을 기다리는 동안 양식이 위에서부터 채워지는 화면을 만들 수 있습니다.

체인을 이을 때 입력이 사라지는 함정

"강아지 눈이 좀 이상해요"처럼 짧게 물어도 어떤 서비스는 질문을 먼저 또렷하게 다듬은 뒤 답합니다. 사용자는 평소처럼 쓰고 답의 품질만 좋아집니다. 체인 둘을 이으면 이런 구조를 만들 수 있습니다.

대화 내용은 설명을 위해 만든 예시입니다. 수의학 조언이 아닙니다.

첫 체인의 답을 다음 프롬프트의 빈칸에 넣으려면 딕셔너리로 이름표를 붙여야 합니다. 여기서 많이 틀립니다. {"better": rewrite}는 결과에 이름표를 붙이지만 원래 입력을 버립니다.

from langchain_core.runnables import RunnablePassthrough

# ① 앞 체인: 질문을 다듬습니다
rewrite_prompt = ChatPromptTemplate.from_template(
    "수의사가 답하기 좋게 다시 쓰세요: {question}"
)
rewrite = rewrite_prompt | model | StrOutputParser()
# ② 뒤 프롬프트: 원래 입력과 앞 결과가 모두 필요합니다
answer_prompt = ChatPromptTemplate.from_template(
    "강아지 나이: {age}\n질문: {better}\n답해 주세요."
)
# ③ 입력은 두고 better 만 추가
chain = (
    RunnablePassthrough.assign(better=rewrite)
    | answer_prompt | model | StrOutputParser()
)
print(chain.invoke({
    "question": "강아지 눈이 좀 이상해요",
    "age": "3살",
}))
터미널 · 누르면 출력이 다시 찍힙니다
$ python rewrite.py 3살이면 결막염일 수 있습니다. 눈곱이 늘면 병원에 가 보세요.

출력은 예시 답입니다. 수의학 조언이 아닙니다.

  1. 체인 하나를 통째로 다른 체인의 칸으로 쓸 수 있습니다. 따로 테스트하기 쉽고 프롬프트 하나가 지나치게 길어지는 것을 막습니다.
  2. 앞 체인의 결과만 필요하면 {"better": rewrite}로 충분합니다. 원래 입력도 필요한 경우에만 아래 방식을 씁니다.
  3. assign은 입력 딕셔너리에 새 키를 더해서 그대로 넘깁니다. 대신 모델을 두 번 부르므로 토큰 비용과 기다리는 시간도 함께 늘어납니다.

모델이 실패해도 답을 내는 재시도와 대체 모델

모델 칸이 실패하면 어떻게 될까요? 대비해 두면 사용자는 답이 조금 늦게 나온다고만 느낍니다. 체인의 모든 칸은 Runnable이라는 같은 약속을 따라서 invoke, stream, batch(여러 입력을 한 번에 처리)를 똑같이 쓸 수 있고 실패 대책도 칸에 붙입니다.

model.with_retry(stop_after_attempt=3)은 같은 칸을 다시 시도하고 .with_fallbacks([claude])는 그래도 안 되면 다른 모델로 넘어갑니다. 모델 옵션 max_retries는 모델 호출에만 쓰고 with_retry는 어떤 칸에든 붙일 수 있습니다. 재시도는 그만큼 시간이 더 걸리므로 횟수를 작게 잡습니다.

LangSmith로 체인 안쪽을 보는 법

"답이 이상해요" 하는 문의를 받으면 어느 칸이 문제였는지 찾아야 합니다. print로 찾기는 어렵습니다. LangSmith는 칸마다 입력, 출력, 시간, 토큰을 기록해 웹 화면으로 보여 주는 서비스입니다. 이런 기록을 트레이스(trace)라고 합니다. 택배 조회처럼 어디를 언제 지났는지 나옵니다.

코드는 고치지 않습니다. 환경 변수 LANGSMITH_TRACING=true와 LANGSMITH_API_KEY만 설정하면 기록이 시작됩니다. 사용자의 입력도 함께 저장되므로 개인 정보가 들어가는 서비스는 저장 범위를 먼저 정해야 합니다.

남이 만든 프롬프트를 가져올 때

어느 날 챗봇 말투가 갑자기 달라진다면 프롬프트 칸이 바뀐 것일 수 있습니다. 질문을 다듬는 프롬프트처럼 잘 만든 프롬프트는 LangSmith 허브(hub)에서 받아 쓸 수 있습니다. 편리하지만 공개 프롬프트는 검증되지 않은 사용자 글이고 그대로 시스템 메시지에 들어갑니다. 그 안에 모델을 속이는 지시가 숨어 있으면 프롬프트 인젝션(prompt injection)이 됩니다.

이름만 적으면 늘 최신 판을 받습니다. 게시자가 내용을 고치면 내 서비스의 답도 함께 바뀝니다. 그래서 내용을 읽고 확인한 판의 번호(커밋)까지 적어 고정합니다.

from langsmith import Client

client = Client()
prompt = client.pull_prompt(
    # ① 판 번호까지 고정
    "owner/prompt-name:abc1234",
    # ② 남의 공개 프롬프트 허용
    dangerously_pull_public_prompt=True,
    # ③ 모델 설정은 받지 않기
    include_model=False,
    # ④ 환경 변수의 비밀값 잠금
    secrets_from_env=False,
)
chain = prompt | model | StrOutputParser()
  1. 콜론 뒤에 커밋 해시(판마다 붙는 고유 번호)를 붙입니다. owner/prompt-name은 예시 이름입니다.
  2. 기본값은 False라서 켜지 않으면 다른 사람의 공개 프롬프트를 받지 못합니다. 게시자의 평판이 아니라 내용을 직접 읽고 켭니다.
  3. 켜면 내가 고르지 않은 모델 설정이 프롬프트에 딸려 옵니다. 끄고 모델은 내 코드에서 정합니다.
  4. True면 남이 적은 설정이 내 컴퓨터의 API 키 같은 비밀값을 읽어 갈 수 있습니다. 문서도 내려받은 프롬프트를 글이 아니라 실행되는 설정처럼 다루라고 적어 두었습니다.
이 설정들이 생긴 배경, 보안 취약점 두 건

CVE-2026-45134(2026년 5월 공개)는 내려받은 프롬프트를 객체로 복원하는 과정의 취약점입니다. langsmith 0.8.0에서 고쳐졌고 위 ②~④가 공식 권고입니다. CVE-2025-68664(2025년 12월 공개)는 langchain-core 직렬화 기능의 취약점으로 1.2.5에서 고쳐졌습니다. 둘 다 프레임워크를 최신으로 유지하면 막을 수 있습니다.

2026년에 LCEL을 쓰는 곳과 넘어갈 곳

LCEL은 2023년 8월에 나왔고 LangChain 1.0은 2025년 10월에 나왔습니다. 지금 공식 문서의 첫 화면은 에이전트(agent, 도구를 골라 쓰며 스스로 여러 단계를 진행하는 AI 프로그램) 중심이어서 LCEL 설명은 거의 보이지 않습니다. 그렇다고 사라진 것은 아닙니다. Runnable과 |는 langchain-core에서 그대로 동작합니다.

공식 문서가 LCEL의 사용 범위를 정해 주지는 않습니다. 아래는 이 글을 쓰며 정리한 제 기준입니다. 흐름이 어떤 모양인지를 먼저 봅니다.

비판도 함께 봐 둘 만합니다. 2024년에는 AI 테스트 회사 Octomind의 LangChain 중단 글이 개발자 커뮤니티 Hacker News에서 크게 논의됐습니다. 추상화 층이 많아 안쪽 코드를 직접 고치기 어렵다는 비판이었습니다. 저는 칸마다 무엇이 지나가는지 이 글처럼 직접 찍어 보면 그런 답답함이 꽤 줄어든다고 봅니다.
