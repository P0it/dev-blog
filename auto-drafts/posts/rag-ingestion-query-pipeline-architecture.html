RAG는 질문이 오기 전에
무엇을 준비해 둘까요?

RAG(Retrieval-Augmented Generation)는 모델이 학습한 적 없는 문서로 답하게 하는 구조입니다. 문서를 나누고 색인하는 일은 질문이 오기 전에 끝나 있습니다. 질문이 오면 그 색인에서 몇 개만 찾아 모델에 건넵니다.

같은 질문을 실제 구성 요소 이름으로 다시 그리면 아래 흐름도가 됩니다. 사서가 손님이 오기 전에 하던 일이 적재 파이프라인이고 질문을 받은 뒤에 하던 일이 질의 파이프라인입니다. 카드에 매긴 위치 번호는 임베딩 벡터입니다.

검색이 빗나갈 때 고치는 곳

답이 틀렸다면 모델보다 검색을 먼저 봅니다. 맞는 청크가 모델 앞에 놓이지 않으면 모델은 답할 근거가 없습니다. 고칠 곳은 두 파이프라인에 나뉘어 있습니다. 아래 기본값과 수치는 2026년 11월에 확인한 문서 기준입니다.

적재 파이프라인에서 정하는 것

  • 청크 크기와 겹침너무 작으면 문맥이 끊기고 너무 크면 엉뚱한 내용이 섞인다. OpenAI 벡터 저장소의 기본값은 800토큰에 겹침 400토큰
  • 청크에 문맥 붙이기Contextual Retrieval. "건조기 DR-900 오류 코드 표의 일부"처럼 50~100토큰짜리 설명을 청크 앞에 붙이고 나서 임베딩한다
  • 메타데이터제품 이름, 문서 종류, 개정 날짜를 청크와 함께 저장해 검색 범위를 좁힌다
  • 임베딩 모델 고정문서와 질문에 같은 모델을 쓴다. 모델을 바꾸면 청크 전부를 다시 임베딩한다

질의 파이프라인에서 정하는 것

  • 하이브리드 검색hybrid search. 벡터 검색은 뜻이 가까운 청크를, 키워드 검색(BM25)은 "E5"처럼 글자가 같은 청크를 찾는다. 두 순위는 RRF(Reciprocal Rank Fusion) 같은 방법으로 합친다
  • 리랭킹후보를 넉넉히 뽑고 질문과 한 쌍씩 다시 채점해 줄인다. Cohere Rerank, Voyage rerank, 오픈 모델 bge-reranker가 이 일을 한다
  • 모델에 넘기는 청크 수많이 넘길수록 모델이 읽을 토큰이 늘어 비용과 지연이 커진다
  • 출처 표시청크마다 문서 이름과 쪽 번호를 함께 넘겨 답에 붙이게 한다

Anthropic이 2024년 9월에 공개한 실험에서는 문맥 붙이기와 하이브리드 검색을 함께 썼을 때 상위 20개 검색 실패율이 5.7%에서 2.9%로 내려갔고 리랭킹까지 더하자 1.9%가 됐습니다.

Agentic RAG와 Graph RAG에서 달라지는 곳

두 변형은 위 흐름도를 버리지 않고 한쪽 파이프라인을 바꿉니다. Agentic RAG는 질의 쪽을 바꾸고 Graph RAG는 적재 쪽을 바꿉니다. 문서가 적다면 둘 다 필요 없습니다. Anthropic은 지식 베이스가 20만 토큰(약 500쪽)보다 작으면 검색 없이 전부 프롬프트에 넣으라고 권합니다.

Agentic RAG · 질의 파이프라인이 루프가 된다

  • 바뀌는 것검색이 항상 한 번 실행되는 단계에서 모델이 필요할 때 부르는 도구로 바뀐다
  • 모델이 정하는 것검색을 할지, 어떤 검색어로 할지, 결과가 모자라면 다시 할지
  • 맞는 질문"E5를 지웠더니 E7이 떠요"처럼 검색 한 번으로 끝나지 않는 질문
  • 늘어나는 비용모델 호출 횟수가 질문마다 달라져 지연과 비용을 미리 알기 어렵다

Graph RAG · 적재 파이프라인에 그래프가 더해진다

  • 바뀌는 것청크에서 LLM으로 엔티티(entity)와 관계를 뽑아 그래프를 만든다
  • 미리 만들어 두는 것가까운 엔티티를 커뮤니티로 묶고 커뮤니티마다 요약 보고서를 써 둔다
  • 맞는 질문"설명서 전체에서 가장 자주 나오는 고장 원인은?"처럼 청크 몇 개로는 답할 수 없고 문서 전체를 종합해야 하는 질문
  • 늘어나는 비용적재 단계에서 청크마다 LLM을 불러 색인을 만드는 데 시간과 비용이 더 든다

Microsoft GraphRAG는 질문 종류에 따라 커뮤니티 보고서 전체를 읽어 종합하는 global search와 엔티티 주변을 읽는 local search를 나눠 씁니다.
