Agent가 일을 잘하는지 어떻게 숫자로 확인할까요?

도구 설명 한 줄을 고쳤더니 어떤 질문은 좋아지고 어떤 질문은 나빠졌습니다. 몇 개를 직접 물어보고 "괜찮은 것 같다"며 배포했는데, 다음 날 환불 질문에서 엉뚱한 도구를 부른다는 제보가 옵니다. Agent는 같은 질문에도 매번 다르게 움직입니다. 그렇다면 잘하고 있는지를 어떻게 숫자로 확인할까요?

Agent는 왜 확인하기 어렵나요?

같은 질문에도 가는 길이 매번 다르고 답이 맞아도 길이 틀렸을 수 있습니다.

일반 프로그램은 같은 입력에 같은 출력을 내서 테스트가 쉽습니다. Agent는 LLM이 매번 조금씩 다르게 판단해서 같은 질문에도 부르는 도구와 순서가 달라집니다. 몇 번 물어보고 잘 되면 괜찮다고 여기기 어렵습니다.

답이 맞아도 안심할 수 없습니다. 위 두 번째 실행은 주문을 확인하지 않고 환불했는데 운 좋게 금액이 맞았습니다. Agent는 최종 답과 함께 거기까지 간 길도 확인해야 합니다.

Agent가 지나간 길은 어떻게 보나요?

실행마다 단계별 기록(trace)을 남깁니다. 어떤 LLM 호출과 도구 실행이 얼마나 걸렸는지가 남습니다.

trace는 요청 하나를 처리하는 동안 일어난 일을 모두 적은 기록입니다. 그 안의 단계 하나하나를 span이라고 합니다. LLM에 무엇을 보냈고 무엇이 돌아왔는지, 어떤 도구를 어떤 값으로 불렀는지, 각각 몇 초와 몇 토큰이 들었는지가 남습니다.

Agent가 이상하게 움직였다는 제보가 오면 그 요청의 trace를 열어 어느 단계에서 길을 잘못 들었는지 봅니다. LangSmith·Langfuse 같은 서비스가 trace를 모아 보여 줍니다. OpenTelemetry에는 LLM 호출을 기록하는 공통 규칙(GenAI semantic conventions)이 있어서 여러 도구가 같은 형식으로 기록합니다.

무엇을 기준으로 잘했다고 하나요?

질문 묶음과 기대 결과를 정해 두고 답·길·비용을 각각 잽니다.

잴 것예누가 채점
최종 답환불 금액이 맞나, 규정을 지켰나코드(정답 비교) 또는 LLM
지나간 길환불 전에 주문 조회를 했나코드(도구 순서 확인)
말투·충실도근거 문서에 없는 말을 했나LLM 채점
비용·시간토큰 수, 걸린 초, 반복 횟수trace에서 그대로

먼저 질문 묶음(데이터셋)을 만듭니다. 실제로 자주 오는 질문, 실패했던 질문, 까다로운 경계 사례를 수십 개쯤 모으고 각각 기대하는 결과를 적습니다. 처음부터 많을 필요는 없습니다. Anthropic은 조사 Agent를 만들 때 실제 사용을 닮은 질문 20개쯤으로 시작해도 변화가 잘 보였다고 밝혔습니다.

최종 답만 보는 평가와 지나간 길까지 보는 평가를 함께 둡니다. 길은 대개 코드로 확인할 수 있습니다. "refund를 부르기 전에 search_orders를 불렀나"는 trace의 도구 목록만 보면 됩니다. 정답이 하나가 아닌 일은 코드로 채점하기 어렵습니다. 그때 LLM에게 채점을 맡깁니다.

LLM에게 채점을 맡겨도 되나요?

기준을 분명히 적어 주면 쓸 만합니다. 사람 채점과 가끔 맞춰 봐야 합니다.

답을 다른 LLM에게 읽혀 채점하게 하는 방법을 LLM-as-judge라고 합니다. "근거 문서에 없는 내용을 말했나", "질문에 답했나"처럼 사람이 읽어야 판단할 수 있는 기준을 빠르게 잽니다.

채점 LLM도 틀립니다. 기준을 "좋은 답인가"처럼 모호하게 쓰면 점수가 들쭉날쭉합니다. 기준 하나에 질문 하나로 쪼개고 예/아니오처럼 단순한 답을 받으면서 이유를 함께 적게 합니다. 채점 결과 일부를 사람이 직접 보고 맞는지 확인하는 일도 빼지 않습니다.

평가는 언제 돌리나요?

프롬프트·도구 설명·모델을 바꿀 때마다 돌려서 전보다 나빠진 곳이 없는지 봅니다.

Agent는 지시 한 줄, 도구 설명 한 줄, 모델 버전 하나만 바뀌어도 움직임이 달라집니다. 그래서 무언가를 바꿀 때마다 같은 질문 묶음을 돌려 전후를 비교합니다. 전체 점수보다 새로 틀린 질문을 찾는 것이 더 중요합니다.

LLM은 매번 다르게 답하므로 질문 하나를 여러 번 돌려 성공 비율로 보는 편이 정확합니다. 배포한 뒤에는 실제 trace에서 실패 사례를 골라 질문 묶음에 계속 더합니다. 질문 묶음이 자랄수록 평가가 실제 사용에 가까워집니다.

코드로 쓰면 어떻게 되나요?

질문 묶음을 돌리며 길은 코드로, 답은 채점 LLM으로 잽니다.

from pydantic import BaseModel
import anthropic

client = anthropic.Anthropic()

# ① 질문 묶음: 질문, 꼭 거쳐야 할 도구 순서, 정답 근거
cases = [
    {"q": "A-1042 환불해 줘", "must_call": ["search_orders", "refund"],
     "facts": "A-1042 는 4,000원, 배달 완료"},
    # … 실제 질문과 실패 사례를 계속 더한다
]

class Grade(BaseModel):
    grounded: bool      # 근거에 없는 내용을 말하지 않았나
    reason: str

def judge(q, answer, facts) -> Grade:
    # ② 기준 하나, 예/아니오, 이유 함께
    r = client.messages.create(
        model="claude-sonnet-5-5", max_tokens=300,
        system="Agent의 답이 사실 목록에 없는 내용을 말했으면 grounded=false.",
        messages=[{"role": "user",
                   "content": f"질문: {q}\n사실: {facts}\n답: {answer}"}],
        output_config={"format": {"type": "json_schema",
                                  "schema": Grade.model_json_schema()}})
    return Grade.model_validate_json(r.content[0].text)

results = []
for c in cases:
    run = run_agent(c["q"])                  # 답과 trace 를 함께 돌려준다
    called = [s.tool for s in run.trace if s.tool]
    # ③ 길은 코드로: 꼭 거칠 도구가 순서대로 있었나
    path_ok = is_subsequence(c["must_call"], called)
    g = judge(c["q"], run.answer, c["facts"])
    results.append({"q": c["q"], "path_ok": path_ok, "grounded": g.grounded,
                    "reason": g.reason, "tokens": run.tokens})
# ④ 전체 비율과 실패 목록을 남겨 다음 실행과 비교한다
print(sum(r["path_ok"] and r["grounded"] for r in results), "/", len(results))
  1. 질문마다 꼭 거쳐야 할 도구 순서와 정답 근거를 적어 둡니다. 실패했던 실제 질문을 계속 더합니다.
  2. 채점 기준은 하나만, 답은 예/아니오와 이유로 받습니다. structured output으로 형식을 고정했습니다.
  3. 도구 순서는 LLM 없이 코드로 확인합니다. is_subsequence는 꼭 거칠 도구가 순서대로 들어 있는지 보는 짧은 함수입니다.
  4. 점수 하나보다 실패한 질문 목록이 중요합니다. 바꾸기 전 결과와 나란히 비교해 새로 틀린 질문을 찾습니다.

run_agent는 Agent를 실행하고 답과 단계 기록을 함께 돌려주는 함수로, 예시라 줄였습니다. LangSmith를 쓰면 trace 수집, 질문 묶음 관리, 채점, 전후 비교 화면을 한곳에서 씁니다.
