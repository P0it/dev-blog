AI Service Track · 06

사진 설명은 잘하는 AI가 그래프 숫자를 틀리는 이유

ChatGPT에 빵집 사진을 올리면 바게트와 베이글을 척척 구분합니다. 그런데 리뷰 그래프를 올리고 숫자 하나를 물으면 틀린 값을 자신 있게 말할 때가 있습니다. 화면 뒤로 내려가 사진이 어떤 모양으로 모델에 들어가는지 보고 사진 한 장을 영어 듣기 문제로 만드는 데까지 가 봅니다.

사진은 모델에 얼마나 크게 들어갈까요?

정해진 크기로 줄어든 뒤 32픽셀 격자로 나뉘어 세어집니다. 픽셀(pixel)은 사진을 이루는 작은 색 점 하나입니다. 격자 한 칸을 패치(patch)라고 부르고 요금도 이 칸 수로 정해집니다. OpenAI가 모델 내부를 공개하지는 않았지만 크기와 요금 계산은 문서에 있습니다. 앞의 빵집 사진으로 계산하면 이렇습니다.

휴대폰으로 찍은 사진은 생각보다 큽니다

이 사진은 가로 4128, 세로 3096픽셀로, 점이 1,278만 개입니다. 32픽셀 칸으로 나누면 12,513칸입니다.

먼저 정해진 크기로 줄입니다

API에는 사진을 얼마나 크게 넣을지 정하는 detail 값이 있습니다. "high"로 보내면 gpt-5.6-luna 모델은 긴 변을 2048픽셀 안에, 칸 수를 2,500칸 안에 맞춥니다. 왼쪽 위 사진이 줄어든 1824×1368이고 점선이 원래 크기입니다.

32픽셀 칸으로 자릅니다

가로 57칸, 세로 43칸으로 모두 2,451칸입니다. 격자는 빵의 생김새를 모르고 일정한 간격으로 자를 뿐입니다. 빨간 동그라미 속 한 칸에는 빵 껍질 한 조각만 들어 있습니다.

한 칸은 숫자 뭉치입니다

빨간 동그라미 속 칸을 확대했습니다. 픽셀마다 빨강·초록·파랑 세 숫자이니, 한 칸에는 32×32×3으로 숫자 3,072개가 들어 있습니다. 함께 적은 숫자는 이 칸의 실제 첫 픽셀들입니다.

칸과 글이 한 줄로 이어집니다

토큰(token)은 모델이 입력을 세는 단위이자 요금의 단위입니다. 칸 수에 모델마다 정해진 수를 곱하면 사진의 토큰이 나옵니다. gpt-5.6-luna는 1.2를 곱합니다. 왜 1.2인지는 문서에 없습니다. 모델에게 사진은 아주 긴 문장과 비슷합니다.

칸 하나는 빵을 모르는데 어떻게 빵을 알아볼까요? 공개된 연구가 실마리입니다. 2020년 논문의 ViT(Vision Transformer)는 사진 칸에 번호를 달아 문장의 낱말처럼 한 줄로 넣습니다. 그러면 칸마다 다른 칸을 함께 살펴 껍질 무늬가 이어지면 "빵"이라는 뜻을 만듭니다.

이 논문은 16픽셀 칸을 썼고 GPT 모델이 똑같이 만들어졌는지는 공개되어 있지 않습니다. "숫자 3,072개"도 칸을 이해하려고 세어 본 값입니다.

다시 요금으로 돌아옵니다. 사진 모양에 따라 칸 수가 이렇게 달라집니다.

사진 크기를 안 정하면 어떻게 될까요?

큰 사진이 줄지 않고 그대로 들어갑니다. detail을 안 적으면 auto가 되는데, gpt-5.6 계열에서 auto는 원본 크기인 original과 같습니다. 빵집 사진의 가격표를 세 값으로 줄여 나란히 놓았습니다.

이 가격표는 high만 돼도 이름과 값이 읽힙니다. high와 original의 요금 차이는 5배입니다. low는 사진 분위기를 물을 때는 충분해도 글자를 물으면 안 됩니다.

큰 사진은 아예 거절됩니다. 한 장의 한도가 30,000칸이고 original은 넘어도 줄여 주지 않습니다. 4800만 픽셀 사진(8000×6000)은 47,000칸이라 detail을 안 적으면 요청이 실패합니다.

그래프 숫자는 왜 유독 틀릴까요?

빵집 사진은 "대체로 무엇이 있나"만 맞히면 되지만 그래프 값은 작은 숫자 하나를 정확히 읽어야 맞습니다. 앞의 격자를 그래프의 숫자 38 위에 얹어 보면 차이가 보입니다. 사진을 작게 넣을수록 칸 하나가 넓은 자리를 덮어서 숫자가 쓸 칸이 줄어듭니다.

크게 넣어도 틀릴 수 있습니다. 그래프의 값 하나를 읽으려면 어느 선인지, 어느 주차인지, 무슨 숫자인지 세 번을 모두 맞혀야 하고 하나만 어긋나도 답이 틀립니다. 빵집 사진을 설명할 때는 이런 관문이 없습니다.

OpenAI 문서도 모델이 약한 곳으로 이런 일을 직접 적어 두었습니다.

연구 결과도 비슷합니다. 그래프 문제 1,162개로 잰 ChartMuseum에서 사람은 93%를 맞혔는데 당시 최고 모델은 63%였습니다. 다만 2025년 모델 기준입니다. 다른 시험인 PlotChain에서 GPT-4o는 61.59점, GPT-4.1은 79.84점으로 세대마다 나아지고 있어 내 그래프로 직접 재 봐야 합니다.

요금을 더 내지 않고 그래프를 잘 읽히는 방법이 있습니다. 물어볼 부분만 잘라서 보내는 것입니다. 사진은 정해진 크기로 줄어드니, 잘라 낸 작은 조각은 같은 요금에 훨씬 많은 칸을 차지합니다.

그림을 거치지 않으면 더 확실합니다. 숫자의 원본 표나 CSV(쉼표로 칸을 나눈 표 파일)가 있으면 그것을 글로 보냅니다. 사진밖에 없다면 더 크게 넣거나 잘라 보내고 "안 보이는 숫자는 '안 보임'이라고 적으세요"라고 지시합니다. 없는 값을 물으면 지어내는 경향이 보고되었기 때문입니다(ChartHal, 2025). 어느 쪽이든 돈이 걸린 숫자는 원본과 맞춰 봐야 합니다.

사진은 어떻게 요청에 실려 갈까요?

앱에서 사진을 올리면 화면에는 작은 미리보기만 보이지만 프로그램은 그 사진을 어떻게든 요청에 실어 보내야 합니다. 가장 쉬운 길은 사진을 글자로 바꾸는 것입니다. API 요청은 프로그램끼리 주고받는 글자 양식인 JSON이라 사진 파일의 숫자를 그대로 넣을 수 없습니다. 이 변환을 base64라고 합니다. 컴퓨터 파일은 0과 1을 8개씩 묶은 바이트(byte)로 되어 있는데, base64는 이것을 6개씩 다시 묶어 글자 64종 가운데 하나로 적습니다.

3바이트가 4글자가 되니 크기는 3분의 1만큼 늘어납니다. 위 빵집 사진의 원본 파일로 재면 4.5MB가 6.0MB가 됩니다. 사진 여러 장을 이렇게 실으면 요청 하나가 금세 수십 MB로 불어납니다.

그래서 사진을 보내는 길은 세 가지입니다. 어느 길이든 모델이 보는 사진은 같고 요청에 실리는 무게만 달라집니다.

import base64
from openai import OpenAI

client = OpenAI()

# ① 사진 파일을 data URL 글자로 바꿉니다
def to_data_url(path, mime="image/jpeg"):
    with open(path, "rb") as f:
        encoded = base64.b64encode(f.read()).decode("utf-8")
    return f"data:{mime};base64,{encoded}"

response = client.responses.create(
    model="gpt-5.6-luna",
    input=[{"role": "user", "content": [
        {"type": "input_text", "text": "이 사진을 두 문장으로 설명하세요."},
        # ② 글과 사진을 한 content 줄에 나란히 놓습니다
        {
            "type": "input_image",
            "image_url": to_data_url("bakery.jpg"),
            "detail": "high",
        },
    ]}],
)

print(response.output_text)
# ③ 사진 값까지 합친 입력 토큰
print("입력 토큰:", response.usage.input_tokens)

사진 두 장의 차이는 어떻게 물을까요?

입력 줄에 글과 사진을 번갈아 놓고 사진마다 글로 이름표를 붙입니다. 모델은 파일 이름이나 촬영 정보를 보지 못하기 때문입니다. reviews_jan.png라고 저장해 둬도 모델에게는 그냥 사진 한 장입니다. "첫 번째 사진" 같은 말보다 A·B 이름표가 답을 읽기도 쉽습니다.

코드로 보기: 사진 두 장 비교하기
from openai import OpenAI

client = OpenAI()

def upload(path):
    # ① 파일을 먼저 올리고 번호를 받습니다
    with open(path, "rb") as f:
        return client.files.create(file=f, purpose="vision").id

jan, feb = upload("reviews_jan.png"), upload("reviews_feb.png")

def image(file_id):
    return {"type": "input_image", "file_id": file_id,
            "detail": "original"}

response = client.responses.create(
    model="gpt-5.6-luna",
    input=[{"role": "user", "content": [
        # ② 사진 앞에 글로 이름표를 붙입니다
        {"type": "input_text", "text": "[사진 A] 1월 리뷰 그래프"},
        image(jan),
        {"type": "input_text", "text": "[사진 B] 2월 리뷰 그래프"},
        image(feb),
        # ③ 안 보일 때 어떻게 할지까지 적습니다
        {"type": "input_text", "text": "A와 B의 차이를 적어 주세요. "
                                       "안 보이는 숫자는 '안 보임'이라고 적으세요."},
    ]}],
)

print(response.output_text)

여기까지가 사진을 읽는 일입니다. 이제 같은 사진 한 장으로 영어 듣기 문제를 만듭니다.

사진 한 장이 듣기 문제가 되면 어떤 화면일까요?

학습 앱이 사진을 보여 주고 문장 네 개를 영어로 읽어 준 뒤, 사진과 맞지 않는 문장을 고르게 합니다. 이 화면 뒤에는 사진을 보고 문제를 쓰는 일과 글을 소리로 바꾸는 일이 차례로 있습니다.

문제는 설명을 위한 예시입니다.

문제를 글로 받으면 왜 프로그램이 깨질까요?

모델이 답을 쓰는 모양이 매번 조금씩 달라서입니다. "질문은 Listening: 뒤에 적어 주세요"라고 부탁하고 그 글자를 기준으로 답을 자르는 split("Listening:") 코드를 생각해 봅니다. 사람 눈에는 셋 다 멀쩡한 답이지만 코드의 결과는 다릅니다.

그래서 답의 모양을 말로 부탁하지 않고 스키마(schema)로 못박습니다. 스키마는 "항목 이름과 종류"를 적은 양식입니다. 이 양식을 지키도록 모델의 출력을 제한하는 기능이 Structured Outputs입니다. 파이썬에서는 Pydantic이라는 라이브러리(남이 만들어 둔 코드 묶음)로 양식을 적습니다. 받은 답은 글자가 아니라 항목 이름으로 꺼내 쓰는 값(객체)이 됩니다.

from pydantic import BaseModel, Field
# ... client, RULES(지시문), url(사진)은 전체 코드에 있습니다

class Quiz(BaseModel):
    question: str
    # ① 보기는 정확히 4개, 정답 번호는 0~3
    choices: list[str] = Field(min_length=4, max_length=4)
    answer_index: int = Field(ge=0, le=3)
    evidence: str

# ② text_format 에 양식을 넘깁니다
response = client.responses.parse(
    model="gpt-5.6-luna",
    instructions=RULES,
    input=[{"role": "user", "content": [
        {"type": "input_image", "image_url": url,
         "detail": "high"},
    ]}],
    text_format=Quiz,
)
# ③ 거절하면 비어 있습니다
quiz = response.output_parsed

# ④ 정답 자리는 코드가 섞습니다
answer = quiz.choices[quiz.answer_index]
random.shuffle(quiz.choices)
quiz.answer_index = quiz.choices.index(answer)

출력은 예시 답입니다. answer_index는 0부터 세니 1은 위 화면의 2번입니다.

  1. min_length는 최소 개수, ge는 이상, le는 이하입니다. 이런 조건은 스키마에 그대로 담겨 모델에 전달됩니다. 이제 split 없이 quiz.choices[0]으로 꺼냅니다.
  2. create 대신 parse를 부르고 양식을 넘기면, 답이 output_parsed에 객체로 담겨 옵니다.
  3. 모델이 답을 거절하거나 길이 한도로 잘리면 이 값이 비어 있을 수 있습니다. 전체 코드는 비어 있을 때 다시 시도합니다.
  4. 모델이 정답을 어느 자리에 몰아 두더라도 상관없도록, 자리를 코드가 다시 정합니다. 섞은 뒤 번호를 다시 찾는 줄이 중요합니다.

스키마는 모양만 보장합니다. "맞지 않는 보기가 정말 하나뿐인가"는 보장하지 않습니다. 그래서 evidence 항목을 두고 내보내기 전에 사람이 근거를 확인합니다.

import base64, random
from openai import OpenAI
from pydantic import BaseModel, Field

client = OpenAI()

class Quiz(BaseModel):
    question: str
    # 보기는 정확히 4개, 정답 번호는 0~3
    choices: list[str] = Field(min_length=4, max_length=4)
    answer_index: int = Field(ge=0, le=3)
    evidence: str

RULES = """사진을 보고 영어 듣기 문제를 만드세요.
보기는 4개, 사진과 맞지 않는 설명은 정확히 1개입니다.
evidence에는 그 보기가 틀린 이유를 사진에서 찾아 한국어로 적으세요."""

def shuffle(quiz):
    # 정답 자리는 코드가 섞습니다
    answer = quiz.choices[quiz.answer_index]
    random.shuffle(quiz.choices)
    quiz.answer_index = quiz.choices.index(answer)
    return quiz

def image_quiz(path, max_trial=3):
    with open(path, "rb") as f:
        url = "data:image/jpeg;base64," + base64.b64encode(f.read()).decode()
    for trial in range(max_trial):
        # text_format 에 양식을 넘깁니다
        response = client.responses.parse(
            model="gpt-5.6-luna",
            instructions=RULES,
            input=[{"role": "user", "content": [
                {"type": "input_image", "image_url": url,
                 "detail": "high"},
            ]}],
            text_format=Quiz,
        )
        # 거절하면 비어 있으니 확인합니다
        if response.output_parsed:
            return shuffle(response.output_parsed)
    raise RuntimeError(f"{path}: {max_trial}번 모두 실패")

if __name__ == "__main__":
    print(image_quiz("bakery.jpg").model_dump_json(indent=2))

글자는 어떻게 목소리가 될까요?

글을 음성으로 바꾸는 TTS(text-to-speech)는 적힌 글자를 읽습니다. 그러니 먼저 귀로 들을 대본을 만들어야 합니다. 화면에는 번호표면 충분해도, 듣기 문제에서는 "One."이라고 소리 내어 말해야 합니다. 데이터를 대본으로 잇는 일은 모델 없이 파이썬 함수로 합니다.

모델이 돌려주는 소리도 사진처럼 결국 숫자입니다. 음성 앱의 소리 그림(파형)을 확대하면 공기의 떨림을 일정한 간격으로 잰 점이 보입니다. 이 점 하나가 샘플(sample)입니다. 24kHz(킬로헤르츠) 음성은 1초에 24,000번 재고 한 번에 2바이트를 쓰니 1초가 48,000바이트입니다.

설명을 위해 계산으로 그린 파형입니다. 실제 음성을 잰 값이 아닙니다.

음성 모델은 무엇을 써야 할까요?

새로 만든다면 gpt-realtime-2.1-mini입니다. 글을 보내면 음성 파일을 돌려주는 Speech API의 모델 gpt-4o-mini-tts, tts-1, tts-1-hd가 2027년 1월 6일에 종료되고 이 모델이 공식 대체 모델이기 때문입니다. 이 모델은 Speech API에서 쓸 수 없어 호출 방식까지 바뀝니다.

Realtime API는 음성 비서처럼 말을 주고받는 서비스에 쓰는 API입니다. 전화처럼 연결을 열어 두고 소리 조각을 이어서 받습니다. 파일 하나를 만들려면 조각을 모아 붙여야 합니다.

대화용 모델이라 대본을 글자 그대로 읽는다는 보장을 문서에서 찾지 못했습니다. 그래서 모델이 실제로 읽은 글을 함께 받아 대본과 맞춰 봅니다.

# ... import 와 script(대본)는 전체 코드에
SESSION = {
    "type": "realtime",
    "output_modalities": ["audio"],
    # ① 덧붙이지 말고 그대로 읽으라고 지시합니다
    "instructions": "Read the user's text aloud exactly as written. "
                    "Add nothing.",
    "audio": {"output": {
        "format": {"type": "audio/pcm", "rate": 24000},
        "voice": "marin",
    }},
}
pcm, spoken = bytearray(), ""
# ② 요청 대신 연결을 엽니다
with client.realtime.connect(
    model="gpt-realtime-2.1-mini",
) as conn:
    conn.session.update(session=SESSION)
    conn.conversation.item.create(item={
        "type": "message", "role": "user",
        "content": [{"type": "input_text", "text": script}],
    })
    conn.response.create()
    for event in conn:
        # ③ 소리 조각이 base64 글자로 옵니다
        if event.type == "response.output_audio.delta":
            pcm += base64.b64decode(event.delta)
        elif event.type.endswith("audio_transcript.done"):
            spoken = event.transcript
        elif event.type == "response.done":
            break
# ④ 읽은 글이 대본과 같은지 확인합니다
print("대본과 같음:", spoken.split() == script.split())

출력은 예시 답입니다.

  1. 세션(연결 하나에 적용되는 설정)에 지시와 형식, 목소리를 적습니다. audio/pcm은 압축하지 않은 샘플 그대로이고 목소리는 문서가 권하는 marin입니다.
  2. 이 연결은 WebSocket입니다. 한 번 묻고 끝나는 요청과 달리 한 번 연결한 뒤 양쪽이 계속 메시지를 주고받는 통로입니다.
  3. 사진을 보낼 때 본 base64가 소리에서도 쓰입니다. 조각(delta)을 풀어 차례대로 이어 붙입니다.
  4. False면 그 문제만 다시 만듭니다. 듣기 시험에서는 낱말 하나가 바뀌면 답이 바뀔 수 있습니다.

듣는 사람에게 AI 음성임을 알려야 합니다. OpenAI 정책이 요구하는 사항으로, 앱 화면에 한 줄 적어 두면 됩니다. 요금은 오디오 출력 100만 토큰에 20달러로 gpt-4o-mini-tts의 12달러보다 비쌉니다(2026-11 확인). 문제를 대량으로 만들기 전에 몇 개로 재 보세요.

pcm에는 샘플만 있어 재생기가 형식을 모릅니다. 전체 코드는 소리 통로 1개, 샘플당 2바이트, 초당 24,000번을 적어 소리 파일 형식인 wav로 저장합니다.

from quiz import client, image_quiz

WORDS = ["One", "Two", "Three", "Four"]
def to_script(no, quiz):
    # ① 데이터 칸을 귀로 들을 대본으로 잇습니다
    lines = [f"Number {no}. {quiz.question}"]
    lines += [f"{w}. {c}" for w, c in zip(WORDS, quiz.choices)]
    return "\n".join(lines)

def speak(script, path, voice="marin"):
    with client.audio.speech.with_streaming_response.create(
        # ② 2027-01-06 종료 예정인 모델입니다
        model="gpt-4o-mini-tts",
        voice=voice,
        input=script,
        # ③ 읽는 방식을 영어로 지시합니다
        instructions="Read like an English listening test. "
                     "Speak slowly. Pause after each option.",
        response_format="mp3",
    ) as response:
        # ④ 받는 대로 파일에 씁니다
        response.stream_to_file(path)

if __name__ == "__main__":
    speak(to_script(1, image_quiz("bakery.jpg")), "1.mp3")
  1. quiz.choices를 앞서 섞었으니 대본의 One, Two 순서와 answer_index가 그대로 맞습니다. image_quiz는 앞의 quiz.py에서 가져옵니다.
  2. 2027-01-06에 사라지는 모델입니다. 그 전까지 짧은 작업에 쓸 수 있습니다.
  3. 목소리는 marin과 cedar를 문서가 권합니다. instructions는 4,096자까지이고 입력은 2,000토큰까지입니다.
  4. 기본 형식은 mp3이고 opus, aac, flac, wav, pcm도 고를 수 있습니다.

사진 기능을 붙이기 전에 정할 것

  1. detail을 꼭 적습니다. 기본값은 원본 크기라 요금이 많이 나오고 큰 사진은 거절됩니다.
  2. 숫자를 물을 거라면 원본 표나 CSV를 먼저 찾습니다. 없으면 잘라서 보내고 "안 보임"을 허락합니다.
  3. 사진 속 얼굴, 차 번호판, 영수증을 확인합니다. 응답은 기본으로 30일 저장되니 필요하면 저장하지 않는 옵션 store=False를 답니다.
  4. 만든 문제와 음성을 사람이 검토하는 단계를 둡니다. 듣는 사람에게는 AI 음성임을 알립니다.
  5. 당장 답이 필요 없는 일은 요청을 모아 맡기는 Batch API로 보내 요금을 절반으로 줄입니다. 24시간 안에 결과를 돌려줍니다.
