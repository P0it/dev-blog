MCP 서버 두 개를 꽂은 에이전트가 시계 도구를 고른 이유

배달 앱 리뷰를 모은 파일을 AI 비서에게 주고 "요약해서 저장해 줘"라고만 했습니다. 비서는 파일을 읽고 오늘 날짜를 확인한 뒤 작성일이 적힌 요약 파일을 만들었습니다. 무엇을 어떤 순서로 하라고 알려 준 적은 없습니다. 새로 온 직원이 책상 위 도구를 훑어보고 알아서 골라 쓰는 것과 비슷합니다. 이렇게 스스로 도구를 골라 쓰는 AI 프로그램을 에이전트(agent)라고 부릅니다. 이 글은 에이전트가 도구를 어떻게 고르는지, 그 도구는 어디에서 오는지 뒷단으로 내려가 따라갑니다.

에이전트는 도구 설명을 읽고 고릅니다

순서를 정한 건 에이전트 안의 AI 모델입니다. 모델은 사용자의 요청과 함께 도구 목록을 글자로 받습니다. 목록에는 도구마다 이름과 설명, 넘길 값의 모양이 적혀 있습니다. 모델은 요청의 "저장해 줘"를 설명의 "파일을 저장합니다"와 짝짓고, 앱이 미리 준 지시문의 "작성일"을 "현재 시각"과 짝짓습니다. 앱이 모델에게 미리 주는 이 지시문을 시스템 프롬프트(system prompt)라고 합니다.

MCP(Model Context Protocol)는 그 목록을 모델 앞까지 배달하고 모델이 고른 도구를 서버에서 실행해 결과를 가져오는 약속입니다. 고르는 일은 하지 않습니다. 식당 메뉴판과 비슷합니다. 주방(서버)이 메뉴판을 만들어 주면 손님(모델)이 읽고 고르고 종업원(MCP 클라이언트, 앱 안에서 서버와 말을 주고받는 부분)은 주문을 주방에 전합니다. 모델이 도구를 "부른다"는 것도 실제로는 도구 이름과 넘길 값을 적은 글을 내놓는 일이고(위 그림의 빨간 글씨) 실행은 앱이 합니다. 다만 메뉴판과 달리 이 목록은 요청할 때마다 모델 입력에 다시 들어가 토큰(token, 모델이 글을 읽는 단위)을 차지합니다.

그래서 설명이 곧 성능입니다. Anthropic은 도구 고르기에 설명이 가장 크게 영향을 준다고 안내합니다. 도구가 30~50개를 넘으면 고르는 정확도가 떨어진다고도 적어 두었습니다. 서버를 많이 꽂을수록 목록이 길어지니 쓰는 서버만 꽂는 편이 낫습니다.

함수 하나가 도구 설명 한 장이 됩니다

MCP 서버는 도구를 담아 두고 요청이 오면 실행하는 작은 프로그램입니다. 파이썬에서는 공식 SDK(Software Development Kit, 개발용 라이브러리 묶음)의 MCPServer 객체를 만들고 함수 위에 @mcp.tool()을 붙이면 됩니다. 데코레이터(decorator)는 함수 위에 @로 붙여 그 함수에 기능을 더하는 문법입니다.

맨 위 그림의 "파일 읽기"가 바로 아래 코드의 read_file 함수입니다. 붙인 순간 함수 이름은 도구 이름이 되고 독스트링(docstring, 함수 몸통 맨 앞에 적는 설명 글)은 도구 설명이 됩니다. 타입 힌트(type hint, path: str처럼 값의 종류를 적은 표시)는 넘길 값의 모양이 됩니다. 앞에서 본 모델 입력의 설명 글은 아래 코드의 독스트링을 그대로 옮긴 것입니다.

from pathlib import Path
from mcp.server import MCPServer
from mcp.server.mcpserver.exceptions import ToolError

mcp = MCPServer("files")                      # ① 서버 이름
ROOT = Path("workspace").resolve()

def inside(path: str) -> Path:
    p = (ROOT / path).resolve()
    if not p.is_relative_to(ROOT):            # workspace 밖이면 거절
        raise ToolError("workspace 폴더 밖은 열 수 없습니다")
    return p

# ② 도구로 등록
@mcp.tool()
def read_file(path: str) -> str:
    """workspace 폴더 안의 글 파일을 읽어 내용을 돌려줍니다.
    path 예: 'reviews.txt'"""
    return inside(path).read_text(encoding="utf-8")

@mcp.tool()
def write_file(path: str, content: str) -> str:
    """workspace 폴더 안에 글 파일을 저장합니다. 같은 이름이 있으면 덮어씁니다."""
    inside(path).write_text(content, encoding="utf-8")
    return f"{path} 저장 완료 ({len(content)}자)"   # ③ 결과 글

if __name__ == "__main__":
    # ④ 통로: 표준 입출력
    mcp.run(transport="stdio")
  1. 서버 이름입니다. 에이전트 쪽 설정에서 서버를 구분하는 이름은 따로 정하므로 여기 이름은 서버 소개용입니다. mcp 2.0부터 클래스 이름이 FastMCP에서 MCPServer로 바뀌었습니다. 옛 이름으로 가져오면 2.x에서는 바로 오류가 납니다. FastMCP라는 이름은 따로 만들어지는 확장 라이브러리 fastmcp에 남아 있고 뒤에 나오는 LangChain 어댑터가 안에서 이 라이브러리를 씁니다.
  2. 함수를 도구로 등록합니다. @mcp.tool(description="…")처럼 설명을 직접 주면 독스트링 대신 그 글이 설명이 됩니다. 둘을 다 쓰면 모델은 description만 봅니다.
  3. 결과는 모델이 읽을 글입니다. 저장한 파일 이름과 글자 수를 돌려주면 모델이 일을 마쳤는지 확인할 수 있습니다. 모델이 엉뚱한 파일을 열거나 덮어쓰지 못하도록 경로를 workspace 안으로 묶어 두었습니다. 거절은 ToolError로 알려야 그 문장이 모델에게 그대로 갑니다.
  4. 메시지를 주고받을 통로입니다. stdio는 에이전트가 이 파일을 직접 실행하고 표준 입출력으로 대화하는 방식입니다. 여러 앱이 주소로 접속하게 하려면 "streamable-http"를 씁니다. 둘의 차이는 아래에서 다시 봅니다.

에이전트 코드에는 서버 목록만 적습니다

도구를 만드는 코드는 서버에 있고 에이전트 쪽에는 어떤 서버를 어떻게 실행할지만 적습니다. LangChain은 1.4부터 MCP 연결을 langchain.mcp의 MCPAdapter로 직접 지원합니다. 따로 깔던 langchain-mcp-adapters 패키지를 대신하며 2026년 11월 기준 아직 베타(beta, 정식 출시 전 시험판)입니다. 어댑터(adapter)는 모양이 다른 두 쪽을 이어 주는 부품으로, 여기서는 MCP 도구를 LangChain 도구 모양으로 바꿔 줍니다.

설정 모양은 Claude Desktop이나 Cursor 같은 앱이 쓰는 mcpServers 형식과 같습니다. 서버마다 이름을 붙이고 실행 명령을 적습니다. 남이 만든 시계 서버는 설치하지 않고 uvx로 바로 실행합니다. uv는 파이썬 패키지를 설치하고 실행해 주는 도구이고 uvx는 패키지를 임시 환경(그 프로그램만 쓰는 패키지 묶음)에 받아 바로 실행하는 명령입니다.

import asyncio
from langchain.agents import create_agent
from langchain.mcp import MCPAdapter

config = {"mcpServers": {
    # ① 내가 만든 서버
    "files": {"command": "uv",
              "args": ["run", "--with", "mcp==2.3.0",
                       "file_server.py"]},
    # ② 남이 만든 서버, 설치 없이 실행
    "clock": {"command": "uvx",
              "args": ["mcp-server-time==2026.11.18",
                       "--local-timezone=Asia/Seoul"]},
}}

async def main():
    # ③ 열어 둔 채로 도구를 받고 에이전트를 실행
    async with MCPAdapter(config) as adapter:
        tools = await adapter.list_tools()
        agent = create_agent(
            model="openai:gpt-6.2-sol",
            tools=tools,
            system_prompt="리뷰 파일을 요약해 저장합니다. "
                          "파일에는 작성일을 꼭 넣습니다.")
        q = "reviews.txt 읽고 summary.md에 요약 저장해 줘"
        async for step in agent.astream(
                {"messages": [{"role": "user", "content": q}]},
                stream_mode="updates"):
            ...  # 단계마다 도구 요청·결과·답을 출력

asyncio.run(main())

  1. 내가 만든 서버를 실행하는 명령입니다. uv run --with mcp==2.3.0은 서버에 필요한 패키지만 담은 환경을 따로 만들어 실행합니다. 서버는 에이전트와 다른 프로그램이라 파이썬 환경도 따로 둘 수 있습니다. 같은 환경에 깔았다면 "command": "python", "args": ["file_server.py"]로 써도 됩니다.
  2. 남이 만든 서버는 패키지 이름과 실행 인자만 적습니다. --local-timezone은 시간대를 넘기지 않았을 때 쓸 기본 시간대입니다. 버전을 적어 두면 서버가 갑자기 바뀌어 에이전트가 달라지는 일을 막을 수 있습니다.
  3. 어댑터를 연 채로 에이전트를 돌립니다. async with는 블록에 들어갈 때 연결을 열고 나올 때 닫는 문법이고 await는 오래 걸리는 일이 끝날 때까지 기다리라는 표시입니다. list_tools()가 두 서버의 도구를 LangChain 도구로 바꿔 한 목록으로 돌려줍니다. async with를 빼도 동작하지만 도구를 부를 때마다 서버가 새로 켜집니다. 아래에서 직접 잰 값을 봅니다. 모델 이름 gpt-6.2-sol은 2026-11-19 OpenAI 모델 문서 기준입니다.

에이전트와 서버가 주고받는 메시지

에이전트와 서버는 JSON-RPC 2.0 형식의 짧은 글을 한 줄씩 주고받습니다. JSON-RPC는 "이 이름의 일을 이 값으로 해 줘"라는 요청과 그 답을 JSON으로 적는 약속입니다. 요청에는 번호(id)가 붙고 답은 같은 번호를 달고 돌아옵니다. 번호가 없는 글은 알림(notification)이라 답을 기다리지 않습니다.

도구를 실행할 때의 요청 이름은 늘 tools/call입니다. 어떤 도구인지는 params 안의 name에 적고 넘길 값은 arguments에 적습니다. 도구 이름은 method 칸에 들어가지 않습니다.

옛 판에서는 먼저 인사를 나눴습니다

2026-07-28 판부터 MCP는 요청 하나하나가 혼자서 읽히게 바뀌었습니다. 그 전 판(2025-11-25까지)은 연결하자마자 initialize 요청으로 버전을 맞추고 notifications/initialized 알림을 보낸 뒤에 tools/list를 불렀습니다. mcp 2.3 서버는 두 판을 다 받습니다. 옛 langchain-mcp-adapters(mcp 1.x를 씀)로 같은 서버에 붙으면 이 인사 과정이 그대로 오갑니다.

도구를 부를 때마다 서버가 새로 켜집니다

에이전트가 도구를 쓸 때마다 한 박자씩 늦거나 방금 한 일을 잊는다면 연결 방식부터 봅니다. 어댑터를 열어 두지 않으면 LangChain은 도구를 부를 때마다 서버에 새로 연결합니다. 서버가 둘인 mcpServers 설정에서는 그때마다 서버 프로그램을 새로 실행합니다. 이를 재려고 시험용 서버를 하나 더 만들었습니다. 부를 때마다 수를 하나씩 올려 돌려주는 도구 bump 하나뿐입니다. 이 서버를 시계 서버와 함께 꽂고 bump를 세 번 불렀습니다.

from mcp.server import MCPServer
mcp = MCPServer("counter")
count = 0                      # 서버가 기억하는 수

@mcp.tool()
def bump() -> int:
    """부를 때마다 1씩 늘어난 수를 돌려줍니다."""
    global count; count += 1
    return count

열어 두지 않으면 세 번 불러도 답이 1, 1, 1입니다. 서버가 매번 새로 켜져 기억하던 수가 사라졌기 때문입니다. 한 번에 0.6초 넘게 걸립니다. 어댑터를 연 채로 부르면 1, 2, 3으로 이어지고 첫 연결 뒤로는 한 번에 2~3밀리초면 끝납니다.

그래서 에이전트를 돌리는 동안에는 async with MCPAdapter(...) 안에서 실행합니다. 다만 열어 둔 연결 하나를 여러 사용자의 요청이 함께 쓰면 상태가 섞일 수 있다고 어댑터 안의 fastmcp 라이브러리가 경고합니다. 웹 서비스라면 사용자 요청 하나마다 열고 닫는 편이 안전합니다.

stdio 서버에서 print는 로그가 아닙니다

로그를 보려고 넣은 print() 한 줄 때문에 에이전트 프로그램이 오류로 끝나기도 합니다. stdio(표준 입출력) 방식에서 에이전트는 서버를 자식 프로세스(process, 자기 아래에서 도는 프로그램)로 실행하고 파이프 세 개로 잇습니다. 요청은 표준 입력(stdin)으로, 답은 표준 출력(stdout)으로 오가고 표준 오류(stderr)는 로그용 옆길입니다.

규격은 서버가 표준 출력에 MCP 메시지가 아닌 글을 쓰면 안 된다고 정해 두었습니다. mcp 2.x는 이를 지키려고 서버가 도는 동안 표준 출력을 표준 오류 쪽으로 돌려 둡니다. 그런데 파이프에 이어진 프로그램의 print()는 글을 바로 내보내지 않고 버퍼(buffer, 모았다가 한꺼번에 내보내는 임시 칸)에 쌓아 둡니다. 서버가 끝나면서 표준 출력을 원래대로 돌린 뒤에야 버퍼가 비워지고 그 줄이 메시지 통로 맨 끝으로 나옵니다.

로그는 처음부터 print(..., file=sys.stderr)나 logging으로 표준 오류에 씁니다.

mcp 1.x로 만든 서버라면 답 사이에 끼어듭니다

mcp 1.30의 FastMCP 서버는 표준 출력을 돌려 두지 않습니다. print(..., flush=True)처럼 바로 내보낸 줄은 답 바로 앞에 끼어 메시지 통로로 갑니다. 시험해 보니 두 클라이언트 모두 그 줄을 건너뛰고 답을 받았고 옛 클라이언트는 Failed to parse JSONRPC message 경고를 남겼습니다. 같은 flush=True도 mcp 2.3 서버에서는 표준 오류로 갔습니다. 어느 쪽이든 로그를 표준 오류에 쓰면 판을 가리지 않습니다.

같은 서버를 LangChain과 LlamaIndex가 함께 씁니다

서버를 따로 켜 두고 주소로 접속하게 하면 여러 앱이 한 서버를 나눠 씁니다. 이 방식을 Streamable HTTP라고 부릅니다. 앱은 웹 페이지를 부를 때처럼 HTTP 요청에 메시지를 실어 보냅니다. 코드에서는 mcp.run(transport="streamable-http") 한 줄만 바꾸면 되고 서버는 http://127.0.0.1:8000/mcp에서 기다립니다. 127.0.0.1은 내 컴퓨터 자신을 가리키는 주소이고 8000은 그 컴퓨터의 문 번호(포트)입니다.

같은 파일 서버를 이렇게 띄우고 LangChain 에이전트와 LlamaIndex 에이전트로 차례로 붙여 봤습니다. 둘 다 같은 두 도구를 받았고 같은 파일을 읽었습니다. 서버는 어느 프레임워크가 부르는지 모릅니다. 메시지 형식만 맞으면 됩니다.

import asyncio
from llama_index.tools.mcp import BasicMCPClient, McpToolSpec

async def main():
    # ① 같은 서버 주소, 다른 프레임워크
    client = BasicMCPClient("http://127.0.0.1:8000/mcp")
    tools = await McpToolSpec(client=client).to_tool_list_async()
    for t in tools:
        print(t.metadata.name, "|", t.metadata.description[:24])
    print(await tools[0].acall(path="reviews.txt"))

asyncio.run(main())

OpenAI API에 서버 주소를 직접 넘기는 방법

Responses API는 tools에 {"type": "mcp", "server_label": "files", "server_url": "https://…/mcp", "require_approval": "never"}를 넣으면 OpenAI 쪽에서 서버에 접속해 도구를 부릅니다. 이때 서버를 부르는 쪽은 내 컴퓨터가 아니라 OpenAI 클라우드라서 127.0.0.1 같은 내 컴퓨터 주소에는 닿지 않습니다. 인터넷에서 열리는 주소와 인증이 필요합니다. require_approval은 도구를 부르기 전에 사람의 허락을 받을지 정하는 값으로, 쓰기 도구라면 허락을 받게 두는 편이 안전합니다.

서버를 꽂기 전에 정할 것

모델은 이름과 설명만 보고 도구를 고릅니다. 그래서 설명을 먼저 씁니다. 무엇을 하는지, 넘길 값의 예, 언제 쓰면 안 되는지를 한두 줄로 적습니다. 도구 목록은 요청마다 모델 입력에 들어가니 쓸 서버만 꽂습니다.

에이전트를 한 번 돌리는 동안은 어댑터를 열어 두어야 서버가 매번 새로 켜지지 않습니다. 내 컴퓨터 안에서만 쓸 서버는 stdio로 두고 로그는 표준 오류로 보냅니다. 여러 앱이 함께 쓸 서버는 Streamable HTTP로 띄웁니다.

남이 만든 서버는 내 컴퓨터에서 내 권한으로 도는 프로그램입니다. 버전을 고정해 두고 파일 서버처럼 쓰기 도구가 있으면 다룰 수 있는 폴더를 묶어 둡니다.
