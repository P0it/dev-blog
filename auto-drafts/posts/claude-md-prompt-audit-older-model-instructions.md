> Claude Code v2.1.283 이 9월 25일 CLAUDE.md 와 스킬, 커맨드에서 구형 모델용 프롬프트 패턴을 찾아내는 `/doctor prompt-audit` 을 더했습니다. 공식 changelog 와 명령 문서, Anthropic 이 공개한 감사 기준 문서를 확인해 무엇이 지적 대상이고 무엇이 그대로 남는지 정리했습니다.

CLAUDE.md 에 `반드시`·`절대`·`CRITICAL` 같은 말을 적어 본 분들이 많을 겁니다. 모델이 지시를 자꾸 흘려서 한 번 더 힘줘 적어 둔 줄입니다. 그런 줄이 지금도 같은 효과를 낼까요? 최신 모델에서는 반대로 움직입니다. 지시를 더 문자 그대로 따르고 더 쉽게 발동하기 때문에, 힘줘 적어 둔 말이 필요 없는 자리에서도 그 규칙을 끌어옵니다. 9월 25일에 나온 Claude Code v2.1.283 이 그런 줄을 찾아내는 명령을 더했습니다. `/doctor prompt-audit` 입니다. 무엇이 걸리는지 알면 CLAUDE.md 와 스킬에서 어떤 줄을 빼고 어떤 줄을 남길지 정할 수 있습니다.

## 9월 25일 릴리스에 붙은 prompt-audit

v2.1.283 changelog 에 적힌 문장은 짧습니다. `/doctor prompt-audit`(`/checkup prompt-audit` 도 같습니다)을 더해 **CLAUDE.md 파일과 스킬, 에이전트, 커맨드를 구형 모델용으로 쓰인 프롬프팅 패턴 기준으로 감사**한다는 것입니다. 같은 릴리스에 이 감사를 손본 항목이 하나 더 있습니다. Claude Code 설정을 볼 때 오래된 경로와 오래된 커맨드, 서로 어긋나는 지시 파일이 보고서 앞쪽으로 올라오게 바꿨고 Claude Code 가 문서로 정한 thinking 키워드는 남겨 두게 했습니다.

명령 문서를 보면 `prompt-audit` 자체는 v2.1.221 이상에서 돌아갑니다. 하는 일은 한 줄로 정리돼 있습니다. 프롬프트와 스킬, 도구 설명에서 구형 모델용으로 쓰인 지시를 찾아내 고칠 내용을 diff 로 제안합니다. 보고서를 먼저 보여 주고 사람이 확인한 뒤에 바꿉니다.

## 압박 어법이 과잉 발동을 부르는 구조

Anthropic 이 공개한 skills 저장소에는 이 감사의 기준을 적어 둔 `prompt-audit.md` 가 들어있습니다. 첫 항목이 압박 어법입니다. 구형 모델은 강하게 밀어야 움직였는데 최신 모델은 반응이 워낙 좋아서 부풀린 강조가 이제는 과잉 발동을 일으킨다고 적혀 있습니다. `CRITICAL: You MUST use this tool` 은 `Use this tool when...` 으로 바꾸라는 것입니다.

반대 방향의 문구도 같이 걸립니다. 요구사항에 `try to`·`if possible` 같은 완충 표현을 붙여 두면 최신 모델은 그것을 문자 그대로 읽고 덜 해도 된다는 허락으로 받습니다. 힘을 준 쪽이든 뺀 쪽이든 모델이 예전보다 곧이곧대로 읽는다는 점이 같습니다.

이 문제는 프롬프트 한 편만 손봐서는 해결되지 않습니다. Anthropic 은 2025년 9월 29일 글에서 프롬프트 엔지니어링과 컨텍스트 엔지니어링을 나눠 설명했습니다. 프롬프트를 한 번 잘 쓰는 작업과, 추론 중에 들어가는 토큰 전체를 계속 관리하는 작업은 다릅니다.

![프롬프트 엔지니어링이 한 번의 작업으로 끝나는 것과 달리 컨텍스트 엔지니어링은 시스템 지시·도구·외부 데이터·대화 기록을 매 차례 다시 골라 담는 반복 작업임을 나란히 보여 주는 다이어그램](https://wzaqtubtqwpddouevwbk.supabase.co/storage/v1/object/public/post-images/2026-09-25/39f4fe28.webp)

같은 글은 목표를 한 문장으로 적었습니다. 원하는 결과가 나올 가능성을 가장 높이는 **가장 작은 고신호 토큰 묶음**을 찾는 것입니다. 토큰이 늘어나면 성능이 떨어지는 현상을 context rot 이라고 부릅니다. CLAUDE.md 에 쌓아 둔 줄은 매 차례 컨텍스트에 들어가므로 이 계산에 그대로 들어갑니다.

## API 기능이 대신하게 된 옛 장치들

감사가 지적하는 둘째 묶음은 지금은 API 기능이 대신하는 옛 장치입니다. `Think step by step` 과 `<scratchpad>` 태그는 adaptive thinking 설정으로 옮기라고 적혀 있습니다. `Use the think tool to plan` 은 지우라고 합니다. 최신 모델은 시키지 않아도 계획을 세우기 때문에 이 문장이 남아 있으면 오히려 계획을 과하게 세웁니다.

JSON 을 억지로 받아내려고 쌓아 둔 프리필 더미는 structured outputs 로 바꾸고 `N 번째 도구 호출마다 진행 상황을 요약하라` 같은 줄은 지운 뒤 기준을 다시 재라고 합니다. `최대 N 단어` 같은 숫자 상한도 `간결하게` 같은 질적 표현으로 바꾸라는 항목이 있습니다. 숫자로 눌러 둔 지시가 특히 자주 남는다고 합니다.

## 금지 목록과 단계 지정이 깎는 품질

판단이 필요한 일에 `STEP 1: ... STEP 2: ...` 식으로 순서를 지정해 두면 결과가 나빠집니다. 순서 대신 결과와 제약을 적으라는 것입니다. `never X, avoid Y` 같은 금지 목록도 같은 부류로 봅니다. 실패 사례를 목록으로 새겨 넣는 대신 원하는 모습을 긍정문으로 적으라고 합니다.

이유를 안 적은 금지는 특히 값이 없습니다. 감사는 `never`·`don't`·`must not` 로 시작하는 줄마다 그것이 실제 업무 제약인지, 그냥 마음에 안 드는 출력 형태를 적어 둔 것인지 가려내라고 합니다. 후자는 긍정문으로 다시 쓰거나 지웁니다.

![시스템 프롬프트의 눈높이를 보여 주는 그림으로 한쪽 끝에는 하드코딩한 if-else 로직으로 부서지기 쉬운 프롬프트가 있고 다른 쪽 끝에는 공유된 맥락을 잘못 전제한 지나치게 일반적인 프롬프트가 있으며 그 사이에 적절한 높이가 있음을 나타낸 스펙트럼](https://wzaqtubtqwpddouevwbk.supabase.co/storage/v1/object/public/post-images/2026-09-25/d755c786.webp)

Anthropic 은 같은 글에서 양쪽 끝을 모두 경고했습니다. 복잡한 하드코딩 로직으로 채운 프롬프트는 부서지기 쉽고 지나치게 막연한 지시는 공유되지 않은 맥락을 있다고 전제합니다. 권하는 방법은 능력 있는 모델로 최소한만 넣고 시작해서 실제로 실패한 것을 보고 한 줄씩 더하는 쪽입니다.

## 도구 설명만은 줄이지 않는다

여기까지 읽으면 전부 줄이라는 말처럼 들립니다. 도구 설명은 예외입니다. 감사 문서는 도구 설명의 기준이 간결함이 아니라 정확성과 계약의 충실함이라고 분명히 적어 뒀습니다. 자세한 설명은 도구 성능에 결정적이어서 오히려 늘어나는 경우가 많습니다.

도구 설명에서 빼야 하는 것은 따로 있습니다. `CRITICAL: You MUST use this tool when...` 같은 행동 유도 문구, 예시 대화, 다른 도구를 꾸짖는 교차 참조, 시스템 프롬프트에 흩뿌려 둔 도구 이름입니다. 대신 계약과 동작 방식, 언제 쓰는지, 파라미터 설명, 주의사항은 남깁니다.

![사람이 쓴 Slack MCP 서버 도구 설명과 Claude 가 다시 쓴 도구 설명의 테스트셋 정확도를 막대로 견준 그래프](https://wzaqtubtqwpddouevwbk.supabase.co/storage/v1/object/public/post-images/2026-09-25/e7ab452e.webp)

Anthropic 이 2025년 9월 11일에 올린 도구 작성 글도 같은 말을 합니다. 도구 설명을 조금만 손봐도 결과가 크게 달라진다는 것을 평가로 보여 줍니다. 줄여야 할 것과 정확히 써야 할 것을 구분하지 않으면 감사 결과를 잘못 적용하게 됩니다.

네 묶음을 나란히 비교해 보면 아래와 같습니다.

| | 감사가 지적하는 것 | 그대로 두는 것 |
|---|---|---|
| 프롬프트 본문 | 압박 어법, 구형 스캐폴드, 과잉 명세, 이유 없는 금지 | 대상·제약·이유 같은 맥락 |
| 스킬 파일 | 하드코딩한 경로와 버전, 시한이 있는 날짜, 사건 기록 | 위험한 작업의 정확한 절차 |
| 도구 설명 | 행동 유도 문구, 예시, 꾸짖는 교차 참조 | 계약과 동작, 파라미터 설명, 주의사항 |
| 요청 설정 | 폐기된 파라미터, 캐시를 깨는 순서, 남은 토큰 노출 | 토큰 집계 |

## 지워서는 안 되는 맥락의 목록

감사 문서에는 무엇이 절대 군더더기가 아닌지도 따로 적혀 있습니다. 대상과 제품, 제약, 이유 같은 맥락은 군더더기가 아닙니다. 되돌리기 어려운 작업은 정확한 절차를 그대로 둡니다. 지금 실제로 재현되는 실패를 막는 금지도 남깁니다.

판정 방식도 정해져 있습니다. 보고서는 항목마다 위치를 `file:line` 으로 적고 원문을 그대로 인용한 뒤, 대상 모델의 동작에 근거한 이유와 확신도를 High·Medium·Low 로 붙입니다. diff 로 제안하는 것은 High 와 Medium 뿐입니다. 이 설계는 감사가 틀렸을 때 사람이 되돌릴 여지를 남겨 둡니다.

## CLAUDE.md 200줄과 훅의 경계

`/doctor` 에는 CLAUDE.md 를 줄이는 검사가 v2.1.206 부터 따로 들어 있습니다. 코드베이스를 읽으면 알 수 있는 내용을 덜어내는 쪽입니다. 디렉터리 구조와 의존성 목록, 아키텍처 개요가 그렇습니다. 남기는 것은 함정과 판단의 이유, 도구 기본값과 다른 관례입니다. 공식 문서는 기준도 적어 뒀습니다. **200줄을 넘는 파일은 컨텍스트를 더 쓰고 준수율을 떨어뜨릴 수 있습니다.**

한 가지는 분명히 구분해 둘 필요가 있습니다. 공식 문서는 CLAUDE.md 와 자동 메모리를 컨텍스트로 다루고 강제되는 설정으로 다루지 않는다고 적었습니다. 모델의 판단과 무관하게 어떤 동작을 막아야 하면 `PreToolUse` 훅을 쓰라고 안내합니다. 그러면 CLAUDE.md 에 금지문을 몇 줄 더 적는 것으로 해결하려던 일 가운데 상당수는 애초에 훅이 맡을 일이었다고 볼 수 있습니다.

## 같은 주에 Cursor 가 줄인 시스템 프롬프트

같은 주에 다른 회사가 같은 방향으로 움직였습니다. Cursor 는 9월 24일 에이전트 품질을 떨어뜨리지 않고 토큰 비용을 약 7% 줄였다고 밝혔습니다. 줄인 방법으로 든 것은 네 가지입니다. 프롬프트를 조였고 도구를 필요할 때만 불러오게 했고 캐싱을 개선했으며 파일 읽기 결과를 압축했습니다.

한쪽은 사용자의 지시 파일을 감사하는 명령을 내놓고 다른 쪽은 자기 시스템 프롬프트를 줄였습니다. 이틀 사이에 나온 두 소식이 같은 곳을 가리킵니다. 2025년에 쌓아 둔 지시가 2026년의 모델에서는 비용이면서 잡음이라는 것입니다. 이 관점에서 보면 규약 문서를 직접 관리하는 쪽에서 먼저 확인할 것은 분량이 아닙니다. 그 줄이 지금 쓰는 모델에서 실제로 동작을 바꾸는지입니다. 바꾸지 않는 줄은 남아 있는 동안 계속 값을 치릅니다.
