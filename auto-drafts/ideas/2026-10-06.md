## 1. 생성 헤드를 떼어 낸 2B 모델이 답 대신 보정된 confidence 를 돌려준다 ⭐ 완성 원고로 선택

**제목 후보**

- `Strands Decider 2B 가 텍스트 대신 돌려주는 숫자`
- `에이전트 분기마다 LLM 을 부르지 않는 방법`
- `115ms 판정과 선택지 개수에 흔들리지 않는 confidence`

**왜 지금인가**

AWS 의 Strands Labs 가 10월 1일 `strands-decider` 저장소를 열고, 10월 5일 기준 모델을
`strands-decider-2B-hobson-v21` 로 올렸습니다. 10월 2일에 Apple silicon(MLX) 추론이,
10월 3일에 이미지 입력이 들어갔습니다. 에이전트 판에서 분기 판정을 생성 모델에게 맡기는 게
기본값이 된 시점에, 생성을 아예 없애고 고정된 선택지 중 하나를 고르는 쪽으로 간 모델이
Apache-2.0 으로 나온 것입니다. 저장소에 preregistration 14건과 figure 21장이 같이 공개돼
있어 실패한 실험까지 그대로 읽힙니다.

**핵심 앵글 한 문장**

에이전트 파이프라인의 분기 판정에서 실제로 필요한 산출물은 문장이 아니라 선택지 개수와
무관하게 같은 뜻을 갖는 confidence 숫자이고, 그 숫자를 받으면 라우팅 임계값을 한 번만 정해
큰 모델 호출을 어디서 멈출지 결정할 수 있다.

**글 구조 아웃라인**

- 분기 판정을 생성 모델에 맡길 때 치르는 비용과 받지 못하는 것
- Hobson 구조 — 사전학습 torso 를 두고 language-modelling head 를 버리고 약 100만 개
  파라미터짜리 pointer head 를 붙인다. `logit_k = ⟨q(h_answer), k(h_opt k)⟩ / √256`
- 같은 masked softmax 에서 `noul`(예/아니오)·`choice`(N 중 1)·`score`(순서 있는 척도) 세 가지가 나온다
- confidence 를 `(N·p_max − 1) / (N − 1)` 로 정규화해 3지선다와 10지선다의 임계값을 같게 만든 선택
- JevBench 231문항 0.762, 난이도별 1.000 / 0.931 / 0.550, ECE 0.064, RTX 3090 에서 115ms
- 정직하게 읽을 대목 — 질문을 바꿔도 답이 같은 구간, "추론을 배운 게 아니다"라는 연구 기록
- 작은 팀이 이 계층을 자기 하드웨어에 두는 의미

**현우 경험과 엮을 지점**

워크플로를 직접 조립하는 1인 개발자 관점에서, 파이프라인의 모든 칸을 같은 크기 모델로 채우지
않고 판정만 떼어 2B 로 내리는 선택이 비용·지연·관측 가능성 셋을 한꺼번에 건드립니다. M3 Pro
에서 돌아간다는 수치가 그 선택을 로컬에서 재 볼 수 있게 만든다는 해석까지. 체험 서술은 검토
단계에서 채운다.

## 2. AI 에이전트 요금을 사용량이 아니라 확인된 결과 단위로 받는다

**제목 후보**

- `에이전트 요금을 리드 한 건 단위로 받기 시작한 곳`
- `사용량 과금을 두고 성과 과금을 더한 Vida 의 계산`

**왜 지금인가**

Vida Global(AMEX: VIDA)이 10월 5일 digital employee 플랫폼에 outcome-based billing 을
추가했습니다. 사용량·구독 단계가 아니라 리드 검증, warm transfer, 온보딩, 이탈 고객 재유입처럼
확인된 결과 단위로 요금을 매기는 방식이고, 기존 사용량 과금과 함께 고를 수 있게 뒀습니다.
처음 적용 대상은 성과 마케팅과 보험처럼 결과 정의가 분명한 업종입니다. 창업자 Lyle Pratt 은
"에이전트가 실제 업무를 맡는데 대부분 여전히 전통적 소프트웨어처럼 가격이 매겨진다"고 말했습니다.

**핵심 앵글 한 문장**

성과 과금으로 가면 "성과"의 정의가 계약 조항이 되고, 에이전트가 만든 결과를 누가 어떤 근거로
확인하는지가 제품의 핵심 기능으로 올라온다.

**글 구조 아웃라인**

- 10월 5일 발표 내용과 적용 업종
- seat·사용량·성과 세 가지 과금을 견주는 표
- 성과 과금이 성립하려면 먼저 필요한 것 — 결과 판정, 분쟁 처리, 귀속
- 왜 성과 마케팅과 보험부터인지(결과가 외부 시스템에 기록되는 업종)
- 반대 시각 — 판정 비용이 요금 절감을 먹는 경우
- CSM 도구에 같은 방식이 들어올 때 생기는 문제(갱신·헬스스코어는 귀속이 어렵다)

**현우 경험과 엮을 지점**

CSM·마테크 쪽을 보는 관점에서, 과금 단위가 바뀌면 제품이 측정부터 다시 만들어야 한다는 해석.

## 3. 에이전트를 띄우고 상태를 읽는 일이 플러그인 공개 API 가 됐다

**제목 후보**

- `Claude Code 가 agent.spawn 을 플러그인에 열며 정리한 것`
- `에이전트 ID 를 하나로 합치고 idle 과 waiting 을 나눈 변경`

**왜 지금인가**

10월 3일 Claude Code 2.1.289 에 `agent.spawn` 이 들어가 teammate 가 공유 에이전트를 띄울 수
있게 됐고, 훅 이벤트마다 달랐던 에이전트 ID 가 하나로 합쳐졌습니다. `$.agent.list()` 에
idle 과 waiting 상태가 분리된 것도 같은 릴리스입니다. 어제 브리핑이 같은 버전의 화면 실패
수정을 다뤘다면 이쪽은 반대편입니다 — 여러 대를 동시에 돌릴 때 필요한 식별과 상태 모델이
플러그인에서 읽고 쓸 수 있는 표면으로 올라온 것입니다. 같은 릴리스에 `@` 로 멘션한 파일이
read deny 규칙을 우회하던 문제도 함께 고쳐졌습니다.

**핵심 앵글 한 문장**

에이전트 여러 대를 조율하려면 식별자와 대기 상태가 먼저 공개 표면이어야 하고, 이 릴리스는
오케스트레이션 도구를 밖에서 만들 수 있는 최소 조건을 정리한 변경이다.

**글 구조 아웃라인**

- 2.1.289 에서 에이전트 쪽에 들어간 세 가지 변경
- 왜 ID 통일이 먼저인가 — 훅 이벤트마다 ID 가 다르면 외부에서 상태를 붙일 수 없다
- idle 과 waiting 을 나눈 이유(놀고 있는 것과 무언가를 기다리는 것은 다른 처리)
- `@` 멘션이 read deny 를 우회하던 수정과 함께 읽기
- 무인·장시간 세션을 돌리는 쪽에 바로 걸리는 대목

**현우 경험과 엮을 지점**

클라우드 루틴처럼 사람이 안 보는 세션을 운영해 본 관점에서, 대기 상태 구분이 없으면 멈춘
세션과 기다리는 세션을 못 가른다는 해석.
