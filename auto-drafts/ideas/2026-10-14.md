## 1. 파일 하나를 고치면 왜 그 위 폴더들의 이름표만 바뀔까 ⭐ 완성 원고로 선택

**제목 후보**

- `git이 파일을 위치 대신 지문으로 부르는 이유` ← 채택
- `파일 하나를 고쳤는데 왜 폴더 이름까지 바뀔까요`
- `Scion이 캐시끼리 연락하지 않아도 되는 이유`

채택 이유: 직전 HTML 글이 `~까요` 질문형이라 이번은 짧은 명사구로 골격을 바꿨습니다. 검색어 `git` 이 맨 앞에 있고,
"왜 지문으로 부르나"의 답(같은지 비교·꼭대기 하나로 확인·복사본이 틀리지 않음)은 본문에 남겨 둡니다.
Scion 은 아직 검색어로 약해 제목 대신 첫 화면 훅에 둡니다.

**훅이 된 소식**

Anthropic 이 10월 13일 엔지니어링 블로그에 [Redesigning source control at Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)
을 올렸습니다. 사내 monorepo 의 하루 merge 수가 2026년 5월 약 2,500 건에서 9월 30,000 건 이상으로 늘자 git 을 걷어 내고
**Scion** 이라는 자체 버전 관리 시스템으로 다섯 달 만에 옮겼다는 글입니다. 일곱 명이 Claude 와 함께 만들었습니다.

**설명할 원리와 이 글이 답할 질문**

**내용 주소(content addressing)와 Merkle tree.** 데이터에 위치가 아니라 **내용에서 계산한 지문(hash)** 으로 이름을 붙이면
무엇이 가능해지는가.
이 글이 답할 질문: *Scion 은 왜 "모든 데이터가 내용 주소이고 바뀌지 않으므로 어느 서버든 조율 없이 캐시할 수 있다"고 말할 수 있는가,
그리고 파일 하나를 고치면 왜 그 파일에서 꼭대기까지 가는 길의 이름만 바뀌는가.*

핵심은 세 겹입니다.
1. **같은 내용 → 같은 이름, 한 글자만 달라도 → 전혀 다른 이름.** git 문서(user-manual "The Object Database")가
   객체 이름은 내용의 SHA-1 이고, 같은 내용은 어느 저장소에서든 같은 이름이 된다고 적어 둡니다.
2. **폴더(tree)의 이름은 그 안에 든 것들의 이름으로 계산한다.** 그래서 파일 하나가 바뀌면 그 파일 → 부모 폴더 → … → 꼭대기
   (root)까지 한 줄만 이름이 바뀌고, 나머지 가지는 그대로입니다. 두 tree 를 비교할 때 이름이 같은 가지는 들여다볼 필요가 없습니다.
3. **이름이 내용이면 그 이름의 데이터는 영원히 바뀌지 않는다 → 아무 데서나 캐시해도 틀릴 일이 없다.** Scion 의 fetch 는
   "내가 가진 것"을 서버에 설명하지 않고 root tree 부터 **원하는 객체의 이름**을 부르며 내려갑니다. 캐시 적중률이 층마다 99% 를 넘는다는 것도 이 성질에서 나옵니다.

**대표 인터랙션 아이디어 한 줄**

작은 프로젝트 폴더 나무(파일 6개)를 그려 두고, 독자가 파일 하나의 글자를 고치면 그 잎에서 꼭대기까지의 지문만 색이 바뀌며
다시 계산된다. 나머지 가지는 회색으로 "그대로"라고 남는다. 지문은 실제 해시 함수로 브라우저에서 계산한다.

## 2. 대화창을 닫아도 AI 가 나를 기억하는 방법

**훅이 된 소식**

Meta 가 10월 12일 첫 frontier 모델 **Muse Wonder** 와 **Muse Wonder Full** 을 냈습니다. 대화를 넘어 맥락을 이어 가는
"Active Memory" 를 앞세웠습니다. 검색 결과로는 API 가격이 입력 100만 토큰당 $4, 출력 $20, context window 1M 입니다.
**⚠ Meta 쪽 1차 소스(`about.fb.com`, `research.meta.ai`)가 모두 DNS 차단이라 원문을 열지 못했습니다.** 이 수치는 검색 요약에서 본 것입니다.

**설명할 원리와 이 글이 답할 질문**

모델 자체는 대화가 끝나면 아무것도 기억하지 않습니다(가중치는 대화 중에 바뀌지 않는다). "기억"은 대화 밖 저장소에 메모를 써 두었다가
다음 대화의 context 에 다시 넣어 주는 장치입니다. 질문: *모델은 그대로인데 무엇이 기억하는가, 무엇을 넣고 무엇을 버리는가.*

**대표 인터랙션 아이디어 한 줄**

대화 세 번이 지나가는 타임라인. 각 대화가 끝날 때 메모장에 무엇이 적히는지, 다음 대화 시작 때 context 창에 그중 무엇이 들어가는지 보이고,
context 창 크기를 줄이면 오래된 메모부터 밀려난다.

## 3. 수만 명이 동시에 같은 칸을 고칠 때 아무도 줄을 서지 않는 법

**훅이 된 소식**

같은 Scion 글에서 ref(브랜치) 이동은 "Spanner 한 행에 대한 compare-and-swap" 이고, 전역 잠금을 쓰는 전통적인 merge queue 는
테스트가 도는 동안 수백 건이 들어오는 에이전트 규모에 맞지 않아 merge 뒤·배포 전 테스트에 투자했다고 적습니다.

**설명할 원리와 이 글이 답할 질문**

**compare-and-swap(낙관적 동시성).** 자물쇠를 걸고 한 명씩 들어가는 대신, "내가 본 값이 아직 그대로면 바꾸고, 아니면 다시 시도"하는 규칙.
질문: *잠그지 않고도 두 사람의 수정이 서로를 덮어쓰지 않게 하려면 무엇을 확인해야 하는가.*

**대표 인터랙션 아이디어 한 줄**

에이전트 점 여러 개가 같은 칸(main 브랜치 끝)을 동시에 옮기려 한다. 잠금 방식과 CAS 방식을 나란히 돌리고, 독자가 동시에 오는 수를 늘리면
잠금 쪽 대기열은 길어지고 CAS 쪽은 실패 후 재시도 점이 튀어 오른다.
