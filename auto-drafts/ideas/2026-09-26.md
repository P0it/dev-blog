## 1. 구형 모델을 달래려고 쓴 지시가 최신 모델을 방해한다 ⭐ 완성 원고로 선택

**제목 후보**
- `CLAUDE.md 에 강하게 적어 둔 지시가 지금은 역효과다` ← 채택
- `Claude Code 가 CLAUDE.md 에서 찾아내는 구형 모델용 지시`
- `"CRITICAL: 반드시" 라고 적어 둔 줄의 값`

**왜 지금인가**
9월 25일에 나온 Claude Code v2.1.283 이 `/doctor prompt-audit` 을 더했습니다. CLAUDE.md
와 스킬, 에이전트, 커맨드를 훑어 **구형 모델용으로 쓰인 프롬프팅 패턴**을 찾아내는
명령입니다. 지시 파일을 줄이라는 권고는 전에도 있었지만, 줄이라는 기준이 "분량"에서
"어느 모델을 상대로 쓴 문장인가"로 옮겨 간 것은 이번이 처음입니다. 하루 앞선 9월 24일
Cursor 도 시스템 프롬프트를 조여 토큰 비용을 줄였다고 밝혀서, 이틀 사이에 양쪽이 같은
곳을 가리켰습니다.

**핵심 앵글 한 문장**
최신 모델은 지시를 더 문자 그대로 읽고 더 쉽게 발동하기 때문에, 구형 모델을 달래려고
힘줘 적어 둔 압박 어법·금지 목록·단계 지정이 이제는 과잉 발동과 품질 저하로 돌아옵니다.

**글 구조 아웃라인**
- v2.1.283 changelog 의 `/doctor prompt-audit` 한 줄과 같은 릴리스의 개선 항목
- 압박 어법이 과잉 발동을 부르는 구조, `try to` 같은 완충 표현이 받는 반대 효과
- 프롬프트 한 편의 문제가 아니라 컨텍스트 전체의 문제라는 자리매김(공식 다이어그램)
- 지금은 API 기능이 대신하는 옛 장치들(`Think step by step`, `<scratchpad>`, 프리필 더미)
- 판단이 필요한 일에 단계를 지정하거나 이유 없는 금지를 쌓을 때 깎이는 품질(스펙트럼 그림)
- 도구 설명만은 예외라는 점 — 기준이 간결함이 아니라 정확성(정확도 비교 그래프)
- 절대 군더더기가 아닌 것들과 High·Medium·Low 확신도 판정 방식
- CLAUDE.md 200줄 기준, 그리고 강제가 필요하면 `PreToolUse` 훅이라는 경계
- 같은 주 Cursor 의 토큰 비용 절감과 두 소식이 함께 가리키는 방향

**현우 경험과 엮을 지점**
이 저장소에도 `CLAUDE.md`·`POSTING.md`·`.claude/commands/*.md` 처럼 직접 관리하는 규약
파일이 여러 개 있습니다. 그 문서들은 정확히 감사가 지적하는 형태를 갖고 있습니다 —
`STEP 1~4` 로 순서를 지정하고, `✗` 로 금지 목록을 쌓고, `0~2장`·`최대 1개` 처럼 숫자
상한을 두고, `★ 가장 중요`·`반드시` 로 강조를 겁니다. 반대로 감사가 남기라고 한 것도
같이 갖고 있습니다. 규약마다 "왜 그렇게 정했는지"와 피드백 날짜가 붙어 있는 대목입니다.
같은 문서 안에 지적 대상과 보존 대상이 섞여 있어서, 분량만 보고 줄이면 남길 것을 먼저
잃게 됩니다. (체험 서술은 검토 단계에서 채워 넣는 것을 전제로, 원고에서는 "이 관점에서
보면" 수준의 해석으로만 두었습니다.)

## 2. 에이전트 950개가 21시간 돌고 보고서 하나가 올라왔다

**제목 후보**
- `에이전트 950개를 21시간 돌려 건진 후보 20개`
- `토큰 2억 1천만 개를 쓰고 사람에게 넘긴 보고서 한 건`

**왜 지금인가**
Anthropic 이 9월 23일 Claude 가 새 효소 계통을 찾아냈다고 발표했습니다. CRISPR 과 닮은
반복 배열을 가진 array-associated reverse transcriptase 입니다. 발표문에 규모가 숫자로
적혀 있습니다 — 에이전트 약 950개, 토큰 2억 1천만 개, 21시간, reverse transcriptase
20만 개 이상 분석, 후보 계통 3,500개, 최종 20개. 그리고 사람이 검토한 것은 한 에이전트가
올린 보고서 한 건입니다.

**핵심 앵글 한 문장**
대규모 팬아웃의 성과는 950개가 만들어 낸 산출물의 총량이 아니라 3,500개를 20개로 줄인
필터와 그 뒤에 붙은 실험실 검증에서 나옵니다.

**글 구조 아웃라인**
- 발표문의 숫자 여섯 개를 먼저 놓고 비율을 본다(20만 → 3,500 → 20 → 1)
- 사람이 준 지시는 "높은 수준의 방향"뿐이었다는 대목의 의미
- 에이전트 하나가 이상한 RT 옆의 반복 패턴을 알아채고 보고서를 올린 지점
- 21시간·2억 1천만 토큰을 지금 단가로 환산해 보는 계산
- 검증이 실험실에 있었다는 점 — 자동화되지 않은 마지막 칸
- 1인 개발자 규모에서 이 구조를 축소해 쓸 수 있는지, 무엇이 필터 역할을 해야 하는지

**현우 경험과 엮을 지점**
팬아웃으로 에이전트를 여러 개 띄워 본 경험이 있으면, 산출물이 늘어날 때 정작 늘어나는
부담이 검토라는 점을 이미 확인했을 것입니다. 발표문의 비율은 그 부담을 어디에 두어야
하는지를 숫자로 보여 줍니다. (체험 서술은 검토 단계에서 채워 넣는 것을 전제로 합니다.)

## 3. 마테크 벤더들이 한꺼번에 "기억"을 팔기 시작했다

**제목 후보**
- `마테크가 파는 기억이 실제로 어디에 저장되는가`
- `캠페인마다 초기화되던 고객 맥락의 값`

**왜 지금인가**
9월 24일 Iterable 이 가을 릴리스를 발표했습니다. Integrations Hub, Nova Conversations,
RCS 메시징, Nova Intelligence Agents 를 묶어 내놓으면서 내세운 문구가 "마테크에 기억을
준다"입니다. 캠페인·채널·대화마다 고객 이해가 초기화되지 않고 누적된다는 주장입니다.
같은 주에 Certinia 는 자율 에이전트 14개와 도구 135개로 늘린 Veda 를 알렸고, 9월 24일
Dataiku 는 여러 플랫폼에 흩어진 에이전트를 목록화하는 Agent Management 를 발표했습니다.
세 발표가 같은 공백을 가리킵니다.

**핵심 앵글 한 문장**
벤더가 "기억"이라고 부르는 것의 실체는 고객 맥락을 어느 계층에 두는지의 선택이고,
그 선택을 벤더에게 넘기면 다음 갈아타기 비용이 거기서 발생합니다.

**글 구조 아웃라인**
- Iterable 이 말한 "연속되는 인텔리전스 루프"가 구체적으로 무엇을 저장한다는 것인지
- CSM 실무에서 초기화되던 맥락의 목록(온보딩 단계, 직전 문의, 헬스스코어 변화)
- 같은 주 Certinia·Dataiku 발표와 겹쳐 보면 드러나는 공통 공백
- 고객 데이터 플랫폼에 두는 것과 엔게이지먼트 도구에 두는 것의 차이
- 1인 개발자·소규모 팀이 이 계층을 직접 들고 있어야 하는 이유
- 벤더 기억을 쓰기로 할 때 확인할 것(내보내기 형식, 보존 기간, 감사 기록)

**현우 경험과 엮을 지점**
CSM·martech 스택을 다뤄 본 관점에서는 "기억"이 새 기능이라기보다 원래 여러 도구에
흩어져 있던 것을 한쪽으로 모으겠다는 제안으로 읽힙니다. 직접 만든 앱에서 고객 맥락을
어디에 두었는지와 대 보면 판단 기준이 생깁니다. (체험 서술은 검토 단계에서 채워 넣는
것을 전제로 합니다.)
