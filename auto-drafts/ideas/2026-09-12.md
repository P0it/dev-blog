## 1. 스킬이 떴다는 것과 결과를 바꿨다는 것은 다르다 ⭐ 완성 원고로 선택

**제목 후보**

- `claude plugin eval 의 Δ, 스킬이 켜졌다고 일한 건 아닙니다`
- `스킬을 껐을 때와 켰을 때가 같으면 0점입니다`

**왜 지금인가**

Claude Code 2.1.269 가 9월 11일 18:12(UTC) npm 에 올라왔고, 여기 `claude plugin eval` 이
들어갔다. 플러그인·스킬을 실제 프롬프트로 돌려 채점하는 명령이다. 핵심은 점수가 아니라
`Δ` 다 — 케이스 하나를 플러그인을 켜고 3번, 끄고 3번 돌려 두 점수의 차를 적는다.
일주일 전 9월 4일 2.1.261 의 `/skill-doctor` 가 "안 쓰인 스킬과 그 컨텍스트 비용"을
보여 줬다면, 이번 것은 "그 스킬이 결과를 바꿨는지"를 잰다.

**핵심 앵글**

스킬이 호출됐다는 사실은 성과가 아니다. 문서 스스로 `tool_used: Skill` 그레이더를
점수에서 빼고(`scored: false`), "두 팔 모두 1.0 이면 그 플러그인이 통과시킨 게 아니다"라고
적어 뒀다. 그리고 Δ 가 0 근처로 나올 때 가장 흔한 원인은 스킬 본문이 아니라 `description`
한 줄이다 — 지식의 문제가 아니라 라우팅의 문제라는 말이다.

**아웃라인**

- 9월 4일 `/skill-doctor` 가 잰 두 가지: 호출 여부와 턴당 컨텍스트 비용. 기여도는 빈칸
- 9월 11일 `claude plugin eval`: 케이스 1개 = 3런 × 2팔 = 6런, 그레이더 6종(4종 무료 /
  `llm`·`baseline` 은 judge 모델 과금), 문서 예시가 74초 · $0.41
- Δ 0 의 범인은 `description` — 문서가 "가장 흔한 첫 발견"으로 못 박은 대목
- 반대 시각: Δ 를 만드는 judge 기본값이 작은 빠른 모델이다. 문서도 "Δ 가 음수면
  플러그인보다 judge 를 먼저 의심하라"고 적었고, LLM-as-judge 연구는 판정 흔들림을
  수치로 보고한다
- CI 게이트: `--threshold` 미달이면 exit 1, `--max-cost-usd` 초과면 exit 2. 모델과
  judge 를 핀으로 고정해야 모델 교체가 회귀로 둔갑하지 않는다
- 마무리: 스킬을 늘리는 일과 스킬이 일하게 하는 일은 다른 작업이다

**현우 경험과 엮을 지점**

이 블로그 저장소 자체가 `skills/portfolio`, `.claude/commands/*.md`, 그리고 매일 아침 도는
클라우드 루틴으로 굴러간다. 규약 문서를 고쳐 가며 커맨드를 손보는 흐름인데, 고친 뒤
결과가 나아졌는지 재는 장치는 지금 없다. `/research` 의 시각자료 방침처럼 규약을 바꾼
대목이 실제로 원고를 바꿨는지 Δ 로 확인할 수 있는 자리다. (체험 서술은 검토 단계에서)

## 2. 아무도 제품을 열지 않으면 헬스스코어의 입력값이 사라진다

**제목 후보**

- `MCP 도구 260개를 연 날, 제품 사용량은 지표에서 빠집니다`
- `로그인 수로 이탈을 예측하던 방식이 끝나는 중입니다`

**왜 지금인가**

Klaviyo 가 9월 9일 연례 행사 K:BOS 에서 플랫폼을 외부 AI 에 열었다고 발표했다. MCP 도구
260개 이상, API 490개 이상이 Claude·ChatGPT 같은 시스템에서 곧바로 닿고, 에이전트가
데이터를 읽고 쓰고 캠페인을 띄우는 데까지 사람이 Klaviyo 화면을 열 필요가 없다는 것이
발표의 요지다. 자연어 질문을 SQL 로 바꿔 자사 데이터에 돌리는 기능도 프리뷰로 붙었다.

**핵심 앵글**

CSM 의 헬스스코어는 로그인 빈도·기능 사용량·세션 길이처럼 "사람이 제품을 얼마나
열었나"를 입력으로 쓴다. 에이전트가 대신 들어오면 그 신호는 줄어드는데, 계정이
건강해서가 아니라 계측 지점이 옮겨 갔기 때문이다. 제품 사용량 지표를 MCP 도구 호출
로그로 다시 깔지 않으면, 가장 잘 쓰는 고객이 이탈 위험군으로 찍힌다.

**아웃라인**

- 발표 내용: MCP 도구 260+ · API 490+ · 화면을 열지 않는 캠페인 집행
- 헬스스코어가 실제로 무엇을 먹고 사는지 — 사용량·로그인·기능 채택
- 계측이 UI 에서 도구 호출로 옮겨 갈 때 생기는 착시: 우량 고객의 점수 하락
- 온보딩도 같이 흔들린다. "첫 캠페인 발송까지 걸린 시간"을 사람이 아니라 에이전트가 줄인다
- 반대 시각: 에이전트 호출도 결국 계정 단위로 로깅되니 지표를 갈아 끼우면 그만이다.
  다만 그 교체를 아무도 먼저 하지 않는다는 게 문제다
- 1인 개발자의 제품에도 같은 질문이 온다 — 내 앱의 사용량은 사람이 만든 것인가

**현우 경험과 엮을 지점**

CSM·martech 를 보는 눈과 직접 만든 앱의 계측을 겹쳐 놓는 자리다. 에이전트가 붙는 제품에서
"활성 사용자"를 어떻게 다시 정의할지는 1인 개발자도 바로 부딪히는 문제다.

## 3. 플래그십을 은퇴시키고 그 호출을 작은 모델로 넘겼다

**제목 후보**

- `상위 모델을 부르면 작은 모델이 답합니다, 요금도 작은 쪽으로`
- `V4-Pro 는 없어졌고 남은 건 552B 짜리 Flash 입니다`

**왜 지금인가**

DeepSeek 이 9월 10일 V4.1-Flash 를 공개했다. 파라미터 552B 규모의 MoE 로, 이전
V4-Flash(284B)의 두 배에 가깝고 컨텍스트는 100만 토큰대다. 회사 설명으로는 훨씬 큰
V4-Pro 보다 성능·비용·속도에서 앞선다. 9월 14일부터 API 의 V4-Pro 요청은 V4.1-Flash 가
받아 작은 쪽 요금으로 청구되고, V4-Flash 와 8월의 실험적 비전 모델은 은퇴한다.

**핵심 앵글**

"상위 모델 / 하위 모델"이라는 요금제 사고가 흔들린다. 상위 티어를 지정해도 하위 모델이
답하고 요금은 하위 기준이라면, 모델 선택은 티어 고르기가 아니라 라우팅 정책을 읽는
일이 된다. 1인 개발자가 모델 ID 를 코드에 박아 두고 쓰는 습관이 가장 먼저 깨진다.

**아웃라인**

- 9월 10일 공개, 552B MoE, 100만 토큰대 컨텍스트, Causal Encoder-Decoder 구조
- 9월 14일부터 V4-Pro 호출이 V4.1-Flash 로 넘어가고 요금은 작은 쪽
- 모델 ID 를 고정해 둔 코드가 조용히 다른 모델을 받는다는 뜻 — 회귀 감지 장치가 필요하다
- 반대 시각: 사용자 입장에선 싸고 빨라지는 변경이라 대부분은 이득이다
- 1번 아이디어와 이어지는 대목 — 모델이 바뀌었을 때 내 프롬프트·스킬이 여전히 통하는지
  재는 장치가 있어야 이런 교체를 감지한다

**현우 경험과 엮을 지점**

앱에 LLM 을 붙일 때 모델 ID 를 상수로 두느냐 설정으로 빼느냐의 선택. 벤더가 라우팅을
바꾸는 날 어느 쪽이 덜 아픈지가 이번 사례로 드러난다.
