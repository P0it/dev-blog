## 1. 비밀 값을 가려 주는 규칙이 문자열 모양 하나에 걸려 빗나갔다 ⭐ 완성 원고로 선택

**제목 후보**

- `Claude Code 로그에서 마스킹을 빠져나가는 비밀번호` ← 채택
- `Claude Code 2.1.285 가 고친 비밀 값 세 건`
- `마스킹된 로그에 남아 있던 비밀번호와 인증서 파일`

**왜 지금인가**

9월 29일 공개된 Claude Code v2.1.285 의 수정 목록에 비밀 값이 빠져나간 건이 세 줄
들어 있다. 하나는 가려진 로그와 트랜스크립트에 URL 비밀번호가 남은 것이고, 나머지 둘은
`/ultrareview` 가 자격증명 파일을 업로드에서 빼지 못한 것이다. 세 건 모두 "값이 위험해서"가
아니라 "이름이나 문자열 모양이 규칙과 조금 달라서" 새어 나갔다.

**핵심 앵글 한 문장**

Claude Code 의 비밀 값 보호는 값의 내용이 아니라 알려진 패턴과 파일 이름으로 판단하기
때문에, 같은 비밀번호라도 `%40` 으로 적혀 있거나 파일 이름에 콜론이 들어가면 그대로 나간다.

**글 구조 아웃라인**

- 도입: 로그나 세션을 남에게 넘길 때 화면에 가려져 보이던 값을 그대로 믿어도 되는지
- `@` 와 `%40` — URL 에서 비밀번호 구간을 가르는 구분자가 비밀번호 안에 들어갔을 때
- `/ultrareview` 가 커밋되지 않은 자격증명 파일을 이름으로 걸러내는 방식과 그 목록
  (`.env`, `*.tfvars`, `id_rsa`, `*.pem`), 그리고 콜론·편집기 백업 표시가 만든 빈틈
- 제외 규칙이 커밋되지 않은 변경에만 적용된다는 점 — 이미 커밋된 `.env` 는 그대로 올라간다
- 문서가 명시한 운영체제는 macOS·Linux·WSL 세 곳이라는 점
- 오류 보고·세션 품질 설문 업로드·`/feedback` 이 각각 무엇을 가리고 무엇을 그대로 보내는지 표로
- 마무리: 세션을 넘기기 전에 확인할 것

**현우 경험과 엮을 지점**

Cisco 파트너사 솔루션개발팀에서 고객 환경의 접속 문자열을 다루는 자리라면, DB URL 에
특수문자가 든 비밀번호는 흔한 편이다. 클라우드 세션과 코드 리뷰를 업무에 붙일 때
"가려졌다는 표시"를 신뢰 경계로 쓸 수 있는지는 검토 항목이 된다. 체험 서술은 검토자가 채운다.

## 2. 상시 가동 에이전트를 내놓은 날, 다른 쪽은 백그라운드 작업에 시간 상한을 걸었다

**제목 후보**

- `24시간 돌아가는 에이전트와 2시간에서 끊기는 백그라운드 작업`
- `에이전트를 계속 켜 두는 쪽과 시간을 끊는 쪽`

**왜 지금인가**

9월 29일 OpenAI 가 DevDay 2026 에서 Dots 를 공개했다. 상시 가동으로 목표를 향해
계속 일하고 자기 클라우드 컴퓨터와 브라우저를 갖는 에이전트라고 소개됐다. 같은 날
공개된 Claude Code v2.1.285 는 반대 방향의 항목을 담았다 — 백그라운드 Bash·PowerShell
명령에 시간 상한을 걸어 기본 30분, 최대 2시간에서 멈추고 그 사실을 모델에게 알린다.

**핵심 앵글 한 문장**

에이전트를 오래 돌리는 일의 난점은 모델의 지속력이 아니라 끝나지 않는 작업을 누가
어떻게 끊느냐이고, 두 제품이 같은 날 그 문제의 양쪽 끝을 택했다.

**글 구조 아웃라인**

- Dots 가 무엇으로 소개됐는지 (상시 가동·자기 클라우드 컴퓨터·4,000개 이상 앱 연결)
- 같은 날 Claude Code 가 백그라운드 명령에 건 30분·2시간 상한
- 상시 가동이 만드는 비용·권한 표면 — 누가 언제 멈추는가
- `CLAUDE_CODE_NONSTREAMING_TIMEOUT_RETRIES` 처럼 재시도 횟수를 제한하는 항목이
  같은 릴리스에 함께 들어온 흐름
- 1인 개발자 관점에서 상시 가동 에이전트를 붙일 때 먼저 정해야 하는 상한

**현우 경험과 엮을 지점**

이 저장소의 매일 아침 루틴처럼 클라우드 세션을 일정으로 돌리는 구성이라면, 상한과
알림은 기능이 아니라 운영 조건이다. 해석 수준으로만 잇고 체험 서술은 검토자가 채운다.

## 3. 접근성 검사를 AI 로 자동화한다는 계획에 "자동화되는 건 30%" 라는 반론이 붙었다

**제목 후보**

- `접근성 검사에서 자동화가 닿지 않는 70%`
- `디자인 시스템 접근성 검사를 코드 리뷰 도구에 맡길 때`

**왜 지금인가**

9월 중 미국 정부 디자인 시스템 USWDS 의 운영진이 교체되고, 접근성 검사를 가능한 만큼
AI 코드 리뷰 도구로 자동화한다는 계획이 나왔다. 전임 엔지니어링 리드를 포함한 접근성
전문가들이 신뢰할 만하게 자동화되는 범위는 30% 선이라고 반박했다. 디자인 시스템을 쓰는
쪽에서는 "검사 통과" 표시가 무엇을 보증하는지 다시 묻게 되는 사안이다.

**핵심 앵글 한 문장**

접근성은 규칙 위반을 찾는 일과 실제 사용자의 경험을 확인하는 일로 나뉘는데, 자동화가
닿는 곳은 앞쪽이고 통과 표시는 뒤쪽까지 보증하지 않는다.

**글 구조 아웃라인**

- 무슨 일이 있었는지 — 운영 주체 교체와 자동화 계획
- 반론의 숫자 두 개 (신뢰 가능한 자동화 30% 선, 자동 도구만 두면 위반의 절반 정도를 놓친다는 추정)
- 자동 검사가 잡는 것과 못 잡는 것의 구분
- 1인 개발자가 쓰는 현실적인 절충 — 자동 검사를 어디까지 믿고 어디서 손으로 확인하는가

**현우 경험과 엮을 지점**

디자인 시스템을 직접 만들어 앱에 쓰는 입장에서, 접근성 항목을 CI 에 넣을 때 통과
기준을 어디에 두는지가 그대로 이 문제다. 해석 수준으로 잇는다.
