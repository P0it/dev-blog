## 1. 이어서 연 세션이 앞 턴 추론을 잃는다 ⭐ 완성 원고로 선택

**제목 후보**
- `Claude Code 를 --resume 하면 앞의 추론을 기억할까요?`
- `도구 하나를 뺐을 뿐인데 앞 턴 추론이 전부 무효가 됩니다`
- `9월 24일 릴리스가 같은 곳을 네 번 고친 이유`

**왜 지금인가**
Claude Code v2.1.282 가 9월 24일에 나왔는데, 고친 항목 가운데 네 건이 전부
이어서 연 세션의 thinking 블록 문제였습니다. 한 릴리스에서 같은 자리를 네 번
고쳤다는 것은 증상이 여러 갈래로 나타나는 한 가지 규칙이 있다는 뜻입니다.
그 규칙은 공식 API 문서의 preserved thinking 절에 적혀 있고, 재현 절차가 붙은
GitHub 이슈가 트랜스크립트 수준에서 같은 현상을 보여 줍니다.

**핵심 앵글 한 문장**
thinking 블록의 signature 는 블록 자체가 아니라 그 앞에 보낸 것 전부
(`system`·`tools`·앞선 messages)에 묶여 있어서, 세션을 이어 열 때 그중 하나만
달라져도 그 뒤의 추론이 통째로 무효가 됩니다.

**글 구조 아웃라인**
- 9월 24일 v2.1.282 changelog 에 몰린 thinking 관련 수정 네 건을 먼저 나열
- thinking 블록과 거기 붙어 오는 `signature` 가 무엇인지 (공식 다이어그램)
- 규칙 A — 마지막 어시스턴트 메시지 안의 thinking 블록은 그대로 돌려줘야 한다
  (GitHub 이슈 #63147 이 보여 주는 `thinking:""` + `signature` 저장 패턴)
- 규칙 B — signature 가 `system`·`tools`·앞선 messages 까지 함께 묶는다(prefix check)
- `--tools` 목록이 좁아졌을 때 앞 턴 추론이 사라지던 것이 규칙 B 로 설명된다
- 모델마다 갈리는 앞 턴 thinking 보관 규칙과 모델 전환 시 방향성
- 편집을 대신하라고 만들어 둔 API 장치들(`tool_addition`/`tool_removal`, 대화 중간
  system 메시지, 메시지별 `output_config`, 서버 쪽 compaction)
- 내 계정이 이미 prefix check 에 걸리는지 확인하는 법(2026-08-31 기준일)

**현우 경험과 엮을 지점**
직접 에이전트를 만들어 `messages` 배열을 손으로 쌓아 본 적이 있다면, "매 요청마다
시스템 프롬프트에 오늘 날짜를 다시 렌더한다" 같은 처리가 여기 정면으로 걸립니다.
append-only 로 만들라는 권고가 왜 나왔는지를 자기 코드에 대 보는 대목으로 열 수
있습니다. (체험 서술은 검토 단계에서 채워 넣는 것을 전제로, 원고에서는 해석
수준으로만 두었습니다.)

## 2. 약정 잔액을 남의 소프트웨어에 쓰게 열어 줬다

**제목 후보**
- `Anthropic 에 건 약정으로 Snowflake 를 사게 한 결정`
- `커넥터 2,000개보다 눈에 걸리는 마켓플레이스의 결제 줄`

**왜 지금인가**
Anthropic 이 9월 23일 Claude Marketplace 를 열었습니다. 커넥터·플러그인 2,000여
개를 한곳에 모은 것이 발표의 앞머리지만, 실제로 성격이 다른 항목은 그 아래에
있습니다. 이미 Anthropic 에 약정해 둔 금액의 일부를 파트너 제품·서비스를 사는 데
쓸 수 있게 했습니다. 모델 회사가 구매 창구까지 겸하기 시작한 것입니다.

**핵심 앵글 한 문장**
마켓플레이스의 진짜 변화는 목록의 크기가 아니라 결제 방식이고, 약정 소진처를
넓혀 준 쪽은 고객이 아니라 판매 채널을 얻은 파트너입니다.

**글 구조 아웃라인**
- 9월 23일 발표에서 실제로 새로 생긴 것과 이미 있던 것을 갈라 놓기
- 커넥터·플러그인, 에이전트·제품, 서비스 파트너 세 갈래의 성격 차이
- 약정 금액을 파트너 구매에 쓰게 하는 방식이 조달 과정에서 무엇을 줄이는지
- 이름이 올라간 파트너의 구성(CrowdStrike·Cursor·Harvey·Lovable·Snowflake 와
  Accenture·BCG·Deloitte)이 가리키는 타깃
- 1인 개발자에게는 무엇이 달라지고 무엇이 그대로인지

**현우 경험과 엮을 지점**
플러그인·스킬을 저장소로 배포해 본 관점에서 보면, 배포 통로가 하나 더 생기는
것과 구매 통로가 생기는 것은 다른 이야기입니다. 후자는 유통이 아니라 정산 문제라
1인 개발자가 곧바로 올라탈 수 있는 종류가 아닙니다.

## 3. CS 플랫폼이 에이전트 호출을 감사 대상으로 만들었다

**제목 후보**
- `에이전트에게 갱신 업무를 맡긴 다음에 남는 질문`
- `CS 도구가 AI 호출 로그를 따로 쌓기 시작한 이유`

**왜 지금인가**
Gainsight 가 4월에 Gainsight CS 와 Staircase AI 를 MCP 로 열어 에이전트가 리텐션
업무를 직접 돌리게 했습니다. 9월 릴리스에서는 그 호출을 기록하는 CS MCP Logs
객체를 더해, Copilot·Slack 에이전트·CS MCP 를 거친 AI 도구 호출을 관리자가
집계할 수 있게 했다고 합니다. 여는 단계 다음에 재는 단계가 붙은 순서입니다.

**핵심 앵글 한 문장**
업무 시스템을 에이전트에게 열어 준 회사들이 반년쯤 뒤에 공통으로 내놓는 기능은
새 자동화가 아니라 누가 무엇을 호출했는지를 남기는 로그입니다.

**글 구조 아웃라인**
- 4월 MCP 개방과 9월 로그 추가 사이의 간격이 말해 주는 도입 곡선
- 고객 데이터에 쓰기 권한을 준 에이전트에서 감사 기록이 왜 먼저 필요해지는지
- 헬스스코어·갱신 플레이처럼 사람이 판단하던 항목을 넘길 때의 경계선
- 같은 패턴이 보이는 다른 martech 사례(Certinia 의 자율 에이전트 확장 등)
- 1인 개발자가 자기 파이프라인에 붙일 수 있는 최소한의 호출 기록

**현우 경험과 엮을 지점**
CSM·martech 축과 AI-Native 워크플로 축이 겹치는 주제입니다. 자동화를 붙일 때
결과만 보고 중간 호출을 안 남기면 나중에 되짚지 못한다는 점은 개인 파이프라인에도
그대로 적용됩니다.
