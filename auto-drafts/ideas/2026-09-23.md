## 1. 40% 라는 숫자가 가격표에 없다 ⭐ 완성 원고로 선택

**제목 후보**

- `Opus 5.5 요금이 20%만 내렸는데 40% 싸다는 이유`
- `모델 이름만 바꿔서 끝나지 않는 Opus 5.5`

**왜 지금인가**

Anthropic 이 **9월 22일** Claude Opus 5.5 를 공개했다. 발표문 첫 문단이 "Opus 5 보다
40% 싸게 돌아간다"고 적었는데, 같은 글의 가격 문단을 보면 입력·출력 단가는 $5/$25 에서
$4/$20 으로 **20%** 내려갔다. 나머지는 단가표 밖에 있고, 발표문은 그 40% 를 **기본
설정에서** 쟀다고 밝혀 뒀다. 그리고 Opus 5.5 에서 바뀐 기본 설정 하나가 `effort`
기본값이다 — Opus 5 의 `high` 에서 `medium` 으로 한 칸 내려갔다. 같은 날 Claude Code
2.1.280 이 Opus 5.5 를 기본 Opus 모델로 올렸고 Pro·Team Standard 플랜의 기본 모델까지
Opus 로 바꿨으므로, 아무 설정도 건드리지 않은 쪽이 오늘부터 새 기본값 위에서 돈다.

**핵심 앵글 한 문장**

Opus 5.5 의 40% 절감은 단가 인하 20% 와 작업당 토큰 감소가 합쳐진 값이고 그 뒷부분은
`effort` 기본값이 한 칸 내려간 상태에서 측정된 것이라, `effort` 를 명시해 둔 코드는
그 40% 를 그대로 받지 못한다.

**글 구조 아웃라인**

- 가격표 여섯 줄 대조 — 입력·출력·캐시 쓰기·Batch 는 전부 정확히 20%,
  캐시 읽기만 60%(배수가 표준 0.1배에서 0.05배로 바뀜)
- 캐시 읽기 비중이 80%인 요청 하나를 계산해도 절감폭은 22% 선 —
  단가표만으로는 40% 가 나오지 않는다
- 발표문이 밝힌 측정 조건: "at default settings", 그리고 "토큰당 값도 싸고
  작업당 토큰도 적게 쓴다"는 내역
- `effort` 기본값이 `high` 에서 `medium` 으로 내려간 것과, effort 가 thinking 뿐 아니라
  응답 전체 토큰·도구 호출 개수까지 걸린다는 점
- 반대 방향의 힘 — 같은 effort 단계에서는 Opus 5.5 가 Opus 5 보다 턴마다 더 많이
  생각한다. `effort: "high"` 로 맞춰 두면 기본 설정에서 벗어나면서 토큰은 늘어난다
- 모델 이름만 바꿔서 넘어가지 않는 네 가지(thinking 끄기 400, 강제 `tool_choice` 400,
  `computer_20251124` 400, thinking 블록이 모델·대화에 묶임)와 실패하지 않는 변화 하나
  (도구 호출 사이 텍스트가 thinking 블록으로 옴)
- 내 파이프라인이 40% 쪽인지 20% 쪽인지 확인하는 세 가지

**현우 경험과 엮을 지점**

이 저장소 자체가 매일 아침 도는 클라우드 루틴이고 GitHub Actions 로 적재까지 이어지는
토큰 파이프라인이다. `effort` 를 적어 둔 적이 있는지, 요청의 캐시 읽기 비중이 얼마인지는
이 루틴에서 바로 확인할 수 있는 값이라 글의 마지막 절과 정확히 겹친다. 실제로 청구서가
어떻게 바뀌었는지의 체험 서술은 검토자가 채운다.

## 2. 대화 도중에 도구를 바꿔도 캐시가 살아남는다

**제목 후보**

- `도구를 하나 더 붙이면 캐시가 통째로 날아가던 자리`
- `대화 중간에 tool 을 추가하는 법`

**왜 지금인가**

9월 22일 API 릴리스 노트에 `inline-tools-2026-09-15` 베타가 올라왔다. 대화 중간의
system 메시지 안에 `tool_addition` 블록으로 **도구 정의 전문**을 실어 보낼 수 있게 됐다.
캐시 프리픽스는 `tools` → `system` → `messages` 순서로 쌓이기 때문에, 지금까지는 도구를
하나 추가하려고 `tools` 배열을 고치면 그 뒤가 전부 캐시 미스였다. 같은 날 공개된 Opus
5.5 는 thinking 블록이 대화 프리픽스에 묶여서, 중간에 `tools` 나 `system` 을 고치면
2026년 8월 31일 이후 만든 계정에서는 400 까지 돌아온다. 두 변화가 같은 쪽을 가리킨다.

**핵심 앵글 한 문장**

에이전트가 쓰는 도구 목록을 대화 도중에 바꾸는 일이 캐시 재계산과 추론 블록 무효화를
동시에 부르던 동작이었는데, 이번 베타로 대화를 덧붙이기만 하는 형태로 유지하면서 도구를
갈아 끼우는 경로가 생겼다.

**글 구조 아웃라인**

- 캐시 프리픽스가 `tools` → `system` → `messages` 순서라는 점과 배열을 고쳤을 때의 결과
- `tool_addition` 블록의 두 형태 — 이미 `tools` 에 있는 도구를 가리키는 참조형과
  정의 전문을 실어 보내는 값형(값형이 이번 베타)
- `tools` 에 비지연 도구를 최소 하나는 남겨 둬야 한다는 조건과 그 이유
- MCP 서버를 이름으로만 가리키는 `mcp_toolset` 형태, 접속 정보는 `mcp_servers` 에 남는다
- 한도 — 지연 도구 1만 개, 첫 user 메시지 이후 정의 1만 개, 도구 정의 텍스트 4MB
- 배치 규칙(첫 메시지가 될 수 없고 `tool_use` 와 `tool_result` 사이에 낄 수 없음)과
  위반 시 400

**현우 경험과 엮을 지점**

`.claude/commands/` 에 커맨드를 두고 MCP 서버를 물려 쓰는 구조에서, 세션 도중에 도구가
늘었다 줄었다 하는 상황은 그대로 겹친다. 스킬·플러그인을 동적으로 붙이는 쪽이 늘어난
만큼 캐시 비용이 어디서 발생하는지 확인해 둘 가치가 있다. 실제 세션 비용 비교는 검토자가
채운다.

**Sources**

- [Mid-conversation system messages — Claude Docs](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages) — `tool_addition` 블록 형태, 베타 헤더, 캐시 보존 원리, 배치 제한, 한도, 원문 확인
- [What's new in Claude Opus 5.5 — Claude Docs](https://platform.claude.com/docs/en/models/opus-5-5/whats-new-opus-5-5) — "Define tools in a message (beta)" 절과 thinking 블록의 대화 결속, 원문 확인

## 3. 에이전트에게 며칠짜리 과제를 줬더니 통과율이 28%였다

**제목 후보**

- `Android 화면 40개를 Compose 로 옮기라고 시켰을 때`
- `며칠짜리 과제에서 28%로 떨어지는 통과율`

**왜 지금인가**

Google 이 **9월 17일** Android Bench 2.0 을 공개했다. 기존 벤치마크가 버그 수정 같은
짧은 변경을 다뤘다면 이번에는 엔지니어가 며칠에서 일주일을 쓰는 과제를 넣었다 — 의존성
업그레이드, 화면 40개 이상을 Jetpack Compose 로 리팩터링, 크로스플랫폼 앱을 Android 로
옮기기 같은 것들이다. 짧은 과제에서 91% 안팎이던 통과율이 **28%** 로 떨어졌고, 그 28%
가 현재 1위(OpenAI GPT-6 Astra)다. 훅 기준 사흘을 넘긴 소식이라 그 점은 감안해야 한다.

**핵심 앵글 한 문장**

에이전트가 잘하는 것과 못하는 것의 경계가 과제 길이에서 갈리는 것이 아니라 새 코드를
쓰는 일과 돌아가는 코드를 고치는 일 사이에서 갈린다는 것이 이 벤치마크의 측정 결과다.

**글 구조 아웃라인**

- 2.0 이 바꾼 것 — 통과·실패 이분법에서 연속 점수로, 기능·시각 충실도·회귀 회피를
  나눠 매기고 지시 이탈에는 감점
- 짧은 과제 91% 와 며칠짜리 과제 28% 의 낙차
- 모델이 잘하는 결정적 변환(Java→Kotlin, Retrofit→Ktor)과 막히는 지점
  (런타임 검증, 프레임워크 파괴적 변경)
- 크로스플랫폼 이식은 어떤 모델도 100% 에 닿지 못하고 최상위가 완성률 80% 선
- 리더보드가 모델·과제별 평균 비용까지 함께 싣는다는 점

**현우 경험과 엮을 지점**

인디 앱을 직접 만들어 내는 쪽에서 보면 "며칠짜리 과제"라는 단위가 실제 작업 단위와 같다.
새로 만드는 화면과 이미 돌아가는 화면을 고치는 일에서 에이전트 성적이 갈린다는 관측은
어느 작업을 맡기고 어느 작업을 직접 할지 가르는 기준이 된다. 실제 적용 서술은 검토자가
채운다.
