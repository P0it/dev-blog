## 1. 걸어 둔 훅이 실패하면 막으려던 명령이 그대로 통과됐다 ⭐ 완성 원고로 선택

**제목 후보**

- `settings.json 오타 하나로 꺼지는 Claude Code 훅` ← 채택 (구체적 장면 + 검색어, 명사 종결)
- `Claude Code 훅이 실패하면 통과되는 명령`
- `Claude Code 훅을 막아 세우는 단 하나의 종료 코드`

**왜 지금인가**

2026년 10월 8일 Claude Code 2.1.295 가 command·HTTP 훅에 `onFailure: "block"` 을 추가했습니다.
공식 설명은 "시작하지 못하거나, 제한 시간을 넘기거나, 예상하지 못한 코드로 끝난 훅이 그 동작을
통과시키는 대신 막는다" 입니다. 즉 그때까지의 기본값은 반대였고, 같은 날 올라온 2.1.294 는
지시문으로 쓴 `prompt`·`agent` 훅이 막아야 할 것을 통과시키던 버그를 고쳤습니다. 하루에 올라온
두 릴리스가 모두 "안전장치가 실패하는 쪽으로 열려 있던" 문제였습니다.

**핵심 앵글 한 문장**

Claude Code 훅이 정책 게이트로 동작하지 못하는 실패 경로(종료 코드 1, 시작 실패 127, 제한 시간
초과, HTTP 비-2xx)를 공식 문서의 문장으로 하나씩 확인하고, 2.1.295 의 `onFailure: "block"` 이
그중 무엇을 덮고 무엇을 안 덮는지 가린다.

**글 구조 아웃라인**

- 훅으로 위험한 명령을 막아 뒀다는 장면에서 출발 → 그 훅이 실패하면 어떻게 되는지 질문 → 대부분
  그대로 통과한다는 직답
- 종료 코드 규칙: 대부분의 이벤트에서 `exit 2` 만 코드 단독으로 막는다. `exit 1` 은
  "Unix 관례상 실패 코드인데도" 비차단 오류로 처리되고 동작은 진행된다
- 시작하지 못한 훅: 경로 오타·실행 권한 없음이면 셸이 127 류로 끝나고 동작은 진행된다.
  공식 문서가 직접 적은 경고 — 오타 하나가 게이트를 표시 없이 비활성 상태로 둔다
- 제한 시간: command·http·mcp_tool 훅은 취소되고 출력이 버려져 아무 판정도 남기지 않는다.
  `PreToolUse` 에서 "멈춰 선 훅이 게이트 역할을 해 주리라 기대하지 말라"는 문장. 반대로 Agent SDK
  콜백 훅은 제한 시간을 넘기면 막는다
- HTTP 훅은 상태 코드만으로 차단을 알릴 수 없다 — 비-2xx·연결 실패는 전부 비차단 오류
- 실패 유형별 동작을 마크다운 표로 정리, 그 위에 2.1.295 의 `onFailure` 가 덮는 범위
  (command·HTTP 만, `mcp_tool`·`prompt`·`agent` 는 아님)
- 무인 실행(클라우드 루틴·CI)에 훅을 걸 때 확인할 것으로 맺는다

**현우 경험과 엮을 지점**

이 블로그의 매일 아침 원고 자체가 아무도 보지 않는 클라우드 세션에서 돌아갑니다. 무인으로 도는
자동화에서 "막아 뒀다고 생각한 것이 실제로 막고 있는지"를 확인할 길이 있는지가 이 글의 관점과
그대로 겹칩니다. 체험 서술은 검토 단계에서 채웁니다.

## 2. 에이전트가 지금 무엇을 기다리는지 밖에서 보이게 만든 변경 묶음

**제목 후보**

- `터미널이 Claude Code 의 상태를 알게 된 OSC 7501`
- `에이전트가 무엇을 기다리는지 밖에서 보이게 하는 방법`

**왜 지금인가**

2.1.295 에 상태 표시 변경이 한꺼번에 들어왔습니다. Program Status Protocol(OSC 7501) 지원으로
이를 구현한 터미널은 Claude Code 가 작업 중인지, 사용자를 기다리는지, 끝났는지 표시할 수 있습니다.
여기에 `claude -p` 가 마지막 턴 뒤에도 열려 있을 때 무엇을 기다리는지 stderr 에 적는 줄,
모드용 `$.ui.notify`, 백그라운드 전환 취소 메시지가 같은 릴리스에 함께 올라왔습니다.

**핵심 앵글 한 문장**

오래 도는 에이전트의 "지금 상태"를 사용자가 어디서 읽는가 — 터미널 탭·알림·stderr 로 상태를
내보내기 시작한 2.1.295 의 변경들을 인터랙션 설계 문제로 묶어 읽는다.

**글 구조 아웃라인**

- 에이전트를 띄워 두고 다른 일을 할 때 "끝났나 기다리나"를 확인하려 창을 다시 보는 장면
- OSC 7501 이 터미널에 전달하는 세 가지 상태와, 구현한 터미널에서만 보인다는 조건
- `claude -p` 가 무엇을 기다리는지 stderr 에 적는 줄 — 스크립트로 돌릴 때 달라지는 것
- 모드가 쓰는 `$.ui.notify` 가 사용자의 알림 설정을 따르고 어느 채널이 보냈는지 밝히는 설계
- 상태를 밖으로 내보내는 일이 왜 에이전트 도구에서만 특히 문제인가 (사람이 자리를 비우는 전제)

**현우 경험과 엮을 지점**

1인 개발자는 에이전트를 띄워 둔 채 다른 창으로 옮겨 갑니다. 상태 표시가 없으면 확인하러 돌아오는
비용이 계속 듭니다. 프로덕트 디자인 관점에서 읽을 자리가 많은 변경입니다.

**Sources**

- Claude Code changelog 2.1.295 (2026-10-08) — https://code.claude.com/docs/en/changelog
- OSC 7501 / Program Status Protocol 의 공개 규격 — **찾지 못했습니다.** 전용 검색에서 동명 자료가
  하나도 나오지 않아, 글에서는 changelog 가 적은 범위 이상을 말할 수 없습니다 ⚠ 원문 미확인

## 3. 기업용 Gemini 에이전트에 자기 Workspace 계정과 감사 기록을 준다

**제목 후보**

- `기업용 Gemini 에이전트가 받는 Workspace 계정`
- `에이전트를 사람처럼 등록하기 시작한 쪽의 계산`

**왜 지금인가**

2026년 10월 8일 Google 이 기업용부터 Gemini 에 에이전트 기능을 넣는다고 발표했습니다. 보도에 따르면
그 에이전트는 사내외 어떤 MCP 서버에도 붙을 수 있고, 자기 Workspace 계정과 감사 기록을 따로
받습니다. 에이전트를 도구가 아니라 "계정을 가진 구성원"으로 등록하는 방향입니다.

**핵심 앵글 한 문장**

에이전트에 사람과 같은 계정·권한·감사 기록을 주는 설계가 무엇을 쉽게 만들고 무엇을 새로 떠안기는가.

**글 구조 아웃라인**

- 에이전트에 권한을 주는 기존 방식(사람 계정의 토큰을 빌려 쓰기)이 남기는 문제
- 계정을 따로 주면 달라지는 것 — 권한 회수, 감사 기록의 주체, 퇴사·교체 처리
- MCP 를 사내외 구분 없이 붙인다는 말의 범위와 거기서 생기는 경계 문제
- 반대 시각 — 계정이 늘면 관리 대상도 늘고, 좌석 단위 과금과 맞물린다
- 1인 개발자가 지금 흉내낼 수 있는 최소 구성 (서비스 계정 분리 수준)

**현우 경험과 엮을 지점**

CSM·martech 도구를 붙일 때 권한을 사람 계정에 매달아 두면 나중에 회수가 어렵습니다. 에이전트
계정을 처음부터 분리해 두는 쪽이 1인 운영에서도 유리한지가 따져 볼 지점입니다.
