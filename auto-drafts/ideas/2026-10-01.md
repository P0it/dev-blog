## 1. 클라우드 세션이 시작되지도 않은 실행이 성공으로 표시됐다 ⭐ 완성 원고로 선택

**제목 후보**

- `시작도 못 한 루틴 실행이 Succeeded 로 표시되던 이유` ← 채택
- `루틴 실행 목록의 초록색이 관찰하는 구간`
- `무인 실행을 확인할 때 실행 목록으로는 알 수 없는 것`

**왜 지금인가**

9월 30일 공개된 Claude Code v2.1.286 의 수정 목록에 루틴 실행 상태 표시가 두 줄 들어 있다.
하나는 클라우드 세션이 아예 시작되지 않은 실행이 Runs 목록과 루틴 페이지, 사이드바에서
Succeeded 로 표시되던 것을 Failed 로 바꾼 것이고, 다른 하나는 예정 시각이 지났는데 아직
시작하지 않은 실행에 대해 과거 시각을 다음 실행 시각으로 보여 주던 루틴 페이지를
예정 시각과 함께 **Due** 로 읽히게 바꾼 것이다. 공식 문서는 초록색 표시가 "세션이 인프라
오류 없이 시작해서 끝났다"는 뜻이고 프롬프트의 작업이 성공했다는 뜻은 아니라고 이미
적어 두고 있었다. 이번 수정은 그 좁은 보장마저 어긋나던 경우를 메운 것이다.

**핵심 앵글 한 문장**

루틴 실행 목록의 상태 표시는 세션의 시작과 종료만 관찰하기 때문에 프롬프트가 한 일은
처음부터 판정 범위 밖이었고, 9월 30일까지는 세션이 시작되지 않은 경우까지 초록색에 묶여 있었다.

**글 구조 아웃라인**

- 도입: 아침에 루틴 페이지를 열어 초록색이 줄지어 있는 것을 보면 무엇을 확인한 셈인가
- v2.1.286 이 Succeeded 에서 Failed 로 옮긴 경우 — 세션이 시작되지 않은 실행
- 공식 문서가 적어 둔 초록색의 범위, 그리고 목록이 아니라 트랜스크립트에만 나타나는 것
  (차단된 네트워크 요청, 없는 커넥터 도구, 작업 자체의 실패)
- 같은 릴리스가 고친 루틴 페이지의 시각 표시와 **Due**
- `/fire` 엔드포인트가 200 을 돌려주는 시점 — 세션 생성까지이고 완료를 기다리지 않는다,
  멱등 키가 없어 재시도가 세션을 여러 개 만든다
- 실행이 목록에 아예 나타나지 않는 조건 — GitHub 연결 만료 시 72시간 건너뛰기,
  시간당 한도, 구독 사용량 한도, 일시정지
- 마무리: 무인 실행에서 실제로 확인할 것

**현우 경험과 엮을 지점**

이 저장소의 원고가 바로 매일 아침 클라우드 루틴으로 적재된다. 1인 개발자가 무인 파이프라인을
붙일 때 상태 표시를 신뢰 경계로 쓸 수 있는지, 결과물 쪽(커밋·PR·파일)에 확인 지점을 따로
두어야 하는지가 그대로 이 문제다. 해석 수준으로만 잇고 체험 서술은 검토자가 채운다.

## 2. 마테크 도구의 에이전트 권한을 스코프와 대시보드 권한의 교집합으로 묶었다

**제목 후보**

- `에이전트에게 내 권한만 물려주는 방식`
- `마케팅 도구를 MCP 로 열 때 권한을 어디서 자르는가`

**왜 지금인가**

9월 29일 Braze 가 Forge 행사에서 BrazeAI Operator Connect 를 베타로 공개했다.
Claude·ChatGPT·Microsoft Copilot 같은 MCP 도구에서 Braze 작업을 하게 열어 주는 기능인데,
동작이 개별 사용자의 신원과 Braze 권한으로 실행된다고 밝혔다. Braze MCP 서버 문서는
접근 범위를 "연결을 승인할 때 부여한 스코프와 본인의 대시보드 사용자 권한의 교집합"으로
설명하고 있다. 같은 날 Usermaven 이 Maven AI 2.0 을 내놓으면서 일정에 따라 분석을 돌리고
프롬프트 없이 결과를 올리는 에이전트를 붙였고, 대시보드·퍼널·세그먼트 변경은 승인 기반
동작으로 두었다.

**핵심 앵글 한 문장**

서비스 계정 대신 로그인한 사람의 권한을 그대로 물려주는 방식은 권한 초과를 막아 주지만,
1인 팀에서는 그 사람이 곧 관리자이므로 교집합이 전체 권한과 같아진다.

**글 구조 아웃라인**

- Operator Connect 가 무엇을 열었는지, 어느 MCP 도구에서 쓰는지
- 권한을 스코프와 대시보드 권한의 교집합으로 잡는 구조와 그 뜻
  (대시보드에서 못 보는 캠페인은 에이전트도 못 본다)
- 서비스 계정 방식과 견주기 — 과도 부여가 쉬운 쪽과 감사 추적이 남는 쪽
- 1인 개발자·소규모 팀에서 이 방식이 실제로 좁히는 것과 좁히지 못하는 것
- 같은 날 Usermaven 이 택한 승인 기반 쓰기 동작과의 비교
- 마무리: 마테크 스택을 에이전트에 열기 전에 정할 것

**현우 경험과 엮을 지점**

CSM·martech 을 관심 축으로 두고 있고 Cisco 파트너사 솔루션개발팀에서 고객 쪽 도구를 다루는
자리라면, 고객 데이터에 닿는 도구를 에이전트에 열 때 권한 모델은 곧 검토 항목이다.
해석 수준으로 잇는다.

## 3. 디자인 도구 안에서 만든 AI 도구를 남이 쓰게 퍼블리시한다

**제목 후보**

- `디자인 도구 안에 생기는 도구 생태계`
- `Weave 커스텀 도구를 커뮤니티에 올린다는 것`

**왜 지금인가**

9월 말 Figma 가 직접 만든 Weave 커스텀 도구를 Figma Community 에 퍼블리시해 다른 사람이
Figma Design 에서 바로 쓰게 하는 경로를 열었다. 같은 시기에 관리자 화면에 AI 크레딧 사용
내역이 사람별로 붙었고, 좌석 등급마다 크레딧 할당량이 정해졌다. 디자인 도구가 AI 기능을
얹는 단계를 지나, 사용자가 만든 AI 워크플로가 유통되고 그 소비가 과금 단위로 계량되는
단계로 넘어가는 모습이다.

**핵심 앵글 한 문장**

디자인 도구의 AI 는 기능 목록이 아니라 크레딧과 유통 경로를 갖춘 플랫폼이 되어 가고 있고,
그 말은 디자인 작업의 비용이 처음으로 항목별로 보이게 된다는 뜻이다.

**글 구조 아웃라인**

- 커스텀 Weave 도구를 커뮤니티에 올리는 경로가 무엇을 바꾸는지
- 크레딧이 좌석 등급에 붙고 사용 내역이 사람별로 보이는 구조
- 코드 에이전트 쪽의 MCP 서버 연결(디자인 토큰·컴포넌트 접근)과 이어 붙는 지점
- 1인 개발자가 디자인과 구현을 혼자 할 때 이 계량이 실제로 쓰이는 방식
- 마무리: 도구가 플랫폼이 될 때 사용자가 지는 것

**현우 경험과 엮을 지점**

UI/UX·프로덕트 디자인을 관심 축으로 두고 직접 앱을 만드는 입장에서, 디자인 산출물을
코드로 넘기는 구간을 에이전트에 맡길 때 크레딧이 곧 예산 항목이 된다. 해석 수준으로 잇는다.
