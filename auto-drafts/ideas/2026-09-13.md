## 1. 에이전트 상한은 256까지 열렸는데, 한 일을 되읽는 장치는 이제야 붙었다 ⭐ 완성 원고로 선택

**제목 후보**

- `Claude Code 2.1.269 의 Bash diff — 에이전트 상한 256보다 이쪽이 큽니다`
- `에이전트가 "고쳤습니다"라고 할 때, 하네스는 그 말밖에 못 봤습니다`

**왜 지금인가**

9월 11일 Claude Code 2.1.269 릴리스 노트에 두 줄이 나란히 들어왔다. 하나는
`CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` 로 Workflow 도구의 동시 에이전트 상한을
1~256 범위에서 올리는 설정이고, 다른 하나는 Bash 도구 결과에 **그 명령이 바꾼 파일의 diff** 를
붙이는 변경이다. 앞은 처리량을 늘리는 쪽이고 뒤는 돌린 결과를 되읽는 쪽이라, 방향이 정반대다.
하루 뒤 2.1.270 은 "세션이 오래 돌아간 뒤 읽기 전용 git 명령이 권한을 묻던" 2.1.269 회귀를
고쳤다 — Bash 주변을 건드린 값이 바로 다음 날 청구된 셈이다.

**핵심 앵글**

에이전트 하네스에서 그동안 "무엇을 했는가"의 유일한 출처는 모델의 자기 보고였고, diff 는
그 자리에 처음으로 **파일에 남은 자국**이라는 독립 경로를 끼워 넣는다 — 256이라는 눈금은
그 뒤에 와야 의미가 있다.

**아웃라인**

- 2.1.269 에 나란히 들어온 두 줄: 상한 1~256, 그리고 Bash 결과의 diff
- 도구 루프가 돌려받는 건 stdout·stderr·종료 코드뿐 — 모델의 "수정했습니다"는 파일을 본 적이 없다
- stdout 은 프로그램이 스스로 적은 말, diff 는 명령이 끝난 뒤 파일에 남은 자국. 출처가 다르다
- 검증이 테스트·린트·PR 로 맨 뒤에 몰려 있던 걸, diff 는 명령 하나 단위로 당겨 놓는다
- 반대 시각: diff 는 공짜가 아니라 컨텍스트로 값을 치른다. 포맷터·빌드 한 번에 수천 줄이 붙는다
- 하루 뒤 2.1.270 의 권한 회귀 — 관측을 붙이는 일에도 마찰이 따른다

**현우 경험과 엮을 지점**

직접 굴리는 자동화 파이프라인(이 블로그의 클라우드 루틴도 그중 하나다)에서 에이전트가
"커밋했습니다 / 적재했습니다"라고 적은 턴과 실제 저장소 상태가 어긋난 적이 있는지 —
검토 단계에서 채울 자리. 규약상 겪지 않은 일은 원고에 쓰지 않고, 해석 수준으로만 남겼다.

## 2. 440대를 열었는데 도메인 관리자는 12곳, 에이전트가 늘린 건 넓이였다

**제목 후보**

- `PaperCut 440대를 연 에이전트 떼가 도메인 관리자는 12곳에서 멈췄습니다`
- `26초에 11곳, 그다음부터 느려진 이유`

**왜 지금인가**

GreyNoise 가 9월 10~11일 "Agents Gone Wild" 로 공개한 캠페인이다. 러시아어권 행위자가
수백 개의 AI 에이전트를 OpenAI Codex 하네스 + DeepSeek 모델 조합으로 굴려 PaperCut NG/MF
취약점 두 개(CVE-2026-81578, CVE-2026-82078)를 엮었고, 48개국 395개 조직의 440대 이상을
열었다고 집계했다. 캠페인 시작은 8월 31일. 에이전트를 공격 쪽에서 대규모로 굴린 사례가
수치까지 붙어 공개된 건 흔치 않다.

**핵심 앵글**

집계를 깔때기로 놓고 보면 440대 침해 → 자격증명 수집 280 → OS·도메인 비밀 147 →
도메인 관리자 12 로 급격히 좁아지는데, 에이전트 떼가 압축한 건 정찰·익스플로잇 같은
**넓이**였지 판단이 필요한 횡적 이동의 **깊이**가 아니었다.

**아웃라인**

- 26초에 11개 조직 — 자동화가 압축한 구간이 어디까지였나
- 440 → 280 → 147 → 12 로 좁아지는 깔때기, 각 단계가 요구하는 일의 성격이 다르다
- 넓이(스캔·시도·반복)는 병렬로 사는 반면, 깊이(환경 파악·경로 선택)는 병렬로 안 산다
- 방어 쪽 함의: 초기 접근 차단보다 횡적 이동 구간의 마찰이 실제로 값을 했다
- 반대 시각: 12곳도 적은 수가 아니고, 다음 판에서 깊이가 따라잡지 말란 법은 없다

**현우 경험과 엮을 지점**

공격이든 자동화든 팬아웃의 이득이 어디서 끊기는지는 같은 질문이다. 1번 아이디어의
"256 상한" 과 붙여 읽으면 한 쌍이 된다 — 다만 같은 주에 둘 다 쓰면 겹치니 간격을 두는 게 낫다.

## 3. 오케스트레이션을 모델처럼 팔기 시작했다

**제목 후보**

- `Fugu Ultra v2 는 프런티어 모델 없이 프런티어 점수를 냈습니다`
- `내가 짜던 라우팅이 API 엔드포인트 하나가 됐을 때`

**왜 지금인가**

Sakana AI 가 9월 11일 Fugu Max v1.0 과 Fugu Ultra v2.0 을 내놨다. 단일 모델이 아니라
**여러 오픈 모델·특화 모델로 작업을 라우팅하도록 학습된 모델**이고, 자기 자신을 재귀
호출한다. 풀에 자사 프런티어 모델을 두지 않고도 Chartography 같은 시각 추론 벤치마크에서
프런티어급 점수를 냈다는 자체 보고가 붙었다. 하네스를 손으로 짜던 층이 SKU 로 팔리기
시작한 시점이다.

**핵심 앵글**

1인 개발자가 직접 조립하던 "모델 고르기 + 라우팅 + 재시도" 층이 API 한 줄로 압축되는 대신,
어느 모델이 무엇을 처리했는지 고정할 수 없는 블랙박스를 값으로 치른다.

**아웃라인**

- 라우터가 모델이 됐다 — 풀·재귀 호출이라는 구조를 먼저 정리
- 가격표를 보면 프런티어 단일 모델과 다른 자리를 노린다
- 자체 보고 벤치마크의 신뢰 문제: 풀 구성이 공개되지 않으면 재현이 어렵다
- 직접 짠 라우팅과 견주기 — 고정·핀·감사 로그를 포기하는 대가
- 반대 시각: 대부분의 1인 개발 작업에서 라우팅을 직접 쥘 이유가 실제로 있는가

**현우 경험과 엮을 지점**

작업 난이도에 따라 모델을 갈아 끼우는 파이프라인을 직접 굴려 본 사람에게는,
"라우팅을 남에게 맡기고 얻는 것과 잃는 것"이 곧바로 체감되는 주제다. 체험 서술은 검토 단계에서.
